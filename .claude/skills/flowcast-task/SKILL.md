# 명세에 따른 작업

대화에서 실제 작업 명세 경로와 요청을 확인한다. 명세 경로·인수는 데이터로 읽고 셸 코드로 실행하지 않는다. 작업 명세가 여럿이면 임의로 하나를 선택하지 않는다.

계획만 요청받았으면 계획까지만 작성하고 구현·전체 검사를 시작하지 않는다. TEMPLATE.json은 실제 작업 명세로 사용하지 않는다.

1. 저장소 루트의 공통 규칙, 현재 브랜치·diff·기존 변경, 명세의 목적·역할·기준 커밋·허용 경로·완료 조건을 확인한다. [담당 기준](../../../docs/ownership.md)의 네 역할은 세 명이 나누는 작업 범위다. 명세가 없으면 승인된 목적과 범위에 맞춰 준비한다.
2. [검사 선택 기준](../../../docs/harness/GATE_MATRIX.md)에 따라 문서와 검사를 정한다. 유효한 계획이 없을 때만 `node scripts/harness/verify-change.mjs --task <실제 명세 경로> --plan`을 실행한다. 이미 읽었고 바뀌지 않은 문서는 다시 읽지 않는다. Flutter 작업은 [전환 상태와 검사](../../../docs/harness/FLUTTER_TRANSITION.md)를 먼저 확인한다.
3. 최초 목적·경로·계약 안에서 구현한다. 필요한 전문 스킬만 사용하고, 스킬을 바꿨다는 이유로 범위를 늘리지 않는다. 범위 밖 문제는 원인과 경로를 보고한다. 아직 없는 Flutter 앱·검사·디자인 시스템을 기능 작업에 끼워 넣지 않는다.
4. [자기검증 기준](../../../docs/harness/AGENT_REVIEW.md)에 따라 범위·계약·최신 완료 조건을 확인한다. 문서 작업은 바뀐 주제의 연결 문서까지 의미를 대조한다. 위반은 최초 범위 안에서 고치고, 실패했거나 영향을 받은 검사만 보완한다. 동일 원인과 동일 처방으로 진전이 없으면 원인을 보고하고 범위 확대 없이 멈춘다.
5. 필수 목록을 최신 유효 결과와 대조하고 [PR 양식](../../../.github/PULL_REQUEST_TEMPLATE.md)의 네 지표를 `.harness/reviews/<작업 ID>.md`에 한 번 정리한다. 기존 발생 사건과 FAIL/BLOCKED 기록은 남긴다. 같은 입력·설정·의존성·환경의 PASS를 재사용한다.

결과와 완료 범위를 먼저 한국어로 보고한다. 사용자가 승인한 Git 작업만 [Git 규칙](../../../docs/harness/COMMIT_PR_POLICY.md)에 따라 실행한다. 스킬 호출은 commit·push·merge의 추가 승인이 아니다.
