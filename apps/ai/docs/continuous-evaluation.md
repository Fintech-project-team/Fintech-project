# 상시 의미 분석 평가 — 2026-11-04

이 문서는 최초 연간 분석 이후의 EX-B 의미 해석을 시험한다. 목표는 기본 분류·의미·사용자 확인 경로 각각 99%, 10건 작업의 결과 조회까지 5초 이내다. 모델 실패도 분모에 포함한다. 실제 금융사 수집, Flutter 변경 탐지, 폰 화면까지의 지연을 측정한 결과는 아니다.

상시 분석의 모든 실행5초 목표는 **미달**이다. 아래 초기 6회 결과와 뒤의 축약 응답 비교는 별도 실행이다. 사용자는 기본 배포 설정의 재검증 결과를 확인한 뒤 현재 변경의 commit/push를 별도 승인했다. 게시 범위는 공통 규격·반복 지출 연결·검증된 경계 보완이며 성능 목표 달성으로 표시하지 않는다.

## 실행 규칙과 시험 경계

- [실행 계약](../../../docs/payse-execution-contract.md)의 EX-B/Q2/EX-R/EX-T/D3를 따른다. 일반 미분류는 10건 또는 60초까지 묶는다. 이 대기 시간은 아래 실행 시간과 별개다. 일반 1건을 발생 후 5초에 분석한다는 의미가 아니다.
- EX-B 요청으로 동일 인증 HTTP·원천 소유권 검증·Java 의미 검증·암호화 저장·결과 조회를 사용한다. 공급자는 실제 OpenAI다. 감마의 새 폐기 PostgreSQL만 사용하며 운영 DB·서비스는 변경하지 않는다.
- 실제 호출은 `gpt-6-luna`, reasoning `none`, 입력/출력 상한 12,000/4,000, 공급자 시간 제한 20초, 시험 동시성 1이다. 10건마다 따로 요청하며 실패를 정상 unknown으로 바꾸지 않는다.
- 자동 재호출·모델 전환은 0이다. 실패 목록에서 사용자가 재시도한다. 전송 후 결과 불명은 중복 과금 가능성 확인이 필요하다.
- 동일 성공의 재조회, 정산, 확정된 분류의 수치 갱신은 AI0 경계다. API의 묶음 대기·결과 재사용·실행 중 원천/분류 변경은 별도 무료 HTTP·실제 PostgreSQL 회귀로 검사한다.
- 현재 계산 의존성의 대기 예외는 아직 연결되지 않았다. API는 검증된 우선 원인 코드가 없어 빈 `reasonCodes`와 일반 Q2만 허용한다. 이번 시험을 앱의 상시 분석 흐름 전체 구현 완료로 해석하지 않는다.

## 정답과 입력 분리

`apps/api/testing/analysis/continuous_evaluation.py`는 새 ID와 문구를 가진 연간 원천 1,825건을 만들고 조건별 표본을 10건씩 묶는다. 명시 자기 이체·한쪽 근거 부족·급여/대여/실비·반복 지출·승인 취소/환불·취소 문의/반려·충돌·복합 구매·분류 범위 밖·적요 속 지시를 포함한다. 금융 금액·반복 수치의 계산 책임은 기존 Dart 규칙에 남는다. 반복 후보 준비기는 최근 3개월의 엄격한 시험 부분집합이며 일반 탐지기를 대체하지 않는다.

`source.json`, `inputs.json`, `expected.private.json`을 실행 전에 각각 SHA-256으로 동결한다. 정답은 생성 원천의 관찰 가능한 의미를 기준으로 만들고 모델 입력에서 제외한다. 실제 결과로 정답을 수정하지 않는다. 변형 개발 자료와 최종 평가의 ID·문구를 분리한다. 모두 합성 자료이며 동일 문장 계열의 반복을 포함하므로 실제 사용자 모집단의 99% 정확도나 독립 표본 수로 일반화할 수 없다.

초기 생성기 v1/v2에서는 `mixed_basket`의 품목 설명이 일반 승인 문구로 치환되는 오류가 있었다. 입력에는 품목이 없는데 정답은 복합 구매로 남는 경우다. 이전 실행·정답을 그대로 보존하고 그 실행의 사용자 확인 경로 점수에는 이 한계를 표시한다. v3는 혼합 구매의 공개 근거를 유지하고 분류 범위 밖/충돌의 근거 문구 누락을 실행 전에 거절한다. 최종 평가에는 v3의 새 자료를 사용한다.

## 비교 설정

`continuous-guidance.json`은 기본 MD에 짧은 근거 문구·공백 축소와 상태/값/사유의 일치 규칙을 덧붙인다. 공개 필드나 검증을 생략하지 않는다. 서버의 기본 프롬프트를 교체하지 않고 감마 비교에서만 선택하며 지시 해시가 결과 캐시 버전에 포함된다. 지시 파일의 사본·해시를 로컬 실행 기록에 남긴다.

Fast도 감마의 `--fast`에서 요청 단위로만 선택한다. 기본 배포 요청은 명시 표준 등급이다. 실제 응답의 등급 확인, 실패 시 자동 전환 금지, 생성 비용 예약/정산 및 DB 단가 2배 적용을 함께 검사한다. Fast 지원을 이유로 5초를 보장하지 않는다. 공식 [Fast 설명](https://developers.openai.com/api/docs/guides/fast-mode)과 [가격표](https://developers.openai.com/api/docs/pricing)를 기준으로 했으며 실제 관측 결과를 우선한다.

응답 처리 점검에서 공식 `phase` 구분의 누락을 발견했다. 이 추가 자료는 14:41:17 KST에 동결했으며 정답 SHA-256은 `1c5dfaa2ba7dd46a8cbd00cc08525b29ca62a7669effde36023f76c1d3462546`이다. 새 ID·배치 조합을 사용하지만 v3 holdout과 같은 문장 계열이므로 독립적인 새 의미 분포라고 주장하지 않는다.

`basicAccuracy`, `meaningAccuracy`, `reviewMatch`를 각각 판정한다. 기본 분류 목표는 `transactions.basicAccuracy`로 평가하여 해당 필드가 없는 반복 후보를 분모에서 제외한다. 개발 표의 210개 실행은 전체 채점기 수치 95.24%를 표시했으며, 기본 분류의 적용 대상 점수는 190/200(95.00%)다. `taxonomy_review`는 정상 검토 경로이므로 정답과 맞으면 확인 경로 성공이다. 기존 채점기의 `accuracy`는 `taxonomy_gap`도 오류로 집계하므로 그것을 이 작업의 목표 지표와 혼용하지 않는다. 실패·미실행은 모든 목표 지표의 분모에 남는다. 의미별 오탐률의 분모는 해당 의미가 아닌 전체 항목이고, 정보 부족 사례의 근거 없는 단정률은 따로 계산한다. 자연어 사유의 타당성은 유형별 표본도 직접 검토한다.

클라이언트 시간은 첫 접수부터 저장 결과 조회까지이며 1초 주기의 상태 조회·암호화 저장을 포함한다. 별도 서버 시간은 DB의 `accepted_at`→`finished_at`이고, 공급자 계수/생성 시간도 분리한다. 서버 시간이나 생성 시간만으로 전체 5초 목표를 통과시키지 않는다.

USD 장부는 마지막 사용자 확인 잔액 $34.83을 시작으로 생성 비용의 보수 상한과 미확정 계수 요금의 공통 예비비 $2를 차감한다. 잔여 $20 하한, 기존 KRW 45,000 차단선을 유지한다. 장부 추정치는 결제 화면의 실시간 잔액이나 최종 청구액이 아니다. Fast는 캐시 할인을 기대하지 않고 2배로 예약·정산한다.

## 검증 상태와 남은 작업

무료 검사는 생성기/정답 무결성·실패 포함 집계·비용 보호 8개, 공급자 경계 18개를 통과했다. 유효한 phase·null/미제공 phase·중간 진행문만 존재·복수 최종 본문·미완료·거절·잘못된 phase를 검사하며 공급자 대역은 요청된 횟수만 호출했다. 실기기 사용자 확인 UI는 별도다.

실제 PostgreSQL의 관련 HTTP 경계는 14개(최초 13개 통과, 잘못 작성한 재사용 검사 1개를 수정 후 통과)다. A/B 각각 1건·9건의 59초 대기/60초 실행, B 10건 즉시 허용, 동일 성공의 재사용, 사용자 재시도/완료 불명 확인, 무관 원천 갱신, 사용자 편집·정산 보존, 관련 분류/금액 변경, 로그아웃, 삭제, 반복 후보의 금융 의무 미생성을 검사했다. 재사용은 descriptor 힌트만으로 확정하지 않고 현재 본문 검증 후 수행한다. 이 계약을 변경하지 않았다. 재사용 단독 재검사에서는 금융 원천 전체 지문도 동일했다. 각 HTTP 검사의 종료 시점 금융 불변 검사를 유지한다.

실패를 더 짧은 타임아웃으로 잘라 5초 성공으로 세거나, 자동 재호출로 성공률을 덮지 않았다. 다음 보완은 허용된 최종 응답 구분의 대규모 재현, 응답 전송량·공급자 계수/생성의 꼬리 지연, 결과 전달 지연을 분리해 다룬다. 계산 의존성 우선 경로는 인증된 서버 근거 정의와 프론트 협의가 남아 있다. 목표 미달 상태에서 Fast 비교를 기본 운영 설정으로 승격하지 않는다.

## 재현과 제거

## 에이전트 대안 검토

원격 Agents API는 세션·실행 환경·저장 상태를 관리한다. 현재 직접 Responses 호출의 지시나 결과가 대시보드 에이전트 설정만으로 자동 바뀌지 않는다. 기존 코드의 한 시도 한 생성·저장/암호화·재시도 정책과 연결해야 한다. 확인한 세션 생성 참조에는 현재 호출처럼 `max_output_tokens`를 지정하는 필드가 없어 기존12,000/4,000 토큰·비용 경계를 그대로 적용했다고 주장할 수 없다. [Agents API](https://developers.openai.com/api/docs/guides/agents-api/overview), [세션 생성 계약](https://developers.openai.com/api/reference/resources/beta/subresources/agents/subresources/sessions/methods/create)

네이티브 다중 에이전트는 확인일 기준 Sol/5.6 계열 지원이며 현재 Luna를 그대로 활성화하는 옵션이 아니다. 여러 검토자를 추가하면 추가 토큰·종합 단계가 생기므로 현재10건의5초 목표에 도움이 된다는 실측 근거가 필요하다. 이전 독립 재검토 역할은 정상 공통325개에서 오류1개를 고쳤지만2개를 새로 만들었다. 그 실험은 원격 Agents API 실행이 아니었다. [다중 에이전트 계약](https://developers.openai.com/api/docs/guides/responses-multi-agent), [기존 비교](agent-comparison.md)

이유를 짧게 쓰는 설정은 공식 `text.verbosity=low`로 비교하되 필수 근거·보존 필드를 생략하지 않는다. 실제 v4의 중단1건을 포함해 평가하므로 설정만으로 개선을 선언하지 않는다. [공식 배포 점검](https://developers.openai.com/api/docs/guides/deployment-checklist)
