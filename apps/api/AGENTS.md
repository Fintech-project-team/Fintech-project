# PAYSE API 개발 규칙

`apps/api/` 전체의 필수 개발 지침이다. 이 파일을 하위 폴더에서 중복 정의하지 않는다. 루트 [공통 지침](../../AGENTS.md), [제품 기준](../../docs/product-baseline.md), [공통 코드 기준](../../docs/harness/CODE_SPEC.md), 담당 기능의 데이터 계약과 함께 적용한다.

Java 주석 의무와 자동 검사는 `src/main/java`·`src/test/java`·`tools` 아래 직접 작성한 Java에 적용한다. 공유 AI Java도 [AI 지침](../ai/AGENTS.md)을 통해 같은 Java 주석·가독성 규칙을 따른다. Flutter/Dart의 규칙과 수정 권한은 변경하지 않는다.

## 역할과 데이터 계약

1. 계좌 합산·U·소비 집계·반복 후보 수치·미래 잔액·시뮬레이션은 Flutter에서 계산한다. 서버는 원천/설정 제공·저장 제약 검증·LLM 해석을 담당한다.
2. 기존 데이터 모델·SQL·JSON 필드 의미를 보존한다. JSON 금액은 원화 정수, dataVersion/expectedDataVersion은 10진 정수 문자열이다. DB data_version은 bigint, sourceVersion/ruleVersion/schemaVersion은 문자열, inputRevision은 정수다. 미확인을 0으로 바꾸거나 날짜에 미확인 시각을 만들지 않는다.
3. 원천으로 분류된 금융 필드는 사용자 수정 불가다. 사용자 편집은 데이터 명세의 수정 권한 열을 따른다. 계좌 포함/별칭·급여/카드 계획·보호 설정·허용된 분류/지급 연결/배정은 원천 사실과 분리한다. 시뮬레이션 가상 입력·결과는 기능 흐름 메모리에만 두고 DB·파일·로그에 영구 보존하거나 기기에서 영구 복원하지 않는다. 확정 설정 저장은 별도 계약을 따른다.
4. 사용자 기본 정보는 users, 타입이 정해진 사용자 속성은 user_attributes, 금융 소유권은 동일 users.id를 사용한다. 테스트를 위해 전용 사용자/금융 테이블·컬럼·서비스 분기를 추가하지 않는다. 승인된 demo_sessions와 /demo-sessions는 유지한다. 기관 기준정보는 reference_data를 읽고, 검증 사례의 설정·이력은 testing/scenarios 도구에서 명시 선택한다. 기본 금융 적재에 시나리오 설정을 몰래 포함하지 않는다.

## 모듈 구조

1. Controller → application service → Repository/외부 adapter로 책임을 나눈다. 필요한 의존성을 생성자로 주입한다. 빈 계층·전역 ServiceLocator·공통 BaseManager를 만들지 않는다.
2. 상태 없는 Spring bean과 연결 풀은 재사용할 수 있다. 사용자·세션·잔액·DB 트랜잭션을 static 또는 singleton bean의 변경 가능한 필드에 보관하지 않는다.
3. Java 파일 추가·이동 시 [Java 패키지 배치](docs/spring-bootstrap.md#java-패키지)를 먼저 확인한다. 기능 안에서 controller/service/mapper를 기본으로 구분하고, 전달 DTO·값 VO·JPA entity를 용도별로 분리한다. mapper는 기존 JPA 저장 계층이며 MyBatis 도입을 뜻하지 않는다. 내부 전용 보조 타입은 불필요하게 공개하지 않고 테스트도 대상 패키지에 둔다. 패키지 이동은 import·엔티티 스캔·검사/문서 참조까지 함께 검증하며 공개 API·SQL·빈 이름을 바꾸지 않는다.

## 명명과 로직 가독성

명명·로직 가독성 규칙은 직접 작성한 코드에 적용한다.

1. 클래스·메서드·변수명은 역할을 구분하는 데 필요한 단어만 사용한다. 호출부·파일 목록에서 식별에 필요하지 않은 문맥을 이름에 반복하지 않는다.
2. 처리 과정·모든 조건·예외를 한 이름에 나열하지 않는다. 테스트도 핵심 검증 의도를 이름으로 표현하고 세부 조건은 본문과 필요한 주석에 남긴다.
3. 짧게 만들기 위해 뜻을 잃지 않는다. `tmp`, `combo`, 역할 없는 `data`나 한 글자 이름 대신 값의 역할을 드러낸다. `id`, `url`, `sql`, `max`처럼 문맥과 관례로 뜻이 명확한 표현은 사용할 수 있다.
4. 클래스는 책임·대상, 변수는 담긴 값의 의미를 표현한다. 일반 작업 메서드는 동작을 표현하고 접근자·프레임워크 진입점은 기존 관례를 따른다. 같은 범위에서 서로 다른 업무 객체에 같은 모호한 이름을 재사용하지 않는다. 값의 단위·식별자 여부가 혼동되면 이름이나 타입에 표시한다.
5. Java는 기존 camelCase/PascalCase, Python은 snake_case/PascalCase 관례를 유지한다. 임의의 글자 수 제한을 두거나 이미 명확한 이름을 일괄 축약하지 않는다.
6. 이름을 바꾸면 선언·호출·관련 주석·검사 참조를 함께 확인한다. 공개 JSON 필드, DB 식별자, 설정·CLI 키, 프레임워크 빈 이름 등 연결 규격은 내부 명명 정리만을 이유로 바꾸지 않는다.
7. 명명 정리에서는 조건·처리 순서·저장 및 인증 정책·기대 결과를 유지한다. 생성 자료의 ID·금액·날짜·원천 내용과 다른 담당 영역을 변경하지 않는다. Java 생성일·수정일 주석은 API 필수 규칙을 따른다.
8. 실패 조건을 먼저 분리해 불필요한 중첩을 줄인다. 인증·입력 검증·멱등성 판정·잠금·커밋의 기존 순서와 오류 계약은 유지한다. 인증 실패에 필요한 제한 기록을 생략하거나 조기 반환·예외로 롤백하지 않는다.
9. 여러 `true`/`false` 인자로 선택 의미를 감추지 않는다. 호출부에서 뜻을 알 수 있도록 목적이 드러나는 메서드·매개변수·지역 변수 또는 기존 타입을 사용한다. 의미가 명확한 단일 boolean은 유지할 수 있으며, 이 규칙을 이유로 공개 JSON 필드나 불필요한 타입·래퍼를 추가하지 않는다.
10. 조회 메서드에 금융 원천·설정의 저장·초기화·상태 변경을 숨기지 않는다. 저장 책임은 호출부에서 식별할 수 있게 표현한다. 조회에 필요한 기존 인증·계정/세션 재검증·사용자 행 잠금·RLS 설정·일관성 확보 절차는 같은 연결·트랜잭션에서 유지하며, 조회라는 이유로 `READ ONLY`를 강제하지 않는다.
11. 같은 변수를 원천 입력·검증된 값·저장 결과처럼 서로 다른 의미로 덮어쓰지 않는다. 출처나 처리 단계가 바뀌면 역할이 드러나는 별도 변수로 구분하되, 값과 의미가 같은데 이름만 바꾼 불필요한 복사본은 만들지 않는다.
12. 실패를 빈 목록·`null`·0·임의 기본값·성공 응답으로 바꾸어 숨기지 않는다. 기존 오류 코드와 실패 처리 계약을 따른다. 계약상 정상인 실제 빈 목록·`null`·0과 정상 접근 제한 응답은 유지하고, 원천 미확보·권한 제한·처리 실패를 서로 구별한다.
13. SQL의 줄바꿈·들여쓰기·파일 책임·생성 출력은 [SQL 작성·구성 기준](docs/sql-style.md)을 따른다. 절·변수 선언·조건·처리 블록을 한 줄에 몰아 쓰지 않는다. 파일 분리나 포맷 때문에 SQL 의미·권한·값·실행 순서를 바꾸지 않는다.

### 긴 식과 평가 순서

1. 함수·메서드·생성자 호출의 인수, for의 초기화·조건·갱신 또는 순회 대상, if/while·삼항식에 중첩 호출·변환·조회·조합이 길게 들어가 의미를 한 번에 읽기 어려우면 그 값을 설명하는 지역 변수로 분리한다. 결과를 쓰는 가장 가까운 위치에서 선언하고 금액·시간·ID 같은 단위를 구분한다. 단순 getter·리터럴·짧고 명확한 식에 이름만 다른 변수를 일괄 추가하지 않는다. 글자 수만으로 치환하거나 공개 인수·필드를 바꾸지 않는다.
2. 분리 전후 수신 객체와 인수의 평가 순서·횟수, null/권한 검사, 예외 발생 시점, 트랜잭션·잠금·암호 자료의 생존 범위를 유지한다. 특히 `&&`·`||`의 오른쪽 식과 삼항식의 선택되지 않은 분기를 미리 실행하지 않는다. 선행 조건을 통과한 분기 안에서 필요한 값만 계산한다.
3. 일반 for/while에서 반복마다 바뀌는 조건·상한·갱신값을 루프 밖 변수로 고정하지 않는다. 기존에 평가하던 시점마다 계산하고, 부수효과·컬렉션 변경·지연 순회를 보존할 수 없으면 원래 평가 구조를 유지한다. stream·generator를 읽기 편하게 만들겠다는 이유로 미리 실행하거나 불필요한 목록으로 복제하지 않는다.
4. 람다·콜백·비동기 작업·예외 검사의 대상 식은 원래 실행 범위 안에서 분리한다. 테스트의 실제 실행을 assertThrows 등 검사 밖으로 옮기거나 기대값을 구현에서 계산하지 않는다. 지역 변수로 정리한 뒤 정상·오류·짧은 조건 평가·반복 변경의 영향을 기존 검사와 diff로 확인한다.

### 문자열 상수

API 운영 문자열 상수는 `src/main/java/com/payse/api/constants/` 한 폴더에서 `ApiFieldConstants`(JSON 필드·DB 매개변수), `ApiCodeConstants`(오류·업무 상태), `ApiConfigConstants`(설정 키·경로·HTTP·고정 규격), `ApiMessageConstants`(진단 문구) 네 파일로 관리한다. 각 파일 안에서 인증·금융·분석·급여·도구 등 의미별 중첩 클래스와 구간 주석으로 구분하고 `ApiFieldConstants.Auth.NAME`처럼 출처를 표시한다. 기능마다 상수 폴더를 추가하거나 모든 용도를 한 Constants 파일에 모으지 않는다. 같은 의미와 값만 합치며 JSON 필드·DB 매개변수·상태의 의미가 다르면 구역을 분리한다. 클래스는 final, 생성자는 private, 문자열은 static final로 선언하고 필요한 참조 범위만 공개한다. 별표 static import는 쓰지 않는다. 테스트 상수는 기존 테스트 경로의 `src/test/java/com/payse/api/ApiTestConstants.java` 한 파일에 독립 리터럴로 모으고, 용도별 중첩 클래스·빈 줄·구간 주석으로 구분한다. 운영 상수로 기대값을 만들지 않으며 테스트 상수 폴더를 추가하거나 테스트 파일을 운영 빌드에 포함하지 않는다. 모든 상수 파일명은 `Constants`로 끝나게 한다. 빈 문자열·단순 구분자·테스트 사례값과 선언 자체가 의미를 설명하는 SQL 원문·정규식·어노테이션은 유지한다. 비밀키·사용자 값·환경별 연결정보의 실제 값은 소스 상수로 옮기지 않는다. 단독 실행 도구가 상수 파일을 참조하면 컴파일·실행 경로를 함께 검증한다.

### Java 개행

Java 메서드의 개행·배치는 다음 기준을 따른다. API·AI의 직접 작성한 운영·테스트·도구 Java에 적용하며 SQL·Python·Flutter의 별도 포맷 기준을 바꾸지 않는다.
- 들여쓰기를 포함해 일반 코드는 한 줄 100자 이내로 작성한다. 기본 들여쓰기와 이어지는 줄의 추가 들여쓰기는 각각 공백 4칸이다. 식별자 길이에 맞춘 과도한 수직 정렬은 하지 않는다. import와 분할하면 값·의미가 바뀌는 SQL·프롬프트·정규식·문자열 원문은 폭 예외로 보존한다.
- 검증, 자료 준비, 객체 구성, 저장, 반환처럼 실제 작업의 의미가 바뀌는 곳에 빈 줄 하나를 둔다. 선언과 바로 이어지는 사용은 붙이고 모든 문장 사이에 빈 줄을 넣지 않는다. 빈 줄 두 개 이상이나 코드 내용을 그대로 읽는 구간 주석은 추가하지 않는다.
- 같은 수신 대상에서 이어지는 호출이 3개 이상이거나 한 줄 폭을 넘으면 호출별로 개행하고 점은 이어지는 줄 앞에 둔다. `requestMatchers(...).permitAll()`처럼 두 호출을 함께 읽는 짧은 체인은 유지한다. builder가 반환한 자식 객체를 부모 객체로 바꾸지 않는다.
- 호출이나 선언의 인수·매개변수를 여러 줄로 나누면 한 줄에 하나씩 두고 닫는 괄호는 독립된 줄에 둔다. 상수 목록은 3개 이상이면 세로로 배치한다. 여러 줄 조건은 `&&`·`||`를 이어지는 줄 앞에 두며 단락 평가를 보존한다.
- `if`·`else`·`for`·`while`·`do`의 단일 문장 본문도 중괄호와 별도 줄로 작성한다. `else if`는 한 조건 연쇄로 유지한다. 한 줄에 실행 문장 여러 개를 넣지 않는다.
- 긴 상수 참조는 출처가 명확하고 이름 충돌이 없을 때 중첩 타입을 명시적으로 import하여 `Schema.TYPE_KEY`처럼 쓸 수 있다. 이름이 겹치는 타입은 기존 바깥 클래스 한정을 유지한다. 별표 import·별표 static import로 줄이지 않으며, 값이 같아도 서로 다른 의미의 상수를 합치지 않는다.
- 줄 수나 폭을 맞추기 위한 메서드·래퍼 추출은 하지 않는다. 독립된 작업에 이름이 필요할 때만 기존 분리 기준을 적용한다. 순수 개행만으로 수정 주석을 늘리지 않으며 실제 구현·참조 변경의 주석은 기존 Java 규칙에 따른다.

기존 코드 개선은 담당 작업의 승인된 범위에서 수행한다. 지침 추가만으로 공통 계약·다른 담당 영역을 바꾸거나 전체 코드를 일괄 수정하지 않는다.

## 저장·인증·보안

1. 사용자 금융 조회·설정 쓰기는 인증 세션의 사용자로 제한한다. 공개 생존 확인은 금융 정보를 반환하지 않으며 로그인은 인증 계약에 따라 검증한 뒤 세션을 발급한다. 클라이언트 userId/deviceId는 인증 근거가 아니다. 기존 활성 세션 우선·로컬 PIN 원칙을 유지한다.
2. 금융 설정·관계 확정 쓰기는 expectedDataVersion·ruleVersion·idempotencyKey를 검증한다. 사용자 잠금·참조 소유권·저장 제약·설정/기록/버전 변경을 같은 트랜잭션에서 처리하고 RLS 사용자 설정도 같은 연결을 쓴다. 처리 순서는 기존 DB 설계를 따른다. 취소·장애는 [SQL 취소·커밋 경계](docs/sql-style.md#취소실패와-커밋-경계)에 따라 미완료 변경만 롤백하고, 이미 커밋된 결과·인증 실패 제한·외부 비용 사실을 미실행으로 지우지 않는다. 인증 발급·종료와 LLM 해석 요청에는 금융 설정 버전을 일괄 요구하지 않는다.
3. SQL은 파라미터 바인딩한다. DB 자격·LLM 키·PIN 원문을 코드·응답·로그에 남기지 않는다. 세션 토큰 원문은 인증 성공 시 해당 클라이언트에 전달하는 경우만 허용하고 서버 코드·DB·로그·일반 금융/오류 응답에는 남기지 않는다. 서버에는 토큰 검증값만 저장한다. DB 역할은 최소 권한으로 구성하고 앱에는 DB 자격을 배포하지 않는다.
4. LLM은 필요한 최소 입력만 받고 허용된 구조로 검증한다. LLM 결과로 금액 원천·권한·지급 상태를 확정하지 않는다. 요청·응답의 민감 본문을 로그로 보존하지 않는다. 이 항목의 구현·검증 또는 실행 조건 변경 시 [실행 공통 계약](../../docs/payse-execution-contract.md)과 [API 실행 상세](docs/llm-execution.md)의 해당 절을 먼저 필수로 확인하고 작업 명세 readBefore에 넣는다. 과거 결정·검사 근거 조사 때만 [이력 색인](docs/history/README.md)과 해당 기록을 필수로 읽는다.
5. 업무 검증 422·인증 401·권한 403·버전/멱등 충돌 409 등 기존 계약을 따른다. Spring 기본 오류 응답에 맞추려고 계약을 바꾸지 않는다.

## Java 주석

1. 이름 있는 클래스·인터페이스·annotation·enum·record, 직접 작성한 메서드·명시적 생성자 바로 위에 Javadoc으로 목적, `@created YYYY-MM-DD`, `@usedBy 주요 클래스.메서드 또는 프레임워크 진입점`을 적는다. 인자·반환·예외의 계약도 필요한 만큼 적는다.
2. DTO/VO 클래스 또는 record 위에는 목적·생성일·주요 사용 클래스/메서드를 기록한다. API 객체와 DB 객체를 무조건 같은 클래스로 만들지 않는다.
3. 작업 기준 커밋에 존재하던 메서드의 구현·시그니처·계약을 수정하면 생성일을 유지하고 같은 Javadoc에 `@modified YYYY-MM-DD - 변경 목적`을 추가한다. 같은 날 같은 목적은 한 줄로 정리하고 다른 수정 기록은 유지한다.
4. 기존 DTO/VO의 필드·타입·의미·검증 조건 변경에도 클래스 주석에 같은 수정 기록을 남긴다. 기준 커밋에 없는 신규 선언을 완성하는 편집은 생성 작업이다. 기준을 바꿔 기존 선언을 신규로 취급하지 않는다.
5. 주요 호출자는 실제 확인한 사용처만 적고 미연결은 `미연결: 예정 사용처 ...`로 구분한다. 기존 코드의 생성일을 확인할 수 없으면 `@created unknown - 이력 확인 불가: 구체적 사유`를 사용한다. 신규 코드에는 실제 날짜를 쓴다.
6. 주석은 짧고 구체적으로 쓴다. API의 필수 수정일·목적만 코드에 남기고 상세 작업 과정·실패 로그는 Git/PR에 기록한다.
7. 생성 코드·record 자동 접근자·람다 본문에는 주석을 복제하지 않는다. 익명 클래스에 직접 선언한 메서드와 직접 작성한 테스트 메서드는 포함한다. 자동 검사와 테스트 실행 결과를 구분한다.

```java
/**
 * 사용자에게 허용된 계좌 원천 정보를 조회한다.
 * @created 2026-10-19
 * @usedBy AccountController.list
 * @modified 2026-10-20 - 소유자 확인 누락 보완
 * @param userId 검증된 서버 세션의 사용자 ID
 * @return 해당 사용자의 원천 계좌 목록
 */
```

예시는 형식만 참고하고 실제 날짜·호출자를 적는다.

## SQL·테스트 자료

1. SQL에 호출별 사용자·계좌·거래 ID를 직접 적지 않는다. 런타임은 인증 문맥과 검증된 입력을 바인딩하고, 데이터 의존 테스트는 검증된 준비 자료의 ID와 관계를 변수로 전달한다. 표시명·배열 순서·임의 `LIMIT 1`로 대상을 선택하지 않는다. 단일 대상의 존재·건수·소유권·참조·필요한 사전 상태를 검사하고 0건 또는 여러 건이면 본 검사 전에 실패시킨다. 실제 변경 행 수도 확인한다.
2. 테스트 준비값은 대상과 사전 상태를 식별하는 데만 쓴다. 경계값·기대 오류·기대 결과를 검사 대상 구현에서 추출해 정답으로 삼지 않는다. 도메인 상수·형식 검사 문자열·경계 입력은 명시적으로 유지할 수 있으며, 재현 가능한 더미 생성과 승인된 이행 매핑은 단일 기준에서 관리한다. 복사한 고정 ID 목록으로 준비 단계를 대신하지 않는다. 테스트 도구를 운영 API·공개 금융 응답·영구 DB 구조의 의존성으로 추가하지 않는다. 실행 방법은 [DB 테스트](docs/database-tests.md)를 따른다.
3. 금융 더미의 상품·가맹점·설명은 자연스러운 가상 명칭을 사용한다. 생성기와 검사는 표시명·첫 행으로 거래를 선택하지 않고 ID·소유권·확인된 관계를 검증한다. 합성 출처와 시나리오 설명은 기술 메타데이터에 남긴다. 은행 기준정보 등재와 사용자 원천 보유·동의·연결 가능 여부를 구분하며 기준 목록 전체를 연결 가능 목록으로 반환하지 않는다.

## 검증·협업

1. 새 기능의 정상·오류·타 사용자 접근·중복/충돌을 해당 계층에서 검사한다. 실제 PostgreSQL의 RLS/동시성 검사를 H2 성공으로 대체하지 않는다. 초기 차단을 인증 구현 완료로 보고하지 않는다.
2. 저장소 루트에서 `node scripts/harness/run-api.mjs check`를 실행한다. 자동 검사는 목적·생성일·사용처의 형식 및 기재된 모든 수정일/목적을 확인한다. 날짜·설명의 사실성, unknown 사용 근거, 수정 이력 누락은 diff 리뷰로 확인한다.
3. 공통 계약 변경은 영향을 받는 담당자와 확인한다. 프론트 동기화가 필요하면 API 담당자와 API 작업 에이전트는 대상 경로, 변경이 필요한 필드·호출부, 변경 이유, 호환 영향, 검증 항목을 정리해 전달한다. **실제 모바일 파일 수정은 프론트 담당자가 수행한다.** API 작업에서는 `apps/mobile/`의 소스·테스트·더미 자산·문서·설정 파일을 읽어 대조할 수 있지만 직접 생성·수정·삭제·포맷하지 않는다. 최소 동기화나 API 검사 통과를 이유로 이 경계를 넘지 않는다. 프론트 담당자의 반영 및 검증 결과를 확인하기 전에는 모바일 동기화 완료로 보고하지 않는다.
