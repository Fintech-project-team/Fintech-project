# 분석 접수·조회·재시도 API 계약

상태: **접수·조회·재시도·보존 기억 기간 목록의 API·DB 연결과 격리 DB·모의 공급자 검증 완료, B 연동 미검증**. 기본 `AnalysisRuntime`은 비활성으로 실제 공급자·KMS 전송을 열지 않는다. 운영 활성화와 격리 DB·모의 공급자의 검사 결과는 구분한다. [공통 실행 정책](../../../docs/payse-execution-contract.md)과 [LLM 실행 상세](llm-execution.md)를 우선한다. 아래 경로·필드는 분석 전용 자원이며 기존 금융 v4 Snapshot에 추가하지 않는다. API 구현·모바일 연동 시 이 문서와 [저장 구조](analysis-storage.md), [업무별 의미 계약](analysis-meaning.md)을 필수로 읽는다.

## 1. 기존 API와의 경계

2026-11-04 확정한 [Java·Dart 연동 합의](../../../docs/analysis-protocol.md)에 공통 HTTP Schema, 공개 지문 30개 사례, tracker·조회 규칙 및 A/B 인수 순서를 기록했다. [모의 공급자 서버](analysis-mock.md)에서 실제 인증·DB 경로로 공동 연동한다.

`GET /analysis-jobs/{id}`에 단일 `Prefer: wait=5` 헤더를 보내면 실행 중인 작업의 완료를 최대 5초 비동기로 기다린다. 기본 조회는 즉시 반환하며 다른 선호 값은 무시한다. 완료·실패 신호 또는 대기 시간 종료 후 같은 상태 봉투를 반환하고 인증·소유권을 다시 검사한다. 작업마다 대기 관찰자는 하나이며 추가 조회는 즉시 상태를 반환한다. DB 트랜잭션과 요청 처리 스레드를 대기 동안 붙잡지 않고 모델을 재호출하지 않는다. 시간 종료의 `running`은 실패나 후보 0개가 아니다. 앱 종료 후 알림·자동 복구 기능은 이 선택적 대기와 별개다. 모바일 반영·실기기 검증은 아직 완료하지 않았다.

- Bearer·HTTPS·UTF-8 JSON·`Cache-Control: no-store`와 [공통 오류 봉투](../../../docs/api-contract.md#6-오류-응답)를 재사용한다. userId는 서버 세션에서 정한다. 요청에 userId·PIN·설치 ID를 받지 않는다.
- ID/Time/Version은 [공통 타입](../../../docs/data-model.md#1-읽는-방법과-공통-규칙)을 따른다. 분석 진행은 금융 `dataVersion`·원천·설정·`write_receipts`를 바꾸지 않는다.
- 아래 `contractVersion`은 분석 통신 버전 `PAYSE-ANALYSIS-1`이다. 금융 `PAYSE-API-0.6-4`, `PAYSE-DRAFT-4`, `PAYSE-CALC-1`은 유지한다. API 구현과 별도로 B의 입력 생성·파서·상태 복구를 공동 확인한다. 기존 금융 v4 소비자가 분석 API까지 지원한다는 뜻은 아니다.
- 접수는 기존 EX-A/B 동작 또는 확정된 만료 작업의 사용자 복구 동작에 종속한다. 독립적인 ‘지금 분석’, 유효 결과 강제 재생성, 조회 중 모델 호출을 추가하지 않는다. C/D/E는 활성 기능으로 자동 포함하지 않는다.
- 금융·기억의 기간 조회는 DB에서 열람할 범위다. 1년·2년 조회를 허용해도 분석 한 요청의 거래60개·반복 후보20개 및 토큰·운영비 제한은 유지한다. 조회한 전체 자료를 자동으로 LLM에 보내지 않는다.

## 2. 요청 단위와 전달 항목

| 이름             | 타입·필수 여부                                         | 의미·검증                                                                                                                                                                             |
| ---------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| context          | 객체·필수                                              | `schemaVersion`, `dataVersion`, `sourceVersion`, `ruleVersion`, `asOf`, `inputRevision`, `localSessionEpoch`, `selectedAccountIds`를 포함. 선택 집합은 분석 접근 권한을 확대하지 않음 |
| triggerKind      | `A`, `B`, `recovery`·접수 필수                         | A/B는 기존 연결·원천 변경 동작. recovery는 만료 작업의 명시 복구이며 이전 작업·현재 입력 검증 필수                                                                                    |
| semanticTaskKind | `transactionMeaning` 또는 `recurringMeaning`·접수 필수 | 표시용 거래 의미/로컬 반복 후보 의미. 수치 판정은 Dart                                                                                                                                |
| items            | 객체 배열·접수 필수                                    | 각 항목에 `itemKey:string`, `evidenceTransactionIds:ID[]`, `candidateIds:string[]`. 빈 후보 집합은 거래 의미 해석에서만 허용. 존재·공개 범위·중복을 검사                              |
| inputHashHint    | string·접수 필수                                       | 서버 모델/프롬프트 설정을 제외한 Flutter 입력 부분의 정규 지문. **힌트만으로 결과 본문 반환·전송·권한 허용하지 않음**                                                                 |
| reasonCodes      | string 배열·접수 필수                                  | 서버에서 허용한 원인과 실제 참조를 대조. 빈 배열 허용. 계산 의존성 예외를 클라이언트 주장만으로 승격하지 않음                                                                         |
| idempotencyKey   | string·접수/제출/재시도/삭제 필수                      | 기존 키 문자·길이 규칙 재사용. 같은 키·다른 요청은 409. 세션 토큰은 요청 지문에서 제외                                                                                                |
| input            | 객체·실행/결과 재사용 검증 시 필수                     | 공통 실행 상세의 필요한 최소 원천/로컬 특징/허용 후보만. 입력 스키마는 의미 작업별로 분리. 원문 전체·기기 인증 정보·가상 소비 영속화 금지                                             |

context의 각 필드는 공통 계약의 타입을 유지한다. `inputRevision`과 `localSessionEpoch`는 서버가 금융 원천을 생성하는 근거가 아니며 응답이 현재 화면에 속하는지 Flutter가 확인하는 값이다. prompt/model/policy/응답 스키마 버전은 서버 승인 설정에서 정한다. 모델의 confidence를 검증된 정답률이나 보존 권한으로 바꾸지 않는다.

A/B 입력·출력 schema와 의미 enum은 [의미 계약](analysis-meaning.md)에 작성했다. 근거60·후보20과 실행/제출 시간창은 [확정 초기 프로필](llm-execution.md#호출-프로필)을 따른다. 본문 상한은 **실제 UTF-8 수신 바이트 64 KiB(65,536바이트)**다. 초과하면413이며 문자 수로 대신 검사하지 않는다. 인증을 먼저 확인하므로 무효 세션과 잘못된 본문이 겹치면401이다.

## 2.1 입력 지문·기억 식별

- `memoryKey`: 거래 의미는 의미 작업 종류+대상 거래 ID, 반복 의미는 의미 작업 종류+직접 근거 거래 ID 집합으로 구분한다. 사용자 범위는 모든 조회·저장·삭제 키에 별도로 강제한다.
- `evidenceHash`: 해당 기억에 관련된 거래 원천 필드·명시 관계·기존 분류·로컬 후보 특징을 정규 JSON으로 만들고 UTF-8의 SHA-256을 `sha256:`+소문자64자리로 표현한다. 원천 문자열을 임의 trim/정정하지 않는다.
- 객체 키는 정렬하고 집합으로 정의된 거래 ID·관계·관찰 월은 안정된 순서로 직렬화한다. 의미가 있는 배열을 임의 집합으로 바꾸지 않는다. 항목별 근거→기억 집합→요청 지문의 단계는 `AnalysisIdentity`/`AnalysisJson`과 대응한다.
- `itemKey`, 후보 임시 ID, 화면 epoch/revision, 전체 dataVersion, 조회 시각, 멱등 키는 같은 기억·관련 근거 식별을 바꾸지 않는다. 모델/프롬프트/정책/응답 버전은 결과 캐시 자격에 포함하되 사용자 삭제 차단의 기억 식별에는 넣지 않는다.
- 지문은 익명화나 권한 증명이 아니다. 현재 사용자·금융사 연결·실제 원천·문맥을 별도 검사한다. 원천이 같아도 다른 사용자 캐시를 공유하지 않는다.

`inputHashHint`는 공개 입력의 항목별 의미 지문만으로 Flutter가 재현한다(`AnalysisIdentity.hint`). DB의 `evidence_hash`는 이 값과 별개로, 서버가 해당 항목의 근거·원거래·명시 관계에 속한 실제 원천 값(금액·날짜 포함)을 결합한 지문이다(`boundItems`). 다른 항목의 거래나 전체 버전만 바뀌면 해당 기억을 무효화하지 않는다. 원천의 userId·sourceVersion·sourceRef는 이 지문에 넣지 않고 사용자 권한과 현재 문맥으로 별도 검증한다. 서버 최종 `analysisInputHash`는 공개 입력 지문·승인 실행 버전·항목별 DB 지문을 결합한다(`boundInputHash`). DB 지문을 클라이언트가 제출하거나 서버 근거 없이 만들어서는 안 된다.

API 요청 JSON의 지문과 모델 전송용 짧은 ID 별칭은 다르다. 별칭이나 임의 SHA 문자열을 영구 기억 식별로 대신 사용하지 않는다.

## 3. 접수부터 복구까지

| 경로                                | 요청                                                                  | 응답·효과                                                                                                                      |
| ----------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `POST /analysis-jobs`               | 접수 항목·context·멱등 키                                             | 새 접수 202, 기존 접수 재관찰 200. 최소 메타데이터만 저장. 접수 성공은 분석 완료가 아님                                        |
| `GET /analysis-jobs/{jobId}`        | 현재 Bearer                                                           | 200 상태. 제출 허가의 발급·갱신은 분석 행만 변경하며 모델 호출·금융 저장은 하지 않음                                           |
| `POST /analysis-jobs/{jobId}/input` | context·input·허용 식별·멱등 키                                       | 재검증한 기존 결과면 200, 새 시도 원자 등록이면 202. 본문은 처리 메모리만 사용                                                 |
| `POST /analysis-results/query`      | 현재 context·semanticTaskKind·최소 input, 선택 resultId               | 조회 전용 200. 검증된 결과 또는 사용 불가 사유. 큰 로컬 특징을 GET 본문/URL에 넣지 않기 위한 POST이며 모델 호출·저장 변경 없음 |
| `POST /analysis-jobs/{jobId}/retry` | context·input·멱등 키, 완료 불명일 때 `acknowledgeDuplicateRisk:true` | 유효 결과 200/실행 중 관찰 200/새 사용자 시도 202. 같은 재시도 연타는 시도 1개                                                 |

1. 접수 단계는 본문 없는 descriptor를 검증한다. 서버가 같은 사용자·정규 descriptor·힌트의 대기 접수를 재관찰하게 할 수 있으나 이를 검증된 의미 지문으로 확정하지 않는다. 다른 descriptor를 같은 키로 보내면 409다.
2. 상태 응답의 `action=submitInput`일 때 단기 실행 허용 식별을 전달한다. 허용 자체로 비용/실행 슬롯을 영구 점유하지 않는다. 제출 허용은 발급부터 최대60초이고 해당 시도의180초 실행창을 넘기지 않으며 사용 직전 권한/입력/작업 상태를 재검증한다. 상태 조회는 이 허가를 발급·갱신하기 위해 분석 작업 행을 변경할 수 있다. 금융 원천·설정·dataVersion과 모델 호출은 변경하지 않는다. 발급 시 비용이나 실행 슬롯을 점유하지 않는다.
3. 본문 제출 시 현재 세션·참조·원천/설정 버전을 재검증하고 서버가 클라이언트 입력 부분의 정규 지문을 다시 만들어 힌트와 대조한다. 불일치하면 422로 거절한다. 일치한 입력에 서버의 모델·프롬프트·응답 스키마·정책 버전과 항목별 DB 원천 지문을 결합해 최종 analysisInputHash를 만든다. 클라이언트 힌트와 최종 서버 지문을 직접 비교하지 않는다. 정규 지문은 §2.1 규격을 따른다. B의 동일 입력 지문 구현은 별도 확인한다. 서로 다른 임시 접수가 같은 검증된 의미 지문이면 사용자 범위 잠금 아래 기존 진행 작업/유효 결과에 합류시킨다. 응답 `jobId`는 이후 관찰할 대표 작업이다. 임시 ID는 그 대표 작업 참조만 유지하며 새로운 전송을 만들지 않는다. 합류 후 임시 ID의 상태 조회·재제출도 대표 jobId를 반환하므로 Flutter는 응답 jobId를 이후 관찰 대상으로 갱신한다.
4. 유효 결과 재사용 검사를 **배치 대기·비용 제한보다 먼저** 수행한다. 일반 신규 전송은 Q2 조건·프로필·슬롯·비용을 모두 검사한다. 아직 실행할 수 없으면 본문을 버리고 대기 상태를 반환하며 영속 큐를 만들지 않는다.
5. 외부 호출 전 짧은 DB 트랜잭션에서 시도를 커밋한다. 유료 경로는 비용 예약까지 함께 커밋해야 하며 비용 장부가 미구현인 현재는 활성화하지 않는다. 호출은 트랜잭션 밖에서 한다. 결과 검증·암호화 후 별도 트랜잭션에서 결과와 완료 상태를 함께 커밋한다.
6. 앱이 입력 제출 전에 종료되면 분석 완료를 보장하지 않는다. 입력 수신·전송 후에는 앱 연결 종료만으로 취소하지 않는다. 서버 재시작으로 본문을 잃으면 자동 재전송하지 않고 사용자 재시도로 복구한다.

독립 결과 조회는 실행 허용·배치 대기·비용 예약과 무관하게 현재 관련 입력을 검증한다. 장기 보존 결과는 작업 식별이 3개월 뒤 삭제되어도 이 경로로 재조회한다. 결과 조회를 위해 현재 관련 입력을 다시 제출하는 것은 모델 재시도가 아니다. 유효 결과라면 비용·모델 호출 0회다. 원래 분석 출처는 보존하고 현재 조회의 epoch/revision은 별도 응답 문맥에 둔다. 조회마다 원래 저장 시각을 갱신하지 않는다.

## 4. 상태와 응답

작업 응답 봉투: `{contractVersion, jobId, state, action, resultAvailability, resultId?, progress?, context?, provenance?, result?}`. 독립 결과 조회 응답은 `{contractVersion, resultAvailability, context, resultId?, provenance?, result?}`이며 삭제된 3개월 작업 ID에 의존하지 않는다. 상태만 조회할 때 현재 화면 문맥을 받지 않으므로 `context`는 생략한다. 현재 구현은 상태/input/retry 응답에 결과 식별과 다음 동작을 반환하고, 해석 본문은 현재 입력을 다시 검증한 `POST /analysis-results/query`에서 반환한다. 상태 조회만으로 본문을 복원하지 않는다. 공개 provenance는 최초 `schemaVersion`, `dataVersion`, `sourceVersion`, `ruleVersion`, `asOf`, 실행 `versions`, `analysisInputHash`만 제공한다. 저장 당시 selectedAccountIds·localSessionEpoch·inputRevision을 출처로 재노출하지 않으며 현재 요청의 값은 응답 context로 구분한다.

| 필드               | 값                                                                                                    | 의미                                                                                      |
| ------------------ | ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| state              | `queued`, `awaitingInput`, `running`, `succeeded`, `failed`, `outcomeUnknown`, `cancelled`, `expired` | 서버 작업 진행. 결과의 현재 사용 자격과 분리                                              |
| action             | `wait`, `submitInput`, `readResult`, `retry`, `refreshInput`, `none`                                  | 서버가 현재 허용한 다음 동작. `retry`는 자동 실행 지시가 아님                             |
| resultAvailability | `unchecked`, `available`, `partial`, `missing`, `inactive`, `stale`, `expired`, `deleted`             | 검증 전 unchecked. 일부 기억만 현재 유효하면 partial. succeeded+stale/partial도 가능      |
| progress           | `{accepted, completed, unresolved}` 정수                                                              | 접수 범위 내 항목 수. 전체 금융 자료 확보/전체 분석 완료 의미 아님                        |
| provenance         | 객체                                                                                                  | 최초 분석의 원천/설정/규칙/모델/프롬프트/응답 버전·asOf·지문. 금융 버전으로 위장하지 않음 |

최소 저장 구조에서 job 하나는 같은 의미 종류의 검증된 입력 묶음과 하나의 완결 응답 단위다. 각 itemKey에 해석 또는 unknown이 모두 있어야 succeeded다. unknown은 의미 미확정이지만 형식상 처리 완료이며 progress.completed에 포함한다. 실패 시 unresolved는 아직 유효 응답이 없는 항목 수다. 일부 항목만 있는 응답을 먼저 최종 결과로 저장하지 않는다. 독립 근거 그룹은 별도 job으로 접수하고 여러 job의 전체 완료를 과장하지 않는다. 다중 shard 집계·항목별 부분 결과의 독립 채택은 후속 설계이며 미확정 4분할 제안을 자동 구현하지 않는다. 상세 기록 제거 후 progress는 생략하며 0으로 꾸미지 않는다. 모델이 구조적으로 정상인 `unknown`을 반환한 것과 모델 장애는 다르다. 의미 출력은 별도 [업무 규격](analysis-meaning.md)을 따르며 금융 category·급여 확정 필드에 전용하지 않는다.

결과 본문은 `items`의 개별 기억 ID·입력 itemKey·현재 사용 가능한 해석과 `itemAvailability`의 항목별 제공/삭제/만료/구근거/비활성 사유로 구분한다. 사유에는 삭제한 본문을 포함하지 않는다. 결과 묶음 ID는 작업 채택/재사용 단위이고 itemId는 기억 관리·삭제 단위다. 현재 요청의 필요 범위와 대조해 모두 유효할 때만 available, 일부만 유효하면 partial로 응답한다. 전부 사용할 수 없으면 최상위는 `missing`이며 `itemAvailability`에 삭제·만료·구근거·비활성 등 실제 항목별 사유를 남긴다. 하나라도 사용 가능하면 일부는 `partial`, 모두는 `available`이다. 삭제한 해석 본문을 사유에 넣지 않는다. 저장 전 모델 출력은 전체 입력 항목의 완결성을 검사하고, 조회 응답은 현재 사용 가능한 부분 집합만 동일 의미·근거 규칙으로 재검증한다(`outputSubset`). 부분 조회를 모델의 불완전 출력 허용으로 해석하지 않는다.

작업의 succeeded/progress는 당시 입력 처리 완료를 뜻한다. 이후 기억 삭제로 과거 작업을 실패로 바꾸거나 progress를 재계산하지 않는다. 모델 응답의 전체 항목을 검증한 뒤 저장 시점의 삭제 차단 항목은 본문 없이 제외 사실만 남긴다. 이것은 불완전한 모델 응답을 부분 채택하는 것과 다르다. 삭제/차단 때문에 제공하지 않는 항목은 자동 재시도 대상으로 삼지 않고 사용자 재시도에서도 차단을 먼저 검사한다.

## 5. 사용자 재시도와 늦은 응답

실패·완료 불명·취소·만료 응답에는 선택 필드 `review`를 제공한다. `reason`은 해당 작업 state, `requiresUserInput:true`, `itemsAvailable`은 항목 키 목록의 보관 여부, `retryRequiresAcknowledgement`는 `outcomeUnknown`일 때 true다. 상세가 남아 있으면 `items:[{itemKey}]`를 제공하고 종료 후 7일 또는 상세 정리 후에는 `items`를 생략한다. 목록 부재는 해결 완료가 아니다. 거래 원문·거래 ID·후보 본문·공급자 오류를 상태 응답에 추가하지 않는다. `action`과 재시도 요청 규격은 유지한다. [화면 연결 및 검증 기준](analysis-recovery.md)을 따른다.

- 로그아웃은 해당 세션의 queued/awaitingInput 작업과 제출 허가를 취소한다. 새 세션은 상태를 조회할 수 있지만 옛 허가로 실행할 수 없다. 현재 권한·같은 근거 검증을 통과한 사용자 명시 retry만 다시 실행한다. 이미 전송된 작업은 로그아웃을 미전송 근거로 삼지 않으며 옛 세션의 응답 채택을 차단한다.
- 실패 후 관련 DB 금액·날짜·분류 등 근거가 바뀌면 공개 inputHashHint가 같아도 같은 작업 retry는409 STALE_DATA로 거절하고 시도를 추가하지 않는다. 현재 원천의 기존 A/B 동작은 별도 접수로 구분한다.
- 기존 실행이 확실히 진행 중이면 관찰로 합친다. 전송 완료 여부가 불명하면 사용자에게 중복 실행·비용 가능성을 표시한 뒤 명시적 동의가 있는 새 시도만 접수한다. 최대 횟수는 미지정이며 자동 재호출은 0회다.
- 같은 유효 입력의 **먼저 검증·커밋된 정상 결과 1개**만 채택한다. 늦은 결과는 이미 채택한 묶음을 덮어쓰지 않으며 그 시도의 비용 사실은 남긴다. 삭제된 기억을 늦은 결과에서 복원하지 않는다. 원천/권한이 달라졌으면 빨리 도착했어도 채택하지 않는다.
- 최초 접수부터 3개월이 지나면 기존 작업을 다시 실행하지 않는다. 현재 자료의 별도 접수 안내를 반환한다. 사용자 명시 복구 동작에서만 `triggerKind=recovery`, `previousJobId`, 현재 `input`을 추가한 새 접수를 허용한다. 이전 작업의 소유권과 고정 식별 기한 경과를 검사하고 현재 유효 결과를 먼저 찾는다. 일반 ‘지금 분석’ 버튼으로 확대하지 않는다. 유효 결과 재사용은 새 분석이 아니며 최초 저장/만료를 변경하지 않는다. 복구가 실제 새 분석을 실행·검증·저장한 경우만 새 결과의 저장 시각부터 달력3개월을 적용한다. 기존 사용자 삭제 차단은 recovery에서도 유지한다. 이전 비용 사실은 별도로 보존한다.
- 최초 작업 실행 deadline과 새 사용자 시도의 실행 시간창은 구분한다. 최초 접수와 각 명시 재시도는 각각180초 실행 시간창을 사용한다. 재시도로 원 작업의3개월 식별 기한은 늘리지 않는다. 최소 식별 기한을 재시도로 늘리지 않는다.
- commit 응답이 유실되면 같은 키/본문으로 먼저 DB 결과를 조회한다. SQL 실패는 미커밋 업무만 롤백하고 이미 전송된 비용·인증 실패 기록을 없애지 않는다.

## 6. 보존 정보의 사용자 확인·삭제

통신비·월세·급여를 한 번에 분석해도 각각 itemId·불변 근거 지문·독립 암호화 키·보존 상태를 둔다. 월세 삭제는 다른 두 기억을 지우지 않으며 다른 묶음의 동일 월세 기억도 차단한다. 금융 원천·확정 설정은 유지한다.

AI가 보존·참조 상태를 지정하는 최신 정책은 공통 실행 계약을 따른다. 서버는 구조화된 보존 결정·근거 ID·사유·정책 버전과 사용자 소유권을 검증한다. 모델 문장에 포함된 SQL/명령/권한 변경 지시는 실행하지 않는다. 필수 참조여도 사용자 정정·원천 사실·유효성·삭제를 우회할 수 없다.

| 경로                                 | 요청/응답                                               | 경계                                                                                                                                |
| ------------------------------------ | ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `GET /analysis-memories`             | `startDate`·`endDate` 선택 쌍, `cursor` 선택 → 200 목록 | 개별 기억 확인·삭제용. 본문 열람 가능 여부와 실제 적용 자격을 구분하며 최신 입력 없이 재사용 가능으로 판정하지 않음                 |
| `DELETE /analysis-memories/{itemId}` | `Idempotency-Key` 헤더, 본문 없음 → 204                 | 해당 기억과 같은 기억·근거의 사본을 즉시 참조 차단·폐기 대상으로 등록. 다른 기억은 유지. 금융 원천·사용자 확정 설정은 삭제하지 않음 |

### 6.1 기억 기간 목록

`MemoryController`·`MemoryCatalog`가 제공하는 관리용 목록이다. 요청은 현재 Bearer 세션의 사용자로 제한한다. 거래 발생일이 아닌 **기억의 최초 `storedAt`**을 기준으로 조회하며, 저장된 기간이 1년·2년이더라도 별도 조회기간 상한을 만들지 않는다. 이 기간 조회가 보관 기한을 연장하거나 만료·삭제 본문을 다시 공개하는 것은 아니다.

- `startDate`·`endDate`: 둘 다 생략하거나 둘 다 `YYYY-MM-DD`로 보낸다. 존재하는 0001~9999년 날짜만 허용하며 시작일이 종료일보다 늦으면 거절한다. 같은 날짜는 허용한다. Asia/Seoul의 시작일 00시부터 종료일 다음 날 00시 전까지로 양끝 날짜를 포함한다.
- 첫 페이지는 `cursor`를 생략한다. 후속 페이지는 받은 `cursor`와 동일한 날짜 쌍을 보낸다. 날짜 없이 시작했다면 후속 페이지에서도 날짜를 보내지 않는다. 필터 변경은 커서 없는 새 조회로 시작한다.
- 페이지 크기는 **최대 20건**, 기억 ID 오름차순이다. `offset`·`limit`·정렬 인자와 전체 `count/total`은 제공하지 않는다. 다음 페이지 유무를 위한 한 행만 추가 조회한다.
- 응답은 `contractVersion: PAYSE-ANALYSIS-1`, `items`, `pageInfo: {nextCursor, hasMore}`이다. 마지막 페이지는 `nextCursor:null`, `hasMore:false`이며 실제 빈 목록은 `items:[]`이다. 다음 페이지가 없다는 것은 현재 기간·권한에 따른 목록의 끝이며 금융 거래 확보 범위를 뜻하지 않는다.

| 항목 필드                                               | 의미                                                                                                          |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `itemId`, `resultId`, `semanticTaskKind`                | 개별 기억·최초 결과 묶음·의미 작업 구분. 삭제 단위는 itemId                                                   |
| `contentAvailability`                                   | 아래 표의 현재 관리용 본문 열람 상태                                                                          |
| `resultAvailability`                                    | 항상 `unchecked`. 실제 적용은 최신 input을 받는 `POST /analysis-results/query`에서 검증                       |
| `active`, `isReference`, `important`, `referencePolicy` | 저장된 AI 보존·참조 상태. active=false 또는 isReference=false만으로 관리용 본문 열람을 막지 않음              |
| `storedAt`, `normalExpiresAt`, `metadataVersion`        | 최초 저장·일반 만료 시각·기억 메타 버전. 금융 dataVersion과 별도                                              |
| `interpretation`, `retentionReason`, `sourceChanged`    | contentAvailability=available일 때만 제공. sourceChanged는 저장 당시 관련 원천 지문과 현재 원천이 다른지 표시 |

| contentAvailability | 본문 처리                                                                                                        |
| ------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `available`         | 현재 소유권·공개 권한·보관 조건을 통과한 관리용 본문 제공. 올바른 최신 해석이거나 실제 적용 가능하다는 뜻은 아님 |
| `expired`           | 일반 만료 또는 폐기 요청. 본문·보존 이유·sourceChanged 생략                                                      |
| `deleted`           | 사용자 삭제 또는 동일 기억·근거 재보존 차단. 본문·보존 이유·sourceChanged 생략                                   |
| `restricted`        | 관련 거래의 현재 금융 연결·소유권을 확인할 수 없음. 숨겨진 거래 ID·본문·보존 이유·sourceChanged 생략             |
| `unverified`        | 011 이전 기억 등 원천 참조 메타 미확보. 근거를 추정하지 않고 본문·보존 이유·sourceChanged 생략                   |

삭제·만료·권한 제한 항목은 소유한 기억의 관리 메타만 반환할 수 있다. 사용자가 삭제할 수 있도록 itemId는 유지하되 암호문·키·서버 내부 source_refs/source_hash는 반환하지 않는다. `sourceChanged:false`도 로컬 반복 특징·현재 사용자 입력까지 검증한 결과가 아니다. 변경된 원천의 과거 해석을 관리 목적으로 보여주는 것과 AI의 현재 적용은 구분한다.

SQL 조회는 기간·사용자·ID 페이지로 제한한다. 커서는 목적·페이지 크기·기간·사용자/세션·금융 공개 문맥·기억 메타 지문에 연결한다. 기억 저장·삭제·메타 변경·만료 전환 또는 금융 조회 문맥 변경으로 달라지면 `409 STALE_DATA`이며 첫 페이지부터 다시 조회한다. 현재 시각 자체를 지문에 넣지는 않는다. 목록 조회·커서 발급으로 금융 dataVersion이나 기억의 최초 저장·만료 시각을 변경하지 않는다.

암호문 복호화/KMS는 DB 트랜잭션 밖에서 수행한다. 반환 직전 다시 인증하고 현재 목록·공개 권한·만료·삭제 상태를 비교한다. 중간 변경은 본문을 반환하지 않고 충돌로 처리하며 종료된 세션은401이다. KMS·DB 실패를 빈 정상 목록으로 바꾸지 않고503으로 반환한다. 복호화한 요약·보존 이유를 평문 DB 열·로그·커서·중간 캐시에 저장하지 않는다.

목록 요청의 추가 오류는 다음과 같다. 인증 검사가 필터 검사보다 먼저다.

- `400 VALIDATION_FAILED`: 허용하지 않은 query 이름 또는 중복 query 값.
- `400 INVALID_CURSOR`: 비어 있거나 형식·무결성·페이지 규격이 맞지 않는 커서.
- `422 VALIDATION_FAILED`: 날짜 쌍 누락·잘못된 날짜·역전된 기간·GET 본문 또는 Content-Encoding 전송.
- `403 RESOURCE_FORBIDDEN`: 유효하게 인증됐지만 커서가 다른 사용자/세션에 속함.
- `409 STALE_DATA`: 기존 커서의 기간/문맥 변경 또는 복호화 전후 재검증 충돌.

삭제 접수와 모든 백업·키의 비가역 파쇄 완료는 다르다. 실제 키/백업 폐기 구현 전에는 완료라고 보고하지 않는다. 단순 중요보존 해제는 원래 3개월 기한으로 돌아가지만 **사용자 삭제는 비활성화와 다르다**. 동일 근거의 자동 재보존은 차단하고 관련 근거가 바뀌면 새 판단을 허용한다. 차단은 사용자·의미 작업·안정된 기억 식별·관련 근거 지문으로 관리하며 본문을 복제하지 않는다. 임의 resultId/itemKey·분석 묶음 구성·모델 요약 문장으로 같은 기억 판정을 바꾸지 않는다. 모델/프롬프트 교체·탭 이동·무관한 dataVersion 증가로 차단을 우회하지 않는다. 삭제와 늦은 응답 채택은 같은 잠금 규칙으로 직렬화한다.

## 7. 오류·남은 구현 및 검증

공급자 정상 응답을 받은 뒤 암호화·원천 재검증·저장이 실패하면 `failed`로 기록하고 이미 확인한 사용량을 보존한다. 공급자 완료 여부를 모르는 경우만 `outcomeUnknown`으로 기록한다. DB/인증 장애로 실패 기록 자체를 남기지 못하면 기존 전송 행을 보존하고 실행창 종료 후 완료 불명으로 관찰한다. 이미 커밋된 결과·확정 사용량은 후속 실패 콜백으로 덮지 않는다.

기존 400/401/403/409/413/422/429/503 봉투를 재사용한다. 없는 ID·타 사용자 ID는 같은 403으로 처리한다. 작업 만료는 소유권 기록이 남아 있을 때 권한 확인 후 상태 expired로 반환하고, 만료 작업 실행 요청은409로 거절한다. 식별이 이미 폐기되어 소유자를 확인할 수 없으면 기존의 없는 자원과 같은 403이며 만료 여부로 자원 존재를 노출하지 않는다. 결과 미준비는 정상 상태 응답이며 빈 정상 결과로 바꾸지 않는다. 구현한 경로는 기존 오류 봉투와 고정 오류 코드를 사용하며 B의 오류 처리·화면 연결은 별도 검증한다.

다음은 별도 미완료 범위다.

- 7일 상세/3개월 식별·기억 정리 작업, 계정 최종 파쇄, KMS·백업/WAL/복제본의 비가역 폐기는 별도 미완료다.
- 실제 공급자/KMS 활성화·실측 품질·토큰·요금, 비용 예약/정산 장부와 정확한 운영비 경계. 기본 runtime은 전송을 거절하며 모의 응답이나 임시 키로 운영을 대체하지 않는다.
- 계산 의존성 예외에 사용할 검증된 `reasonCodes`, 다중 shard·미확정 일별/항목별 한도. 현재 reasonCodes는 빈 배열만 허용하며 일반 Q2 조건을 적용한다.
- Flutter 분석 입력 생성·개별 기억 응답 파서·재시도/삭제 표시, 실제 모바일 연동. 기존 금융 v4·모바일·계산 패키지는 변경하지 않는다.

격리 PostgreSQL·실제 loopback HTTP·모의 공급자 검증은 실제 클라우드 연결·배포·폰 통합 완료를 의미하지 않는다. 작업별 결과와 팀원 인계는 [분석 API 연결 이력](history/2026-11-01-analysis-api-handoff.md)과 [기간 조회·기억 관리 인계](history/2026-11-01-memory-period-handoff.md)에 기록한다.
