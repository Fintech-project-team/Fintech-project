# API 문서의 작성·변경·검증 이력

2026-10-22 보존. 아래는 출처별 과거 문구를 보존한 역사자료이며 **현행 개발 규칙이 아니다**. 과거 문구의 정책·구현 상태·미검증 표현을 현재 규칙으로 적용하지 않는다. 현행 기준은 [공통 데이터 모델](../../../../docs/data-model.md), [DB 사전](../../../../docs/database-schema.md), [API 계약](../../../../docs/api-contract.md), [응답 모델](../../../../docs/api-response-models.md)과 각 담당 구현 문서다.

### 보존 문구 1

> recordKind·원천 계좌/카드의 소유자·기관을 검증한 뒤 공개 여부를 판정한다. 주 원천 참조가 실제로 없거나 모순되면 공개 기준을 추정하지 않고 계약 오류로 처리한다. 원천은 연결됐지만 반대쪽 참조가 원래 미상이면 null을 유지한다. originalTransactionId·relatedTransactions·관계의 양 끝에도 동일한 거래 공개 기준을 적용한다. 부분 연결 후 사용자 선택 included는 이 판단에 쓰지 않는다. 확보된 거래에는 위 원천 필드 검증을 적용한다. 실제 미확보 원거래는 원천 관계에 대해 검증된 사용자·기관 근거가 있을 때만 공개 가능한 ID로 유지한다. 거래가 미확보라는 이유만으로 공개 권한까지 추정하지 않는다. 소유/기관 근거가 없어 권한을 판정할 수 없으면 503으로 실패하며, 임의 not_connected 표식·가짜 원거래·null로 대체하지 않는다. 기존 `refund-unavailable-original`의 referenceResolutions는 ID/상태/사유만 제공하므로 이 항목만으로 기관 권한 검증을 완료했다고 볼 수 없다. 후속 adapter가 그 미확보 ID를 정상 응답에 포함하려면 검증 가능한 원천 관계 근거를 확인해야 한다. 근거를 확보하지 못한 상태의 오류 처리는 허용되며 이번 결정이 원본 fixture 수정이나 전체 기관 강제 연결을 요구하지 않는다.

> ## 유지하는 저장 구조
>
> - user_id 및 같은 사용자 복합 FK는 다른 사용자 객체 연결을 차단한다. statement_items.card_id는 같은 카드의 청구·거래 연결을 검증한다.
> - 계획 식별자·계획 버전·개별 편집·확정 의무는 각각 다른 수명과 수정 범위를 가진다. 한 회차의 편집과 의무가 중복 존재하지 않도록 검사한다.
> - released_krw와 release_evidence는 요약값과 추적 근거이며 합계·소유권·정산 한도를 함께 검증한다. 두 값을 독립 권위로 수정하지 않는다.
> - transaction_references는 원거래가 조회 범위 밖이거나 미확보인 관계를 보존한다. dataVersion/sourceVersion/ruleVersion/schemaVersion은 서로 다른 변경을 식별한다.
> - 추가로 제거할 근거가 확인되지 않은 테이블·컬럼은 유지했다. 23개 테이블·181개 컬럼을 모든 서비스의 최소 개수라고 주장하지 않는다.
>
> ## 호환성과 이행
>
> - 원본 PAYSE-DRAFT-2와 HTTP/FakeRepository PAYSE-API-0.6-2를 구분한다. 구 형식을 새 형식으로 묵시 수용하지 않는다. 원본의 금액·UUID·asOf·sourceVersion·dataVersion·고정 버전은 이번 구조 정리로 바꾸지 않는다.
> - B 담당자는 계획에서 직접 금액을 읽는 소비자가 있다면 버전 선택으로 변경하고, 부분 연결 때문에 버전이 숨겨진 경우 해당 계획의 새 미래 회차 계산을 보류한다. 접근 제한 슬롯과 기존 회차 보존은 [응답 모델](../v0.6/response-models.md)을 따른다. Flutter 계산 위치·공식은 유지한다.
> - 로그인 요청은 name/phone/code만 받는다. 제거된 설치 식별 키는 알 수 없는 본문 필드로 422다. 기존 로그인 유지·새 로그인 거절·PIN 복구 정책은 그대로다.
> - 초기 DDL 수정은 새 검증 DB용이다. 기존 DB에 ALTER/DROP/TRUNCATE를 실행하거나 사용자의 자료를 지우지 않았다. 기존 DB를 사용 중이면 별도 마이그레이션 검토 후 적용해야 한다.
> - 앞서 확정한 단일 name은 문서 목표이며 이번 감사에서도 기존 SQL/합성 시드의 구 이름 두 필드 이행은 실행하지 않았다. 이름 이행과 설치 식별 컬럼 감소를 섞어 완료로 보고하지 않는다.
> - API 실제 구현·접근 제한 projector·Flutter 소비자·실기기 실행 완료를 이 문서나 원본 검사 통과로 주장하지 않는다.
>
> ## 검증 경계와 공식 근거
>
> - Python 원본 검사는 형식·관계·버전 시점·급여 근거·중복값 금지를 대상으로 한다. SQL 제약/극한/추가 회귀는 격리된 PGlite에서 실행하며 실제 실행 버전은 배포 보고서에 기록한다.
> - 네이티브 PostgreSQL 15는 initdb 단계의 Windows DLL 오류로 차단됐으며 17 실행 파일은 없었다. 네이티브 동시성·운영 DB 검증은 완료로 표시하지 않는다. 전체 하네스 결과와 직접 실행 근거는 적용 패키지에 별도 제공한다.
> - [PostgreSQL 17 제약 문서](https://www.postgresql.org/docs/17/ddl-constraints.html)는 복합 FK/UNIQUE와 행 간 조건의 CHECK 한계를 설명한다. PAYSE의 구체 급여·회차 규칙은 사용자 결정과 데이터 명세가 근거다.
> - [OWASP 세션 관리](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)는 서버 세션 관리와 토큰 보호를 뒷받침한다. 설치 식별값 제거와 기존 세션 우선은 PAYSE의 사용자 결정이며 OWASP의 의무 규칙이라고 해석하지 않는다.
