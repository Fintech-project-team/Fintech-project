### C 항목별 과거 처리 내역

> ## 과거 C 항목의 처리
>
> - C01~C03은 확정 유지: 기존 세션 PIN 복구, 급여 입금 후 지출 반영, 선택 잔액 합산.
> - C04는 복원 직후 연결0·선택0·미계산 → 지정 계좌 선택 후 기준 금액 검증으로 단계 분리한다. 새 제품 정책 선택이 아니다.
> - C05는 연결 전 목록/건수/버전, 연결 후 금융 자료, 의무 출금/급여 입금 계좌를 데이터 계약에 보완했다. 물리 테이블 수를 자동 증가시키지 않는다.
> - C06은 총 2명·공동 PM으로 해결했다. C07의 과거 계정 수·HMAC 이력은 현행 요구가 아니다.
> - C08은 결과에 최초·최대·종료 부족 의미를 명시했다. C10은 우발 입력 수신 가능성과 폐기를 구분하고, C11은 일중 순서를 만들지 않는다.
> - C12의 구현 패키지는 담당자 선택이다. C14의 토큰 종료·소실·유효 토큰 복구는 [HTTP 인증 계약](../../../../docs/api-contract.md)을 따른다. 기기 토큰만 소실되고 서버의 기존 활성 세션이 남아 있으면 운영 종료 전에는 새 로그인을 허용하지 않는다.
> - C09의 모호한 `category`는 v0.6 계약에서 제외한다. v0.7에서는 기존 네 거래 분류의 `transactionType`을 쓰는 **설계 권장안**으로 한정하고, 반복 후보는 ID·이름·이유·근거로 표현한다. 별도 소비 카테고리를 추가한 결정이 아니다. API/화면 담당자가 의미·응답 계약을 확인한다.
> - C13은 실패 연출을 **계정의 연결 흐름별 최초 시도 1회**로 관리하는 재현 가능한 구현 권장안이다. 실제 서버 실패와 구별하며 같은 흐름 재시도에서 재추첨하지 않는다. 사용자가 이 세부 구현안을 직접 선택했다고 기록하지 않는다.
>
> M2·M3·M4·M5·M6·인증 입력 수명·API 비용은 확정돼 [제품 기준](../../../../docs/product-baseline.md)과 [계산 기준](../../../../docs/calculation-rules.md)에 반영했다. 검증 미실행, 기술 선택 미완료, 사용자 정책 미결정은 같은 상태가 아니다.

> ## 4. 자체 의미 검토와 보완
>
> - **정정과 R 상한:** 오연결로 해제했던 보호액을 복원하는 것은 새 설정 증액과 다르다. 정정 기록을 근거로 해당 배정만 복원하고 부족은 표시하도록 보완했다.
> - **분석일과 현금일:** 구매 기준 연간 소비와 실제 출금 기준 시뮬레이션은 다른 목적이다. 연간 분석의 출금일 대체가 카드 구매 시점 현금 차감으로 번지지 않게 구분했다.
> - **환불:** 원래 구매를 삭제하면서 환불 반영일에도 차감하면 두 번 빠진다. 인식된 구매·환불 사건을 구분하고 환불 기간 순소비 음수를 허용했다.
> - **내부 이체:** 선택 계좌 사이만 합계 불변이다. 선택 밖으로 이동한 돈까지 B 불변이라고 쓴 과도한 요약을 수정했다.
> - **계정 격리:** 이름/전화번호/기기ID를 인증 근거로 사용하지 않고 세션 userId와 모든 대상 관계를 확인한다. 데모 자격 공유 시 사람별 격리를 보장한다고 쓰지 않는다.
> - **1차 완료:** 설계 기초 MD를 만들었다고 실제 더미 JSON·완성 ERD·OpenAPI·DB/API 작동까지 완료한 것으로 확대하지 않는다.
> - **검증과 결정:** 반복 초기 수치·급여일 처리·계좌 합산은 확정이다. 성능/사용 검증을 남은 정책 선택으로 다시 분류하지 않는다.
> - **권장안 표시:** C09 transactionType, C13 연결 흐름 단위, 물리 DB/경로는 설계 권장안으로 표시했다. 사용자가 해당 세부안을 직접 채택했다고 기록하지 않는다.
> - **DB 시드와 동의:** 계좌/카드 시드는 형식 동의 전에 존재한다. 원천 레코드 생성에 동의 완료 행을 필수 FK로 요구하지 않고 기관 코드와 별도 연결 상태로 조회 권한을 검사하도록 보완했다.
> - **DB 원문/설정:** CODEF 전체 응답 JSON과 거래 조각을 구별하고, 거래 분류 수정 컬럼·환불 원거래 참조를 보완했다. 사용자 테이블과 user_settings의 기본키 예외도 명시했다.
> - **정산 후 배정 한도:** 이미 해제한 배정을 다시 현재 R/E 한도에 넣으면 정상 정산이 거절될 수 있다. 미해제 배정액 합계를 검사하도록 계산·API·DB 문구를 통일했다.
> - **로컬 후보 승인:** 서버가 로컬 후보 ID만으로 근거를 조회할 수 있다는 전제를 제거했다. 승인/제외 요청의 근거 집합·버전·확정 설정 전달을 명시했다.

> ## 6. 공식 근거의 적용 한계
>
> - 의존성 주입·Repository/ViewModel 분리는 [Flutter 공식 권고](https://docs.flutter.dev/app-architecture/recommendations)에 근거한다. 특정 라이브러리 강제나 2인 분업의 정답을 뜻하지 않는다.
> - 다중 행 제약·원자 저장은 [PostgreSQL 제약](https://www.postgresql.org/docs/current/ddl-constraints.html), [트랜잭션](https://www.postgresql.org/docs/current/tutorial-transactions.html)을 참고했다. 문서상의 제약이 실제 DB에 설치됐다는 의미는 아니다.
> - 서버 세션 검증·민감 토큰 취급은 [OWASP 세션 지침](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)을 참고했다. PAYSE의 고정 코드·무만료 데모 정책을 공식 권장 인증으로 주장하지 않는다.
> - [OpenAI 지출 한도](https://developers.openai.com/api/docs/guides/spend-limits)는 알림과 한도 적용을 구별한다. 공급자 한도만으로 PAYSE의 원화 총상한·기간을 보장하지 않으므로 서버의 비용 통제가 필요하다.
>
> 반복 수치·날짜 집계·보호 한도·역할 배치의 근거는 사용자의 제품 결정과 이번 업무표다. 외부 공식 자료가 이 숫자나 사업 결정을 증명한다고 비약하지 않는다.
>
> ## 7. 검증 결과
>
> 검증 결과는 [validation-results.json](../../../../docs/validation-results.json)에 기록한다. 검증 대상을 최신 정책으로 바꿨으므로 이전 32개 검사 통과 수치를 이번 결과로 재사용하지 않는다.
>
> 검사 범위: 원문 보존, 현행 링크/표/코드 블록, 27개 ID 대응, 43개 화면 ID, 계산 위치·인증·2인 운영·이미 결정된 항목 정리, 산술/날짜/정정 예시, 이전 이력 표시, 배포 ZIP과 파일 일치.
>
> **실행하지 않은 검증:** Flutter 빌드·기기 성능·DB 마이그레이션/경합·서버/API·LLM 실제 호출·CODEF 9개 기관 공식 샘플 전체 대조·사용성 검증. 이 항목은 문서 PASS로 대체하지 않는다.
>
> - 1차 구조/정책 검사: 첫 실행은 56 통과·1 불일치. 제공 원문의 HTML 문자 표기를 검사기가 문자로 해석하지 못한 문제였으며, 원문을 바꾸지 않고 검사기를 수정한 뒤 **57 통과·0 실패**.
> - 2차 의미 검토: 최신 업무표·직접 결정과 계산/인증/DB/화면/역할을 대조한 **14개 항목 확인**. 동의 전 시드 관계, 거래 원문/수정 필드, 미해제 배정 한도, 로컬 후보 승인 요청을 보완.
> - 보완 후 재검증: **57 통과·0 실패**. 27개 결정 ID·43개 화면/상태 ID, 링크/표/코드 블록·원문 보존·산술/날짜 예시를 확인.
> - 검증 기록은 작업 폴더의 pass-1.json, pass-1-corrected.json, pass-2.json, semantic-review.json에 보존했다. 내부 의미 검토는 별도 사람의 독립 검수가 아닌 자체 재검토다.
> - 전달 ZIP은 현행 17개 파일과 파일별 바이트/해시 일치를 검사한다. 결과는 작업 폴더 package-validation.json에 기록한다. 문서 검증 통과는 명시된 개발 설계값이나 실제 구현 검증까지 끝났다는 의미가 아니다.
