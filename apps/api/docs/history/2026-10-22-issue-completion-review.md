# 2026-10-22 이슈 검토 메모 — 임시 기록

> 이 문서는 대화 보고를 위해 작성한 임시 검토 메모다. API 개발 규칙·확정 요구사항·새 인수 조건으로 사용하지 않는다. 개발 시에는 기존 공통 계약과 인증 설계·검증 문서를 따른다. 이후 이슈 판단이 바뀌어도 이 기록만으로 구현 범위를 확대하지 않는다.

검토일: 2026-10-22. 대상: [#21 식별·인증 설계](https://github.com/Fintech-project-team/Fintech-project/issues/21), [#22 세션·조회 API 구현](https://github.com/Fintech-project-team/Fintech-project/issues/22). 아래 표는 당시 누락을 확인하고 사용자에게 결과를 보고할 때 사용한 점검 항목이다. 기존 [제품 기준](../../../../docs/product-baseline.md), [API 계약](../../../../docs/api-contract.md), [응답 모델](../../../../docs/api-response-models.md), [인증 설계](../v0.6/auth-design.md)가 실제 개발의 참조자료다.

## #21 설계 검토에 사용한 항목

당시에는 각 항목의 정책·예외·담당 경계·검증 사례가 기존 문서에 있는지, 상위 계약과 충돌하는지 확인했다. 실제 구현 통과를 설계 완료의 증거로 요구하지 않으며, 설계 완료를 실제 인증 성공으로 표시하지 않는다.

| ID  | 검토 항목                                                                                                 | 주된 확인 근거                                            |
| --- | --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| D01 | 합성 정보 대조, 별도 코드, 내부 사용자 ID를 구분하고 이름·전화번호만으로 접근할 수 없음을 정의한다.       | API 계약 §2; 인증 검증 A01/A02                            |

| D03 | 서버 세션과 로컬 PIN을 분리하고 기존 세션 우선·계정당 활성 세션 하나·명시 종료 정책을 정의한다.           | API 계약 §2; 인증 검증 A03/A04/A14                        |

## #22 서버 구현 검토에 사용한 항목

당시에는 아래 항목으로 구현 누락을 점검했다. 표 자체가 새 요구사항을 확정하지 않는다. 실제 구현·검증의 범위는 기존 계약과 사용자 결정을 따른다. 클래스·테스트 추가만으로 실제 로그인·조회가 구현됐다고 보고하지 않는다.

| ID  | 검토 항목                                                                                                                                                        | 확인할 실행 증거                                                                                                                                                     |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| S01 | 로그인은 합성 name·phone·code만 받고 계약의 정규화·형식·추가 키 거절을 적용한다. 성공 시 저장된 userId/name과 새 세션을 반환한다.                                | 실제 HTTP 정상·누락·Unicode 경계·구 installationId·없는/비활성 사용자·DISABLED 코드·일반 오류 응답 검사. A01/A02/A05/A20/N01/N05                                     |
| S02 | 활성 세션은 계정당 하나이며 기존 세션을 유지한다. 재확인은 새 토큰/세션 없이 같은 계정에서만 성공한다. 로그아웃 후 해당 토큰이 무효가 된다.                      | 실제 PostgreSQL 동시 로그인에서 성공 정확히 1개, 서버 재시작·응답 유실·재확인·로그아웃 경합의 DB 상태 확인. A03/A04/A07/A08/A14                                      |
| S03 | 조합 실패 제한과 IP 제한을 영속화하고 성공/실패/파싱 오류에서 계약상 집계 순서를 지킨다.                                                                         | 실제 HTTP+PostgreSQL로 시간 경계, 5번째 실패·61번째 IP 요청, Retry-After, 동시 생성/정리, 실패 커밋, 재시작, 저장 장애 503 확인. A09~A13/A19                         |
| S04 | 검증한 토큰으로 사용자 잠금 후 계정/세션을 재검사하고 동일 연결·트랜잭션에서 RLS를 적용한다.                                                                     | 실제 제한 역할로 사용자 간 접근·역할 전환·직접 비밀 조회 거절; 풀 재사용/롤백 후 문맥 잔류 없음. A05/A06/A08                                                         |
| S05 | 금융사 연결 전 Snapshot은 응답 모델 §1.1의 허용 키 10개만 제공한다.                                                                                              | 실제 HTTP 응답에 금융 배열·설정·거래 페이지·비공개 식별값이 없는지 확인. 연결 전 계약 사례와 일치                                                                    |
| S06 | 금융사 연결은 최종 동의 집합을 원자 저장한다. 허용 기관·중복·은행 최소 1개·버전·멱등 키·영수증을 검증하고 최신 Snapshot을 반환한다. 계좌를 자동 선택하지 않는다. | 실제 PostgreSQL에서 저장 성공·재시도·버전 충돌·동시 수정·부분 실패 롤백 확인. API 계약의 institution-links 및 공통 W 규칙                                            |

| S09 | 로그아웃·재로그인·서버 재시작 후 금융사 연결과 기존 사용자 설정/선택이 유지된다. 시작 시 DB를 초기화하지 않는다.                                                 | 실제 DB에 저장한 값을 재조회하여 동일한지 확인; 고정 더미의 asOf/sourceVersion이 단순 재시작으로 바뀌지 않는지 확인                                                  |
| S10 | 인증·조회·연결 API는 계약의 상태 코드·헤더·오류 구조를 사용한다. 실패를 빈 데이터·0원·성공으로 바꾸지 않는다.                                                    | no-store, 비밀/SQL/스택/숨긴 ID 비노출, 무효 토큰·장애·오류 로그 검토. 응답 계약과 비교                                                                              |
| S11 | 기존 데이터 모델·더미·SQL과 호환되고 실제 Spring HTTP/PostgreSQL 검증을 통과한다.                                                                                | 공통/Java/Python 검사, 실제 DB 역할·RLS·행 잠금·원자성 결과, 요청/응답의 Flutter 계약 대조. H2/mock은 실제 DB 근거를 대체하지 않음                                   |

## 당시 검토한 범위와 증거 구분

- #22에는 세션 생명주기에 필요한 로그인·재확인·로그아웃, Snapshot/거래 조회, 금융사 연결 저장을 포함한다. 금융사 연결 저장이 공통 쓰기 규칙의 첫 소비자라고 해서 #23의 계좌 선택·별칭·예정 지출·모아둘 돈 CRUD까지 완료로 포함하지 않는다.
- 탈퇴/1년 보관/파쇄는 v1.0 정책으로 유지하되 별도 구현 범위다. 해당 계정 상태가 도입되면 #22 인증도 비활성 계정을 거절해야 한다. #22 통과만으로 탈퇴·파쇄 완료를 보고하지 않는다.
- Flutter HTTP 연결, 로그인 name 소비, OS 보안 저장, PIN·앱 재시작·두 기기 검증은 B와 통합할 별도 증거다. 서버 단위검사나 Fake 통과로 기기 완료를 대체하지 않는다.
- 이슈 판정은 대화에서 보고한다. 이 임시 기록을 필수 개발 문서로 연결하거나 GitHub 이슈 상태 변경의 자동 근거로 사용하지 않는다.
