이 문서는 작업 당시 범위·인계와 후속 설계를 기록한다. 현행 필드는 [급여 모델](../../../../docs/data-model.md#급여-회차와-예정일), 공개 형태는 [응답 모델](../../../../docs/api-response-models.md), 쓰기는 [HTTP 계약](../../../../docs/api-contract.md)이 단일 기준이다.

## 작업 경계와 이전 기록

사용자 정정에 따라 급여일·휴일 보정·급여 구간·가용 금액의 기본 계산은 Flutter, AI는 분석·판단, 서버는 DB 조회·저장·권한·데이터 검증·응답 전달을 담당한다. 서버 날짜 계산기나 계산된 예상 일정 응답은 추가하지 않는다.

#98의 head는 `refactor/api/common-user-financial-storage`의 `4eaf3a8`이다. 현재 API 브랜치에는 이후 `53eb845`, `96ff609` 두 커밋이 있다. #98 기반 팀원 동기화 작업과 API 브랜치를 같은 브랜치로 취급하지 않는다. 확인 시점 원격 브랜치·열린 PR 목록에는 팀원의 별도 동기화 브랜치 이름이 없었다. #98은 모바일 v3 동기화·통합 확인 전 병합하지 않고 develop을 유지한다. 실제 저장소·GitHub·develop·모바일·계산 패키지에는 쓰지 않는다.

[10월 23일 인계](2026-10-23-salary-contract-handoff.md)의 “다른 회차가 동일 예정일이면 정보 부족”이라는 일괄 판정은 대체한다. 동일 예정일의 원천은 보존하며 길이 0인 구간·회차 구분이 불가능한 계산만 제한한다. 각 입금의 잔액 반영과 다음 경계·시작 상태가 독립적으로 확인되어 앞 구간의 미확정 값에 의존하지 않으면 이후 현재 구간은 계산할 수 있다. 실제 판정·계산 구현은 B 담당이다.

기존 Python·SQL 검증에는 날짜 간격·예정일 순서·급여액 배율 제한이 없었다. 제품 검증 로직에서 제한을 제거한 작업이 아니라 계약 표현·회귀 검증을 보완한 작업이다. SQL 분리·가독성 및 인증 DB 기능은 보존한다.

## 입금 전 예정 원천 비교

`SalaryReceipt` 네 필드, `PAYSE-DRAFT-3`, `PAYSE-API-0.6-3`, `PAYSE-FIXTURE-3`는 유지한다. 제공·미제공의 새로운 비교 자료만 추가하며 기존 15개 snapshot·계정 시드·은행 기준정보를 덮어쓰지 않는다. catalog·manifest에 새 파일을 등록한다.

| 비교 fixture             | 조회 기준                      | 원천 급여 근거                                                                        |
| ------------------------ | ------------------------------ | ------------------------------------------------------------------------------------- |
| salary-schedule-provided | 2026-10-29T12:00:00+09:00      | payMonth=2026-11, expectedPayDate=2026-10-30, confirmation=unknown, transactionIds=[] |
| salary-schedule-absent   | 같은 기준시각·사용자·금융 내용 | 해당 회차 원천 없음                                                                   |

기존 `asOf`는 날짜가 아닌 시각 문자열이므로 기존 fixture의 12:00 KST 표기로 날짜를 구체화했다. 반복 급여 설정은 기존 준비 함수의 25일을 유지한다. 제공 날짜는 사용자가 지정한 명시 원천이며 반복일이나 공휴일 알고리즘으로 계산한 값이 아니다. 미제공 사례에서 예상 날짜를 만드는 것은 Flutter 책임이다.

새 공통 원천을 두 사본으로 나누고 급여 근거 제공 여부만 달리한다. 내용이 다른 원천은 서로 다른 sourceVersion으로 구분한다. 두 사본의 실제 잔액·거래·원천 시각·입금 상태는 같으며 지급 거래를 추가하거나 잔액에 급여를 더하지 않는다. 테스트 기대값도 원천 제공·보존에 한정하고 Flutter 계산 결과를 대신하지 않는다.

## 구현 여부

- `fixtures/validate.py`와 `002_storage_guards.sql`은 필수 명목 회차·형식·같은 회차 중복·입금 관계를 검증한다. unknown·빈 transactionIds·미래 예정일은 유효하다.
- `fixtures/export_sql.py` 및 시나리오 도구는 fixture의 receiptEvidence를 DB `source_contexts.salary_evidence`에 저장한다. 검증에는 이 방향의 적재·재조회 보존을 포함한다.
- **실제 DB→HTTP Snapshot 조회 controller·repository·mapper는 아직 없다.** Java는 health 이외 경로를 차단한다. 문서의 응답 조립 규격과 fixture 제공을 실제 HTTP 응답·배포 완료로 보고하지 않는다.
- 조회 구현 시 공개 권한이 있는 DB 근거를 값 그대로 receiptEvidence에 전달하고 unknown·미래 날짜라는 이유로 필터링하지 않는다. 기존 접근 제한의 부모 키 생략·표식은 유지한다. 원천이 없으면 서버에서 생성하지 않는다.

## 별도 후속 기능 — 결정 보존, v3 미반영

아래는 이 대화에서 선택된 방향이다. 정정 지시에 따라 후속 설계로 분리한다. 현재 v3의 필드·엔드포인트·DB 구조 또는 자동 기능으로 추가하지 않았다. 이미 받은 답변을 다시 미결정으로 만들지 않는다.

1. 사용자 확인 예정일은 해당 payMonth 한 회차에만 적용하며 반복 월급일을 유지한다. 원천 → 해당 회차 사용자 확인 → 반복 예상 순이다. 이후 원천 도착 시 원천을 우선하고 다른 사용자 확인 날짜는 별도 기록으로 보존한다.
2. 큰 입금 후보는 지정 급여 계좌의 실제 입금 중 설정 예상 급여 초과 및 회차·성격 미확인 거래로 한정한다. 예상 급여가 없으면 자동 판정하지 않는다.
3. 보호 목표는 미확인 입금 전체다. 입금 600만 원·예상 급여 300만 원이면 보호 목표 600만 원이다.
4. 기존 보호금과 겹치는 자금은 거래·보호금·금액을 명시 연결하여 한 번만 차감한다. 잔액 부족으로 목표를 자동 축소하지 않고 부족 상태를 표시한다. 기존 수동 보호금 M5 상한과 자동 보호를 구분한다.
5. 사용자는 입금 성격, 해당 회차(알 때만), 보호 유지·해제·변경을 명시한다. 상여금·밀린 급여는 반복 월급일을 자동 변경하지 않고, 선지급도 금액만으로 회차를 건너뛰지 않는다. 다음 회차가 불명확할 때만 추가 확인한다. 무응답으로 정상 확인·보호 해제하지 않는다.

## 후속 최소 확장 검토

현재 SalaryPatch에는 회차별 확인일이 없고 reserves에는 입금과의 관계·검토 상태가 없다. 기존 테이블의 라벨이나 원천 confirmation으로 이를 대신 표현하지 않는다.

| 최소 추가 대상(제안) | 필요한 정보                             | 재사용·주의점                                                                  |
| -------------------- | --------------------------------------- | ------------------------------------------------------------------------------ |
| 회차별 사용자 일정   | payMonth, 사용자 확인일, 확인 기록 시각 | 기존 설정 PATCH·Snapshot 확장. 사용자/회차별 현재 설정 하나                    |
| 입금 검토 상태       | 거래 ID, 확인 상태·내용, 생성·확인 시각 | 동일 사용자/거래의 검토·보호 중복 생성 방지                                    |
| 기존 보호와의 관계   | 거래·보호금 ID, 명시 연결 금액          | 현재 보호액은 reserves를 재사용하며 같은 돈을 별도 금액으로 다시 차감하지 않음 |

탐지·보호 목표·가용 금액·구간 재계산은 Flutter에서 수행한다. 서버는 원천·소유권·설정·금액 일치·저장 제약을 검사한다. 입금 검토·보호·필요한 확인 설정을 같은 요청·트랜잭션으로 저장해야 하며 기존 write_receipts의 버전·멱등·변경 이력을 재사용한다. 일반 보호금 수정·취소도 검토 관계를 재검증해야 한다. reserve_allocations는 보호금→예정 지출 관계이므로 입금 관계로 전용하지 않는다.

후속 착수 전에는 이 최소 저장 관계, 공개 필드·상태값·쓰기 명령과 버전 전환 영향을 A/B가 함께 확인한다. 이는 이미 확정한 금액·판정 정책을 다시 묻는 절차가 아니다. 새 조회 엔드포인트·푸시 인프라를 먼저 늘리지 않는다.

## B 담당 인계·검증 한계

- 기존 v3 파싱·명목 회차 식별·급여 경계 처리와 위 두 신규 자료의 모바일 자산/테스트 반영은 B 담당이다. API 작업에서 모바일을 복사·수정하지 않는다.
- 정상·먼 예정일·역전·동일 예정일·큰 확정 입금은 원천 검증 대상으로, 계산 정보 부족은 구간별 계산 결과로 구분한다. 원천 오류를 정상 빈 목록·0원으로 바꾸지 않는다.
- 실제 HTTP에서 미래 근거를 누락하지 않는지와 부분 연결 투영은 조회 구현 후 검증한다. 현재 자료로 해당 구현 PASS를 주장하지 않는다.
- 기존 순수 검증의 반복 호출·unknown 보존 검사를 HTTP 멱등성·보호 유지/해제 구현 검사로 해석하지 않는다. 자동 보호·무응답·중복 보호 방지 업무 검증은 후속 저장/조회 구현과 함께 수행한다.
- #28/#96 정상 시나리오의 직전 급여 근거 보완은 별도다. 계산 규칙·ruleVersion 전환은 B가 실제 계산 변경 범위에 맞춰 확인한다.

`002_storage_guards.sql` 주석도 입력 해시를 바꾸므로 과거 급여 이행 계획을 재사용하지 않는다. 적용 배치는 파일만 갱신하며 실제 DB 마이그레이션·Git 쓰기를 실행하지 않는다. 폐기용 PostgreSQL의 검증 결과와 사용자 DB 적용을 구분한다.
