# 2026-10-29 청구 항목 공동 적용 인계

관련 이슈: #29. 같은 작업 브랜치의 인증 HTTP는 #22다. 이 기록은 작업 인계이며 필드의 단일 기준은 [데이터 모델](../../../../docs/data-model.md#v4-청구-항목), 공개 규칙은 [응답 모델](../../../../docs/api-response-models.md#v4-공동-전환과-청구-항목-공개), 저장은 [DB 사전](../../../../docs/database-schema.md#statement_items)이다.

## 반영한 API 담당 범위

- 기존 v3 원본과 준비본을 유지하고 v4 원본/응답/fixture 버전을 구분했다. v4 공동 배포가 완료된 상태는 아니다.
- 청구 항목 ID·nullable 거래 연결·표시/금액/회차를 기존 statement_items에 저장한다. 같은 구매가 여러 청구 또는 같은 청구의 여러 항목에 연결될 수 있다. includedTransactionRefs는 항목에서 중복 제거해 파생한다.
- 음수는 새 항목의 feeOrAdjustmentAmountKRW·billedAmountKRW에만 추가 허용한다. 거래·원이용금액·청구 원금·청구 총액·의무·정산의 기존 금액 규칙은 유지한다.
- 신규 001과 기존 DB용 원자적 006을 준비했다. 실제 서비스 DB에는 실행하지 않았다. 구 연결의 미확보 세부 값은 null이며 구매액·개월 수로 채우지 않는다.
- generated-v4는 기존 21개 변환본과 별도 alpha/beta/gamma-billing-items 3개다. 기존 기본 시연 선택과 v3 파일은 보존한다.
- billing_projection.py는 청구 공개 조각의 검증용 참조 구현이다. 실제 금융 조회 HTTP와 전체 Snapshot 조립은 미구현이며 새 금융 엔드포인트를 배포하지 않았다.

경로는 apps/mobile/ 기준이며 API 담당자는 이 파일들을 수정하지 않았다. 연결 권한과 현재 페이지의 포함 여부는 다르다. 권한이 확인된 다음 페이지 거래 ID는 유지하고, 현재 페이지에 없다는 이유로 제한 표식·가짜 미확보 상태를 만들거나 거래를 복제하지 않는다.

## 공동 적용 전 실행할 반례

1. 음수 할인과 음수 청구액은 허용하고 거래 금액·청구 원금의 음수는 거절한다.
2. 금액 null·거래 연결 null·독립 연회비를 정상으로 읽으며 null을 0이나 가짜 거래로 바꾸지 않는다.
3. 부분 연결의 itemId 표식·부모 refs 표식을 함께 검증하고 숨겨진 ID를 노출하지 않는다.
4. 다음 페이지 거래, 동일 구매의 여러 청구, 구버전 응답과 새 버전의 누락/잘못된 필드를 각각 검사한다.
5. 기존 21개 사례의 v4 상세만 추가된 경우 기존 홈 계산 결과가 유지되는지 실제 Flutter 계산 테스트로 확인한다. 새로운 3개 사례에는 별도 청구 의무가 추가되므로 이 불변 검사의 비교 기준으로 쓰지 않는다.
6. API·Fake·Flutter가 동일한 원천/권한 조건으로 같은 공개 항목·참조·제한 표식을 내는지 확인한다.

팀원이 전달한 사전 검토는 코드 정적 확인이다. Python 계약·PostgreSQL 저장 검사와 Flutter 실행·실제 기기 검증을 별개로 보고한다. 실제 HTTP 응답 제공·DB 이행·v4 공동 적용은 이 자료의 생성만으로 완료 처리하지 않는다.
