# 분석 API·DB 연결 인계 기록 — 2026-11-01

관련 이슈: #32. 이 문서는 해당 작업의 인계 기록이며 현행 계약은 [분석 API](../analysis-api.md), [의미 계약](../analysis-meaning.md), [저장 구조](../analysis-storage.md), [실행 상세](../llm-execution.md)를 따른다.

## A 반영 사항

- 분석 전용 접수·상태·본문 제출·결과 조회·명시 재시도·개별 삭제를 기존 인증/DB와 연결하는 구현을 추가했다. 현재 금융 v4 Snapshot·원천·설정·Flutter 계산은 바꾸지 않는다.
- 현재 권한·DB 근거 대조, 사용자별 기억/캐시 격리, 개별 봉투 암호화, 동일 키 중복 억제와 늦은 결과의 삭제 차단을 검사 대상으로 연결했다.
- 본문65,536바이트, 대기 사용자2/전체20, 실행 사용자1/전체2를 적용한다. 상태의 제출 허가는 현재 실행창 안에서 최대60초이며 일반 Q2는10개 또는60초다.
- 같은 공급자 내부 응답은 output+memories다. 기존 의미 output 규격은 유지하고 API가 기억별 저장·사용 가능 상태로 조립한다.
- 만료 작업 recovery는 유효 cache를 먼저 확인한다. 실제 새 분석의 새 결과에만 새3개월을 적용하고 일반 재시도·재사용·삭제 차단은 기존 기준을 유지한다.

## B 반영 필요

1. 기존 A/B 동작에 descriptor 접수를 연결하고 action=submitInput일 때만 현재 최소 입력·permit을 제출한다. 독립 ‘지금 분석’이나 자동 재시도를 추가하지 않는다.
2. 공개 최소 입력의 inputHashHint·항목 대응·현재 context를 생성한다. 서버의 DB 결합 지문은 앱에서 생성하거나 제출하지 않는다. 금융 전체 페이지의 버전·관계·coverage·미연결 제한을 유지하고 누락 원거래 ID를 추측하지 않는다.
3. 상태 조회에는 본문이 없다. 현재 input으로 result-query를 요청하고 결과별 available/partial/missing 및 항목별 실제 사유를 처리한다. 현재 itemKey·epoch/revision과 최초 provenance를 구분한다. 합류 응답의 jobId가 달라지면 대표 작업을 관찰한다.
4. 결과 불명 재시도에는 사용자의 중복 실행 위험 확인을 전달한다. 로그아웃으로 취소된 대기는 옛 permit을 재사용하지 않고 새 세션에서 사용자 명시 재시도로 처리한다. 같은 작업의 근거가 바뀐409 STALE_DATA는 현재 자료의 A/B 접수와 구분한다. 삭제는 개별 itemId·Idempotency-Key를 사용하고 삭제한 기억의 기기 캐시도 무효화한다.
5. 보존 정보 목록 API·Flutter 파서/화면은 미완료다. 기존 앱이 분석 API를 자동 지원하거나 공동 검증까지 끝났다고 간주하지 않는다.

## 검증 상태와 미완료

PostgreSQL 15.13의 새 임시 클러스터와 실제 loopback HTTP를 사용했다. 공급자와 키 관리만 테스트 대역이며 실제 LLM/KMS·유료 호출은 0회다. 기존 실행 DB 연결·서비스 변경은 0건이고 검사 클러스터는 종료했다.

위 전체 검사와 수정 영향을 받은 3개 보완 검사를 합쳐 API Java 303개의 유효한 통과 근거를 확보했다. 재현 명령은 `python -B apps/api/database/test_analysis_service.py --pg-bin <PostgreSQL bin> --work-dir <새 검사 디렉터리>`이며 기존 DB 주소를 받지 않고 전용 클러스터를 만든다. 보완 검사는 동일 준비 환경에서 세 테스트를 지정해 실행했다. 공통 하네스 최종 결과는 커밋 메시지의 검사 runId에 기록한다.

실제 LLM/KMS 연결·유료 호출·폰 통합은 수행하지 않는다. 기본 runtime은 비활성이다. 보존 목록, 7일/3개월 자동 정리, 모든 백업·키의 비가역 파쇄, 비용 예약/정산 장부, 검증된 계산 의존성 reasonCodes 예외는 별도 미완료다.

작업 식별 기록의 실제 정리 작업을 구현할 때는 만료 recovery의 이전 소유권 확인과 함께 설계해야 한다. 현재는 이전 기록이 남은 경우만 recovery를 확인할 수 있으며, 기록이 없어지면 존재 여부를 노출하지 않는 403이다. 이 제약을 이유로 식별 보관기간을 자동 연장하지 않는다.

기존 금융 공개 계약과 분석 경로를 대조해 미확보 원거래의 권한 검증 누락을 수정했다. referenceResolutions의 ID·상태·사유만으로 기관 권한이 확인되지는 않는다. 기존 FinancialProjection/FinancialPages가 해당 원거래를 공개하지 못하는 경우 분석 API도 임의 허용하지 않고 503으로 거절한다. 정상 원거래가 확보된 기존 시연은 유지하며, 실제 미확보 사례는 원천 관계의 검증 가능한 소유·기관 근거를 준비한 뒤 별도로 연결해야 한다.
