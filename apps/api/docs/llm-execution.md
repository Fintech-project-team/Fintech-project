# LLM 실행 상세 — API 내부 설계

서버 LLM 게이트웨이·입출력 검증·호출 제어·운영 메타데이터를 구현·검증할 때 **이 문서의 해당 절과 [실행 공통 계약](../../../docs/payse-execution-contract.md)을 필수로 읽는다**. 작업 명세의 readBefore에 두 경로를 넣는다. 과거 결정/검사 조사에만 [검토 이력](history/2026-10-27-execution-review.md)을 함께 읽는다.

**상태: 구현 제안·미구현.** 공통 Q1~Q4·D1~D4와 [제품 비용 정책](../../../docs/product-baseline.md#api-비용)은 확정이며 나머지 운영 수치는 미확정 권고다. 내부 job 키·상태·접수 통신은 공개 HTTP·DB·v3 스키마 확정이 아니다. 확정 프로필·단가·실제 사용액·저장/통신 계약·구현이 갖춰지기 전 유료 경로는 비활성이다. 세션·금융 조회/쓰기·로컬 계산의 기능 완료와 구분한다.

Flutter 분석 연동 작업도 **입력과 재사용 지문·요청과 결과 복구·AI 접수와 스케줄러**를 필수로 읽는다. 아래 이름·상태·통신 단계는 논리 계약이며 기존 v3 필드/엔드포인트를 확정하거나 구현한 것이 아니다.

## 입력과 재사용 지문

논리 출처는 source(원천)·confirmedSetting(확정 설정)·localCalculation(로컬 산출)·utteranceSpan(발화 구간)·aiInterpretation(해석 후보)·jobMetadata(운영 기록)로 구분한다. 검토용 이름이며 기존 Snapshot에 추가된 필드가 아니다.

| 입력                                                                       | 출처·필수 조건                                                      | 검증·수명                                                                                                                                            |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 인증 사용자·현재 sessionId / localSessionEpoch                             | 서버 세션 / Flutter 세션 생성 시 증가하는 메모리 값. 모든 요청 필수 | 사용자ID는 본문을 권위로 삼지 않음. 토큰·이름·전화·PIN은 LLM 제외                                                                                    |
| schemaVersion/dataVersion/sourceVersion/ruleVersion/asOf                   | 동일 Snapshot. 모든 금융 분석 필수                                  | v3 지원 여부·접근 범위 검증. 시각은 원천 기준이며 서버 현재 시각으로 바꾸지 않음                                                                     |
| inputRevision / 선택 계좌 ID 집합 / 관련 설정 참조                         | Flutter. 금융 영향·설정·시뮬레이션 필수                             | 입력 수정마다 revision 증가. 순서 무관 집합만 정렬해 지문 생성                                                                                       |
| evidenceTransactionIds / 필요한 원천 필드                                  | 접근 가능한 Snapshot. 거래 해석 필수                                | ID·recordKind·direction·status·반영 근거·필요한 merchantName/description만. 원천 전체 JSON·인증·계좌번호 자동 전송 금지                              |
| candidateKey / 허용 후보 ID / 의미 미상 표식 / 로컬 특징                   | Flutter. A/B/D 후보 작업 조건부 필수                                | 금액·간격·횟수는 Dart 산출. 서버는 존재·소유·버전·허용 타입 검증, 수치 재산출 안 함                                                                  |
| resultRef / metricId / 계산값·한계·근거                                    | Dart. C/E 및 D 결과 설명 필수                                       | 결과와 동일 입력 버전. ‘검증’은 로컬 규칙·스키마·참조 검증이며 서버 금융 재계산 뜻 아님                                                              |
| utterance / spans / requestDateKst                                         | 사용자 발화·Dart 고정 날짜. 자연어 D만 필수                         | 사용자가 실제 쓴 구간과 일치해야 함. 발화 원문은 요청/현재 흐름만 유지                                                                               |
| triggerKind / semanticTaskKind / reasonCodes / requestedAt / policyVersion | Flutter 동작 ID·의미 작업 종류·운영 정책. AI 작업 필수              | triggerKind는 A~E, semanticTaskKind는 거래분류/반복의미/발화추출/설명/회고. 서버는 허용 enum·근거 참조·우선순위 표만 적용. 금융 영향 임의 승격 안 함 |
| promptVersion / pinnedModelId / responseSchemaVersion / analysisInputHash  | 서버 승인 설정·정규화된 최소 입력                                   | 별칭 대신 고정 모델. 미설정이면 AI 작업 비활성. hash는 무작위 작업ID와 별개이며 익명화 보장 아님                                                     |

`analysisInputHash`는 semanticTaskKind·관련 원천 값/참조·설정·로컬 특징·기준 날짜·규칙·프롬프트·모델·응답 형식 버전의 정규 직렬화로 만든다. triggerKind·화면 탭·재조회 시각은 포함하지 않는다. 따라서 A와 B가 같은 거래의 같은 의미 판단을 요구하면 공유하고, 설명과 분류처럼 목적이 다르면 공유하지 않는다. 전체 dataVersion만 바뀌었고 관련 입력은 같으면 로컬에서 동일 의미를 확인할 수 있으나, **기존 응답 버전을 직접 덮어 적용하지 않는다.** 새 버전에서 권한·참조를 재검증한 재사용 경로만 허용한다.

## AI 접수와 스케줄러

G0~G7은 AI 하위 작업에만 적용한다. 공통 계약의 EX-A~W와 응답 채택·저장 경계를 먼저 확인하며 금융 API를 이 게이트에 종속시키지 않는다. 아래는 먼저 맞는 행 하나를 적용한다.

| 순서 | 조건                                                                        | 결과                                                                                               |
| ---- | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| G0   | 세션 종료·소유자 불일치·접근권한 없음                                       | 요청/응답 폐기, 타 사용자 데이터 노출 없음; 신규 AI 0회                                            |
| G1   | 원천 형식 오류·지원하지 않는 버전·잘못된 참조                               | 계약 오류. null/0/AI 추정으로 보충하지 않음; AI 0회                                                |
| G2   | 필요한 근거 미수신·부분 coverage·계좌 asOf 불일치                           | 가능한 조회/계산 유지. 영향 대상만 정보 부족. 미확인 관계 확정 금지                                |
| G3   | 동일 사용자·작업·입력 지문의 활성·보관 허용·관련 입력이 유효한 DB 결과 있음 | 현재 인증·버전·참조 재검증 후 재사용; 저장 당시 세션과 동일할 필요 없음; 공급자 호출0회            |
| G4   | 동일 지문의 작업이 queued/running                                           | 접수는 기존 작업에 연결하고 새 작업 발급0회. queued 작업의 스케줄러는 아래 별도 재평가 경로를 진행 |
| G5   | AI 기능 비활성·운영 설정 누락·예산/한도 부족·오프라인                       | 후보/템플릿/로컬 계산 유지. `analysisUnavailable`는 논리 상태, 기존 HTTP 오류코드 신설 아님        |
| G6   | 공통 계약의 해당 동작 조건이 AI 대상이고 호출 슬롯 확보                     | 아래 호출 프로필의 승인된 상한 안에서 실행. 원천/설정 쓰기는 수행하지 않음                         |
| G7   | 그 외                                                                       | 해당 동작의 기본 처리. AI 0회, 저장 0회                                                            |

입력은 먼저 근거가 독립적인 하위 작업으로 나누고 G0~G7을 각각 평가한다. G2는 근거가 부족한 하위 작업만 보류한다. 일부 카드 연결이 제한돼도 다른 공개 거래의 표시용 해석은 가능하지만 전체 소비 분석 완료를 선언하지 않는다.

동일 queued 작업에 현재 계산 의존성이 추가되면 같은 jobId에 검증된 대기 예외를 반영하고 재평가한다. 새 작업/시도 카운터를 만들지 않는다. 독립적인 ‘지금 분석’이나 강제 새 분석 요청은 받지 않는다. 실패 복구용 다시 시도는 아래 복구 순서를 따른다.

스케줄러 재평가는 신규 접수가 아니다. 기존 queued 작업에 대해 ① 세션/권한·입력 버전 유지 ② 취소·deadline 미도달 ③ 해당 동작의 건수/시간/우선순위 조건 충족 ④ 프로필·예산·슬롯 확보 순서로 검사한다. 통과하면 같은 jobId를 running으로 바꾸며 G4로 되돌아가지 않는다. 조건이 아직 충족되지 않으면 queued를 유지하고, 만료·무효화면 종료한다. 작업ID와 의미 지문이 같다는 이유로 실행이 영구 대기하지 않게 한다.

외부 모델 호출 도중 DB 사용자 행 잠금을 유지하지 않는다. 호출 전·응답 채택·확정 저장 때 각각 권한/버전을 검증한다. 응답 채택은 금융 저장 승인과 다르며 금융 쓰기는 기존 HTTP 계약을 따른다.

## 요청과 결과 복구

사용자 앱은 서버와만 통신한다. 서버는 DB와 LLM에 각각 연결하며 기본 금융 계산은 Flutter에 유지한다. 앱 연결 종료만으로 이미 접수된 분석을 취소하지 않는다. 새 요청/상태 조회/결과 조회에는 현재 인증을 적용한다.

1. Flutter가 기존 EX 조건에서 요청한다. 서버는 인증·소유권·근거·형식·지문을 검증하고 **유효 DB 결과부터 조회**한다. 있으면 재사용하고 모델을 호출하지 않는다.
2. 결과가 없으면 같은 의미 작업의 진행/완료/실패와 전송 시도를 확인한다. queued/running은 합류하고, 완료 여부 불명은 미전송으로 취급하지 않는다. 새 작업 접수와 실패 복구를 구분한다.
3. 일반 대기는10건/60초 조건을 적용한다. 대기 항목 본문은 Flutter 메모리에 두며 실행 허용 확인 후 필요한 입력을 제출한다. 본문을 접수해 LLM에 전송한 이후 앱 연결이 끊겨도 살아 있는 서버는 결과 검증·저장을 마칠 수 있다. 입력을 받기 전 앱 종료와 서버 자체 장애의 완료를 보장하지 않는다.
4. 짧은 DB 트랜잭션으로 중복 작업·전송 시도·비용 예약을 연결해 기록하고 종료한 뒤 외부 호출한다. 모델 응답은 허용 구조·참조를 검증하고 암호화한다. 별도 짧은 트랜잭션에서 **분석 결과와 완료 상태를 함께 커밋한 뒤** Flutter에 전달한다. LLM 호출 동안 DB 트랜잭션/잠금을 유지하지 않는다.
5. 앱 종료/응답 유실 후에는 현재 인증과 관련 입력으로 DB 결과를 조회한다. 유효 결과는 반환하고 보관 종료·비활성·구근거 결과는 현재 분석으로 사용하지 않는다. 저장 당시 localSessionEpoch를 재로그인 복구 조건으로 강제하지 않는다. 새 조회 응답에는 현재 요청의 epoch/revision을 적용하며 원래 분석의 출처/버전은 보존한다.
6. 결과가 없는 실패 복구는 사용자가 **다시 시도**를 눌러 요청한다. 서버는1~2단계를 다시 검사해 뒤늦게 저장된 결과나 진행 작업이 있으면 재호출하지 않는다. 재시도 버튼은 유효 결과를 강제로 새로 만드는 기능이 아니다. 자동 모델 재호출·SDK 숨은 재시도는 허용하지 않는다.

접수·실행 허용·본문 제출·상태/결과 조회·재시도라는 **통신 단계는 공동 필수 계약**이다. 경로/요청·응답 필드·상태코드·실행 허용 유효시간·본문 제출 중 슬롯 처리 방식은 A 작성/B 확인으로 구체화하며 기존 HTTP/v3 계약에 임의 추가하지 않는다. 분석 요청 본문의 영속 큐나 푸시 인프라까지 확장하지 않는다.

## 분석 결과·운영 기록과 보관

수명·중요보존 예외·해제·탈퇴는 [공통 보존 기준](../../../docs/payse-execution-contract.md#보존복구-확정-기준)이 단일 기준이다. 아래는 후속 DB 설계의 최소 책임과 필드 의미이며 **새 테이블/컬럼·공개 스키마를 구현한 것이 아니다**.

| 논리 저장 단위      | 최소 정보·제약                                                                                                                                                                                    | 수명·관계                                                                                                               |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 분석 결과           | 결과ID·userId·작업 종류·관련 입력 지문·원천/설정/규칙/모델/프롬프트/응답 버전·최초 저장 시각·일반 폐기 기준시각·암호문·키 참조/암호 메타정보·활성 상태·참조 정책·AI 참고자료 구분·중요보존 플래그 | 일반 결과3개월과 중요보존 예외를 적용. 결과 자체에 출처/재사용 근거를 보존하며 상세 작업 기록 삭제에 연쇄 삭제되지 않음 |
| 분석 작업·전송 시도 | 작업/시도ID·userId·입력 지문·최초 접수·시작/종료·진행 상태·공급자 요청 식별(확보 시)·본문 없는 오류·누적 시도 수                                                                                  | 상세 기록은 종료 후7일. 사용자별 중복 접수·시도 생성을 원자 제어. 횟수는 관측값이며 고정 최대 횟수 미지정               |
| 최소 재시도 식별    | userId·작업ID·지문·최초 접수·보관 기한·누적 시도 수·완료 불명/복구 상태·필요한 결과/미정산 시도 참조                                                                                              | D4: 최초 접수부터 달력3개월, 연장 없음. 상세 기록7일 삭제 뒤에도 동일 작업 복구를 식별. 본문·전체 로그 복사 금지        |
| 비용 장부           | 프로젝트·시도 식별·예상/실제 비용·예약/정산 상태·단가/환산 기준                                                                                                                                   | 결과/작업 삭제·SQL 업무 롤백과 별개. 상세 보관기간·정산 구현 미확정. 미정산 예약은 TTL로 자동 해제하지 않음             |

인증 원문·원천 전체·가상 소비 입력/결과의 영구 저장은 승인되지 않았다. 최소 요청 입력과 암호화 전 평문 응답은 처리 메모리에서만 다루고 로그에 남기지 않는다. 플래그·분류·상태의 실제 컬럼명/enum·설정 주체/허용 전이는 별도 API 설계에서 정한다. 중요보존을 `필수 참조`나 `활성` 값에 합치지 않는다. 모델 문장 속 보존 요구만으로 플래그를 바꾸지 않는다.

최초 저장 시각과 원래 3개월 기준시각은 중요보존 중에도 유지한다. 폐기 판정은 참고자료 여부·중요보존·탈퇴 기한을 함께 검사한다. 일반 만료 자료나 중요보존 해제 후 기한 경과 자료는 즉시 조회/참조를 차단하고 폐기 대상으로 처리한다. 중요보존 중 비활성화/원천 정정은 현재 참조를 막지만 그 이유만으로 보존 예외를 해제하지 않는다. 파쇄 이후 재활성화로 복구하지 않는다. 3개월은90일이 아니며 시간대·대응 일이 없는 달의 계산·삭제 실행 간격은 구현 전에 구체화한다.

새 저장 단위에도 기존 userId 소유권·RLS·런타임 최소 권한을 적용하되 현재 금융 `users.data_version`·`write_receipts`를 분석 진행/비용 장부로 전용하지 않는다. `source_contexts`는 현재 원천 버전만 유지하므로 과거 결과의 sourceVersion을 현재 행과 반드시 같게 만드는 FK를 두지 않는다. 결과에는 당시 버전을 보존하고 재사용 시 현재 관련 원천을 검증한다. 결과가7일 후 지워지는 작업 행에 필수로 의존하거나 작업 삭제로 함께 지워지지 않게 한다. 실제 FK·인덱스·허용 상태·마이그레이션은 미구현이다.

### 키 관리와 복구본 폐기

D1은 **외부 관리형 키 서비스 + 결과별 데이터 키의 봉투 암호화**로 확정한다. 데이터 키는 결과를 암호화하고 상위 키는 데이터 키를 보호한다. 키 참조·버전·복호화에 필요한 암호 메타정보와 암호문을 관리하며 평문 키를 DB 행·로그·앱·Git에 보관하지 않는다. 인증된 암호화의 알고리즘/라이브러리·키 제품·운영 권한·회전/장애 복구 절차는 구현 전에 정한다. 관리형 키 서비스의 도입 비용이 승인되거나 무료라는 뜻은 아니다.

D2는 폐기 대상 결과를 백업/WAL/복제본에서 복원해도 다시 참조하거나 복호화할 수 없도록 하는 안이다. 즉시 조회 차단과 최종 파쇄 완료를 구분한다. 암호학적 파쇄를 사용하면 복호화 가능한 모든 데이터 키 사본·감싼 키 사본·복구 경로를 함께 처리해야 한다. 현재 DB의 키 행만 지워도 백업의 감싼 키와 유효한 상위 키로 복호화할 수 있으면 완료가 아니다. 단순 키 회전·취소 가능한 삭제 예약도 완료로 보지 않는다. 중요보존 결과는3개월 일괄 키 삭제 대상에서 제외하고, 다른 결과와 공유하는 상위 키를 삭제해 보존 자료까지 잃지 않게 한다.

복구 후 서비스 재개 전에 현재 보존/탈퇴 정책을 적용하며, 옛 백업의 중요보존 값을 그대로 복원해 해제·폐기 결정을 되돌리지 않는다. 폐기 결정의 복구 절차·키 사본 범위·백업 만료/검증 방식은 인프라 선정 후 구체화한다. 실제 비가역 폐기가 검증되기 전 ‘3개월 후 완전 파쇄 완료’라고 보고하지 않는다.

근거: [Google Cloud 봉투 암호화](https://docs.cloud.google.com/kms/docs/envelope-encryption)는 키 역할 분리, [PostgreSQL 연속 아카이빙](https://www.postgresql.org/docs/current/continuous-archiving.html)은 WAL/백업 복구 범위, [NIST SP 800-88r2](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-88r2.pdf)는 암호학적 파쇄 시 키 사본 처리의 참고다. 제품 선택·실제 파쇄 검증을 대신하지 않는다.

## 중도 취소·서버 재시작

상태를 ‘미전송’, ‘전송 가능/완료 여부 불명’, ‘응답 수신·저장 미완료’, ‘DB 저장 완료’, ‘취소/실패’로 구분해 복구한다. 이름은 논리 상태이며 공개 enum 확정이 아니다. 전송 전 내구 기록·원자 중복 접수·시도/예약의 연결로 서버 재시작이 누적 시도 기록이나 비용 예약을 초기화하지 않게 한다.

- 커밋 전 감지한 SQL 취소/실패는 해당 결과·완료 상태 등 업무 변경을 함께 롤백하고 성공 응답을 반환하지 않는다. [SQL 취소 기준](sql-style.md#취소실패와-커밋-경계)을 따른다.
- DB 커밋 후 응답 유실은 미실행이 아니다. 기존 결과를 조회/반환한다. 커밋 확인 자체가 유실됐으면 작업/시도 식별로 결과를 대조하기 전 재저장·재호출하지 않는다.
- LLM 전송 뒤 서버 장애/timeout은 SQL 롤백으로 외부 실행·청구를 취소할 수 없다. 비용 예약과 전송 사실을 보존하고 자동 재전송하지 않는다. 공급자 조회가 가능하면 먼저 확인한다. 완료 불명 상태에서도 D3의 사용자 재시도를 허용하되 아래 재시도 절의 확인·중복 방지·비용 조건을 적용한다. DB 결과 없음만으로 미전송·비용0을 확정하지 않는다.
- 앱 연결 종료는 업무 취소가 아니다. 명시 로그아웃/접근 취소는 기존 세션 정책대로 처리하되 이미 커밋된 결과는 지우지 않고 해당 기기로 전달하지 않는다. 이전 작업의 늦은 응답이 새 사용자 화면에 반영되지 않게 한다.

정상·SQL 중도 실패/취소·커밋 응답 유실·서버 재시작·재시도 연타·결과 저장 경합·종료/탈퇴와의 경합을 검사한다. 비용 및 작업 기록까지 모두 롤백해 ‘아무 일도 없었다’고 처리하지 않는다. 실제 SQL·HTTP·공급자 호출 구현/실행 검증은 아직 없다.

우선순위 세부값은 미확정 권고다. 현재 계산 의존성 미해결은 Q2의 대기 예외, 일반 미분류는10건/60초 기준을 적용한다. 독립적인 수동 분석 요청을 최상위 작업으로 등록하지 않는다. salaryEvidenceMissing·classificationConflict·settlementRelationUnresolved 같은 내부 reasonCode는 관련 회차/거래/의무/계좌 근거로 검증하며 단순 큰 금액이나 confidence로 승격하지 않는다. 재시도는 기존 실패 작업 복구로 구분하고 한도 우회용 새 작업으로 취급하지 않는다.

건수는 이미 처리·제외된 항목을 뺀 안정된 의미 작업 ID의 개수다. 같은 거래가 재조회되거나 같은 후보가 중복 접수돼도 늘지 않는다. `firstEligibleAt`은 서버 대기 메타데이터의 최초 접수 시각으로 고정하며 재접속으로 초기화하지 않는다. 사용자 기기의 requestedAt은 진단용이며 한도·deadline·TTL의 권위가 아니다. 서버는 제출 항목 수·허용 enum·지문·필드 범위·소유권을 대조하되 금융 수치·반복성을 재계산하지 않는다. 프로젝트24시간 한도도 사용자 한도와 같은 이동 구간을 사용한다. 대기 중 deadline 만료는 숨기지 않고 deferred로 표시한다.

EX-A/B 분할, EX-C의 설명/대안, EX-D의 후속 자연어 추출/설명, EX-E 회고는 서로 다른 작업 목적을 유지한다. 고정 시도 횟수와 분할 수를 곱해 최대 호출 수를 만들지 않는다. EX-U/R/AC/S/T/L/O/W 자체의 모델 호출0회와 유효 결과 재사용 시0회는 유지한다. 의미 분석의 별도 EX-B 분기를 추가 재시도 허가로 해석하지 않는다.

## 재시도와 모델 전환

작업 deadline의 기존 권고값은 사용자 재시도의 시간창을 확정하지 않는다. 최대 횟수는 미지정이며, 논리 작업·시도 누계·D4 식별 보관기한·개별 재시도의 실행 시간창을 구분한다. 최초 deadline 경과 뒤 복구 절차와 D4 식별 만료 뒤 동일 작업 확인 방식은 구현 전에 정한다. 식별 기록이 없다는 이유로 이전 전송/미정산 비용이 없었다고 단정하지 않는다.

공급자 재호출은 사용자의 실패 복구용 다시 시도 요청을 서버 한 계층에서 검증한 뒤 수행한다. Flutter/SDK/서버의 자동 모델 재호출은0이다. 상태/DB 결과 조회·동일 결과의 DB 저장 재처리는 새 모델 호출이 아니다. SDK 기본 재시도를 확인하고 끈다.

재시도 접수에는 유효 DB 결과·기존 작업/전송 상태·현재 권한/관련 입력·동시 중복·비용을 검사한다. DB가 유효 결과를 가지면 재호출0회, 서버가 같은 작업을 실행 중이면 관찰로 합친다. 기존 시도의 완료 여부를 확인할 수 없으면 그 상태·예약을 보존하고 **중복 실행/토큰 사용·과금 가능성을 알린 뒤 사용자가 다시 시도할 수 있게 한다**. 같은 논리 작업에 새 시도를 원자 등록하고 기존 시도를 미전송으로 바꾸지 않는다. 재시도 연타는 한 접수로 처리하며 늦게 도착한 응답이 이미 채택한 결과를 조용히 덮어쓰지 않게 한다. 결과 채택의 유일성·경합 규격은 구현 계약에서 검증한다.

429의 Retry-After는 다음 사용자 재시도의 가능 시각 제약이며 시간이 지나도 자동 호출하지 않는다. 잘못된 입력·권한·스키마·모델 설정 오류는 같은 본문 재전송으로 해결된다고 가정하지 않는다. 서버/LLM 장애가 항상 토큰 사용·과금0을 뜻하지 않는다. 현재 유료 호출 미구현과 향후 전송된 요청의 과금 여부는 구분한다. [공급자 요청 식별 안내](https://developers.openai.com/api/reference/overview#debugging-requests)의 요청ID는 추적 근거이며 그 자체로 정확히 한 번 실행이나 멱등성을 보장한다고 가정하지 않는다.

자동 모델 전환은 공통 Q2를 따른다. Jev 채택을 확정한 것은 아니다. 후속 평가 뒤 전환을 켜려면 허용 작업·사유·임계값·전환 횟수·총시도 한도를 별도로 확정한다. 최대 횟수 미지정 결정을 자동 모델 전환 승인으로 해석하지 않는다. ‘confidence가 낮다’ 하나만으로 자동 전환하지 않는다. 정답 후보 자체가 없으면 더 큰 모델에 같은 잘못된 선택지를 보내지 않고 unknown으로 남긴다.

## 비용 예약

총상한·차단선·여유액과 **유료 API 종료 시각의 잠정 폐기**는 [제품 기준](../../../docs/product-baseline.md#api-비용)을 단일 원본으로 사용한다. 아래는 예약·정산의 구현 권고이며 구현 완료가 아니다.

- 시작 전 기존 모든 API 사용액을 입력하고, 사용액+미확정 예약액+새 시도 최대 예상비용이 예약 한도 **이하**일 때만 원자 예약하는 기존 권고안을 유지한다. 누적 실제/예약 비용이 제품 기준의 차단선 이상이면 새 유료 호출은 차단한다. 예약·환산 세부 구현은 미완료다. 원화 환산·세금·수수료·단가 버전·출력 최대 토큰을 포함한다. 미설정이면 신규 호출0회다.
- 취소/timeout 예약은 실제 청구 확인 전 반납하지 않는다. 공급자 대시보드 알림만으로 차단했다고 주장하지 않는다. 로컬 기능·금융 조회는 AI 비용 차단과 별개다.
- 자동 예약으로 통제할 수 있는 것은 공통 장부를 거친 호출이다. 다른 개발자의 직접 공급자 호출·별도 키 사용액은 사전 예약 또는 사용량 동기화가 필요하다. 이를 확인하지 못하면 제품 기준의 프로젝트 총상한이 보장된다고 보고하지 않으며, 확인 전 새 유료 호출을 열지 않는 안을 권고한다.

달력 날짜를 기준으로 신규 유료 호출을 닫는 운영 종료 시각은 잠정 폐기했다. 이전 날짜를 새 요청·재시도·대기 작업 전송의 차단 조건으로 사용하지 않는다. 이 결정은 총예산 초기화나 세션·개별 요청 timeout·작업 deadline·결과 보관기간 변경이 아니다.

예약은 무기한 전송 허가가 아니다. 승인한 자기 예약 때문에 같은 시도를 이중 집계하지 않도록 예약·전송 판정 지점을 구체화하고 전송 직전 현재 권한·작업 상태·비용 조건을 다시 검사한다. 예약 한도/정산 방식은 아직 미정이므로45,000원에 정확히 도달하는 예약의 전송 여부를 임의 구현하지 않는다. 예시44,900원+새100원, 동시 두 예약, 완료 불명 재시도의 기존/신규 예약, 결과만 조회를 별도 경계 벡터로 확정해야 한다. 폐기된 날짜 차단이나 고정 최대 시도 수를 이 검사에 되살리지 않는다.

## Jev 평가안

Jev는 **도입 미확정 후보**다. 공식 공급자 TypeSafe의 문서를 확인했으며 실제 모델·한국어 품질·계정 접근·비용 절감은 검증하지 않았다.

| 작업        | 적용 검토 범위                                                 | 적용하지 않는 범위                                               |
| ----------- | -------------------------------------------------------------- | ---------------------------------------------------------------- |
| A/B         | 로컬이 제시한 분류·후보 ID 중 선택. `unknown/none` 선택지 포함 | 후보 밖 거래/금액/급여 완료 생성, 자동 설정 저장                 |
| C/E         | 고정 설명 유형·근거/대안 ID 선택은 검토 가능                   | Jev만으로 자유 설명·회고 전체 대체                               |
| D           | 로컬이 추출한 원문 span·조건 종류 선택                         | 후보에 없는 열린 해석·자유 텍스트 추출 전부 대체, 날짜·금액 계산 |
| 확인 후처리 | 적용하지 않음                                                  | 입금 확정·계획 저장·승인·보호 해제·경계 계산                     |

공식 [Introduction](https://docs.typesafe.ai/introduction)과 [원문 후보 추출](https://docs.typesafe.ai/cookbooks/pre_parsed_value_extraction_cookbook)은 선택형 구조·사전 후보 선택의 근거다. [날짜 추출 예제](https://docs.typesafe.ai/cookbooks/date_extraction_cookbook)의 날짜 조립은 PAYSE에서는 Dart 책임이며 예제의 연도 기본값·허용 범위를 가져오지 않는다.

[Confidence 정의](https://docs.typesafe.ai/confidence)의 confidence는 선택/점수 분포 통계다. 0.9를 PAYSE 정답률90%로 해석하지 않는다. 공식 예제 임계값은 PAYSE 합의가 아니다. [모델 문서](https://docs.typesafe.ai/models)에 따라 고정 모델 ID로 평가하고 한국어 거래명·선택지 순서·정답 후보 없음·유사 상호·가족 입금/급여·취소를 포함한다.

평가 묶음은 사용자/기간·유사 반복 거래가 훈련·임계값 조정·최종 평가에 중복되지 않게 나눈다. 분류별 정밀도·누락률·보류율·잘못된 금융 영향 제안 수·수정률을 보고한다. 미수정/무응답을 정답 라벨로 쓰지 않는다. 점수 cutoff·자동 표시 범위·전환 조건은 평가 전 미정이며, 모델값만으로 금융 설정 자동 승인하지 않는다.

모델 전환 평가에는 전환건수/전체Jev건수, 전환후정답개선·악화, 실제시도수, 총비용, 올바른결과1건당비용, 지연을 포함한다. 공식 [cascade 예제](https://docs.typesafe.ai/cookbooks/sde_cascade)의 성과를 PAYSE 절감률로 인용하지 않는다. [공식 재시도](https://docs.typesafe.ai/sdk/python/api/retries)를 확인해 위 재시도 절의 단일 재시도 주체를 지킨다. 이 링크가 Python SDK 도입 결정은 아니다.

운영 원칙 참고: [AWS의 timeout·retry·jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)는 재시도 중복·부작용 주의의 근거이며 이 문서의 초/횟수를 정한 자료가 아니다. [Google Cloud 예산 문서](https://docs.cloud.google.com/billing/docs/how-to/budgets)는 예산 알림과 사용량 자동 차단이 다름을 확인하는 자료이며 Google Cloud 도입 권고가 아니다.

## 구현·검증 시 확인

공개 계약은 기존 데이터 모델·HTTP·응답 모델에서 A 작성/B 영향 확인으로 확정한다. 기존 키·테이블을 분석 큐로 전용하거나 sourceVersion/v3 필드를 임의 추가하지 않는다. 누락 금융 원천의 임의 생성과 사용자 금융 금액 산출은 서버 구현 범위가 아니다. 서버의 원천 조회·공개·Snapshot 조립 책임은 유지한다.

현재 미구현·문서 충돌·fixture 기준 및 **AT01~AT22는 [공통 계약](../../../docs/payse-execution-contract.md#공통-반례인수-조건)에 남아 있다**. API 입력/출력·권한·중복·예약·timeout·세션 무효화 테스트에는 해당 AT와 G0~G7을 필수 대조한다. Dart 계산·화면 검증은 B 담당이며 API 문서나 하네스 PASS로 대체하지 않는다.
