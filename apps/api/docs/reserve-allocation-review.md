# 준비금 배정·분석 후보 연결 검토

2026-11-04, `fix/api/data-refresh-consistency`. 검토 대상은 [모바일 PR #207](https://github.com/Fintech-project-team/Fintech-project/pull/207)의 `c8ea3fa`와 현재 API다. #207은 `hyeyeon-dev`에 병합됐으며 확인한 `develop`은 `5218a5c`다. 모바일 수정·브랜치 병합·배포·기존 DB 이행은 포함하지 않는다.

## 서버 저장 보완

`AllocationWrites.change`는 생성 → 수정 → 제거를 수행한 **최종 상태**에서 같은 `user_id/reserve_id/obligation_id`의 미해제 행(`amount_krw > released_krw`)이 둘 이상이면 `409 RELATION_CONFLICT`로 전체 요청을 롤백한다. 사용자 잠금을 보유한 기존 인증 트랜잭션에서 검사하며 영수증·버전 확정 전이다. 기존 연결 금액 변경에는 기존 `allocationId`를 사용한다.

- 한 요청의 create 중 같은 의무 ID, update/remove 중 같은 배정 ID 중복은 기존 `422 VALIDATION_FAILED`다. 저장된 기존 행과의 충돌은 `409`로 구별한다.
- 서로 다른 준비금이 같은 의무를 분할 부담하는 것은 허용한다. 각 준비금과 의무의 **미해제 합계** 한도는 계속 검사한다.
- 완전히 해제된 행과 지급 근거는 삭제하지 않는다. 이력 행과 새 미해제 행의 공존은 허용하지만 둘을 동시에 미해제 상태로 만드는 갱신은 거절한다.
- 미사용 연결을 명시 remove하고 같은 요청에서 새로 만드는 원자 교체는 허용한다. 생성 직후 임시 중복만 보고 거절하지 않는다. 모바일의 제거 취소/재선택에는 원래 ID를 재사용하는 편이 적절하다.
- 과거 중복 행을 자동 합산·삭제하지 않는다. 명시 변경의 최종 상태가 유일해져야 성공한다. 배정 변경이 없는 별칭 편집 같은 요청까지 기존 중복을 이유로 새로 차단하지 않는다.
- 같은 키·같은 본문의 재시도는 기존 영수증을 반환한다. 같은 버전의 다른 키 동시 요청 중 후행 요청은 `409 STALE_DATA`, 최신 버전으로 다시 시도한 중복 생성은 `409 RELATION_CONFLICT`다.

화면 금액은 미해제액, API `update.amountKRW`는 **미해제액 + 이미 해제된 금액**이라는 #207 변환을 유지한다. 사용한 행의 해제는 총액을 `releasedKRW`까지 낮추고, 사용 이력 없는 행만 remove한다. 원천 잔액·거래를 수정하거나 해제를 새 지급으로 기록하지 않는다.

## DB 유일성 제약을 바로 적용하지 않은 이유

현재 DB에는 해당 조합의 유일성 제약이 없다. 이번 보호는 API 경로에 적용되며 직접 SQL까지 차단하는 제약은 아니다. 실제 서비스 DB의 기존 중복은 조사하지 않았다. 폐기 DB의 합성 중복만 준비해 API에서 명시적으로 복구하는 경로를 검사한다.

즉시 부분 UNIQUE를 추가하면 현재 생성 → 제거 순서의 정상 교체가 중간 flush에서 실패한다. 완전 해제 이력을 다시 미해제 상태로 만드는 정산 정정도 별도 검토가 필요하다. 현재 지급/정정 HTTP는 구현된 API가 아니므로 해당 API까지 안전하다고 주장하지 않는다.

이행 전에는 아래와 같은 읽기 전용 집계로 기존 중복을 확인하고, `release_evidence`와 `write_receipts`를 대조해야 한다. 같은 소유자 잠금, 지연 제약의 최종 상태 검사, 직접 쓰기 권한, 동시 갱신, 실패 롤백을 함께 설계한다. 기존 중복 정리 또는 정산 복원을 자동 데이터 수정으로 해결하지 않는다. 정정으로 기존 지급을 되돌릴 때 새 배정과 충돌하면 최신 상태의 명시 조정이 필요하다.

```sql
SELECT user_id, reserve_id, obligation_id, count(*) AS open_rows
FROM payse.reserve_allocations
WHERE amount_krw > released_krw
GROUP BY user_id, reserve_id, obligation_id
HAVING count(*) > 1;
```

## LLM과 금융 확정의 경계

기존 [의미 계약](analysis-meaning.md), [실행 공통 계약](../../../docs/payse-execution-contract.md), [AI 공급자 경계](../../ai/docs/README.md)를 유지한다. 로컬 LLM으로 교체해도 같은 입력·검증·저장 인터페이스를 사용한다.

1. LLM은 거래/반복의 **의미 후보**만 반환한다. 의무·급여·준비금·배정·정산을 확정하거나 직접 저장하는 도구를 주지 않는다. 분석의 succeeded는 금융 저장 성공이 아니다.
2. 앱은 최신 Snapshot에서 기존 의무/반복 계획·회차·출금 계좌와 후보 근거를 대조한다. 이름만 같다는 이유로 중복 또는 같은 의무라고 단정하지 않는다. 이미 연결된 근거·동일 계획/회차를 먼저 제시하고 모호하면 사용자가 확인한다. 이 비교/승인 화면은 아직 서버 기능으로 대신 구현하지 않았다.
3. 분석 중 원천·지급·월급 주기·설정이 바뀌면 최신 버전으로 결과를 다시 조회하고 Flutter의 계산·미리보기를 갱신한다. 관련 거래/권한이 바뀐 늦은 결과는 서버가 거절한다. 무관한 설정 변경 뒤 의미만 재사용 가능한 경우도 과거 버전을 최신으로 위장하지 않는다.
4. 금액·주기·사용 가능액·한도 미리보기는 Flutter가 계산한다. 서버는 사용자 확정 요청의 소유권·활성 상태·이력·합계·버전만 검증한다. 분석 실패·판단 유보에도 기존 수동 설정 경로는 유지한다.
5. 현재 의미 결과를 금융 설정으로 자동 변환하는 승인 API는 없다. 분석 결과만으로 `POST /obligations` 등을 호출하지 않는다. 별도 사용자 확인 뒤 기존 금융 쓰기 규약을 따른다.

## 표시·편집의 미결정 사항과 권고

- 신규 선택을 이번 월급 주기로 제한하는 것은 Flutter 화면 정책으로 유지한다. 서버에 별도 급여 주기 계산을 중복 구현하지 않는다.
- 주기 밖으로 이동한 기존 연결과 급여 대기 상태의 연결을 자동 제거하지 않는다. 기존 연결과 사용 이력을 보존하고 현재 계산 포함 여부를 구별해 보여준다.
- #207은 다음 주기 연결에 해제만 제공하고, 주기 미확정에는 감소/해제를 제공한다. 주기 밖 기존 연결의 감소도 허용할지 B/사용자 확인이 남아 있다. 안전한 기본안은 증액·신규 선택을 막고 근거를 표시한 감소·명시 해제만 허용하는 것이다.
- 빈 선택 목록은 자료 부족/주기 미확정과 실제 선택 가능 지출 0건을 구별한다. 미수신을 0건으로 표시하지 않는다.

## 검증 기록

추가 검사는 합성 자료와 새 PostgreSQL 클러스터에서 실행한다. 실제 공급자는 모의 응답으로 대체하며 비용·암호화·저장 경계는 기존 구현을 통과한다. 실제 지급 HTTP, Flutter 계산/화면, 모바일 기기, 운영 DB·배포 검증은 포함하지 않는다.

| 검사                          | 결과와 한계                                                                                                                  |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 폐기 PostgreSQL 전체 회귀 2차 | API 378건 중 377 PASS, SKIP 0. 반복 후보 1건은 새 테스트가 응답의 `interpretation` 경로를 빠뜨려 FAIL. 실패 기록은 유지한다. |

| DB 구조·원천 갱신·비용 원장   | 각각 13/8/10건 PASS. 금융 원천 및 기존 인증·급여 자료 보존 확인.                                                             |

배정 7건은 저장 중복/다른 준비금 분할, 동일·다른 키 동시 요청과 replay, create/remove 원자 교체와 실제 변경 영수증, 사용 이력 보존·재활성 충돌, 과거 중복의 명시 복구, 형식/버전/권한 순서와 UUID, 고정 반복 버전의 계좌 접근이다. 분석 3건은 분석 중 부분 지급·일정·급여일 변경, 분석 실패 후 수동 저장, 기존 의무와 겹치는 반복 후보의 금융 불변이다.

부분 지급 도착은 **폐기 DB 준비 변경**으로만 모사했다. 아직 없는 지급 HTTP나 Flutter 주기 계산을 실행한 것으로 해석하지 않는다. LLM 공급자는 이 검증에서 모의 구현이며 새 실제 LLM 정확도 평가가 아니다.

로컬 근거는 `.harness/reserve-analysis-pg-01`, `reserve-analysis-pg-02`, `reserve-recurring-pg-03`의 결과/로그와 `.harness/reserve-followup-cases-02.json`이다. 최초 실행의 시드 참조 선택 오류 및 영수증 기대값 오류, 2차 응답 경로 오류도 보존했다. 재현은 [DB 검사](database-tests.md)의 `test_analysis_service.py`를 새 작업 폴더에서 실행한다. 전체 실행을 PASS로 바꾸어 기록하거나 건너뛴 검사를 DB 검증으로 계산하지 않는다.
