# 인증·금융 저장·분석 서비스 연결 경계

[#22](https://github.com/Fintech-project-team/Fintech-project/issues/22)·[#23](https://github.com/Fintech-project-team/Fintech-project/issues/23)·[#32](https://github.com/Fintech-project-team/Fintech-project/issues/32)의 연동 설계다. HTTP·DB·LLM 전체 구현 완료를 뜻하지 않는다. API 구현 때 [공통 HTTP](../../../docs/api-contract.md), [응답 투영](../../../docs/api-response-models.md), [분석 API](analysis-api.md)를 함께 읽는다. 같은 DTO·테이블을 강제로 공유하지 않는다.

## 1. 재사용할 구현

| 구성요소                       | 기존 역할                               | 다음 연결                                                     |
| ------------------------------ | --------------------------------------- | ------------------------------------------------------------- |
| AuthService                    | login/logout/reverify/rejectMalformed   | 인증 HTTP 어댑터에서 결과·오류·Retry-After/no-store로 매핑    |
| AuthTransactions.run           | 짧은 JDBC 트랜잭션·LOCAL 역할·연결 반환 | 금융/분석의 DB 작업. LLM 호출을 콜백 안에 넣지 않음           |
| AuthRepository.authorize       | 토큰 확인·사용자 잠금·RLS 문맥          | 해당 DB 읽기/쓰기와 같은 연결·트랜잭션에서 수행               |
| BootstrapSecurityConfiguration | 생존 확인 외 차단                       | 구현·검증된 경로만 후속 허용. 문서 추가로 permitAll 확대 금지 |
| 기존 SQL의 제약·권한           | 금융 관계/소유권과 인증 DB 함수         | 새 역할/함수는 필요한 권한만 추가. 기존 원천 전체 UPDATE 금지 |

토큰을 HTTP 필터에서 한 번 확인한 것으로 저장 시점의 권한 확인을 대체하지 않는다. Java 요청 객체를 DB 객체에 통째로 바인딩하지 않는다. 각 서비스는 생성자 주입을 사용하고 사용자별 가변 상태를 singleton/static에 두지 않는다.

## 2. 조회·쓰기 분리

| 영역           | 입력/버전                        | 저장·응답                                                              |
| -------------- | -------------------------------- | ---------------------------------------------------------------------- |
| 인증           | 합성 자격 또는 현재 Bearer       | 기존 AuthResult와 세션 DB 처리. PIN·설치 ID 추가 없음                  |
| 금융 조회      | 현재 세션·조회 범위·기존 cursor  | 현재 공개 범위의 일관 Snapshot. 다른 버전의 페이지 혼합 금지           |
| 금융 설정 쓰기 | 기존 W와 허용 필드               | 설정·영수증·dataVersion 증가 원자 처리. 현재 권한의 최신 Snapshot 반환 |
| 분석           | 의미 입력·원천 문맥·별도 멱등 키 | 독립 작업/결과 상태. 금융 dataVersion·write_receipts·원천 변경 없음    |

금융 쓰기 순서는 현재 세션/사용자 확인 → 형식 → 같은 키 replay/충돌 → 신규 요청의 버전/소유권/관계 → 설정+영수증+버전 커밋이다. 이미 성공한 같은 키를 옛 버전이라는 이유로 거절하지 않는다. 조회도 기존 authorize의 잠금/RLS 준비를 유지하므로 READ ONLY를 무조건 강제하지 않는다.

Snapshot 조립은 users/source_contexts/설정/관계를 동일하게 검증된 버전으로 읽는다. 기존 권한 투영·accessRestrictions·거래 원천별 연결 기준·급여 receiptEvidence는 [응답 모델](../../../docs/api-response-models.md)을 그대로 사용한다. 서버는 U·급여 구간·미래 잔액을 계산하지 않는다.

## 3. 구체화할 구현 순서

1. #22: 기존 AuthService에 HTTP 요청 파싱·엄격한 허용 키·오류 매핑을 연결한다. malformed JSON도 IP 제한에 정확히 1회 포함한다. 실제 클라이언트 IP는 직접 연결 또는 명시 신뢰 프록시에서만 취득한다.
2. #22: Snapshot 조회 투영·거래 페이지·기관 연결 저장을 구현한다. fixture 파일을 응답으로 그대로 반환하는 것으로 DB 저장/재로그인 유지 완료를 대신하지 않는다.
3. #23: 단순 계좌 선택·별칭·급여/카드 설정부터 기존 W로 구현하고, 예정 지출·보호금·배정 취소까지 기존 계약 순서로 확장한다. 각 단계의 일부 완료를 이슈 전체 완료로 표시하지 않는다.
4. #32: 위 인증 문맥을 재사용해 독립 접수/상태/결과/사용자 재시도 저장을 구현한다. 가짜 공급자로 실패·경합을 검사한 뒤 승인 프로필과 키/비용 준비가 갖춰진 유료 어댑터를 연결한다.

필요한 실제 클래스부터 Controller → Service → Repository/adapter로 나눈다. 아직 사용하지 않는 BaseService·전역 상태 관리자·모든 기능 공용 ‘data’ DTO를 만들지 않는다. 재사용 가능한 것은 인증/트랜잭션 규칙이며 금융 쓰기와 분석 쓰기의 업무 순서를 하나로 합치지 않는다.

## 4. 함께 확인할 경합

| 사례                      | 보장할 결과                                                                      |
| ------------------------- | -------------------------------------------------------------------------------- |
| 동일 금융 저장 재전송     | 효과·영수증 1회, 같은 키 다른 본문 409                                           |
| 다른 키로 동시 금융 저장  | 같은 구 버전에서 하나만 성공, 다른 요청 409                                      |
| 금융 설정 변경 중 분석    | 이미 수신한 원천은 보존, 관련 입력이 달라진 분석은 현재 결과로 적용 금지         |
| 무관한 설정 변경          | 관련 입력 동일성 재검증 후 재사용 가능, 과거 provenance 직접 덮어쓰기 금지       |
| 로그아웃/탈퇴와 늦은 응답 | 새 사용자 화면에 이전 결과 전달 금지. 커밋된 결과를 로그아웃만으로 삭제하지 않음 |
| DB 취소/응답 유실         | 미커밋 업무 롤백, 성공 커밋/인증 제한/외부 비용 보존                             |
| 다른 사용자 자원 ID       | 기존 동일 403 규칙, 숨겨진 원천/키/로그 비노출                                   |

실제 PostgreSQL 권한·동시성·롤백 검사는 구현 단계에서 수행한다. 문서/하네스 PASS를 DB나 Flutter 통합 PASS로 표현하지 않는다.

## 5. 구현 전 확인 항목

인증 본문 4 KiB(4096바이트)는 사용자 확정값이며 초과는 413이다. 일반 쓰기 64 KiB·Label 1~80 grapheme는 제안 상태이므로 실제 적용 전에 확정한다. 분석 input/output 상한은 별도이며 인증 상한을 그대로 전용하지 않는다. 공개 분석 경로·DTO는 B 확인, 서버 네트워크/프록시/KMS 운영값은 해당 운영 설계가 필요하다.

## 6. Flutter 연동 시 확인할 호출부

- `ConnectionReviewScreen.analysisReceived`는 표시용 boolean이며 분석 접수·작업 succeeded만으로 true가 되면 안 된다. 현재 입력에 유효한 결과와 실제 완료 범위를 따로 검증한다. 거래 의미만 분석했을 때 모아둘 돈 제안까지 검사해 ‘제안 없음’으로 표시하지 않는다.
- 기존 `UserFinancialRepository`와 금융 v3 Snapshot에 분석 상태를 섞지 않는다. 분석 요청·상태·결과·보존 정보의 별도 DTO/Repository 연결은 B가 구현한다.
- 홈 `calculation_input_adapter.dart`의 고정 inputRevision을 분석용 변경 추적으로 재사용하지 않는다. 분석용 현재 epoch/revision과 원 분석 provenance를 분리하고 로그아웃/재로그인/입력 변경의 늦은 응답을 검사한다.
- `MemoryFirstCalcRecordStore`는 첫 계산 안내 기록이다. AI 장기 기억 저장소나 가상 소비 영속 저장소가 아니다. 보존 정보 목록·개별 기억 삭제 UI는 B가 연결한다. resultId와 itemId를 구분하고 부분 제공·삭제 범위를 표시하며, 삭제 응답 후 같은 기억의 기기 캐시도 무효화한다.
- 급여 설정 저장은 기존 SalaryPatch만 변경하고 receiptEvidence를 유지한다. 관련 설정이 바뀐 분석 결과는 현재 입력으로 재검증하며, 실제 입금 확인 저장이나 원천 변경으로 확대하지 않는다.

모바일 코드·테스트·문서는 API 작업에서 수정하지 않는다. 호출부 대조는 통합 검사 완료를 뜻하지 않는다.
