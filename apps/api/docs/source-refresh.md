# 원천 자료 갱신

현재 금융 공급자는 준비된 합성 자료다. 조회 시각이 바뀌어도 자료의 `asOf`는 그대로다. 새로 확보한 거래·잔액 묶음이 있을 때 `sourceVersion`, `asOf`, 잔액 기준 시각, 실제 `coverage`를 함께 바꾸고 현재 `dataVersion`을 한 번 증가시킨다. 의미는 [데이터 모델](../../../docs/data-model.md#기준-시각asof과-원천-갱신)을 따른다.

`tools/refresh_source.py`는 이 갱신을 위한 관리용 SQL 생성기다. API의 조회 경로에 fixture 의존성이나 갱신 쓰기를 추가하지 않는다. 실시간 금융기관 수집기·정기 거래 생성기·새 공개 HTTP API는 아니다.

## 사용

1. 이전에 적재한 원천 전체 JSON과 새로 확인한 원천 전체 JSON을 준비한다. 같은 사용자·스키마·계산 규칙을 사용하고 기존 ID를 유지한다. 기존 자료의 날짜를 일괄 이동하거나 새 잔액을 서버에서 계산하지 않는다.
2. 대상 DB 이름과 **현재** `users.data_version`을 확인한다. fixture의 초기 `dataVersion`을 현재 값으로 사용하지 않는다. 원본 및 생성 SQL은 저장소 밖의 접근 제한된 디렉터리에서 관리한다.
3. 기본 검증 SQL을 새 파일로 생성한다. 다음 명령의 경로·DB 이름·버전은 실제 검토 값으로 지정한다.

```text
python -B apps/api/tools/refresh_source.py --before <이전원천.json> --after <신규원천.json> --expected-data-version <현재버전> --database <대상DB명> --out <저장소밖/검증.sql>
```

생성만으로 DB에 접속하지 않는다. 출력은 파일 해시와 실행 모드이며 자격·금융 본문을 출력하지 않는다. 기존 파일을 덮어쓰거나 저장소 내부에 SQL을 저장하지 않는다.

4. 검토한 SQL을 올바른 서버에 연결한 `psql -X -v ON_ERROR_STOP=1 -f <검증.sql>`로 실행한다. 접속 자격은 기존 비공개 properties·환경 설정에서 제공하며 명령줄·Git에 넣지 않는다. 해당 사용자 원천의 조회·갱신 권한을 가진 별도 관리 연결을 사용한다. 일반 앱 역할의 원천 쓰기 권한은 늘리지 않는다.
5. 기본 SQL은 실제 제약까지 확인하고 **ROLLBACK**한다. 검증 동안 해당 사용자의 잠금을 짧게 잡으며 새 영수증이나 버전을 남기지 않는다. 운영 적용이 승인된 때에만 같은 명령에 `--apply`를 추가해 별도 적용 SQL을 생성·검토한 후 실행한다. 이 옵션도 자동 DB 실행은 하지 않는다.

SQL에는 대상 DB 이름·사용자·이전 원천·현재 버전 검증이 포함된다. DB 이름만으로 서버 주소까지 식별하지는 않으므로 관리자는 연결한 서버를 함께 확인한다. 잠금 대기 5초, SQL 30초 제한을 적용하며 제한에 걸리면 변경 전체를 롤백한다. 준비된 규모를 넘는 자료는 별도 검토 후 처리한다.

## 갱신과 보존

| 항목                                                                 | 처리                                                                                         |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 원천 문맥·coverage·급여 입금 근거                                    | 새 묶음에서 제공한 값으로 반영                                                               |
| 계좌 잔액·기준 시각, 카드 원천, 거래, 청구·청구 항목, 원천 참조·관계 | 기존 ID를 보존하면서 한 트랜잭션에서 반영                                                    |
| 계좌 선택·별칭, 기존 거래의 사용자 분류                              | DB의 현재 값을 보존. 새 계좌는 미선택·별칭 없음, 새 거래 분류는 미확정                       |
| 연결·급여/카드 설정·계획·의무·보호·배정·정산·과거 승인 버전          | 원천 교체 대상에서 제외. 입력 묶음에서 이 설정을 변경하려 해도 거절                          |
| 사용자·인증 자격·세션·분석 결과                                      | 재생성·초기화하지 않음. 탈퇴 사용자는 거절                                                   |
| 현재 dataVersion                                                     | 성공 시 정확히 1 증가. 설정 저장과 같은 사용자 행 잠금을 사용                                |
| 동일 sourceVersion 재시도                                            | 현재 원천이 새 묶음과 같고 버전 증가가 확인될 때만 무변경 완료. 같은 이름의 다른 원천은 거절 |

이전 묶음과 실제 DB 원천이 다르거나 갱신 전에 사용자 설정이 저장돼 버전이 바뀌면 중단한다. 현재 상태를 다시 확인한 뒤 새 SQL을 생성한다. 기존 원천의 삭제·ID 재배정·기관 메타 변경·원천 형식 이행·사용자 설정의 자동 정정은 지원하지 않는다. 새 사실이 기존 정산·보호 관계와 충돌하면 저장 제약에 따라 전체 실패하며 사용자 관계를 자동 해제하지 않는다.

## 조회·재사용 점검과 추가 갱신 항목

| 경로                              | 현재 처리와 이번 보완                                                                                                                               |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Snapshot 기준 시각                | API가 계좌 시각과 Snapshot 시각의 같은 순간 여부, 실제 거래 날짜의 서울 업무일 상한, 거래 시각의 asOf 상한을 검사. 예정일과 사용자 기록 시각은 구분 |
| 거래 페이지                       | 기존 커서가 사용자·세션·dataVersion·sourceVersion·asOf·조회 조건에 묶임. 새 원천 반영 후 구 커서는 거절되고 앱은 새 Snapshot부터 수집               |
| 설정 저장                         | 기존 API가 버전 증가와 쓰기를 원자 처리. 앱의 `snapshot_assembly.dart`가 성공 응답의 새 Snapshot과 후속 페이지를 수집                               |
| AI 입력·결과·기억                 | 기존 분석 흐름이 현재 원천과 입력 지문·권한을 재검증. 원천 갱신 도구가 결과 버전을 덮어쓰거나 새 유료 호출을 수행하지 않음                          |
| 앱 복귀·다른 경로에서 갱신된 자료 | 홈의 명시 새로고침은 연결됨. 복귀 시 자동 재조회·중복 억제·실패 시 이전 기준 표시의 제품 정책과 프론트 연동은 별도 보완 대상                        |
| 연결 오류·오프라인                | 이전 자료를 현재 자료로 재표기하지 않음. 원천 노후도 TTL과 시간 경과만으로 AI를 재호출하는 정책은 추가하지 않음                                     |

프론트 전달 대상은 `apps/mobile/lib/app/main_entry.dart`, 세션/PIN 복귀 흐름, `apps/mobile/lib/data/connection/snapshot_assembly.dart`다. 유효 세션·잠금 해제 후 복귀 시 한 번 재조회하고, 기존 조회와 합치며, 모든 페이지의 같은 버전 수집 완료 후 화면을 교체하는 방식이 후보이다. 실패 시 기존 `asOf`와 오류를 유지하고 이전 세션의 늦은 응답을 버리는 검증이 필요하다. 이번 API 작업에서는 모바일 파일을 수정하지 않는다.

## 검사

- 기존 fixture 검사에 원천 갱신 입력 검사를 포함한다: `python -B -m unittest discover -s apps/api/tests -p test_fixtures.py`.
- API JUnit의 `FinancialRefreshTest`는 v3/v4 날짜·시각·잔액·예정일 보존을 확인한다. 기존 커서·분석 회귀도 전체 API 검사에 포함된다.
- `python -B apps/api/database/test_source_refresh.py --pg-bin <PostgreSQL-bin> --work-dir <새검사폴더>`는 별도 포트의 새 PostgreSQL만 사용한다. 준비 자료를 한 번 적재한 전용 DB에서 검사별 독립 DB를 만들고 실제 잠금·충돌·롤백·재시도·사용자 설정 보존을 검사한다.
- 기존 `test_analysis_service.py`에도 같은 원천 갱신 DB 검사를 연결해 CI에서 실행한다. 실행 이력과 통과 여부는 해당 작업 보고서로 확인한다. 운영 DB 적용·실제 기기 새로고침은 별도 결과다.

SQL 값 변환과 충돌 처리는 PostgreSQL 15의 [JSON 함수](https://www.postgresql.org/docs/15/functions-json.html), [INSERT와 ON CONFLICT](https://www.postgresql.org/docs/15/sql-insert.html)를 따른다.
