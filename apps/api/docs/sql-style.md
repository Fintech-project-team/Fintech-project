# API SQL 작성·구성 기준

`apps/api/`의 직접 작성한 SQL과 SQL 생성기의 출력에 적용한다. 데이터 의미·권한·트랜잭션 순서는 [API 필수 규칙](../src/AGENTS.md), 저장 필드는 [DB 사전](../../../docs/database-schema.md)을 따른다. 이 문서는 표기와 파일 구성을 정의한다.

## 줄바꿈과 주석

- 들여쓰기는 공백 2칸이다. 탭으로 열을 맞추지 않는다. 서로 독립적인 SQL 명령 사이에는 빈 줄을 둔다.
- `DECLARE`는 변수마다 줄을 나눈다. `BEGIN`, `IF` 조건, `THEN` 이후 본문, `ELSE`/`ELSIF`, `END IF`는 블록 구조를 들여쓰기로 구분한다. `IF ... THEN RETURN ...; END IF;`처럼 조건·동작·종료를 한 줄에 모으지 않는다.
- 조회·변경문의 `SELECT`, `INTO`, `FROM`, `JOIN`, `WHERE`, `GROUP BY`, `HAVING`, `ORDER BY`, `SET`, `RETURNING` 절을 구분해 줄을 나눈다. 단순 함수 호출 한 문장(`SELECT payse.auth_limit(?);` 등)은 한 줄로 둘 수 있다.
- 복합 조건은 `AND`/`OR`별로 줄을 나누고 괄호의 그룹을 유지한다. 줄바꿈을 위해 조건의 순서나 괄호를 바꾸지 않는다. `BETWEEN ... AND ...`의 `AND`는 하나의 범위 조건으로 취급한다.
- 긴 열·값·인자·권한 대상 목록은 항목별로 줄을 나눈다. 생성 `INSERT`는 열과 값을 각각 한 항목씩 같은 순서로 표시한다. 한 줄의 여러 대입문·SQL 명령을 세미콜론으로 이어 쓰지 않는다.
- 문자열·JSON·정규식·동적 SQL 리터럴 내부는 줄 길이를 줄이려고 수정하지 않는다. 긴 리터럴은 그대로 둔다. 데이터 값을 임의로 나누거나 새 줄 문자로 바꾸지 않는다.
- 파일 첫머리에 목적, 호출 진입점, 실행 순서 의존성을 적는다. 함수 바로 위에는 작성일·목적·실제 사용처를 적고, 주요 명령 묶음에는 무엇을 검사·변경·보존하는지 짧게 설명한다. 생성일과 확인된 수정 기록은 보존한다.

## 파일의 책임

| --------------------------------------------------- | ---------------------------------------------------------------------- |
| `database/001_initial.sql`                          | 빈 DB의 공통 테이블·기본 제약·인덱스·RLS 정의                          |
| `database/002_storage_guards.sql`                   | 저장 관계·금액 상한·불변 조건의 함수·트리거 정의                       |
| `database/003_auth_access.sql`                      | 인증 SQL의 실행 순서와 하나의 적용 트랜잭션 관리                       |
| `database/auth/preflight.sql`                       | 기존 스키마·RLS·역할·권한 사전 검사와 권한 역할 준비                   |
| `database/auth/storage.sql`                         | 비활성 시각·요청 제한 저장 구조·RLS·테이블 권한                        |
| `database/auth/limits.sql`                          | 실행 환경 검사·행 잠금·IP/자격 조합 제한 함수                          |
| `database/auth/sessions.sql`                        | 자격 후보 조회와 활성 세션·사용자 확인 함수                            |
| `database/auth/permissions.sql`                     | 함수 소유권·PUBLIC 회수·runtime 실행 권한                              |
| `database/004_auth_sessions.sql`                    | 003 이후 세션 전이 추가의 사전 검사·함수·권한을 단일 트랜잭션으로 실행 |
| `database/auth_sessions/`                           | 004 전용 사전 검사·세션 생성/종료·최소 권한 정의                       |
| `database/test_*.sql`                               | 준비 자료 대조 또는 주제별 DB 검증. 제품 초기화와 분리                 |
| `reference_data/export_sql.py`                      | 기관 기준정보 적재 SQL 생성                                            |
| `fixtures/export_sql.py`                            | 일반 사용자·금융 원천 적재 SQL 생성                                    |
| `testing/scenarios/`                                | 명시 선택한 검증 사례의 설정·이력 준비                                 |
| `tests/legacy/*.sql`, `database/migrations/*v2.sql` | 과거 DB 구조·함수 본문 대조 기준. 일반 포맷 대상에서 제외              |

`auth/`의 파일은 `003_auth_access.sql`, `auth_sessions/`의 파일은 `004_auth_sessions.sql` 내부에서만 순서대로 실행한다. 004를 적용하려고 기존 001/002/003을 재실행하지 않는다. 트랜잭션 제어용 `BEGIN`/`COMMIT`은 진입점에만 두고 하위 파일은 단독 실행하지 않는다. 함수 내부의 `BEGIN`/`END` 블록은 유지한다. 초기 테이블 정의와 저장 제약은 기존 이행 도구의 입력이므로 파일을 옮길 때 해당 도구도 함께 검증한다. 같은 정의를 편집 가능한 복사본 두 곳에 보관하지 않는다.

## 실행 경로와 분리 파일

인증 진입점은 psql 스크립트다. `psql -X -v ON_ERROR_STOP=1 -f <003_auth_access.sql 경로>`로 실행하며, DB 접속 자격은 기존 환경 설정으로 전달한다. `\ir auth/...`는 진입 파일 기준 상대 경로다. 표준 입력으로 파일 내용만 전송하거나 JDBC에 `\ir`를 SQL로 전달하지 않는다. GUI 도구를 사용하는 경우에도 psql 스크립트 지원 여부를 먼저 확인한다.

진입점은 `ON_ERROR_STOP`을 켜고 단일 `BEGIN`/`COMMIT`으로 하위 파일을 감싼다. 파일 누락·SQL 실패 시 실행을 중단하고 연결 종료로 미완료 트랜잭션을 롤백한다. 경로 순서 변경, 파일 분리, 실행기 수정에는 성공뿐 아니라 중간 실패의 전체 롤백을 확인한다. 배치파일은 저장소 파일만 적용하고 DB SQL을 실행하지 않는다.

## 변경 검증

가독성 수정은 식별자·열/값 대응·문자열·연산자·명령 순서를 유지한다. SQL 토큰을 대조할 때 인용 문자열 안의 공백까지 제거하지 않는다. 달러 인용 함수 본문은 SQL/PLpgSQL 코드로 별도 대조한다. 형식 대조만으로 권한·잠금·트랜잭션 검사를 대신하지 않는다.

현재 이행 도구는 `001`의 2칸 컬럼 선언과 `CREATE TABLE ...`/`);`, `002`의 `CREATE FUNCTION 이름(` 및 `END $$;` 경계를 읽는다. 이 경계를 바꾸려면 추출기·이행 검사를 함께 고친다. `002` 원문 해시가 달라지면 예전에 만든 급여 이행 계획은 재사용하지 않고 새 입력으로 다시 검토·생성한다. 실행 방법은 [DB 테스트](database-tests.md)를 따른다.

근거: PostgreSQL의 [psql 파일 실행·상대 포함·오류 중단](https://www.postgresql.org/docs/15/app-psql.html) 규칙을 따른다.
