# v0.6 식별·인증 내부 설계 — #21

관련 이슈: [#21 식별·인증 설계](https://github.com/Fintech-project-team/Fintech-project/issues/21). 기준 커밋 `f513eb03557bc73f512cf9b40dd3523b9d70345f`, 작성일 2026-10-21. A가 서버, B가 Flutter를 담당하며 두 사람 모두 공동 PM이다.

이 문서는 [#20 API 계약](api-contract.md) §2·§6을 구현하기 위한 **설계 초안**이다. 아래의 역할·암호 형식·저장 구조는 구현 제안이며 이미 구현됐다는 뜻이 아니다. 사용자 후속 결정에 따라 이름을 `name`으로 통합하고 로그인 201에 `name`을 추가한다. 다른 API·인증 정책은 유지한다. 검증 사례와 인계는 [인증 검증 기준](auth-verification.md)에 있다. 이번 통합은 공통 코드 지침, 이름 관련 계약·모델·DB 설계, 사용자별 연결 전·부분 연결 응답과 화면 인계 문서를 수정한다. SQL·Java·더미·Flutter 구현 파일은 유지하며, 문서 반영과 실제 데이터 이행 완료를 구분한다.

## 1. 확정된 경계

- 사전 생성한 **합성 이름·전화번호 + 별도 고정 6자리 데모 코드**로 기존 UUID `userId`를 확인한다. 입력으로 사용자를 새로 만들지 않는다. 주민번호·통신사·실제 SMS·본인확인은 추가하지 않는다.
- 서버는 사용자별 활성 세션 하나를 유지한다. 기존 세션이 있으면 신규 발급을 거절하고 자동 만료를 추가하지 않는다. `installationId`는 설치 식별값이며 인증 자격이 아니다.
- PIN 생성·확인·재설정은 Flutter에서 수행한다. PIN 원문·검증값을 서버에 보내지 않는다. 서버는 원천/설정 제공과 저장 제약을 담당하고 금액·U·시뮬레이션은 Flutter에서 계산한다.
- 정상 재로그인은 같은 사용자 자료를 이어 쓴다. 로그아웃은 금융 설정을 초기화하지 않는다. 탈퇴는 비활성화·세션 종료 후 1년 보관 정책이며 자동 재가입/재활성화 경로는 없다.
- 코드 표시 타이머 3분과 ‘다시 받기’는 표시 기능이다. 서버 코드 만료·재발급을 뜻하지 않는다. 응답 유실로 토큰을 잃으면 운영자가 기존 세션을 종료하기 전 신규 로그인은 거절한다.

## 2. 입력·비밀값 처리

### 정규화 제안과 형식

기존 문서가 정하지 않은 공백 코드포인트를 아래와 같이 좁혀 **A/B가 같은 벡터로 구현할 제안**으로 둔다. 기존 결정으로 소급하지 않는다. 다른 문자 허용이 필요하면 이 표와 양쪽 테스트를 함께 바꾼다.

| 입력           | 정규화와 허용 값                                                                                                       | 예시                                                       |
| -------------- | ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| name           | 앞뒤 U+0020 공백만 제거. 나머지는 `[가-힣A-Za-z]{2,20}`. 내부 공백·자모·탭·NBSP 거절. 대소문자 접기/NFC 자동 변환 없음 | `김데모` → `김데모`; `Kim`과 `kim`은 다른 값               |
| phone          | U+0020 공백·U+002D 하이픈만 제거한 뒤 `010[0-9]{8}`                                                                    | `010-0000-0001` → `01000000001`; `+82`, 전각 숫자, 탭 거절 |
| code           | 정규화하지 않는 `[0-9]{6}`                                                                                             | `000001` 허용 형식; 공백·숫자형 JSON·전각 숫자 거절        |
| installationId | #20의 UUID 검증                                                                                                        | 소유자 판정·제한 키로 사용하지 않음                        |

형식 오류는 422이며 형식에 맞는 자격 불일치·기존 세션·비활성 계정은 같은 `401 AUTH_REJECTED`다. 원문을 포함하지 않는 일반 메시지를 사용한다. 없는 계정도 코드 비교에 대응하는 연산을 수행하되, 이것만으로 응답 시간의 완전한 동일성을 보장한다고 주장하지 않는다. 원문은 요청 메모리에서만 취급하고 DB·접근 로그·예외 추적·LLM에 기록하지 않는다. 사전 합성 시드 저장과 제출 원문 저장은 구분한다.

### 단일 이름·저장 공백 — 사용자 확정

name의 서버 사용 범위는 합성 계정 조회·인증 입력 대조, name+phone 기반 인증 시도 제한, 로그인 201의 화면 표시값 반환이다. 금융 소유권·권한은 userId가 기준이며 이름을 금융 FK나 권한으로 사용하지 않는다. 이름은 인증 조회와 허용된 화면 호칭에 같은 `name`을 사용한다. 호칭을 표시할 화면 위치는 B가 정하며 이번 문서에서 특정 화면을 지정하지 않는다. 별도 표시명·인증명 필드를 두지 않으며 이름 변경/별명 편집 API를 추가하지 않는다. 로그인 201의 `name`은 검증된 서버 저장값이다. 실패 응답·로그·LLM에 이름을 추가하지 않고, 기기의 이름 값으로 사용자 소유권을 판단하지 않는다.

| 기존 시드 키 | 유지할 userId                        | 통합 name |
| ------------ | ------------------------------------ | --------- |
| alpha        | f0a4be6c-01d7-53eb-ab2c-74675b22fd8c | 데모알파  |
| beta         | 87f7bbf9-2355-5210-9325-f25d83a8ff35 | 데모베타  |
| gamma        | d04073fd-f7ab-518d-8938-f2920d593db2 | 데모감마  |

- DB에 저장하는 인증 식별값은 공백을 포함하지 않는다. `name`은 위 입력 문자 집합, 저장 전화번호는 `010[0-9]{8}`을 따른다. 허용된 앞뒤 U+0020/전화 구분자 정규화 후 검증하며 이름 내부 공백·탭·줄바꿈·NBSP·전각 공백을 임의 삭제하지 않고 거절한다.
- 코드 원문은 DB에 저장하지 않는다. `code_verifier`·`token_digest`는 지정된 알고리즘/인코딩 형식으로 생성하고 식별용 UUID는 UUID 타입을 유지한다. 공백 제거 함수를 비밀값·토큰에 적용하지 않는다.
- 상품명·거래 메모·사용자 계좌 별칭 등 금융 원천/설정에는 이 공백 금지를 확대하지 않는다. 기존 입력·저장 규칙을 유지한다.
- 현재 `synthetic_name`·`display_name` 컬럼과 서버 시드는 이행 전 구조다. 목표 저장 컬럼은 `name` 하나이며 `UNIQUE(name, synthetic_phone)`과 NOT NULL·허용 문자 검증이 필요하다. 기존 phone 컬럼명·전화번호 값은 이번 결정으로 바꾸지 않는다.
- 기존 DB와 이미 적재된 시드의 초기화/재생성을 전제하지 않는다. 후속 이행은 위 UUID로 매핑하고 원래 두 이름의 이행 근거를 보존하며, 미등록 UUID·매핑 불일치·중복·형식 오류면 쓰기 전에 중단한다. 사용자·금융·세션 데이터 삭제, 원문 덮어쓰기 또는 임의 열 삭제를 이 문서가 승인하지 않는다. 구 컬럼의 보존 위치·전환 DDL은 별도 검토 대상이며 이번에 SQL을 실행하지 않는다.

### 검증값 제안

| 대상      | 서버 저장·처리                                                                                                                                       | 이유·한계                                                                                                                   |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 세션 토큰 | Java `SecureRandom` 32바이트 → Base64url 무패딩. `token_digest`는 `sha256:` + 원문 UTF-8의 SHA-256 소문자 hex. 원문은 최초 201 응답에서만 전달       | 무작위 256비트 제안. 재전송·로그·DB 원문 저장 없음. UUID `sessionId`와 별개                                                 |
| 데모 코드 | `code_verifier`에 `hmac-sha256:<keyId>:<hex>` 저장. HMAC 입력은 UTF-8 `payse-code-v1\n<소문자 userId>\n<6자리 code>`. 비교는 일정 시간 비교 API 사용 | 저엔트로피 6자리 값을 단순 SHA-256으로 저장하지 않기 위한 데모 설계. 고정 데모 코드를 실사용자 인증 강도로 설명하지 않음    |
| 제한 키   | 조합은 UTF-8 `payse-limit-combo-v1\n<정규화 name>\n<정규화 phone>`, IP는 `payse-limit-ip-v1\n<정규 IP>`의 HMAC-SHA256 hex                            | 원문 대신 제한 상태 식별에만 사용. 사용자 UUID나 Participant 식별자를 대체하지 않음                                         |
| 비밀 키   | 코드용·제한용 키 분리, 각 32바이트 무작위 값. DB·Git·fixture와 분리한 서버 비밀 설정으로 주입                                                        | 누락/미지원 keyId이면 발급 거절. 키 버전 변경 시 기존 코드 검증과 제한 상태의 연속성을 검증하고 활성 제한을 초기화하지 않음 |

`Mac`/digest의 변경 가능한 연산 인스턴스를 요청 간 공유하지 않는다. 암호 프리미티브를 직접 구현하지 않는다. HTTPS·Bearer·`Cache-Control: no-store`는 #20을 따른다. 토큰을 URL·쿠키 대체 경로로 받지 않는다. [Java SecureRandom](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/security/SecureRandom.html), [Java Mac](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/javax/crypto/Mac.html), [OWASP 세션 관리](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

## 3. 서버 구조와 사용자 격리

예정 의존 방향은 `HTTP 필터/Controller → AuthService → AuthRepository·Crypto·Clock`이다. 클래스 이름은 구현 시 이 책임을 지키는 범위에서 정한다. 금융 Repository는 인증 서비스에 역으로 의존하지 않고, 검증된 요청별 사용자 문맥을 받는다. 무상태 서비스/연결 풀의 Spring bean은 허용하되 사용자·토큰·잔액·실패 횟수를 가변 static/singleton 필드에 두지 않는다.

- HTTP 세션 쿠키를 별도로 만들지 않는다. Bearer를 요청마다 검증하고 요청별 SecurityContext를 사용한다. `NullSecurityContextRepository` 등으로 HttpSession 저장을 막고 요청 종료 때 문맥을 정리한다. DB의 `demo_sessions` 유지와 HTTP 계층의 무상태 처리는 양립한다. [Spring Security 인증 보관](https://docs.spring.io/spring-security/reference/servlet/authentication/persistence.html)
- 기존 FORCE RLS는 `payse.user_id`만 비교한다. **유효 토큰·활성 계정 검증을 대신하지 않는다.** 클라이언트 userId·설치 ID를 RLS 값으로 사용하지 않는다.
- 인증 전 조회는 아래 제한된 함수 경로로 분리한다. 일반 서버 역할에 SUPERUSER·BYPASSRLS 또는 테이블 소유권을 부여하지 않는다. `SECURITY DEFINER`라는 선언만으로 FORCE RLS가 해결된다고 가정하지 않는다.

| 역할 제안          | 허용 범위                                                                                                                                                                                                                                                                                |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `payse_runtime`    | 서버 연결 역할. 금융 테이블의 필요한 권한 + 소유자 RLS. demo_users는 id/data_version SELECT와 data_version UPDATE만 추가 허용해 기존 저장 트리거·버전 갱신을 지원. 인증 비밀 컬럼/demo_sessions는 직접 접근 금지, 전용 함수 EXECUTE만 허용. 인증 소유 역할의 멤버가 아니며 SET ROLE 금지 |
| `payse_auth_owner` | NOLOGIN·NOBYPASSRLS. 인증 함수 소유 전용. `demo_users`의 식별/인증/비활성 컬럼, `demo_sessions`, 아래 신규 인증 상태에 필요한 권한만 부여                                                                                                                                                |
| 마이그레이션 역할  | 역할·정책·DDL 설정 전용. 앱 연결에 사용하지 않음                                                                                                                                                                                                                                         |

인증 테이블에만 `payse_auth_owner` 대상의 명시 RLS 정책을 추가해 인증 조회/전이를 허용한다. 금융 테이블의 정책을 전체 허용으로 바꾸지 않는다. 함수는 입력 범위와 반환 컬럼을 고정하고 동적 SQL을 쓰지 않는다. 고정 `search_path=pg_catalog,payse,pg_temp`, 스키마 쓰기 권한 제한, PUBLIC EXECUTE 회수와 명시 GRANT를 생성 트랜잭션에서 함께 처리한다. 인증 함수에서 읽은 verifier는 서버 내부 비교에만 쓰며 API DTO에 노출하지 않는다. 이 경로는 신뢰된 서버 자격으로 호출되므로 SQL 바인딩과 호출부 검증도 필요하다. 기존 `check_storage_owner()`가 호출하는 `assert_user_storage(uuid)`의 EXECUTE와 내부 금융 조회 권한은 runtime에 필요한 범위만 부여하고 전체 함수 일괄 GRANT는 하지 않는다. [PostgreSQL RLS](https://www.postgresql.org/docs/18/ddl-rowsecurity.html), [SECURITY DEFINER 보안](https://www.postgresql.org/docs/18/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY)

금융 접근은 **같은 연결·같은 트랜잭션**에서 인증 전용 함수가 토큰 digest로 사용자를 찾고 사용자 행 잠금 → 계정/세션 재검증 → `set_config('payse.user_id', 검증된ID, true)`까지 수행한 뒤 runtime의 소유자 제한 SQL로 이어진다. 인증 전 RLS 문맥이 없는 runtime이 직접 demo_users를 찾아 잠그는 구조가 아니다. 기존 002의 SECURITY INVOKER 저장 트리거는 이후 동일 사용자 잠금을 재사용하며 data_version 갱신 권한을 유지한다. 커밋/롤백 뒤 사용자 문맥이 풀에 남지 않아야 한다. 최초 HTTP 필터의 검증만으로 이후 DB 쓰기를 허용하지 않는다. 일반 조회도 이 순서를 사용해 탈퇴 확정 뒤 새 조회가 승인되지 않게 한다. 이미 완료한 조회 응답의 네트워크 전달을 소급 취소한다는 뜻은 아니다.

### 값의 출처와 코드 작성

공통 [코드 구조와 설정값](../../../../docs/harness/CODE_SPEC.md)을 따른다. 이 설계의 `Controller → AuthService → Repository`는 책임 방향이며 빈 계층·1줄 전달용 래퍼를 의무화하지 않는다. 보안 설정은 상태 관리·인증·접근 권한·오류 처리를 독립된 문장/블록으로 구분한다.

| 값                                                    | 출처·변경 경계                                                                                                              |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| name·phone·code·installationId·Bearer                 | 요청별 인자/문맥. 원문을 전역 필드나 운영 설정에 보관하지 않음                                                              |
| DB 주소·자격, 풀 크기·연결 대기시간, 신뢰 프록시 목록 | 기존 서버 설정 체계에서 타입·단위·허용 범위를 정의해 주입. 새 운영 기본값은 만들지 않음. 프록시 미사용은 명시적인 배포 모드 |
| 코드/제한 HMAC 키·keyId                               | 서버 비밀 설정. 인증 기능 활성화 시 시작 필수값 검증. 빈 값·예시 키·임시 키로 대체하지 않음                                 |

## 4. 인증 제한과 트랜잭션

사용자 확정 수치는 조합 실패 **5회/5분 후 5분 차단**, IP **60회/60초**다. 로그인과 재확인이 대상이며 금융 조회에는 적용하지 않는다. 동시 서버 인스턴스가 같은 PostgreSQL 제한 상태를 사용한다. #20 §2의 Retry-After·503·차단 중 종료시각 비연장 규칙을 유지한다. [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)은 제한 필요성의 근거이며 이 수치를 정한 자료가 아니다.

처리 순서는 다음과 같다. 아래 `now`는 행 잠금을 얻은 직후 `clock_timestamp()`로 한 번 읽은 값이며 `(now - window, now]` 구간을 사용한다. PostgreSQL `now()`/`CURRENT_TIMESTAMP`는 트랜잭션 시작 시각이므로 잠금 대기 뒤 제한 판정에 사용하지 않는다. [PostgreSQL 현재 시각](https://www.postgresql.org/docs/18/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)

1. 로그인·재확인 경로의 IP 제한은 Bearer 검증/본문 파싱 실패 응답보다 먼저 짧은 트랜잭션에서 한 번 판정·저장·커밋하고 연결을 반환한다. 누락/무효 토큰·잘못된 JSON도 IP 요청에 센다. 프록시가 없으면 연결 원격 IP만, 있으면 운영에서 지정한 신뢰 프록시가 덮어쓴 값만 사용한다. 임의 `X-Forwarded-For`는 신뢰하지 않는다. IPv4-mapped IPv6는 같은 IPv4로 정규화한다.
2. 본문이 정규화 가능한 경우 조합 제한 행을 생성/잠금한다. IP에서 이미 거절됐어도 활성 조합 차단 종료 시각은 확인해 두 제한 중 늦은 시각으로 `Retry-After=ceil(남은 초)`를 산정한다. IP 거절 요청은 자격 대조·실패 누적·세션 발급을 하지 않는다. 정규화 불가능한 본문에는 조합 키를 만들지 않는다.
3. IP가 허용되고 조합이 차단되지 않았다면 자격을 대조한다. 잘못된 조합/코드는 실패를 기록하고 1~4회는 401, 5회는 429를 **커밋 후** 응답한다. 성공 대조가 과거 실패 기록을 지우지는 않는다. 기존 차단이 끝났을 때는 그 이전 실패 창을 비운다.
4. 올바른 자격은 같은 트랜잭션에서 사용자 행을 잠그고 계정·세션 상태를 다시 확인한 뒤 로그인/재확인 결과를 확정한다. 올바른 자격이지만 기존 세션/비활성으로 거절되면 조합 실패를 늘리지 않는다. 재확인의 다른 소유자 자격은 대조 실패다.
5. 실패 결과는 예외로 전체 롤백시키지 않고 제한 저장을 커밋한 뒤 HTTP 오류로 매핑한다. DB/제한 저장 실패는 503이며 인증을 통과시키지 않는다. 커밋 성공을 확인한 뒤에만 201을 보낸다.

잠금 순서는 `조합 제한 행 → 사용자 행 → 세션/탈퇴 영수증`이며 IP 트랜잭션은 그 전에 끝낸다. 금융 작업은 사용자 행부터 시작하며 조합 제한을 나중에 잡지 않는다. 사용자 잠금/연결을 잡은 채 `REQUIRES_NEW`로 추가 연결을 기다리지 않는다. 현재 코드의 풀 크기 5는 현황이며 정책 기본값의 근거로 승격하지 않는다. 후속 구현은 검증한 풀 설정을 주입하고 중첩 연결 대기 없이 순차 트랜잭션으로 구성한다. 행 잠금을 쓰는 조회 트랜잭션에 READ ONLY를 강제하지 않는다. 잠금 중 외부 API/LLM 호출을 하지 않고 DB 작업 커밋·연결 반환 뒤 HTTP 응답을 전송한다. [PostgreSQL 행 잠금](https://www.postgresql.org/docs/18/explicit-locking.html)

기존 `002_storage_guards.sql`의 owner 잠금 대상에는 demo_sessions가 없다. 인증 서비스가 명시 잠금을 구현해야 하며, 기존 트리거로 이미 해결됐다고 보고하지 않는다. 토큰 digest·이름/전화번호·활성 세션의 기존 UNIQUE 인덱스와 신규 제한 PK/영수증 인덱스를 이용한다. 인증마다 1년 금융 거래 전체를 읽지 않는다. 실제 지연시간·동시 처리량은 #22에서 측정한다.

## 7. 현재 구현 공백·인계

- 현재 시드 `code_verifier=DISABLED:auth-design-pending`는 인증 불가 표식이다. 기존 두 이름은 §2의 확정된 단일 이름으로 이행해야 한다. #22의 인증 구현 전에 서버 시드 생성기·검증기·SQL exporter·DB 이행·이름 문자열에 의존하는 DB 테스트를 함께 조정하고 UUID·전화번호·금융 자료·세션을 보존해야 한다. 미등록 사용자의 이름을 공백 삭제나 추측으로 생성하지 않는다. #21 문서 추가만으로 로그인 가능한 시드가 생기지 않으며 서버 시작/로그인마다 시드를 초기화하지 않는다.
- 현재 Java는 생존 확인 외 경로를 차단하는 초기화 상태다. 이번 작업은 인증 구현·RLS 동작·실제 폰 검증을 완료하지 않는다.
- 기존 product-baseline/data-model의 ‘탈퇴=세션 정리’, 모바일 보완 문서의 ‘탈퇴 후 재가입’보다 #20 §2의 최신 비활성화 정책을 적용한다. 기존 파일은 보존하고 B에게 화면 연결 시 차이를 전달한다. 기존 database-design의 ‘#20 구현’ 표기는 현재 일정상 #21 설계/후속 구현으로 읽는다.
- B는 재실행·10분 무입력·10분 이상 백그라운드 후 PIN 잠금, 5회 오류/분실의 기존 토큰 재확인, 토큰의 OS 보안 저장을 구현한다. 오류 횟수 저장/정상 해제 시 초기화 같은 로컬 상세는 B의 기능 문서에서 정리하고 서버 제한과 합치지 않는다. 서버에서 기기 PIN의 성공 여부를 신뢰하지 않는다.
- 탈퇴의 1년 보관은 사용자 제품 결정이며 법정 기간이라고 주장하지 않는다. 파쇄 구현에서는 FK RESTRICT 관계 순서·원천 파일·백업·영수증까지 검토해야 한다. 현재 DB에 사용자 행 하나를 즉시 삭제하는 구현은 추가하지 않는다.
- 자동 세션 만료 없음은 확정된 **합성 데모 정책**이다. OWASP의 유휴/절대 만료 권고와 차이가 있으며 실금융 서비스 보안 충족으로 보고하지 않는다. 활성 세션 하나만으로 토큰 복제·탈취까지 차단했다고 주장하지 않는다.
