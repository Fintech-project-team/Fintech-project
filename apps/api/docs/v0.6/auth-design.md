# v0.6 식별·인증 내부 설계 — #21

관련 이슈: [#21 식별·인증 설계](https://github.com/Fintech-project-team/Fintech-project/issues/21). 서버 내부 인증 설계이며 담당 범위는 [소유권 기준](../../../../docs/ownership.md)을 따른다.

이 문서는 [공통 API 계약](../../../../docs/api-contract.md)을 구현하기 위한 서버 내부 **설계안**이다. 암호 형식·DB 역할·제한 저장·트랜잭션·후속 DDL을 정의한다. 구현된 DB 함수·권한과 호출 순서는 [인증 DB 접근](../auth-database.md)을 따른다. 실제 HTTP 인증 구현 완료를 뜻하지 않는다. 이름·세션·탈퇴 등 외부 정책은 상위 계약에만 정의한다. [인증 검증](auth-verification.md)은 후속 구현의 사례이고 실제 실행 결과는 별도 기록이다.

## 1. 계약과 현재 구현 경계

합성 자격·설치 식별값 제거·기존 세션 우선·PIN/복구·로그아웃·탈퇴·입력 수명은 [공통 API 인증 계약](../../../../docs/api-contract.md#2-인증탈퇴)을 따른다. 금융 소유권·원천/계산 경계는 [공통 모델](../../../../docs/data-model.md), 실제 초기 DDL과 이름 이행 상태는 [DB 사전](../../../../docs/database-schema.md)을 따른다. 설치 식별값 제거는 초기 DDL에 반영돼 있으나 기존 DB에 ALTER를 실행했다는 뜻은 아니다. 초기 DB·시드는 단일 name이며 기존 DB 전환은 [전환 도구](../identity-migration.md)의 별도 실행이다. 실제 인증 API와 Flutter HTTP 연동은 후속 작업이다. Flutter Fake 인증·로컬 PIN 구현 상태와 실제 서버 연결 완료를 구분한다.

## 2. 서버 비밀값 처리

입력 문자·정규화·공백·단일 이름 매핑은 [API 이름 계약](../../../../docs/api-contract.md#인증-입력과-단일-이름)의 한 정의를 사용한다. 아래는 그 입력을 검증할 서버 내부 암호 형식 제안이다.

### 검증값 제안

| 대상      | 서버 저장·처리                                                                                                                                       | 이유·한계                                                                                                                   |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 세션 토큰 | Java `SecureRandom` 32바이트 → Base64url 무패딩. `token_digest`는 `sha256:` + 원문 UTF-8의 SHA-256 소문자 hex. 원문은 최초 201 응답에서만 전달       | 무작위 256비트 제안. 재전송·로그·DB 원문 저장 없음. UUID `sessionId`와 별개                                                 |
| 데모 코드 | `code_verifier`에 `hmac-sha256:<keyId>:<hex>` 저장. HMAC 입력은 UTF-8 `payse-code-v1\n<소문자 userId>\n<6자리 code>`. 비교는 일정 시간 비교 API 사용 | 저엔트로피 6자리 값을 단순 SHA-256으로 저장하지 않기 위한 데모 설계. 고정 데모 코드를 실사용자 인증 강도로 설명하지 않음    |
| 제한 키   | 조합은 UTF-8 `payse-limit-combo-v1\n<정규화 name>\n<정규화 phone>`, IP는 `payse-limit-ip-v1\n<정규 IP>`의 HMAC-SHA256 hex                            | 원문 대신 제한 상태 식별에만 사용. 사용자 UUID나 Participant 식별자를 대체하지 않음                                         |
| 비밀 키   | 코드용·제한용 키 분리, 각 32바이트 무작위 값. DB·Git·fixture와 분리한 서버 비밀 설정으로 주입                                                        | 누락/미지원 keyId이면 발급 거절. 키 버전 변경 시 기존 코드 검증과 제한 상태의 연속성을 검증하고 활성 제한을 초기화하지 않음 |

`Mac`/digest의 변경 가능한 연산 인스턴스를 요청 간 공유하지 않는다. 암호 프리미티브를 직접 구현하지 않는다. HTTPS·Bearer·`Cache-Control: no-store`는 #20을 따른다. 토큰을 URL·쿠키 대체 경로로 받지 않는다. [Java SecureRandom](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/security/SecureRandom.html), [Java Mac](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/javax/crypto/Mac.html), [OWASP 세션 관리](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

## 3. 서버 구조와 사용자 격리

예정 의존 방향은 `HTTP 필터/Controller → AuthService → AuthRepository·Crypto·Clock`이다. 클래스 이름은 구현 시 이 책임을 지키는 범위에서 정한다. 금융 Repository는 인증 서비스에 역으로 의존하지 않고, 검증된 요청별 사용자 문맥을 받는다. 무상태 서비스/연결 풀의 Spring bean은 허용하되 사용자·토큰·잔액·실패 횟수를 가변 static/singleton 필드에 두지 않는다.

- HTTP 세션 쿠키를 별도로 만들지 않는다. Bearer를 요청마다 검증하고 요청별 SecurityContext를 사용한다. `NullSecurityContextRepository` 등으로 HttpSession 저장을 막고 요청 종료 때 문맥을 정리한다. DB의 `demo_sessions` 유지와 HTTP 계층의 무상태 처리는 양립한다. [Spring Security 인증 보관](https://docs.spring.io/spring-security/reference/servlet/authentication/persistence.html)
- 기존 FORCE RLS는 `payse.user_id`만 비교한다. **유효 토큰·활성 계정 검증을 대신하지 않는다.** 클라이언트 userId·설치 ID를 RLS 값으로 사용하지 않는다.
- 인증 전 조회는 아래 제한된 함수 경로로 분리한다. 일반 서버 역할에 SUPERUSER·BYPASSRLS 또는 테이블 소유권을 부여하지 않는다. `SECURITY DEFINER`라는 선언만으로 FORCE RLS가 해결된다고 가정하지 않는다.

| 역할 제안          | 허용 범위                                                                                                                                                                                                                                                                           |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `payse_runtime`    | 서버 연결 역할. 금융 테이블의 필요한 권한 + 소유자 RLS. users는 id/data_version SELECT와 data_version UPDATE만 추가 허용해 기존 저장 트리거·버전 갱신을 지원. 인증 비밀 컬럼/demo_sessions는 직접 접근 금지, 전용 함수 EXECUTE만 허용. 인증 소유 역할의 멤버가 아니며 SET ROLE 금지 |
| `payse_auth_owner` | NOLOGIN·NOBYPASSRLS. 인증 함수 소유 전용. `users`의 식별/인증/비활성 컬럼, `demo_sessions`, 아래 신규 인증 상태에 필요한 권한만 부여                                                                                                                                                |
| 마이그레이션 역할  | 역할·정책·DDL 설정 전용. 앱 연결에 사용하지 않음                                                                                                                                                                                                                                    |

인증 테이블에만 `payse_auth_owner` 대상의 명시 RLS 정책을 추가해 인증 조회/전이를 허용한다. 금융 테이블의 정책을 전체 허용으로 바꾸지 않는다. 함수는 입력 범위와 반환 컬럼을 고정하고 동적 SQL을 쓰지 않는다. 고정 `search_path=pg_catalog,payse,pg_temp`, 스키마 쓰기 권한 제한, PUBLIC EXECUTE 회수와 명시 GRANT를 생성 트랜잭션에서 함께 처리한다. 인증 함수에서 읽은 verifier는 서버 내부 비교에만 쓰며 API DTO에 노출하지 않는다. 이 경로는 신뢰된 서버 자격으로 호출되므로 SQL 바인딩과 호출부 검증도 필요하다. 기존 `check_storage_owner()`가 호출하는 `assert_user_storage(uuid)`의 EXECUTE와 내부 금융 조회 권한은 runtime에 필요한 범위만 부여하고 전체 함수 일괄 GRANT는 하지 않는다. [PostgreSQL RLS](https://www.postgresql.org/docs/18/ddl-rowsecurity.html), [SECURITY DEFINER 보안](https://www.postgresql.org/docs/18/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY)

금융 접근은 **같은 연결·같은 트랜잭션**에서 인증 전용 함수가 토큰 digest로 사용자를 찾고 사용자 행 잠금 → 계정/세션 재검증 → `set_config('payse.user_id', 검증된ID, true)`까지 수행한 뒤 runtime의 소유자 제한 SQL로 이어진다. 인증 전 RLS 문맥이 없는 runtime이 직접 users를 찾아 잠그는 구조가 아니다. 기존 002의 SECURITY INVOKER 저장 트리거는 이후 동일 사용자 잠금을 재사용하며 data_version 갱신 권한을 유지한다. 커밋/롤백 뒤 사용자 문맥이 풀에 남지 않아야 한다. 최초 HTTP 필터의 검증만으로 이후 DB 쓰기를 허용하지 않는다. 일반 조회도 이 순서를 사용해 탈퇴 확정 뒤 새 조회가 승인되지 않게 한다. 이미 완료한 조회 응답의 네트워크 전달을 소급 취소한다는 뜻은 아니다.

### 값의 출처와 코드 작성

공통 [코드 구조와 설정값](../../../../docs/harness/CODE_SPEC.md)을 따른다. `Controller → AuthService → Repository`는 인증 책임의 방향이며 아래 표는 인증 구현에 필요한 값의 출처만 구분한다.

| 값                                                    | 출처·변경 경계                                                                                                                 |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| name·phone·code·Bearer                                | 요청별 인자/문맥. 원문을 전역 필드나 운영 설정에 보관하지 않음                                                                 |
| DB 주소·자격, 풀 크기·연결 대기시간, 신뢰 프록시 목록 | 기존 서버 설정 체계에서 타입·단위·허용 범위를 정의해 주입. 새 운영 기본값은 만들지 않음. 프록시 미사용은 명시적인 배포 모드    |
| 코드/제한 HMAC 키·keyId                               | 서버 비밀 설정. 인증 기능 활성화 시 시작 필수값 검증. 빈 값·예시 키·임시 키로 대체하지 않음                                    |
| 5회/5분·5분 차단, IP 60회/60초, 6자리 코드            | 확정된 #20 정책을 이름 있는 값으로 표현. 클라이언트 입력·배포 환경에 따라 임의 변경하지 않음                                   |
| 정규화·digest 접두사·암호 형식·32바이트 제안          | 정규화는 상위 API 입력 계약, 나머지는 §2의 명시된 구현 제안. 임의 런타임 설정으로 바꾸지 않고 A/B 계약·저장 호환성을 함께 검토 |
| 급여일·선택 계좌·모아둘 돈                            | 기존 사용자별 DB 저장/조회 계약. 서버 환경변수·가변 전역 설정으로 이동하지 않음                                                |

인증이 활성화된 배포는 필요한 설정을 시작 시 검증한다. 시작 이후 외부 비밀 저장소/DB 장애는 #20의 503 처리 대상이다. 현재 인증 미구현 bootstrap에 인증 키를 당장 요구하지 않는다. 설정값을 매 요청 인자로 금융 DTO에 추가하거나 기존 API 필드를 변경하지 않는다.

## 4. 인증 제한과 트랜잭션

제한 수치·대상·Retry-After·실패 상태는 [공통 인증 제한](../../../../docs/api-contract.md#인증-시도-제한--사용자-확정)의 단일 정의를 사용한다. 동시 서버 인스턴스가 같은 PostgreSQL 제한 상태를 사용하도록 아래 알고리즘을 구현한다. [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)은 제한 필요성의 근거이며 이 수치를 정한 자료가 아니다.

처리 순서는 다음과 같다. 아래 `now`는 행 잠금을 얻은 직후 `clock_timestamp()`로 한 번 읽은 값이며 `(now - window, now]` 구간을 사용한다. PostgreSQL `now()`/`CURRENT_TIMESTAMP`는 트랜잭션 시작 시각이므로 잠금 대기 뒤 제한 판정에 사용하지 않는다. [PostgreSQL 현재 시각](https://www.postgresql.org/docs/18/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)

1. 로그인·재확인 경로의 IP 제한은 Bearer 검증/본문 파싱 실패 응답보다 먼저 짧은 트랜잭션에서 한 번 판정·저장·커밋하고 연결을 반환한다. 누락/무효 토큰·잘못된 JSON도 IP 요청에 센다. 프록시가 없으면 연결 원격 IP만, 있으면 운영에서 지정한 신뢰 프록시가 덮어쓴 값만 사용한다. 임의 `X-Forwarded-For`는 신뢰하지 않는다. IPv4-mapped IPv6는 같은 IPv4로 정규화한다.
2. 본문이 정규화 가능한 경우 조합 제한 행을 생성/잠금한다. IP에서 이미 거절됐어도 활성 조합 차단 종료 시각은 확인해 두 제한 중 늦은 시각으로 `Retry-After=ceil(남은 초)`를 산정한다. IP 거절 요청은 자격 대조·실패 누적·세션 발급을 하지 않는다. 정규화 불가능한 본문에는 조합 키를 만들지 않는다.
3. IP가 허용되고 조합이 차단되지 않았다면 자격을 대조한다. 잘못된 조합/코드는 실패를 기록하고 1~4회는 401, 5회는 429를 **커밋 후** 응답한다. 성공 대조가 과거 실패 기록을 지우지는 않는다. 기존 차단이 끝났을 때는 그 이전 실패 창을 비운다.
4. 올바른 자격은 같은 트랜잭션에서 사용자 행을 잠그고 계정·세션 상태를 다시 확인한 뒤 로그인/재확인 결과를 확정한다. 올바른 자격이지만 기존 세션/비활성으로 거절되면 조합 실패를 늘리지 않는다. 재확인의 다른 소유자 자격은 대조 실패다.
5. 실패 결과는 예외로 전체 롤백시키지 않고 제한 저장을 커밋한 뒤 HTTP 오류로 매핑한다. DB/제한 저장 실패는 503이며 인증을 통과시키지 않는다. 커밋 성공을 확인한 뒤에만 201을 보낸다.

잠금 순서는 `조합 제한 행 → 사용자 행 → 세션/탈퇴 영수증`이며 IP 트랜잭션은 그 전에 끝낸다. 금융 작업은 사용자 행부터 시작하며 조합 제한을 나중에 잡지 않는다. 사용자 잠금/연결을 잡은 채 `REQUIRES_NEW`로 추가 연결을 기다리지 않는다. 현재 코드의 풀 크기 5는 현황이며 정책 기본값의 근거로 승격하지 않는다. 후속 구현은 검증한 풀 설정을 주입하고 중첩 연결 대기 없이 순차 트랜잭션으로 구성한다. 행 잠금을 쓰는 조회 트랜잭션에 READ ONLY를 강제하지 않는다. 잠금 중 외부 API/LLM 호출을 하지 않고 DB 작업 커밋·연결 반환 뒤 HTTP 응답을 전송한다. [PostgreSQL 행 잠금](https://www.postgresql.org/docs/18/explicit-locking.html)

| ------------------------------------ | -------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| POST /demo-sessions                  | 자격 대조 결과·비활성 여부 재확인, 활성 세션 없음 확인 후 무작위 토큰 세션 삽입                                | 커밋 후 201에 저장된 name 포함. 동시 요청의 패자는 401 AUTH_REJECTED. 기존 세션 종료 없음 |
| DELETE /demo-sessions/current        | 현재 토큰의 사용자·세션을 다시 확인하고 ended_at 기록                                                          | 204. 재시도 시 무효 토큰 401은 이미 종료된 상태 확인이며 금융 설정 유지                   |
| POST /demo-sessions/current/reverify | 유효 토큰의 소유자와 입력 조합/코드가 모두 일치하는지 확인                                                     | 200 verified:true. 동일 userId/sessionId, 새 토큰·세션 없음                               |
| 운영 세션 종료                       | 운영 권한으로 같은 사용자 잠금·ended_at 처리                                                                   | 공개 복구 API로 노출하지 않음. 이후 정상 로그인 가능                                      |
| POST /account-deactivation 최초      | 활성 여부·토큰 재검사 후 deactivated_at/purge_after, 모든 활성 세션 ended_at, 전용 영수증을 한 트랜잭션에 저장 | 200 최소 완료 응답. 금융 dataVersion을 늘리거나 Snapshot 반환하지 않음                    |
| 탈퇴 응답 유실 재시도                | 별도 제한 경로에서 종료된 토큰 digest→세션→동일 userId/sessionId/키 영수증을 대조                              | 동일 영수증, replayed:true. 일반 사용자 문맥·금융 접근 권한을 부여하지 않음               |

무효 토큰은 `401 SESSION_INVALID`, 유효 토큰으로 재확인했으나 합성 자격이 틀리면 `401 AUTH_REJECTED`다. **후자는 기존 토큰을 폐기하라는 뜻이 아니다.** 재확인 화면에서 입력을 정정해 재시도한다. 네트워크 오류/503/429로 로그아웃 성공이나 PIN 재설정 성공을 처리하지 않는다.

탈퇴 날짜와 기산일·재시도 정책은 [공통 탈퇴 계약](../../../../docs/api-contract.md#탈퇴-처리)을 따른다. 다른 탈퇴 키·세션·사용자의 영수증, 금융 쓰기의 영수증으로 replay를 허용하지 않는다. 계정 비활성화가 먼저 커밋되면 대기 중 금융 쓰기는 재검사에서 거절되고, 금융 쓰기가 먼저 커밋되면 그 결과를 유지한 채 이후 비활성화한다.

## 6. DB 재사용과 후속 변경안

**초기 001/002와 별도 적용하는 003_auth_access.sql을 구분한다. 003은 users의 비활성 시각 2개·auth_rate_limits·제한된 역할/함수를 구현하며 기존 DB에 자동 실행하지 않는다. 아래 탈퇴 영수증·세션 전이·서비스 전체 구현은 후속이다.** 실제 인증 구현은 #22의 세션·조회 작업과 후속 탈퇴 구현 범위를 연결해 진행한다. #23은 금융 설정 저장 작업이다.

| 구조                                 | 현재 상태 / 필요한 설계                                                                                                                                                                                                                                                                               | 이유                                                                                                                             |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| users                                | id·전화번호·code_verifier 유지. 초기 DDL의 name·제약과 기존 DB 전환은 [DB 사전](../../../../docs/database-schema.md#단일-name-저장과-기존-db-전환)을 따름. 003에 nullable `deactivated_at timestamptz`, `purge_after timestamptz` 추가. 둘 다 null 또는 둘 다 유한값이며 purge_after > deactivated_at | 기존 사용자 UUID 유지와 접근 차단. 1년 정확성은 서울 달력 계산·검증으로 확인                                                     |
| demo_sessions                        | id, user_id, token_digest UNIQUE, issued_at, ended_at 유지. 설치 식별 컬럼은 새 초기 SQL에서 제거. 기존 `active_session_per_user` 부분 UNIQUE 유지                                                                                                                                                    | 앱 판단 외에 DB에서도 사용자당 활성 하나 보장. expires_at/JWT/refresh token 도입 없음                                            |

IP 행은 판정 전에 최근 60초 기록을 거르고, 새 요청을 추가한 뒤 최신 60개를 유지한다. 거절 요청도 기록하므로 IP 요청이 계속되면 허용 시점이 늦어질 수 있다. 조합은 차단 중 실패를 추가하거나 차단 종료를 연장하지 않는다. 모든 갱신은 같은 키의 행 잠금 안에서 수행한다. 유효 이벤트와 차단이 모두 없는 행은 정리할 수 있으나, 정리와 동시 삽입의 경합으로 활성 상태를 삭제하지 않아야 한다. 키 교체로 제한을 우회시키지 않는다.

영수증의 operation_key는 #20의 1~128 ASCII 키 규칙을 따른다. 시각은 유한값·사용자 비활성화 시각과 일치해야 한다. 기존 `write_receipts`는 금융 result_version·저장 제약 트리거에 결합되어 있으므로, 이 제안에서는 인증 전용 영수증을 분리한다. 기존 금융 영수증을 탈퇴 응답으로 재사용하지 않는다.

기존 DB에 설치 식별 컬럼이 남아 있어도 초기 SQL을 재실행하거나 DB를 초기화해 제거하지 않는다. 기존 DB 전환은 보존 대상과 영향 검토를 거친 별도 migration이다. 초기 DDL과 문서 적용 도구를 기존 DB 변경 수단으로 사용하지 않는다. 설치 식별값을 요청하거나 인증 근거로 재사용하는 호환 경로는 두지 않는다.

기존 `002_storage_guards.sql`의 owner 잠금 대상에는 demo_sessions가 없다. 인증 서비스가 명시 잠금을 구현해야 하며, 기존 트리거로 이미 해결됐다고 보고하지 않는다. 토큰 digest·이름/전화번호·활성 세션의 기존 UNIQUE 인덱스와 신규 제한 PK/영수증 인덱스를 이용한다. 인증마다 1년 금융 거래 전체를 읽지 않는다. 실제 지연시간·동시 처리량은 #22에서 측정한다.

## 7. 현재 구현 공백·인계

- 현재 시드 `code_verifier=DISABLED:auth-design-pending`는 인증 불가 표식이다. 생성기·검증기·SQL exporter·초기 DDL은 [API 이름 매핑](../../../../docs/api-contract.md#인증-입력과-단일-이름)을 사용한다. 기존 DB는 별도 전환 후 사용하며 UUID·전화번호·금융 자료·세션을 보존한다. 미등록 사용자의 이름을 공백 삭제나 추측으로 생성하지 않는다. #21 문서 추가만으로 로그인 가능한 시드가 생기지 않으며 서버 시작/로그인마다 시드를 초기화하지 않는다.
- 현재 Java는 입력/암호·DB 연결 기반과 003의 함수 호출 Repository·트랜잭션 실행 기반을 갖추고 생존 확인 외 경로를 차단한다. 구현된 Java 호출 경계는 [인증 DB 접근](../auth-database.md#java-호출-기반)을 따른다. 실제 인증 Service/HTTP·요청별 순서 집행·Flutter HTTP 연동과 기기 검증은 미완료다. Flutter Fake 인증·로컬 PIN 구현과 구분한다.
- 현재 정책은 상위 API 계약에 통합돼 있다. 과거 원문 references의 탈퇴/재가입 표현을 새 요구사항으로 적용하지 않는다. 인증 내부 설계와 후속 세션·조회·탈퇴 구현을 구분한다.
- B는 재실행·10분 무입력·10분 이상 백그라운드 후 PIN 잠금, 5회 오류/분실의 기존 토큰 재확인, 토큰의 OS 보안 저장을 구현한다. 오류 횟수 저장/정상 해제 시 초기화 같은 로컬 상세는 B의 기능 문서에서 정리하고 서버 제한과 합치지 않는다. 서버에서 기기 PIN의 성공 여부를 신뢰하지 않는다.
- 탈퇴의 1년 보관은 사용자 제품 결정이며 법정 기간이라고 주장하지 않는다. 파쇄 구현에서는 FK RESTRICT 관계 순서·원천 파일·백업·영수증까지 검토해야 한다. 현재 DB에 사용자 행 하나를 즉시 삭제하는 구현은 추가하지 않는다.
- 자동 세션 만료 없음은 확정된 **합성 데모 정책**이다. OWASP의 유휴/절대 만료 권고와 차이가 있으며 실금융 서비스 보안 충족으로 보고하지 않는다. 활성 세션 하나만으로 토큰 복제·탈취까지 차단했다고 주장하지 않는다.

작성·변경·검증 이력은 [API 문서 이력](../history/2026-10-22-api-doc-history.md)에 보존한다.
