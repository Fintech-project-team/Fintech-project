# v0.6 인증 검증 기준·인계 — #21

[인증 내부 설계](auth-design.md)와 [외부 계약](../../../../docs/api-contract.md) §2·§6의 구현 검증 기준이다. **아래는 실행된 테스트 결과가 아니다.** #21은 문서 간 호환성을 검토하고, #22 및 관련 후속 구현에서 실제 Spring/PostgreSQL·Flutter로 아래 결과를 확인한다. 문서 하네스 PASS를 제품 인증 PASS로 사용하지 않는다.

## 이름 통합·저장 검증 — 후속 구현 기준

- N01: 세 UUID가 지정된 name으로 201을 받고 요청의 앞뒤 허용 공백이 응답에 복제되지 않는다. syntheticName/displayName 키를 중복 반환하지 않는다. 이름·전화번호만으로는 여전히 로그인할 수 없다.
- N02: 서버 시드의 활성 이름은 name 하나다. 공백 포함 이름/전화번호, 누락·빈 이름·다른 UUID의 이름 매핑·중복 조회 조합을 거절한다. code 원문 DB 저장은 여전히 금지다.
- N03: API를 거치지 않는 잘못된 저장도 DB 제약으로 거절하는지 실제 PostgreSQL에서 확인한다. 이름 내부 U+0020·탭·줄바꿈·NBSP·전각 공백을 검사하고 금융 상품명/메모/별칭에는 인증 식별값의 공백 금지를 적용하지 않는다.
- N04: 이행 전후 사용자 UUID·전화번호·코드 검증값·세션·금융 행·FK가 유지되고 기존 이름 이행 근거가 보존되는지 확인한다. 실패 시 부분 적용이 없어야 한다. 기존 exporter를 기존 DB 초기화 수단으로 실행하지 않는다.
- N05: 로그인 응답만 name을 추가하고 reverify·금융 Snapshot·실패 응답은 확장하지 않는다. 구 이름을 읽는 consumer가 남아 있으면 배포 전 함께 전환하고 서버·기기 로그에 이름을 추가하지 않는다.

위 N01~N05는 문서에 정의한 검증 사례이며 현재 SQL/더미/인증 실행 테스트가 아니다.

## 코드 구조·설정값 적용 검토

공통 [작성 규칙](../../../../docs/harness/CODE_SPEC.md)과 인증 설계의 ‘값의 출처’ 표를 함께 확인한다. 아래도 **후속 구현 때 실행할 검증 기준**이며 문서 검사를 제품 테스트로 표시하지 않는다.

- 세션/접근 권한/오류 설정의 책임 경계와 처리 순서를 직접 확인한다. 체인·람다 자체를 금지하거나 줄 수를 줄이기 위한 헬퍼를 추가하지 않는다.
- 인증 활성화 시 필수 비밀 설정의 누락·빈 값·잘못된 타입/범위로 시작이 실패하는지 확인한다. 비활성 bootstrap에 미사용 인증 설정을 요구하지 않는다.
- 두 개의 유효한 운영 설정으로 풀/연결 제한 등이 주입되는지 확인하고, 임의 기본값으로 대체되지 않는지 검사한다. 확정된 5회/5분·60회/60초 정책은 같은 결과를 유지한다.
- 사용자별 금융 설정을 서버 환경변수로 이동하지 않는다. 로그인 요청은 name·phone·code만 사용하고, 응답의 name·로컬 PIN·Flutter 계산 위치를 유지하는지 확인한다. 금융 응답의 v2 변경은 response-models와 같은 벡터로 별도 검증한다.
- Java 수정 시 기존 생성일·사용처를 유지하고 필요한 수정일·목적을 남긴다. BootstrapSecurityConfiguration의 책임 구분과 DatabaseConfiguration의 운영값 주입은 관련 기능 구현에서 검토한다. 구조 정리만으로 보안 동작·운영 정책을 바꾸지 않는다.

## 구현 상태와 검증 경계

- 인증 책임·DB 변경안·동시성·인수 조건은 설계로 정의돼 있다. 설계 검토와 실제 API 동작 검증을 구분한다.
- #22 착수 범위: 코드 검증값 준비, 역할/함수·인증 제한 저장, 단일 세션·조회 구현과 해당 실제 테스트. 기존 초기화의 denyAll을 전체 permitAll로 바꾸지 않는다.
- 탈퇴/파쇄의 상세 구현은 관련 작업에 범위를 명시해 진행한다. #22가 탈퇴·1년 후 파쇄까지 이미 완료했다는 보고를 하지 않는다.
- #23은 금융 설정 저장이다. 초기 SQL에 설치 식별 컬럼이 없는 것과 별개이며, 기존 DB migration이나 금융 저장 API 구현이 완료된 것은 아니다. Flutter 실제 API 통합·Android/iOS 검증은 구현 이후 별도 근거를 남긴다.

작성·변경·검증 이력은 [API 문서 이력](../history/2026-10-22-api-doc-history.md)에 보존한다.
