# 금융 자료 준비와 사용

모델·저장 구조는 [공통 데이터 모델](../../../../docs/data-model.md), [DB 사전](../../../../docs/database-schema.md)을 따른다. 일반 사용자·금융 테이블에 준비한 값을 넣으며 데모 전용 사용자/금융 테이블이나 구분 플래그를 만들지 않는다. `/demo-sessions`와 세션 정책은 유지한다.

## 자료와 초기 상태

`generate.py --out <새 폴더>`는 정적 계정 세 개와 금융 원천·검증 사례 21개의 버전 있는 JSON 및 무결성 manifest를 생성한다. 기관명은 [공통 기준정보](../../reference_data/docs/README.md)를 읽는다. 상품명·거래명은 자연스러운 표시 값이며 실제 금융기관의 특정 판매 상품이라고 주장하지 않는다. 거래 선택은 ID·소유자·관계로 하고 표시명·첫 행·LIMIT 1로 대체하지 않는다.

`server-seeds.json`의 phone은 일반 users.phone 대응이며 제출 원문 저장소가 아니다. 계정의 codeVerifier는 현재 비활성 sentinel이다. 준비 파일만으로 인증을 활성화하거나 이름·전화번호만으로 로그인시키지 않는다. 실제 인증 기능과 외부 금융기관 연결은 별도 구현이다.

`export_sql.py <생성 폴더> --out <새 파일>`은 사용자와 금융 원천 INSERT를 생성한다. 기관 기준정보가 먼저 존재해야 하고 기존 사용자에 재적재하지 않는다. 사용자의 속성 행은 급여 값 null·카드 계획 빈 배열로 생성한다. 연결 동의·계산 계좌 선택·반복 계획·모아둘 돈·정산·쓰기 이력은 기본으로 넣지 않는다. 자료 버전·기준시각·원천 급여 입금 근거는 유지한다.

예전 검증 사례의 확정 설정·부분 정산은 [별도 시나리오 준비](../../testing/scenarios/README.md)를 선택할 때만 일반 테이블에 적재한다. 생성 JSON에는 그 사례의 상태가 보존되므로 JSON 직접 로딩과 기본 DB 적재의 초기 상태를 동일하다고 가정하지 않는다. 앱용 공개 Snapshot은 DB 상태에 권한/연결 투영을 적용해 구성한다.

## 검사

`validate.py <생성 폴더>`는 해당 준비 묶음의 무결성·관계·금액·일정·출처를 확인한다. 이 검사를 실제 금융 공급자 응답 검증기 또는 서비스의 사용자 제한으로 사용하지 않는다. SQL·RLS·경합·이행 검사는 [DB 검사](../../docs/database-tests.md)를 따른다. 모바일 자산은 API 담당자가 수정하지 않고 변경 파일·버전·초기 상태 차이를 담당자에게 전달한다.

## 일상 지출 시연

데모알파의 준비 도구 기본 원본은 `server-seeds.json`의 `initialCase=demo-life`다. `demo-ready`와 `alpha-ready`는 기존 회귀 사례로 계속 선택할 수 있다. 사례 이름은 준비 도구의 식별자이며 사용자 DB의 별도 타입·플래그가 아니다. 모바일의 기본 진입과 자산 목록은 같은 자료를 사용한다.

일반 금융 초기 적재는 계좌 선택·사용자 설정을 비워 둔다. 이미 연결·설정을 마친 시연 상태까지 재현하려면 신규 개발 서버의 `init --demo-state`를 사용한다. 이 옵션은 각 계정의 initialCase를 기존 시나리오 적재기에 넘겨 원천·연결·급여 설정·예정 지출·보호금을 함께 준비한다. 기존 DB 덮어쓰기·원천 금액 변경·서버 계산은 하지 않는다. 서버 준비 자료는 v3이고, 앱의 v4 청구 상세 공개 전환은 별도 공동 적용이다.

`demo-ready`는 기준시각 `2026-10-19T12:00:00+09:00`의 독립 원천 버전을 사용한다. 월세 300,000원·10/22는 같은 금액의 7/22·8/22·9/22 신규 합성 거래, 승인 결정, 반복 계획·버전, 저장된 10월 회차로 연결한다. 기존 1,200,000원 주거비와 같은 지출로 해석하지 않는다. 이 과거 거래는 시연 작성값이며 실제 수집 결과가 아니다. 후속 회차 생성 서비스의 구현을 전제하지 않는다.

카드값 110,000원·10/10은 출금 완료, 통신비 50,000원·10/25는 다음 기간의 등록된 예정 지출이다. 통신비의 10/15 출금과 10/25 계획이 같은 납부인지 알 수 없으므로 지급 연결을 추가하거나 일정 변경 이력을 지어내지 않는다. 비상금 400,000원은 지출 배정 없이 둔다. 기존 수리비 원천 출금 40,000원은 잔액에 반영된 거래로 남기고 새 시연의 수리비 의무·배정·정산 연결만 제외한다.

9/25 급여 거래를 확인한 `payMonth=2026-09`·`confirmed` 근거를 제공한다. 급여와 이미 출금된 금액을 현재 잔액에 다시 더하거나 빼지 않는다. `catalog.json`의 계산 기대값은 독립 Flutter 검사용이며 API 금융 응답·DB에 계산 결과를 저장하는 규격이 아니다. 기존 정상 사례의 급여 근거 보완은 별도 범위다.

`database/test_demo_ready.py --pg-bin <PostgreSQL bin> --work-dir <존재하지 않는 폴더>`는 새 폐기용 클러스터에서 기본/선택 적재와 관계·롤백을 검사한다. 실제 서버 주소를 받거나 기존 DB를 변경하지 않는다.

## 급여 자료의 회차 근거

기존 generated 묶음은 PAYSE-FIXTURE-3·PAYSE-DRAFT-3를 사용한다. 청구 항목의 별도 v4 묶음은 아래 전환 기준을 따른다. salary-wait·salary-partial·salary-confirmed의 payMonth는 작성된 2026년 10월 급여 사건을 근거로 `2026-10`으로 명시한다. 거래의 입금월을 잘라 모든 자료에 적용하는 규칙이 아니다. 과거 승인 기록의 sourceVersion은 승인 당시 버전을 보존한다.

휴일 이동·계획 밖 조기 입금·서로 다른 회차의 같은 예정일은 검증 도구의 독립 입력으로 검사한다. 기존 사용자 사례를 수정해서 검사 전제를 만들지 않는다. 원천 준비는 구간 금액을 계산하거나 접근 제한을 적용한 API 응답을 생성하는 기능이 아니다.

`salary-schedule-provided`와 `salary-schedule-absent`는 같은 사용자·`asOf=2026-10-29T12:00:00+09:00`의 독립 비교 사례다. 전자는 `payMonth=2026-11`, `expectedPayDate=2026-10-30`, `confirmation=unknown`, `transactionIds=[]`를 수동 준비 원천으로 제공하고, 후자는 급여 근거를 `[]`로 유지한다. 원천 버전 표식과 이 급여 근거 외의 거래·잔액·보호 설정은 같다. 두 사례의 반복 월급일 설정은 기존 템플릿의 25일이며, 준비 도구가 이 설정으로 예정일이나 급여 근거를 계산하지 않는다. 다음 날짜 선택·반복 규칙·말일 보정·계산 결과는 Flutter에서 검증한다.

두 사례는 같은 사용자 ID를 사용하므로 시나리오 적재에서 각각 별도의 빈 사용자 범위에 하나씩 선택한다. 둘을 함께 적재하는 요청은 기존 사용자 중복 검증에서 거절한다. 기존 시나리오를 덮어쓰거나 신규 필드·API를 추가하지 않으며, 제공 일정은 실제 입금 확인을 의미하지 않는다.

## 거래명과 적요

`transaction_labels.py`는 오프라인 작성 키로 가린 가상 인명·창작 가맹점/지점·기관명을 재현한다. 실거래 자료나 실제 상호 목록을 가져오지 않는다. `merchantName`은 상대방/통장 표시이고 `description`은 CMS·급여·타행이체·모바일이체·체크카드·신용카드·자동이체·이자·카드환불·승인취소 등의 거래 방법이다. 새 필드나 사용자 수정 권한을 추가하지 않는다. 카드 납부/이자 내역은 연결된 카드·상품을 구분하는 표기를 쓰며 가상의 금융사를 원래 기관으로 대체하지 않는다.

이름은 ID 생성·거래 선택·관계/급여 확인의 기준이 아니다. 원천 표시와 저장된 계획의 label·승인의 normalizedName을 분리한다. 같은 카드 구매와 통장 출금, 구매와 환불/취소는 상대방을 일치시키고 방법만 사건에 맞춘다. 베타의 같은 가맹점 별도 구매는 같은 표시를 유지한다. 감마의 모호한 입금에는 급여·대출 등 정답 단서를 쓰지 않는다.

표시 근거가 바뀐 생성 자료는 sourceVersion에 `:reversals-1:labels-1`을 추가한다. PAYSE-DRAFT-3·PAYSE-FIXTURE-3 스키마와 과거 승인 sourceVersion은 보존한다. 이는 새 준비 자료이며 이미 운영 중인 DB의 원천을 일괄 UPDATE하는 절차가 아니다. 기본/선택 적재는 기존 일반 financial_transactions.merchant_name·description 컬럼을 그대로 사용한다.

## 승인 취소·환불 준비

각 기본 계정에는 새 원결제 3건과 승인 취소·전액 환불·부분 환불 각 1건을 함께 준비한다. 작성 사례 ID는 catalog.preparedReversalIds로 검증하며 표시명·첫 행으로 고르지 않는다. 추가 사건은 카드 원천이며 계좌 현금 입금이나 새 청구로 변환하지 않는다. 기존 경계 사례의 사건은 삭제하지 않는다. 실제 저장은 일반 financial_transactions와 transaction_references를 사용한다.

취소일은 공통 cancellationDate 규격을 따른다. 최신 원본에는 키를 제공하고, 이전 v3에서 키가 없으면 적재 시 null을 유지한다. validate는 날짜만 있는 취소, 종류·시각 일치, 조회 기준시각·coverage를 확인한다. 원천 SQL 생성은 취소일을 계산하지 않는다. 새 DB는 001, 기존 공통 DB의 추가 이행은 005_cancellation_date.sql이며 준비 파일 생성 자체는 DB에 접속하지 않는다.

## 청구 항목의 공동 버전 전환

`generated`의 기존 v3 파일은 보존한다. `billing_cases.py --out <새 폴더>`는 `PAYSE-FIXTURE-4`·`PAYSE-DRAFT-4` 묶음을 작성하며 준비본은 `generated-v4/`에 둔다. 기존 21개 사례를 변환한 자료와 별도 `alpha-billing-items`·`beta-billing-items`·`gamma-billing-items` 3개, 총 24개다. server-seeds의 기본 사례 선택은 바꾸지 않는다. 실제 DB 적재·모바일 자산 복사는 자동 실행하지 않는다.

기존 사례의 ID·금액·날짜·잔액·의무·설정·계산 기대값은 유지한다. 원천 버전과 사건 전이의 버전 참조만 v4 묶음에 맞추며 과거 승인 버전은 보존한다. 기존 청구의 거래 참조는 안정된 항목 ID로 연결하고, 확보하지 않은 새 표시명·금액·이용일·회차는 null로 둔다. 거래 금액을 청구 원금으로 복사하지 않는다. 필드 의미와 부호 범위는 [데이터 모델](../../../../docs/data-model.md#v4-청구-항목)을 따른다.

새 3개 사례에는 같은 600,000원 구매 하나를 두 청구의 2/6·3/6회차로 연결한다. 첫 청구에는 음수 할인·거래 연결 없는 연회비·음수 청구 조정·금액 미상 항목을 함께 제공한다. 각 새 청구에는 기존 계약의 청구 의무 하나만 대응한다. 이 독립 사례는 새 청구 의무도 추가하므로 기존 기본 사례와 홈 결과가 같다는 의미가 아니다. 기존 사례에 상세 items만 추가할 때 홈 계산 입력·기대값이 유지되는지와 구분한다.

`statement_items.py`는 항목의 타입·부호·참조를 검증하고, `billing_projection.py`는 v4 청구 공개 조각의 참조 구현이다. 인증된 사용자·기관 연결로 검증한 권한 집합을 입력받으며 실제 HTTP·전체 Snapshot 조립을 대신하지 않는다. 다음 페이지에 있다는 이유만으로 연결을 숨기지 않는다. 제한 표식·구버전·음수·null·여러 청구 참조 반례는 `tests/test_billing_projection.py`에서 확인한다.

v4 적용은 API·Fake 서버·Flutter의 모델, 응답 형식 검사, 제한 표식 검사, 버전 전환과 계산 회귀 검증을 함께 완료한 뒤 진행한다. 이전 refs 배열을 남기는 것만으로 구 앱과 호환됐다고 판단하지 않는다. Flutter의 실제 반영 범위는 [인계 기록](../../docs/history/2026-10-29-statement-items-handoff.md)에 정리한다.
