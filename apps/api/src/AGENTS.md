# PAYSE API 필수 개발 규칙

공통 개발 원칙은 `apps/api/` 전체에 적용한다. 이 파일은 사용자가 지정한 `src/` 아래에 보관하며 루트 지침·데이터 계약과 함께 적용한다. Java 주석 의무·자동 검사는 `src/main/java`·`src/test/java`·`tools`의 직접 작성한 Java 코드에 적용한다. Flutter/Dart의 규칙은 변경하지 않는다.

1. 계좌 합산·U·소비 집계·반복 후보 수치·미래 잔액·시뮬레이션은 Flutter에서 계산한다. 서버는 원천/설정 제공·저장 제약 검증·LLM 해석을 담당한다.
2. 기존 데이터 모델·SQL·JSON 필드 의미를 보존한다. JSON 금액은 원화 정수, dataVersion/expectedDataVersion은 10진 정수 문자열이다. DB data_version은 bigint, sourceVersion/ruleVersion/schemaVersion은 문자열, inputRevision은 정수다. 미확인을 0으로 바꾸거나 날짜에 미확인 시각을 만들지 않는다.
3. 이름 있는 클래스·인터페이스·annotation·enum·record, 직접 작성한 메서드·명시적 생성자 바로 위에 Javadoc으로 목적, `@created YYYY-MM-DD`, `@usedBy 주요 클래스.메서드 또는 프레임워크 진입점`을 적는다. 인자·반환·예외의 계약도 필요한 만큼 적는다.
4. DTO/VO 클래스 또는 record 위에는 목적·생성일·주요 사용 클래스/메서드를 기록한다. API 객체와 DB 객체를 무조건 같은 클래스로 만들지 않는다.
5. 작업 기준 커밋에 존재하던 메서드의 구현·시그니처·계약을 수정하면 생성일을 유지하고 같은 Javadoc에 `@modified YYYY-MM-DD - 변경 목적`을 추가한다. 같은 날 같은 목적은 한 줄로 정리하고 다른 수정 기록은 유지한다.
6. 기존 DTO/VO의 필드·타입·의미·검증 조건 변경에도 클래스 주석에 같은 수정 기록을 남긴다. 기준 커밋에 없는 신규 선언을 완성하는 편집은 생성 작업이다. 기준을 바꿔 기존 선언을 신규로 취급하지 않는다.
7. 주요 호출자는 실제 확인한 사용처만 적고 미연결은 `미연결: 예정 사용처 ...`로 구분한다. 기존 코드의 생성일을 확인할 수 없으면 `@created unknown - 이력 확인 불가: 구체적 사유`를 사용한다. 신규 코드에는 실제 날짜를 쓴다.
8. 주석은 짧고 구체적으로 쓴다. API의 필수 수정일·목적만 코드에 남기고 상세 작업 과정·실패 로그는 Git/PR에 기록한다.
9. Controller → application service → Repository/외부 adapter로 책임을 나눈다. 필요한 의존성을 생성자로 주입한다. 빈 계층·전역 ServiceLocator·공통 BaseManager를 만들지 않는다.
10. 상태 없는 Spring bean과 연결 풀은 재사용할 수 있다. 사용자·세션·잔액·DB 트랜잭션을 static 또는 singleton bean의 변경 가능한 필드에 보관하지 않는다.
11. 사용자 금융 조회·설정 쓰기는 인증 세션의 사용자로 제한한다. 공개 생존 확인은 금융 정보를 반환하지 않으며 로그인은 인증 계약에 따라 검증한 뒤 세션을 발급한다. 클라이언트 userId/deviceId는 인증 근거가 아니다. 기존 활성 세션 우선·로컬 PIN 원칙을 유지한다.
12. 금융 설정·관계 확정 쓰기는 expectedDataVersion·ruleVersion·idempotencyKey를 검증한다. 사용자 잠금·참조 소유권·저장 제약·설정/기록/버전 변경을 같은 트랜잭션에서 처리하고 RLS 사용자 설정도 같은 연결을 쓴다. 처리 순서는 기존 DB 설계를 따른다. 인증 발급·종료와 LLM 해석 요청에는 금융 설정 버전을 일괄 요구하지 않는다.
13. 원천으로 분류된 금융 필드는 사용자 수정 불가다. 사용자 편집은 데이터 명세의 수정 권한 열을 따른다. 계좌 포함/별칭·급여/카드 계획·보호 설정·허용된 분류/지급 연결/배정은 원천 사실과 분리한다. 시뮬레이션 가상 입력·결과는 기능 흐름 메모리에만 두고 DB·파일·로그에 영구 보존하거나 기기에서 영구 복원하지 않는다. 확정 설정 저장은 별도 계약을 따른다.
14. SQL은 파라미터 바인딩한다. DB 자격·LLM 키·PIN 원문을 코드·응답·로그에 남기지 않는다. 세션 토큰 원문은 인증 성공 시 해당 클라이언트에 전달하는 경우만 허용하고 서버 코드·DB·로그·일반 금융/오류 응답에는 남기지 않는다. 서버에는 토큰 검증값만 저장한다. DB 역할은 최소 권한으로 구성하고 앱에는 DB 자격을 배포하지 않는다.
15. LLM은 필요한 최소 입력만 받고 허용된 구조로 검증한다. LLM 결과로 금액 원천·권한·지급 상태를 확정하지 않는다. 요청·응답의 민감 본문을 로그로 보존하지 않는다.
16. 업무 검증 422·인증 401·권한 403·버전/멱등 충돌 409 등 기존 계약을 따른다. Spring 기본 오류 응답에 맞추려고 계약을 바꾸지 않는다.
17. 새 기능의 정상·오류·타 사용자 접근·중복/충돌을 해당 계층에서 검사한다. 실제 PostgreSQL의 RLS/동시성 검사를 H2 성공으로 대체하지 않는다. 초기 차단을 인증 구현 완료로 보고하지 않는다.
18. 저장소 루트에서 `node scripts/harness/run-api.mjs check`를 실행한다. 자동 검사는 목적·생성일·사용처의 형식 및 기재된 모든 수정일/목적을 확인한다. 날짜·설명의 사실성, unknown 사용 근거, 수정 이력 누락은 diff 리뷰로 확인한다.
19. 생성 코드·record 자동 접근자·람다 본문에는 주석을 복제하지 않는다. 익명 클래스에 직접 선언한 메서드와 직접 작성한 테스트 메서드는 포함한다. 자동 검사와 테스트 실행 결과를 구분한다.
20. 공통 계약/Flutter 변경은 영향을 받는 담당자와 확인한다. 이 파일을 이유로 다른 담당자의 Dart 코드·주석·SDK·UI를 일괄 수정하지 않는다.
21. SQL에 호출별 사용자·계좌·거래 ID를 직접 적지 않는다. 런타임은 인증 문맥과 검증된 입력을 바인딩하고, 데이터 의존 테스트는 검증된 준비 자료의 ID와 관계를 변수로 전달한다. 표시명·배열 순서·임의 `LIMIT 1`로 대상을 선택하지 않는다. 단일 대상의 존재·건수·소유권·참조·필요한 사전 상태를 검사하고 0건 또는 여러 건이면 본 검사 전에 실패시킨다. 실제 변경 행 수도 확인한다.
22. 테스트 준비값은 대상과 사전 상태를 식별하는 데만 쓴다. 경계값·기대 오류·기대 결과를 검사 대상 구현에서 추출해 정답으로 삼지 않는다. 도메인 상수·형식 검사 문자열·경계 입력은 명시적으로 유지할 수 있으며, 재현 가능한 더미 생성과 승인된 이행 매핑은 단일 기준에서 관리한다. 복사한 고정 ID 목록으로 준비 단계를 대신하지 않는다. 테스트 도구를 운영 API·공개 금융 응답·영구 DB 구조의 의존성으로 추가하지 않는다. 실행 방법은 [DB 테스트](../docs/database-tests.md)를 따른다.

```java
/**
 * 사용자에게 허용된 계좌 원천 정보를 조회한다.
 * @created 2026-10-19
 * @usedBy AccountController.list
 * @modified 2026-10-20 - 소유자 확인 누락 보완
 * @param userId 검증된 서버 세션의 사용자 ID
 * @return 해당 사용자의 원천 계좌 목록
 */
```

예시는 형식만 참고하고 실제 날짜·호출자를 적는다. [초기화 안내](../docs/spring-bootstrap.md), [데이터 계약](../../../docs/data-contracts.md), [필드별 명세](../docs/data-model-draft.md), [DB 설계](../docs/database-design.md), [상태 수명](../../../docs/app-architecture.md)을 함께 따른다.
