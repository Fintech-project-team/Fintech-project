# PAYSE 거래 해석 품질·토큰 절감 실행 계획

작성일: 2026-11-01. 계획과 로컬 검사를 실제 LLM 성능 측정으로 구분한다. 실제 공급자 연결·유료 호출은 아직 실행하지 않는다.

## 목표와 현재 근거

- 목표: 독립된 최종 평가 100,000건에서 오분류·불필요한 유보·누락·실패의 오류 사례 합계가 10건 이하, 즉 관측 오차율 0.01% 이하.
- 이는 PAYSE의 목표이며 달성 보장이나 전체 실사용 모집단에 대한 통계적 보증이 아니다. 모델 confidence를 정답률로 사용하지 않는다.
- 평가 단위는 사전에 고정한 한 의미 판단 항목이다. 같은 항목의 여러 오류는 대표 실패 사유 1건으로 집계하고 상세 오류는 별도 기록해 중복 집계를 피한다.
- 근거가 부족한 입력의 올바른 unknown은 오류가 아니다. 근거가 충분한데 unknown으로만 답하면 불필요한 유보로 집계한다.
- 기본 자료 104건은 보존한다. 확장 생성기는 **5,083건(거래 5,078·반복 5), 344개 명목 사례군**을 만든다. 기존 자료의 이름·숫자만 다른 5개 별칭은 확장 집계에서 제외한다. 원본 104건의 목록은 삭제하지 않는다.
- 41개 의미의 긍정·혼동쌍과 명시 목적의 부정·정정·미실행 예약·실패·과거 내역·적요 지시문·기존 분류 충돌·원천 관계·근거 누락을 교차한다. 원거래 가시성 5조건과 짧은 은행 적요·상태·관계 범위 36조건도 포함한다.
- **합성 조건 조합**이며 독립적인 실거래 5,083건이라는 뜻이 아니다. 생성 문법·개발 기준을 공유하므로 연결된 개발 집합 하나로 관리한다. 독립 최종 holdout 100,000건은 아직 0건이다.
- 취소·환불은 원천 recordKind가 유지되면 적요가 수입을 암시해도 사건 의미가 유지된다. 상태·잔액 반영·표시 의미는 서로 구별한다.
- 합성 정답 응답, 문구 변형, 캐시 반복의 로컬 PASS를 실제 모델 100,000건의 성공으로 보고하지 않는다.

## 단계별 실행

| 단계              | 작업                                                                                                             | 통과 근거                                                                |
| ----------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 1. 로컬 구조 검사 | Schema·ID/관계·항목 대응·금액 범위·정답 분리·채점기 반례를 외부 호출 없이 검사                                   | 합성 oracle 성공과 잘못된 응답 거절을 구분한 테스트 결과                 |
| 2. 평가 자료 구성 | 정상·근거 부족·혼동쌍·관계 누락·정정·삭제·적요 공격을 준비하고 사용자/기간/유사 거래군으로 개발·최종 평가를 분리 | 정답 출처·허용 답·근거 충분성·중복 검사·자료 버전과 지문                 |
| 3. 소량 측정      | 실제 호출 준비 확인 후 개발 표본 100 → 1,000 → 10,000건 순으로 품질·토큰·비용·지연 측정                          | 단계별 오류 유형·분류별 성능·비용 전망. 개선할 때는 개발 표본으로만 비교 |
| 4. 최종 동결      | 모델 ID·프롬프트·Schema·의미 규칙·입력 투영·허용 답·100,000건 manifest를 고정                                    | 튜닝에서 보지 않은 독립 자료와 변경 이력. 모호한 정답은 실행 전에 검토   |
| 5. 최종 1회 평가  | 준비·예산 확인 후 동결한 100,000건을 실행하고 모든 응답/실패를 채점                                              | 전건 완료와 오류 10건 이하를 모두 충족해야 목표 통과                     |

오류가 11건에 도달하면 해당 최종 실행은 목표 미달이 확정되므로 중단할 수 있다. 부분 실행을 100,000건 완료로 보고하지 않는다.
최종 자료를 보고 수정한 프롬프트는 새 후보 버전이다. 같은 최종 자료를 반복 튜닝하여 독립 검증으로 재명명하지 않는다.
표본의 크기만 늘리기 위한 이름·공백·ID 변경, 같은 입력/캐시 결과 반복은 독립 100,000건으로 세지 않는다. 동작 변형 검사는 별도다.
실제 호출 단계마다 계정·모델 접근·단가·기존 사용액·환산·세금/수수료·KMS 준비 및 남은 예산을 확인한다.
총예산 50,000원, 신규 유료 호출 차단선 45,000원, 오차 여유 5,000원을 유지한다. 비용이 부족하면 범위/예산을 보고하며 임의 증액·상한 우회하지 않는다.

## 토큰을 줄이면서 정확도를 유지할 개발

1. 원천 전체 대신 허용된 최소 거래 필드·필수 관계·로컬 후보 특징만 전송한다. 금융 계산·반복 수치·날짜 산출은 Flutter에 유지한다.
2. 긴 중복 설명을 제거하고 타입 있는 의미 코드·사유 코드·ID 참조를 사용한다. 공급자 전용 짧은 ID를 쓰면 요청 메모리에서 원래 ID로 역매핑하고 검증한다.
3. 같은 근거 거래는 한 번만 넣고 후보들이 참조하게 한다. 근거를 잘라서 작은 요청처럼 만드는 것은 금지한다.
4. 유효 개별 결과 재사용과 진행 작업 합류를 먼저 검사하고 미해석 항목만 전송한다. 재사용으로 최초 저장/3개월 기한을 연장하지 않는다.
5. 중요보존과 필수참조를 구분하고 관련성·활성·권한·삭제·현재 근거를 검사한 기억만 사용한다. 삭제한 기억은 다른 묶음으로 재보존하지 않는다.
6. 입력 6,000·출력 1,200토큰, 근거 60·후보 20의 승인된 초기 상한을 유지한다. 필수 출력이 1,200토큰에 들어가는지는 실제 사용량으로 측정한다.
7. 출력이 잘리거나 필수 항목이 빠지면 성공으로 처리하지 않는다. 독립 후보를 더 작은 묶음으로 나누되 같은 후보의 필수 근거는 나누지 않는다.
8. 상세 문단보다 필요한 의미·근거·짧은 이유를 반환한다. 출력 단축과 입력 축소는 한 번에 한 변경씩 기준 성능과 비교한다.
9. 채점에 추가 LLM 호출을 사용하지 않는다. 고정 허용 답·코드 검증과 필요한 사람의 근거 검토를 사용한다.
10. 자동 공급자 재호출·자동 모델 전환은 하지 않는다. 실패·응답 유실은 현재 DB 결과와 시도 상태 확인 후 사용자 재시도 정책을 따른다.

## 평가 기록과 오판 방지

- 근거 충분 자료의 정답·불필요 유보, 근거 부족 자료의 무근거 확정, 분류별 혼동, Schema/참조 오류, 누락·실패를 각각 보고한다.
- 입력/출력 토큰·공급자 요청 수·재사용 건수·비용·지연·올바른 결과 1건당 비용을 함께 기록한다. 미측정은 0으로 채우지 않는다.
- 감마의 비공개 작성자 정답 loan을 입력에 넣지 않는다. 제공 정보만으로 구분할 수 없으면 unknown/미확정 후보가 올바른 답이다.
- fixture 작성 분류를 사용자 확인 또는 금융사 원천으로 바꾸지 않는다. 금액·날짜·상호만으로 내부 이체·청구 납부를 확정하지 않는다.
- 거래 적요 속 지시는 데이터로 취급한다. 다른 사용자·허용 밖 ID·금융 설정 변경·원천 잔액/급여 근거 변경은 거절한다.

## 로컬 검사와 자료 사용

저장소 루트에서 `python -B -m unittest discover -s apps/api/testing/analysis -p test_*.py`를 실행한다. API Gradle test/check에도 연결되어 있다.

- `build_schemas.py --write`, `build_cases.py --write`: 분석 전용 JSON 재생성. 기존 금융 fixture·DB를 수정하지 않는다. 인자 없이 실행하면 게시 파일과 생성 결과를 대조한다.
- `evaluate.py --export-input <새 파일 경로>`: 비공개 정답을 읽지 않고 모델용 최소 입력만 새 파일로 내보낸다. 입력 전체 또는 expected.private.json을 공급자에 업로드하지 않는다.
- `evaluate.py --responses <응답 파일>`: case ID별 저장된 응답을 itemKey로 채점한다. 실제 호출 기능은 없다. 토큰/비용/지연은 사용량 근거가 없으므로 null이다.
- `--usage <시도 기록 JSON>`: 요청별 사용량을 별도 `recordedUsage`에 집계한다. 실패·수동 재시도·미채택 응답도 포함하고 미측정은 0이 아닌 null로 남긴다. 원화는 PAYSE 장부의 정산/미정산 기록만 사용하며 단가·환율을 추정하지 않는다. 파일만으로 기록 진위나 운영 전체 잔여 예산을 인증하지 않는다. 내부 평가 기록 형식과 검증은 `usage.py`에 정의되어 있으며 공개 API·DB 계약이 아니다.
- `cases/expected.private.json`: 작성자 근거·판단 가능성·허용 답. 테스트 저장소 내부 자료이며 원천 DB/앱 자산/모델 본문으로 배포하지 않는다. 실제 민감 자료는 없다.
- `expansion.py`: `expansion.py`의 조건 조합과 `bank_cases.py`의 짧은 원천 사례를 합쳐 전건 검사한다. 저장소 루트의 `.harness/analysis-evaluation/`에 입력 JSONL·분리된 비공개 정답 JSONL·파일/생성기 지문 manifest·검사 보고서를 생성한다. 대용량 생성본은 Git에 올리지 않으며 생성기와 검사는 Git으로 공유한다.
- `evaluate.py --dataset expanded --export-input <새 경로>`: 생성한 입력 JSONL만 읽어 모델용 입력을 내보낸다. 정답 파일이 없어도 내보내기가 가능하다. `--responses`, `--routes`, `--baseline-responses`는 저장된 실제 기록으로 채점·비교할 때만 사용한다.
- `measure.py --limit 100`: 생성된 개발 자료에서 조건별 작은 표본의 JSON 바이트를 측정한다. 입력/출력 토큰이나 비용 측정이 아니다. `OpenAiGateway.countInput`도 외부 전송이므로 승인 전 호출하지 않는다.
- `schema_check.py`: 이 계약에서 쓰는 제한된 Schema 키워드의 오프라인 검사기이며 미지원 키워드를 거절한다. 범용 JSON Schema·실제 소유권/RLS 검사를 대체하지 않는다.

현재 테스트의 합성 정답 응답은 채점기의 검사용이다. 해당 응답의 0오류는 실제 모델의 성능이 아니다. 정상 구조여도 설명이 근거를 뒷받침하는지는 사람 검토가 필요하다. 실제 DB 불변·사용자 권한·암호화·삭제·늦은 응답은 저장/HTTP 구현 후 별도 검증한다.

## 다양성·전체 판단 평가

`python -B apps/api/testing/analysis/expansion.py`로 5,083개 전건의 계약·기준 응답·중복·분할 검사를 수행한다. `diversity.py`는 원본 104개를 별도로 점검한다. 참조 그래프의 타깃·간선을 유지하면서 ID/배열 순서를 정규화하고, 이름·숫자만 다른 입력도 별도로 검사한다. 그래프 색상 정제는 보수적 중복 검사이며 의미 독립성의 증명은 아니다.

전체는 거래 판단 5,078개와 반복 후보 5개다. 고유 목표 거래 ID는 5,077개이며 기존 감마 거래의 적대적 입력 사례 1개가 같은 ID를 사용한다. 다수 사례가 11개 공통 조건 문장 틀과 244개 목적쌍을 공유하므로 독립적인 실제 거래 5,083건으로 보고하지 않는다.

같은 판단 문제의 긍정/혼동 사례는 같은 groupId로 둔다. 중복 통합의 alsoCoversGroups도 연결된 묶음으로 취급해 개발/최종 평가에 나누지 않는다. ID·금액·날짜·상호 문자열 치환만으로 수를 늘리지 않는다. 새 표본은 기존과 다른 근거·누락·관계·충돌·분류 난점을 가져야 한다. 실제 사용 빈도와 드문 오류의 비율은 수집/검토 이후 정하며 임의 가중 정답률로 목표를 대신하지 않는다.

`partitions.py`는 groupId·alsoCoversGroups·familyLinks·공유 원천·배치에서 분리한 거래 지문을 연결해 개발/최종 영역의 겹침을 거절한다. `--final`은 개발 노출 자료를 요구하고 개발 자료 승격·10만 고유 거래 미달·배치 재포장 중복·개발군 중복을 거절한다. 이 구조 검사도 사람의 독립 정답 검토를 대신하지 않는다. 공유 템플릿을 감춘 뒤 groupId만 바꾸어 최종셋으로 등록하지 않는다.

확정 목표의 대상은 PAYSE 전체 판단이며 LLM에10만 번 요청하는 조건이 아니다. 원천으로 확인한 사실·사용자 정정·유효 결과 재사용을 먼저 적용하고, 나머지 필요한 의미 작업만 LLM에 보낸다. 각 입력의 최종 기본/세부 답을 채점하며 LLM 처리분의 표본·오류는 분리한다. 같은 사례 반복/캐시 재조회는 새 표본이 아니다.

채점기의 `--routes <경로 기록 JSON>`은 `{caseId:{itemKey:route}}`를 받는다. route는 source_fact/user_confirmed/reused_result/llm/unresolved/processing_failure 중 하나다. 실제 실행 제어부의 기록을 사용하며 모델 자기신고값을 쓰지 않는다. 경로 기록이 없으면 분리 지표는 null이고 임의로 LLM 실행으로 세지 않는다. 이 도구는 기록의 진위·실제 호출·권한을 입증하지 않는다.

기본/세부 분류 중 하나라도 오류이거나 불필요 유보·누락/실패이면 거래1오류다. 명확한 거래 의미가 분류표에 없는 coverageGap도 오류로 센다. 불충분한 입력의 올바른 유보만 정답이다. 알려진 목록 밖 거래를 unknown 정답으로 처리해 성능을 부풀리지 않는다. 10만 건/10오류는 표본 목표이며 모든 미래 거래에서 같은 오류율을 보장하는 통계적 증명은 아니다.

현재 `score`가 받는 것은 분석 후보 계약의 응답이다. **저장된 유효 기본 분류와 새 후보를 합친 PAYSE 최종 판단의 실행 어댑터는 미구현**이다. 따라서 `wholePipelineMeasured=false`, 목표 상태는 `not_evaluated`로 유지한다. 특히 기존 분류와 충돌하는 후보의 `classification=null`을 기존 DB 분류 삭제로 해석하지 않는다. 누락·무효 응답·처리 실패·의미/기본 유보·범위 부족을 각각 기록하고, `compare`는 같은 총점에서도 개선/악화 목록을 따로 보인다.

## 드러난 범위 한계와 남은 구현

- 현재 기준 응답을 전건 넣어도 **288개가 범위 부족**이다: 주된 목적을 고를 근거가 없는 복수 목적 281개, 단일 코드가 없는 서비스 7개. 단일 meaning 계약에서 억지로 하나를 선택하지 않는다. 복수 목적 표현·분류표 확장은 별도 계약 검토 후 반영한다.
- 장문의 통제된 목적 문장과 의미쌍 조합 비중이 크다. 실제 금융 원천의 짧고 불완전한 적요, 사용자별 습관·기관별 차이·현실적인 발생 비율은 이 자료가 대표하지 않는다. source_relation은 양쪽의 상충하는 목적 적요보다 명시 관계를 우선하는 검사이며, 모두 같은 관계 형태이므로 독립 관계 유형 수로 주장하지 않는다.
- 41개 기준표의 긍정/반례에는 정답이 있다. 파일 전체를 프롬프트에 넣지 않는다. `criteria_only`는 코드·표시명·필수/불충분 근거만 내보내고 positive/contrast/basicTypePolicy 등 예시 의존 항목을 제외한다.
- 승인 후 100건 개발 파일럿에서 기본 입력과 압축 입력을 각각 측정하고, 정확도 악화·유보·실패·토큰·비용·지연을 비교한다. 프롬프트를 고정한 뒤 1,000→10,000으로 확대한다. 독립 최종 100,000건은 별도로 작성·검토·동결한다.

## 오프라인 입력 절감 도구의 경계

`efficiency.py`는 필요한 항목과 **그 항목의 전체 근거**를 함께 선택한다. 원거래나 관계가 다른 항목에 걸려 있으면 잘라서 보내지 않는다. 짧은 ID는 요청 안에서만 쓰며 전용 출력 스키마로 검사한 뒤 원래 ID·공개 계약으로 다시 검증한다. 공개 JSON/DB ID는 변경하지 않는다. 역매핑은 실제 연결 시 job/attempt·응답 문맥에 결합해야 한다. 별칭 자체가 응답 출처를 인증하지 않는다.

`compact_criteria`는 동일 기준 문장을 한 번만 둔 실험 표현이다. 원래 기준으로 완전히 복원되는지 검사하지만 실제 프롬프트에는 아직 적용하지 않는다. 기준 압축과 ID 압축의 모델 정확도는 별도 실측 대상이다. 100건 로컬 표본의 입력 본문은 최소 투영 대비 약23% 작고, 기준 JSON은 18,758→10,506바이트다. 실제 토큰 절감률로 바꾸어 보고하지 않는다. 출력 스키마·지침도 입력 한도에 포함된다.

`routing.py`는 **이미 서버에서 검증했다고 가정한 자료**를 받는 오프라인 사전 검사다. 소유권·현재 근거/관계·기존 분류·정정·삭제·활성·버전·보관 기한이 맞는 결과를 먼저 찾는다. 정상 unknown 저장 결과도 재조회 때문에 다시 호출하지 않으며, 평가에서는 여전히 불필요 유보 여부를 채점한다. 중요 AI 참고자료의 일반 3개월 예외와 해제·탈퇴 보관 종료를 구분하고 최초 기산일을 유지한다. 단순 기존 분류는 검증된 원천 사실이나 사용자 확인으로 승격하지 않는다.

검증된 원천 확인 → 해당 거래 사용자 확인 → 유효 LLM 결과 순으로 선택하며 같은 권위의 상충 답은 미해결로 남긴다. 과거 unknown이 확인된 원천 답을 가로막지 않는다. 원천/사용자 확인은 현재 근거·정책·응답 형식의 검증을 요구하고, LLM 결과 재사용은 모델·프롬프트 버전도 대조한다. 모델 교체만으로 확인된 원천 사실을 다시 해석하지 않는다.

실제 DB 권한/보관 검증, 진행 작업 합류, 부분 기억의 운영 DTO, 최종 판단 합성은 연결하지 않았다. 이 도구의 verified 플래그나 임시 지문을 공개 인증·영구 DB 규격으로 사용하지 않는다. 유효 결과가 남아도 관계를 분리할 수 없는 배치는 그대로 보존한다. 자동 재호출·새 모델 전환·예산 증액 기능은 추가하지 않는다.

## 저장 응답으로 경로 재현하기

`replay.py`는 원천/유효 결과 재사용 → 미해결 입력 준비 → 기록된 공급자 응답 검증을 연결한다. 외부 호출 함수·DB 저장·금융 계산은 없다. 기존 `currentClassifications`와 새 후보를 분리해 기록하며, 기존 분류가 없다는 이유로 후보를 자동 확정하지 않는다. 최종 적용 어댑터·실제 3개월 정확도는 여전히 미검증이다.

내부 실행 파일은 `{caseId: {payload, ownerScope, versions, records, now, requestId, attemptId}}`다. `payload`는 분석 입력, `versions`는 policy/model/prompt/schema, `records`는 `routing.py`가 검사하는 합성 검증 자료다. `now`는 이 재현 실행의 고정 검사 시각이다. 비공개 정답은 별도 파일이며 실행 파일에 추가할 수 없다. 이 문맥은 실제 서버 인증·DB 조회를 대신하지 않는다.

```text
python -B apps/api/testing/analysis/replay.py --cases <실행파일> --export-requests <새 요청파일>
python -B apps/api/testing/analysis/replay.py --cases <실행파일> --responses <저장응답> --output <새 재현결과>
python -B apps/api/testing/analysis/replay_score.py --cases <실행파일> --responses <저장응답> --expected <비공개정답> --output <새 채점결과>
```

- 요청 파일에는 미해결 항목의 최소 입력·공급자 출력 Schema·버전·실행 식별자·지문만 있다. 소유자 문맥, 재사용 기록, 정답, 원래 ID 대응표는 포함하지 않는다. 실제 공급자에는 이 파일 전체가 아닌 승인된 입력/Schema만 전달해야 하며 현재 전송 기능은 없다.
- 저장 응답은 `{caseId, requestId, attemptId, requestFingerprint, status, output}` 객체의 배열이다. status는 completed/failed/incomplete/refused이며 completed 외에는 output이 null이다. completed의 output은 해당 요청의 짧은 ID를 사용한 응답이다. 요청·사용자 문맥·현재 입력/버전/별칭 대응을 결합한 지문을 먼저 대조한다. 이 지문은 오프라인 자료 혼입 방지이며 전송·권한·기록 진위의 인증 수단이 아니다.
- 같은 i1/t1이라도 다른 요청의 응답은 채택하지 않는다. 중복 사례/시도·미발급 ID·항목 누락을 거절한다. 공급자 배치는 전부 성공하거나 전부 실패하며, 독립 재사용 성공은 보존한다. 정상 unknown은 결과, 실패는 별도 error와 result:null로 기록한다.
- `responses`에는 완전 성공한 사례만 들어간다. 부분 실패를 채점할 때는 기존 `evaluate.py`에 이 부분 목록만 넘기지 말고 `replay_score.py`를 사용한다. 그래야 재사용 성공까지 실패로 세지 않으며 누락·실패·불필요 유보·범위 부족을 항목당 한 오류로 집계한다.
- recordedLlmTransactionError는 요청과 결합된 **기록의** 완료·실패·미완료·거절을 포함한다. 실제 호출 확인이나 모델 정확도 인증이 아니다. 경로별 재사용/실패도 함께 보고하며 wholePipelineMeasured=false, actualModelPerformanceMeasured=false를 유지한다.
- 기존 파일은 덮어쓰지 않는다. 실행 입력·응답·채점 산출물은 `.harness/` 등 Git 제외 경로에 둔다. 모형 테스트의 정답 응답을 실측 결과로 등록하지 않는다.

## 실제 Java 실행 경로와 대조

운영 의미 실행은 [공유 AI 모듈](../../../ai/docs/README.md)의 `AnalysisService`를 사용한다. 이 폴더는 API 원천·개발 사례·오프라인 채점/재사용 재현 도구이며 운영 요청이 Python을 실행하지 않는다. 기존 기준표와 네 Schema 원본은 `apps/ai/contracts`로 이동했다. Java 테스트는 같은 5,083개 개발 자료의 계약·투영·복원을 대조하지만 정답을 서비스나 모델에 전달하지 않는다. 실행 서비스의 대역 테스트도 실제 정확도·HTTP/저장 완료를 증명하지 않는다.
