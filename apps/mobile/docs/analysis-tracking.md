## 3. 작업 흐름

1. 01-2 스냅샷(거래 페이지를 이미 합친 것)으로 2단계 묶음을 만든다. 후보 0개면 아무 호출 없이 끝(F)이다.
2. 묶음마다 현재 입력으로 `POST /analysis-results/query`를 먼저 해 `available`이면 재사용한다(EX-R, 모델 호출 0회).
3. 없으면 `POST /analysis-jobs`로 접수한다. 연결 저장 뒤 처음 공개된 범위는 `triggerKind: "A"`다. 기기 기록의 자료 버전과 달라진 스냅샷이면 `B`다.
4. 상태 응답이 `awaitingInput`·`submitInput`이면 받은 `permit`으로 `/input`을 한 번 제출한다.
5. `queued`는 약 3초마다, `running`은 `Prefer: wait=5`로 조회한다. 서버가 기다리지 않고 바로 답하면 약 1초 뒤 다시 묻는다. 429·503은 `Retry-After`만큼, 응답이 없으면 3초 뒤 다시 묻는다.
6. `succeeded`만으로 끝내지 않고 결과 조회로 `available`을 확인해야 분석 완료다. `partial`·`stale` 등은 실패로 보인다.
7. 서버가 다른 대표 `jobId`를 돌려주면 그 번호로 관찰하고 기기 기록도 바꾼다.
8. 작업마다 요청은 한 번에 하나다. 멈췄다 돌아와도 앞선 요청이 끝난 뒤에 다음 요청을 보낸다.

## 4. 멱등 키

| 요청             | 키                                                                         |
| ---------------- | -------------------------------------------------------------------------- |
| 접수             | 묶음마다 하나. 응답이 없으면 같은 키로 다시 보내 재확인한다                |
| 입력 제출        | 허가(`permit`)마다 하나. 같은 허가의 재확인은 같은 키, 허가가 바뀌면 새 키 |
| 사용자 다시 시도 | 누를 때마다 새 키                                                          |
| 복구 접수        | 새 키. `previousJobId`와 현재 `input`을 함께 보낸다                        |

## 5. 화면 상태

| 서버·추적 상태                                                            | 화면                                                                                              |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 접수 전·`queued`·`awaitingInput`·입력 전송 중·제출 응답 유실              | 준비 중: '분석을 준비하고 있어요. 잠시만 기다려 주세요.'                                          |
| 서버 응답이 `running` 이후를 알림                                         | 분석 중: '보통 3~5분 걸려요. 앱을 나가도 분석은 계속돼요. 나중에 돌아와 결과를 확인할 수 있어요.' |
| 분석 중 5분 지남(앱 시계)                                                 | '생각보다 오래 걸리고 있어요. 조금만 더 기다려주세요.'                                            |
| 결과 `available`                                                          | E(후보 있음)·F(후보 0개)                                                                          |
| `failed`·`cancelled`, 실행창 180초 경과, 결과 사용 불가, 보내지 못한 후보 | G: '내용 분석은 마치지 못했어요.' + 다시 시도(새 키로 `/retry`)                                   |
| `outcomeUnknown`                                                          | G-1: '분석 결과를 확인하지 못했어요.' + 다시 시도 → 확인 창 → `acknowledgeDuplicateRisk: true`    |
| `expired`이고 결과 조회로도 재사용할 결과 없음                            | G-2: '이전 요청이 만료됐어요.' + 다시 분석 → recovery 접수, '현재 거래 내역으로 다시 분석해요.'   |

- 묶음이 여럿이면 하나라도 진행 중일 때 기다리는 중이고, 모든 묶음이 입력 수신을 확인했거나 끝났을 때만 분석 중 문구다. 모두 끝나면 결과 불명 → 만료 → 실패 → 완료 순으로 대표 결과를 고른다.
- 설명 칸은 세 줄 높이로 고정해 단계가 바뀌어도 그림이 움직이지 않는다(글씨를 크게 키우면 늘어날 수 있다).
- 확인 창에는 비용을 쓰지 않는다. 서버 운영 비용이지 사용자에게 청구되는 비용이 아니다.

## 6. 기기 기록과 앱 나감·복귀

- 기록은 사용자별 `analysis-job.<userId>` 한 건이다. 담는 것: 자료 버전, 화면 세션 번호(`localSessionEpoch`, 처음 시작 시각 밀리초), 묶음별 입력 지문·`jobId`·접수 키. 분석 본문·거래 원문·`permit`·토큰은 담지 않는다.
- 백그라운드로 가면(`AppLifecycleListener.onHide`) 반복 조회를 멈춘다. 서버 작업은 취소하지 않는다. 돌아오면(`onShow`) 끝나지 않은 작업을 결과·상태 조회부터 다시 확인한다.
- 앱을 다시 켜면 홈에 들어가기 전에 기록이 있는지 본다. 있으면 분석 대기 화면부터 이어 보인다. 같은 자료 버전이면 기록의 작업을 상태 조회부터 잇고, 다르면 기록을 버리고 결과 조회 → 접수(`B`)로 새로 한다.
- '다음'을 누르면 그 사용자의 기록을 지운다. 로그아웃·세션 무효·기기 로그인 정보 지우기 때는 모든 사용자의 기록을 지운다.
- 서버가 더는 모르는 작업(403)이면 다시 시도 때 새 접수 키로 처음부터 한다. 가짜 서버 모드에서 앱을 다시 켜 메모리가 사라진 경우도 같다.

## 7. 확인 결과와 남은 확인

- 2026-11-05 테스트폰(SM-G988N)·실제 서버(`https://121.134.219.114`, mTLS)·데모감마
  - 로그인 세션으로 스냅샷과 거래 페이지를 끝까지 받았다(거래 1,825건). 탐지 결과는 반복 후보 5개, 묶음 1개다.
  - 준비 중 문구 뒤 서버 입력 수신 확인 후 분석 중 문구로 바뀌고, 실제 LLM 분석 결과가 완료(E)로 끝났다.
  - 다시 열면 결과 조회(`available`)만 하고 접수·LLM 호출 없이 바로 결과를 보였다(EX-R).
  - 데모감마는 월급 입금 확인이 없어 01-2 계산하기가 꺼져 있다. 그래서 로컬 전용 확인 진입(커밋 안 함)으로 같은 추적·API·화면을 열었다. 01-2 경로 자체는 에뮬레이터에서 확인했다.
- 에뮬레이터(가짜 분석 서버): 01-2 → 준비 중 → 분석 중 → 홈 나갔다 복귀 → E → 다음(기록 삭제) → 01-3을 확인했다. 분석 중 강제 종료 → 다시 켬 → 분석 대기부터 이어짐 → (가짜 서버 메모리 소실) G → 다시 시도 → E도 확인했다.
- 남은 확인
  - 실제 서버에서 분석 진행 중 홈 나갔다 오기, 강제 종료 후 다시 켜기. 저장 결과가 있으면 바로 재사용돼 진행 중 상태를 만들 수 없다.
  - 실패·결과 불명·만료(G·G-1·G-2)의 실제 서버 동작. 성현님 모의 서버 네 모드(success·unknown·invalid_once·timeout_once)로 확인한다. 앱 서버 설정(`ApiConfig`)은 https 주소만 받아, 모의 서버에 앱 화면으로 붙이려면 개발용 http 허용이 필요하다.
  - 01-2에서 계산 조건을 채우지 못해 '나중에 확인하고 홈으로'만 고를 수 있는 사용자는 첫 분석이 시작되지 않는다. 흐름 변경은 별도 결정이다.
- `Prefer: wait=5`는 통신 제한 시간(`PAYSE_API_TIMEOUT_SECONDS`, 확인 때 20초)이 5초보다 충분히 길어야 한다.
