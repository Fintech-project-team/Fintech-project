## 1. 점검 환경

| 기호 | 환경                   | 실행                                                                                                      | 확인할 수 있는 것                                                 |
| ---- | ---------------------- | --------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| E1   | 에뮬레이터 · 가짜 서버 | `flutter run`(서버 주소 없음). 세션·PIN·연결은 메모리에만 있다                                            | 화면 흐름·문구·입력 규칙·계산 표시. 앱 재시작 뒤 유지는 확인 불가 |
| E2   | 테스트폰 · 개발 서버   | `--dart-define=PAYSE_API_BASE_URL=…`([서버 연결](server-connection-plan.md)), 등록 기기 인증서(mTLS) 필요 | 실제 저장·재로그인 유지·동시 로그인 거절·재실행 뒤 복원·분석 작업 |

- 에뮬레이터는 기기 인증서가 없어 개발 서버에 붙지 않는다([기기 인증서](device-certificate.md)). 서버가 필요한 항목은 E2에서만 판정한다.
- E1에서 앱을 다시 시작하면 세션·연결이 사라지는 것은 가짜 모드의 알려진 한계다. 문제로 기록하지 않는다.
- 처음부터 끝까지 보는 점검이므로 `lib/main.dart`로 실행한다. 개발용 바로 진입 파일(`zz_dev_*`)로 본 결과는 메모에 그 사실을 적는다.
- 같은 계정도 환경에 따라 원본 사례가 다르다(아래 §3). 결과에는 환경을 꼭 적는다.

## 2. 결과와 문제 기록 방법

결과 칸에는 `정상`·`문제(번호)`·`미확인(이유)`·`해당 없음(이유)` 중 하나를 환경별로 적는다(예: `E1 정상 / E2 문제 Q-03`). 실행하지 못한 항목을 정상으로 적지 않는다.

문제는 §7 목록에 번호를 매기고, 같은 내용을 #236 댓글에 아래 양식으로 남긴다.

```text
[Q-번호] 한 줄 요약
- 체크리스트 항목: A-05
- 화면: 10-3 인증번호
- 환경: E2 테스트폰 · 개발 서버 · 데모베타 · 기준 커밋
- 재현 방법: 1) … 2) … 3) …
- 기대: (근거 문서와 절)
- 실제: (캡처·로그)
- 심각도: 치명 / 높음 / 보통 / 낮음
- 담당: B(앱) / A(서버·데이터) / 미정
```

| 심각도 | 기준                                                                         |
| ------ | ---------------------------------------------------------------------------- |
| 치명   | 다음 단계로 갈 수 없음, 쓸 수 있는 돈이 기대값과 다름, 다른 계정 정보가 보임 |
| 높음   | 금융 정보를 잘못 이해하게 하는 표시(실패를 0원으로, 저장 실패를 성공으로 등) |
| 보통   | 규칙과 다른 동작이지만 우회할 수 있음                                        |
| 낮음   | 문구·간격·정렬 등 시안과의 차이                                              |

서버·데이터가 원인이면 재현 방법과 경로를 적어 A 담당 이슈로 따로 연다. A는 4주간 LLM 작업에 집중하므로 처리는 후속 일정이다.

### E. 예외·중단 상황

A~D는 문서에 적힌 정상 규칙을 본다. E는 문서에 따로 적히지 않았더라도 서버를 부르는 모든 지점에서 연결이 끊기거나 서버가 응답하지 않을 때 앱이 버티는지 본다. 지점 목록은 앱 코드(`lib/data/`)의 서버 호출에서 뽑았다.

**방해 상황**

**모든 지점에 공통으로 기대하는 것**

1. 앱이 멈추거나 빈 화면·끝없는 로딩에 머물지 않는다.
2. 실패를 성공·0원·빈 목록·'거래 없음'으로 보이지 않는다(09-3). 이전 숫자를 최신처럼 보이지 않는다(09-1).
3. 입력한 내용이 사라지지 않는다. 다시 시도할 길이 있다.
4. 결과를 모르는 저장(X2)은 성공으로도 실패로도 단정하지 않고 '결과를 확인하지 못했어요'처럼 알린다. 다시 시도해도 같은 항목이 두 번 생기지 않는다.
5. 연타(X6)로 요청이 두 번 가거나 항목이 두 개 생기지 않는다.
6. 화면을 떠났다 돌아오거나(X7) 다시 켜도 진행 상태가 앞뒤가 맞는다. 늦게 온 응답이 다른 화면이나 다른 계정에 섞이지 않는다.
7. 세션이 끝나면(X5) 10-2 신규 로그인으로 안내한다(09-13). 금융 정보가 남아 보이지 않는다.

## 5. 점검 전에 알아둘 것

**문서끼리 어긋난 곳.** 점검 중 '규칙과 다름'으로 잘못 기록하지 않도록 최신 결정을 기준으로 본다. 문서 정리는 이번 점검 범위가 아니다.

- 12-1 카드사만 골랐을 때의 경고: 규칙 보완 §1에는 있지만 connection §6(2026-10-27)이 없앴다.
- 01-1 기본 선택: 화면 규칙은 '입출금 기본 선택', connection §6은 '처음 모두 미선택'(2026-10-27)이다.
- 홈 '월급 입금 확인하기' 버튼: design·overview 일부에 남아 있지만 PR #147이 없앴다.
- 이번 기간 내역 문구: 계좌·거래 §9의 입금 전·주기 미상 문구는 #194 이전 것이고, design 230행이 최신이다.
- 남겨둘 돈 규격: design 280행은 #205 이전 구조('연결한 예정 지출'·'n원 배정')이고, plan-tab §4가 최신이다.
- 10-4 세션 해제·월급일 변경 판정: 규칙 보완 §1·§2에는 아직 'A 확인'인데, #58 댓글에서 A가 답했다(A-24·B-26).

**PR에서 기기로 확인하지 못하고 남은 것.** 위젯 테스트로만 확인했으므로 이번 점검에서 먼저 본다.
