# 현재 MVP 다음의 확장 기준

현재 개발 기준은 [MVP v0.3](mvp-scope.md)다. 다음 단계는 사용자가 지정한 **예정 지출 입력·분류 LLM 보조**다. 미래 기능을 위한 빈 폴더·패키지·에이전트 프레임워크를 지금 만들지 않는다. 기능을 구현할 때만 계약·담당 경로·검사를 함께 연결한다.

## 바로 다음: 예정 지출 입력·분류 보조

| 경계            | 도입할 때 필요한 것                                                                             |
| --------------- | ----------------------------------------------------------------------------------------------- |
| 사용자 입력     | 지출 설명 문장, 기준일·시간대·대상 기간. F07 거래 수집을 선행 조건으로 두지 않음                |
| API의 후보 생성 | 선택한 제공자 1개와 검증된 JSON 출력. 비밀키는 서버에 보관                                      |
| 후보 표현       | 이름·금액·예정일·반복 의도·분류 제안, 입력의 근거, 모르는 값·확인 필요 상태                     |
| 사용자 확인     | 후보를 수정·확인·거절. 확인 전에는 계산에 차감하지 않음                                         |
| 기존 기능 연결  | 확인한 후보를 기존 F02 명령으로 검증·저장하고 F09 재계산. 지급·잔액 보정은 실행하지 않음        |
| 실패·변경       | 모델 오류·시간 초과·잘못된 JSON이면 입력 보존·수동 입력 유지. sourceVersion이 오래됐으면 재확인 |

제공자 선택과 프롬프트는 이 기능 착수 때 정하고 외부 SDK를 현재 추가하지 않는다. 여러 제공자를 동시에 구현하지 않는다. 추출 보조에 규칙을 사용하더라도 최종 금액 계산은 기존 결정적 계산 코드가 담당한다.

평가에는 합성 문장의 정상 추출, 날짜·금액이 모호한 입력, 분류 오류, 형식 오류, 실패 후 수동 입력, 확인 전 미반영, 확인 후 중복 저장 방지를 포함한다. 분류 체계는 F02의 새 필수 필드로 몰래 추가하지 않고 후보 메타데이터·저장 확장 필요를 그때 검토한다. 모델 응답의 지시를 코드 실행이나 확정 데이터 변경 명령으로 받아들이지 않는다.

## 그 이후: 선택 기능과 조건

| 기능                          | 현재 위치                                                   | 구현할 때 함께 결정할 것                                                                                                |
| ----------------------------- | ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| F07 자동 소비 반영            | MVP Should, 최종 제품 Must. 이번 최소 완료의 선행 조건 아님 | 합성 제공자·계좌 출금/체크카드·외부 ID·같은 금액의 예정 지출 매칭·중복 차감 방지. 금액이 다른 매칭은 최종 제품에서 검토 |
| F12 전체 자산                 | Should, 계좌 1개 잔고부터                                   | 홈의 쓸 수 있는 돈과 구분. 다계좌·자산 평가를 자동 포함하지 않음                                                        |
| F06 주간·사용 현황            | 현재 MVP 제외                                               | 월~일 경계·현재 기간과의 교집합·사용액 원천·일별 반올림·기준값. 수동 잔액 차이를 곧바로 소비로 추정하지 않음            |
| F11 자동 마감·이월            | 첫 월급일 이후, 현재 제외                                   | 자동 마감 기본값·요약·사용자 수정, 잔여 금액 처리·반복 재생성·오프라인 시점·중복 실행 방지                              |
| F13 별도 대비금               | 현재 제외                                                   | 인터뷰 후 F03의 비상금과 차이를 먼저 결정                                                                               |
| What-if·계좌별 배분·은행 링크 | 과거 확장 아이디어, 현재 Must 아님                          | 입력과 계산 영향·다계좌 의미·네이티브 경계·실제 이체와의 구분                                                           |
| 추가 수입·목표·추천·대화형 AI | 후속 선택                                                   | 현재 첫 기간/단일 계좌 계약과의 차이, 데이터 근거·사용자 확인·금액 결정 권한                                            |
| 실제 금융기관 연결·iOS 배포   | 별도 후속 범위                                              | 접근 동의·기관별 계약·플랫폼별 준비·기기 검증                                                                           |

## 호환성 원칙

- 저장 입력·후보·계산 결과를 구분한다. 확정 입력은 서버, 읽기 캐시는 기기라는 기존 원칙을 유지한다.
- stable ID, schemaVersion, 데이터 version, calculationVersion의 목적을 섞지 않는다. 이름·필드·화면 용어의 기준은 [contracts](contracts.md)와 [MVP 용어](mvp-scope.md)다.
- 지급 처리와 잔액 보정을 구분한 현재 명령을 유지한다. F07 거래 수집이 생겨도 이미 지급된 항목이나 수동 보정한 잔액을 두 번 반영하지 않는다.
- 기능은 공개한 경계로 연결한다. 새 경로는 실제 담당자·초기화 명세·policy.json과 동시에 맞추며 기존 역할 이름만 바꿔 범위를 우회하지 않는다.
- 계약 변경은 사례·소비자·저장 데이터 전환·오류 처리·필요한 검사를 함께 검토한다. 아직 없는 기능을 위한 추상화나 CI를 선행 구축하지 않는다.
- E2E 시스템·디자인 시스템은 사용자 요청에 따라 이후 진행한다. 이미 구현하는 기능의 필수 검사는 그대로 지키고 유효한 PASS는 재사용한다.
