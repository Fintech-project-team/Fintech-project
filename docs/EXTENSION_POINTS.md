# MVP 이후 기능 확장 기준

핵심 하네스가 지정한 필수 설계 문서다. 기능 추가 시 먼저 읽고 담당 경로·계약·검증 영향을 작업 명세에 반영한다. 아래는 확장 방향이며 아직 구현된 기능이 아니다.

## 1. 하나의 서비스 안에서 기능 모듈을 늘린다

처음에는 Expo 앱 + 앱 API + 별도 더미 서버를 유지한다. 새로운 사용자 기능은 mobile/src/features 아래 독립 폴더, 서버 동작은 api/src/modules 아래 모듈로 추가한다. 기능 추가만으로 새 서버·별도 DB·거대한 플러그인 프레임워크를 만들지 않는다. 실제 성능·운영 요구가 생겼을 때 분리한다.

| 확장 기능                     | 주 구현 위치                                            | 재사용할 것                          | 선행 결정·검증                                                |
| ----------------------------- | ------------------------------------------------------- | ------------------------------------ | ------------------------------------------------------------- |
| 수입 관리·저축 목표·미래 계획 | mobile features/income, goals 및 api modules/goals      | 확정 현금흐름·배분 계획·finance-core | 목표 기간, 저축 우선순위, 시나리오 가정, 기존 가용금액 회귀   |
| 일·주·월 예산과 소비 추적     | spending 하위 budget/history, 필요 시 독립 budgets 모듈 | 동일 스냅샷·소비 분류·계산 정책      | 달력 경계·수입/지출 확정 시점·계좌별 부족·합계 일치           |
| 대화형 AI                     | mobile features/chat, api modules/chat                  | 분석 결과·확정 계획·조회 서비스      | 읽기 전용 조회 도구, 근거 snapshotId, 모델 실패/비용 제한     |
| 규칙/범용 LLM/Jev 교체        | api infrastructure/analysis                             | 분석 입력·후보 출력 계약             | 같은 fixture 평가, timeout·미지원 기능·fallback 명시          |
| 실제 금융기관 연결            | api infrastructure/financial-providers                  | 정규화 contracts, 앱 화면            | 별도 권한/동의/인증·실제 제공자 계약 검증. MVP 구현 대상 아님 |
| iOS                           | mobile 및 플랫폼 어댑터                                 | feature 화면·contracts·finance-core  | Mac/Xcode, 서명, 링크/로그인/저장 동작별 실제 검증            |

위 경로는 추가 시점의 제안이다. 빈 미래 기능 폴더를 미리 대량 생성하지 않는다. 새 경로를 추가하면 소유권 정책과 검증 선택표를 같은 PR에서 갱신한다. 기존 담당 역할의 범위 밖이면 명시적으로 배정한다.

## 2. 지금 분리할 공통 경계

### 데이터 제공자

앱은 은행별 원본 응답을 모른다. api의 제공자 어댑터가 원본을 contracts의 정규화 스냅샷으로 바꾼다. mock-bank는 첫 제공자다. 계좌 식별자·외부 거래 ID·원천 종류·조회 시각을 보존하여 중복 수집과 기관 변경을 처리한다. 실제 금융사 API와 동일한 인증·스펙이라고 표현하지 않는다.

### 계산과 정책

finance-core는 기준 시각·계산 기간·스냅샷·확정 계획·정책 버전을 입력으로 받는다. 지금의 다음 월급일 범위를 화면 코드에 하드코딩하지 않는다. 일·주·월·장기 목표는 명시적 기간과 정책으로 확장한다. 결과에는 합계뿐 아니라 차감 근거·날짜별/계좌별 부족을 두어 화면별로 같은 숫자를 재사용한다.

장기 목표에서 쓰는 기대수익률·인플레이션 등은 별도의 시나리오 가정이다. 당장 쓸 수 있는 돈과 미래 예상 자산을 하나의 확정 잔액으로 섞지 않는다. MVP는 KRW 정수로 제한하며 이후 다중 통화는 환율 시점·반올림 정책까지 포함해 계약을 개정한다.

### 조회와 변경

계좌/분석/계획을 읽는 서비스와 사용자 계획을 바꾸는 명령을 구분한다. 대화형 AI의 첫 버전은 읽기 전용 도구만 호출한다. 향후 변경 제안을 지원해도 초안 제안→명시적 사용자 확인→기존 저장 API 순서를 사용하며 AI가 DB나 이체를 직접 실행하지 않는다.

### 저장

화면에서 DB나 SQLite를 직접 다루지 않고 저장 어댑터를 호출한다. 서버는 계획의 기준본, 기기는 읽기 캐시다. schemaVersion, record version, snapshotId, calculationVersion을 구분한다. DB 마이그레이션과 기기 캐시 버전을 분리하고 호환되지 않는 캐시는 재조회한다. 변경 충돌을 최근 저장 우선으로 조용히 덮지 않는다.

### 화면과 플랫폼

feature는 공개 export를 통해 라우터에 연결하고 다른 feature 내부 파일을 직접 참조하지 않는다. 라우터·공통 UI·API client는 통합 담당자가 관리한다. 은행 앱 링크, SecureStore, SQLite 같은 플랫폼 의존 기능을 어댑터로 분리하여 Android/iOS별 검증 지점을 드러낸다. 웹 미리보기 성공을 네이티브 기능의 검증으로 간주하지 않는다.

## 3. 계약을 바꿀 때 기존 기능을 보호한다

- 외부 공개 필드를 바로 삭제하거나 의미를 바꾸지 않는다. 선택 필드 추가→양쪽 소비자 반영→이전 형식 제거 순서를 정한다.
- 같은 저장소라도 설치된 이전 앱과 서버가 동시에 존재할 수 있다. 지원 버전과 업그레이드 안내/이전 응답 유지 정책을 결정한다.
- 새 feature는 contracts·finance-core 수정 필요 여부부터 확인한다. 공통 변경은 작은 선행 PR로 합친다.
- 기준 fixture를 유지하면서 확장 사례를 추가한다. 기존 normal/shortage/changed-expense 기대 결과가 바뀌면 정책 변경 이유를 기록한다.
- 정책/계약 변경은 현재 기능의 모든 소비자 검증을 실행한다. 통과를 위해 예전 기대값만 임의 수정하지 않는다.

## 4. 확장 PR 완료 조건

담당 경로·공개 인터페이스·데이터/계산 버전·마이그레이션·기존 기능 회귀·실패 시 복귀 방식을 설명한다. 새 명령은 package.json에 실제로 연결하고 policy.json/GATE_MATRIX에 누락 없이 반영한다. 제품 테스트가 없으면 검사기는 BLOCKED로 남겨야 한다.

확장 가능 구조를 정리한 것은 구현·성능·규제 준비가 끝났다는 뜻이 아니다. 먼저 최소 MVP의 두 흐름을 완성한 뒤 실제 필요에 맞춰 확장한다.
