# 기능 확장 기준

기능 추가 전에 이 문서를 읽고 변경할 경로·데이터 형식·검사를 작업 명세에 적는다. 아래 기능은 확장 계획이며 구현 완료 상태가 아니다.

## 추가 위치

Expo 앱, 앱 API, 별도 더미 서버 구조를 유지한다. 기능이 늘었다는 이유만으로 서버·DB를 분리하지 않는다.

| 기능                     | 추가할 위치                                 | 먼저 정할 것                                       |
| ------------------------ | ------------------------------------------- | -------------------------------------------------- |
| 수입·저축 목표·미래 계획 | mobile의 income/goals, api의 goals 모듈     | 기간·저축 우선순위·시나리오 가정                   |
| 일·주·월 예산            | spending의 budget/history 또는 budgets 모듈 | 날짜 경계·수입/지출 반영 시점·계좌별 부족          |
| 대화형 AI                | mobile과 api의 chat 모듈                    | 읽기 전용 조회·근거 snapshotId·모델 실패·비용 제한 |
| 규칙·범용 LLM·Jev 교체   | api의 infrastructure/analysis               | 같은 합성 데이터 평가·시간 초과·대체 처리          |
| 실제 금융 연결           | api의 infrastructure/financial-providers    | 권한·동의·인증·기관별 API 확인; MVP 범위 밖        |
| iOS                      | mobile과 플랫폼별 연결 코드                 | Mac/Xcode·서명·로그인·링크·저장 검증               |

위 경로는 제안이다. mobile 기능은 apps/mobile/src/features/, API 기능은 apps/api/src/modules/ 아래에 둔다.
빈 미래 기능 폴더를 미리 만들지 않는다. 새 경로는 담당자를 배정하고 policy.json과 검사 목록을 함께 갱신한다.
개발 관리자도 4명 기여자 중 한 명이다. 공통 변경을 조정하고 다른 기여자의 작업 범위를 존중한다.

## 기존 기능을 유지할 기준

- 앱에는 공통 데이터 형식을 전달한다. 기관별 원본은 api에서 contracts 형식으로 변환한다. mock-bank가 첫 데이터 제공자다.
- 계좌 ID·외부 거래 ID·원천 종류·조회 시각을 보존한다. 실제 금융사 API와 인증·형식이 같다고 주장하지 않는다.
- finance-core는 기준 시각·기간·스냅샷·확정 계획·계산 버전을 입력받는다. 다음 월급일 기간을 화면에 고정하지 않는다.
- 결과에 합계·차감 근거·날짜별/계좌별 부족을 포함해 여러 화면에서 같은 값을 사용한다.
- 기대수익률·물가상승률은 별도 가정이다. 미래 예상 자산을 지금 쓸 수 있는 확정 잔액에 섞지 않는다.
- MVP는 KRW 정수다. 다중 통화를 추가할 때 환율 시점과 반올림 규칙을 함께 정한다.
- 데이터 조회와 계획 변경을 구분한다. 대화형 AI는 처음에는 읽기 전용 조회만 한다.
- AI가 계획 변경을 제안할 경우 초안→사용자 확인→기존 저장 API 순서를 지킨다. DB나 이체를 직접 실행하지 않는다.
- 화면에서 DB·SQLite를 직접 호출하지 않는다. 서버는 확정 계획, 기기는 읽기 캐시를 저장한다.
- schemaVersion, 데이터 version, snapshotId, calculationVersion을 구분한다. 서버 DB 변경과 기기 캐시 변경을 따로 처리한다.
- 호환되지 않는 캐시는 다시 조회한다. 저장 충돌을 마지막 요청으로 조용히 덮지 않는다.
- 기능은 공개한 함수·컴포넌트로 연결한다. 다른 기능의 내부 파일을 직접 import하지 않는다.
- 라우터·공통 UI·API 클라이언트는 integration이 조정한다. 은행 링크·SecureStore·SQLite는 플랫폼별 연결 코드를 분리한다.
- 웹 미리보기 성공만으로 Android/iOS 기능 검증이 끝났다고 보고하지 않는다.

## 데이터 형식 변경과 검사

1. 공통 변경이 필요하면 작은 선행 PR로 통합한다. 필드 추가→앱·서버 반영→이전 형식 제거 순서를 정한다.
2. 이전 앱과 새 서버가 함께 쓰일 수 있으므로 지원 버전과 업데이트 안내 또는 이전 응답 유지 방법을 정한다.
3. normal/shortage/changed-expense 테스트용 데이터를 유지하고 새 사례를 추가한다. 기존 기대값 변경에는 정책 변경 이유를 적는다.
4. 바뀐 형식을 사용하는 모든 앱·서버를 검사한다. 통과하려고 기존 기대값만 바꾸지 않는다.
5. PR에 담당 경로·입출력·데이터/계산 버전·저장 데이터 변경 방법·기존 기능 검사·실패 시 복구 방법을 적는다.
6. 실제 검사 명령을 package.json과 policy.json/GATE_MATRIX에 연결한다. 필요한 검사가 없으면 BLOCKED로 보고한다.

먼저 최소 MVP의 사용 여유와 배분 흐름을 완성한다. 이 문서는 구현·성능·실제 금융 서비스 운영 준비의 완료를 뜻하지 않는다.
