# Java·Dart 분석 연동 합의

상태: **2026-11-04 사용자 결정 반영**. A는 서버·AI·공통 계약·공개 대조 사례·모의 공급자를, B는 모바일 입력 어댑터·지문·API 클라이언트·작업 추적·화면을 담당한다. 공유 순수 Dart 반복 계산은 이번 A 변경에 포함되므로 B의 1단계와 중복 구현하지 않는다. 이 문서는 [실행 계약](payse-execution-contract.md), [분석 API](../apps/api/docs/analysis-api.md), [의미 계약](../apps/api/docs/analysis-meaning.md)의 구체적인 공동 인수 기준이다.

## 1. 버전과 입출력

`PAYSE-ANALYSIS-1`, `PAYSE-MEANING-1`, 금융 `PAYSE-API-0.6-4`, 계산 `PAYSE-CALC-1`을 유지한다. 새로운 분석용 금융 Snapshot 필드를 추가하지 않는다.

| 자료           | 원본·역할                                                                                                                                                                                             |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 의미 입력·출력 | [기존 JSON Schema](../apps/ai/contracts/). `transactionMeaning`과 `recurringMeaning`은 서로 다른 타입이다.                                                                                            |
| HTTP 봉투      | [analysis-http.schema.json](../apps/api/contracts/analysis-http.schema.json)의 `$defs.acceptRequest`, `inputRequest`, `retryRequest`, `queryRequest`, `jobResponse`, `queryResponse`, `errorResponse` |
| 공동 지문 사례 | [identity-vectors.json](../apps/api/testing/protocol/fixtures/identity-vectors.json), 형식 `PAYSE-IDENTITY-VECTORS-1`                                                                                 |
| 실제 HTTP 예제 | [모의 서버](../apps/api/docs/analysis-mock.md)가 현재 합성 DB에 맞춰 만드는 비공개 `requests.json`                                                                                                    |
| 반복 계산·확인 | [공유 Dart 설명](../packages/payse_calculation/docs/recurring.md), [승인 저장 API](../apps/api/docs/recurring-recommendations.md)                                                                     |

필드 이름과 대소문자, 필수 여부, 타입을 그대로 맞춘다. 필수 nullable 필드는 `null`을 보내며 생략·빈 문자열·0으로 대체하지 않는다. `dataVersion`은 큰 정수를 보존하는 **10진 문자열**이고 원화·횟수·일자는 계약 범위의 정수다. `double`이나 지수 표기로 바꾸지 않는다. `asOf`는 서버 Snapshot 값을 보존하고 기기 현재 시각으로 교체하지 않는다. 동일 원천의 페이지를 모두 받은 뒤 같은 문맥으로 입력을 구성한다.

JSON Schema는 형식을 검사한다. 사용자 소유권·현재 공개 범위·버전·근거 관계·토큰/비용 한도·상태별 허가는 서버에서 별도로 검사한다. 스키마 통과가 실행 허가는 아니다. `reasonCodes`의 현 구현 허용값은 빈 배열이다. 알 수 없는 분류 코드를 가장 비슷한 값으로 바꾸지 않는다.

[공개 HTTP 예제 14개](../apps/api/testing/protocol/fixtures/http-examples.json)도 제공한다. 요청·진행 상태·성공/정상 유보·실패를 DTO와 화면 상태 파서에서 대조하는 자료다. ID/permit은 합성 설명값이며 실제 실행용 자격이 아니다.

## 2. 공통 입력 지문

B가 구현할 대상은 Java `AnalysisIdentity.hint(input)`의 **`inputHashHint`**다. 실제 DB 원천·사용자 범위·모델/프롬프트 버전까지 결합하는 서버 `analysisInputHash`와 같게 만들지 않는다. 힌트는 권한 확인이나 결과 재사용 검증을 대신하지 않는다.

정규화 프로필 `PAYSE-IDENTITY-1`은 다음을 따른다.

1. 모든 객체 키를 UTF-16 코드 단위 사전순(Java `String.compareTo`, Dart `String.compareTo`)으로 재귀 정렬한다. 키 사이 공백·개행 없이 JSON을 직렬화한다. 배열은 아래에서 **집합으로 지정한 것만** 정렬한다.
2. 문자열 원문·대소문자·공백·Unicode 조합 형태를 보존한다. NFC 변환·trim을 하지 않는다. JSON의 따옴표·역슬래시·제어 문자 이스케이프만 적용한다. 한국어·보조 평면 문자·U+2028은 UTF-8 원문으로 인코딩한다. BOM과 마지막 개행은 없다.
3. `null`, boolean, 정수를 그대로 보존한다. `sha256:` 뒤 UTF-8 바이트 SHA-256의 소문자 64자리 16진수를 붙인다.
4. 항목의 `memoryKey`는 거래 의미라면 `{kind: semanticTaskKind, target: targetTransactionId}`, 반복 의미라면 `{kind: semanticTaskKind, evidence: 직접 근거 ID를 정렬한 집합}`의 지문이다. 같은 의미 대상이 중복되면 입력 오류다.
5. 근거는 직접 근거에서 시작해 원거래 ID와 명시 관계의 양끝을 더 이상 늘지 않을 때까지 확장한다. 해당 ID의 `transactions`, `currentClassifications`, `unavailableReferences`를 각각 `transactionId`순으로 정렬한다. 연결 관계는 정규 JSON 문자열순으로 정렬한다. 다른 항목의 무관한 원천은 넣지 않는다.
6. 반복 항목의 `candidate`는 해당 후보에서 `candidateKey`, `sourceVersion`, `ruleVersion`만 제외한다. 직접 근거 ID와 `features.observedMonths`를 각각 정렬한다. 이름·제안 금액·제안 일자·다른 특징 값은 보존한다. 이 근거 객체의 지문이 `evidenceHash`다.
7. `{semanticTaskKind, items: [{memoryKey, evidenceHash}, ...]}`에서 items를 `memoryKey`순으로 정렬한 뒤 지문을 만든다. 이것이 `inputHashHint`다.

`itemKey`와 후보 임시 이름표, epoch/revision, 전체 `dataVersion`, 조회 시각만 바뀌어서는 같은 근거의 힌트가 바뀌지 않는다. 반대로 관련 원천 필드·관계·현재 분류·로컬 반복 특징이 달라지면 바뀐다. 문맥 변화의 유효성은 지문과 별도로 서버가 검사한다. 금액·날짜 등 서버에만 있는 원천 변화는 서버의 DB 결합 지문에서 추가로 검사한다.

각 사례는 `input`, `expected.canonicalInput`, `expected.items[]`의 `memoryKey/evidenceHash/canonicalEvidence`, `expected.canonicalHint`, `expected.inputHashHint`를 제공한다. `canonicalInput`은 직렬화 진단용이지 최종 힌트의 직접 해시 대상이 아니다. B는 최종 해시만 비교하지 말고 중간 결과도 대조한다.

독립 [Dart 참조 검사](../apps/api/testing/protocol/dart/check.dart)도 제공한다. 해당 디렉터리에서 `dart pub get`, `dart run check.dart`를 실행하면 실제 Dart 직렬화와 SHA-256으로 30개 전체 중간값을 대조한다. 테스트 도구의 crypto 의존성은 잠금 파일로 고정하며 모바일 의존성·DTO를 변경하지 않는다. B는 참조 결과와 별개로 **제품 코드의 지문 함수**에 같은 사례를 넣어 인수한다.

| 사례    | 검증 경계                                                       |
| ------- | --------------------------------------------------------------- |
| P01–P04 | 기본 한글, 객체 키 순서, itemKey 변경, 문맥만 변경              |
| P05–P12 | 공백·빈 문자열·null·이스케이프·Unicode 조합형·이모지·대소문자   |
| P13–P17 | 복수 항목, 입력 순서, 기존 분류, 본인 이체 관계 확장            |
| P18–P21 | 취소·환불 원거래, 원거래 미확보와 사유 차이                     |
| P22–P30 | 반복 근거, 임시 키, 순서, 이름·금액·일자·횟수·관찰 월·원천 버전 |

`sameHintAs`가 있는 쌍은 힌트 동일성을 함께 검사한다. P20/P21은 지문 대조용으로 유효한 공개 의미 입력이며, 실제 서버에서 미확보 원거래의 권한을 확인할 수 없는 경우 503으로 거절하는 현 정책을 우회하지 않는다. 벡터 생성 기대값을 클라이언트의 계산 결과로 덮어써서 통과시키지 않는다.

## 3. 작업 추적과 조회

화면과 분리된 tracker가 `jobId`, 현재 입력 문맥과 힌트, 요청별 멱등 키, 상태·다음 동작·결과 자격을 보관한다. 인증 토큰·permit·금융 본문을 평문 로그나 공유 사례에 넣지 않는다. 서버가 같은 작업을 합쳐 다른 `jobId`를 반환하면 **반환된 ID로 갱신**한다.

1. 새 로그인/앱 복귀 시 유효 세션과 현재 Snapshot을 확인한다. 현재 입력으로 결과 조회를 먼저 하고, 진행 중 ID가 있으면 상태를 조회한다. 옛 화면의 epoch/revision 응답은 화면에 채택하지 않는다.
2. 기존 EX-A/B 조건에서만 `POST /analysis-jobs`로 접수한다. `submitInput` 허가를 받은 뒤 해당 permit과 전체 최소 입력을 `/input`에 한 번 제출한다. 같은 요청의 전송 재확인은 같은 멱등 키, 사용자의 새로운 재시도는 새 키를 쓴다.
3. `queued`는 약 3초 간격, `running`은 `GET /analysis-jobs/{id}`에 `Prefer: wait=5`를 보낸다. 동시에 작업당 한 요청만 둔다. 완료 대기 미지원 서버의 즉시 `running` 응답은 약 1초 간격으로 조회한다. 네트워크 제한 응답은 서버의 재요청 안내를 존중한다.
4. 화면 이탈/백그라운드에서는 반복 조회를 중단한다. 이는 이미 제출·전송한 서버 작업의 취소가 아니다. 다시 열면 현재 인증/입력으로 조회부터 복원한다. 상태 `succeeded`만으로 결과 본문을 사용하지 말고 `/analysis-results/query`의 현재 자격을 확인한다.
5. `failed`/`outcomeUnknown`의 review 목록을 표시하고 사용자 **다시 시도** 또는 직접 확인·설정을 제공한다. 공급자 자동 재호출은 0이다. `outcomeUnknown` 재시도는 중복 과금 가능성 확인 후 `acknowledgeDuplicateRisk=true`가 필요하다. `expired` 복구는 기존 recovery 계약을 따른다.

5초는 상태 조회의 최대 대기 시간이다. 분석 완료 SLA나 큐 대기를 포함한 전체 응답 시간으로 표시하지 않는다. 클라이언트 읽기 타임아웃은 이 대기와 통신 여유보다 길게 설정한다.

| 구분                                                                 | 앱 처리                                                                           |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 로컬 완전 조회 + 반복 후보 0개                                       | 정상 0개. 빈 분석을 억지로 접수하지 않는다.                                       |
| `succeeded` + 사용 가능한 결과 + 의미 `unknown`                      | 분석은 완료. 해당 근거의 판단 유보·사용자 확인을 표시한다.                        |
| `failed` / `outcomeUnknown`                                          | 실행 실패/완료 불명. 0개로 표시하지 않는다. review로 재시도·직접 입력을 안내한다. |
| `partial` / `missing` / `stale` / `inactive` / `expired` / `deleted` | 결과의 현재 사용 자격. 성공 상태와 독립적으로 확인한다.                           |

앱 종료 전에 입력 제출을 마쳤고 서버가 살아 있는 동안에는 진행·저장 결과를 다시 받을 수 있다. 제출 전 종료, 서버 재시작, 인증/원천 변경까지 무조건 완료를 보장하지 않는다. 따라서 “앱을 나가도 계속 진행돼요”는 **입력 제출 후** 조건부 문구로만 사용한다. push 알림이나 서버 재시작 후 자동 공급자 재전송은 구현된 기능으로 안내하지 않는다.

## 4. 반복 후보와 이번 달 사용 가능 금액

공유 `detectRecurring`가 최근 달력 3개월, 서로 다른 달에서 3회 이상, 날짜 ±5일·금액 중앙값 ±10% 등 기존 계산 규칙을 적용하고 마지막 확인 금액을 제안한다. 과거 9개월로 최근 근거 부족을 채우거나 새로운 가중 점수를 만들지 않는다. AI는 후보의 의미·이름·이유·유보만 반환한다.

`reviewRecurring`는 현재 문맥과 근거를 대조한다. 이번 달 아직 관측되지 않은 직접 출금·미경과 일정·일정 금액·유효 AI 의미 후보를 우선 확인 목록에 둔다. 나머지는 정보 부족/추가 확인/카드 청구 영역을 구분한다. **사용자 승인 전에는 U에 반영하지 않는다.** 승인은 `/recurring-decisions`로 저장하고 새 Snapshot의 확정 계획만 `expandRecurring`와 기존 계산에 연결한다. 카드 구매 예상일을 현금 출금일로 바꾸지 않는다.

## 5. 공동 인수 순서

반복 후보 1단계는 공유 패키지에 준비한 `detectRecurring`·`reviewRecurring`·`expandRecurring`를 연결한다. B는 모바일 원천/DTO 매핑과 화면·추적을 담당하며 같은 계산 로직을 별도 모듈로 중복 구현하지 않는다. A의 승인 저장 API와 계산 패키지를 함께 적용할 때의 제약은 위 상세 문서를 따른다.

1. A의 실제 Java 테스트·독립 Python 참조·독립 Dart 참조로 공개 30개 벡터를 대조한다. B는 같은 파일을 자신의 제품 Dart 구현에 입력해 모든 중간 정규 문자열·지문을 비교한다.
2. A의 [모의 공급자](../apps/api/docs/analysis-mock.md)에서 성공·정상 유보·검증 실패·전송 후 완료 불명·사용자 재시도·결과 복원·인증 실패를 실제 HTTP로 확인한다.
3. B의 tracker에서 상태→동작→결과 자격을 독립 파싱하고 로그인 변경/늦은 응답/중복 접수/화면 재생성을 검사한다. A와 B가 같은 원천의 입력을 교환해 최종 비교한다.
4. 공동 연동이 통과한 뒤에만 실제 유료 모델·실기기로 확인한다. 모의 공급자 지연은 실제 LLM 속도·정확도의 증거가 아니다.

완료 범위와 검사 결과는 변경 보고에 구분한다. B의 제품 Dart 지문·앱 화면·실기기 인수는 A의 Java/모의 서버 검사만으로 완료 처리하지 않는다.

2026-11-04 A의 로컬 인수: 실제 Java·독립 Python·독립 Dart에서 공개 30개 전체 일치. 공개 HTTP 예제 14개와 형식/누락/타입 경계 검사 통과. 별도 PostgreSQL·실제 Spring HTTP에서 success/unknown/invalid_once/timeout_once 네 모드가 모두 통과했다. 각 모드에서 로그인·접수·입력·저장·결과 조회·재로그인 복원·무인증 거절을 확인했고, 실패 두 모드는 사용자 재시도 전 추가 시도 0·후 1회만 실행했다. 이 과정의 외부 공급자 호출은 0이다. 제품 Dart와 실제 기기의 공동 인수는 B에게 전달할 다음 단계다.

## 6. 프론트의 사용 가능 금액 연결 범위

이번 변경으로 **원천 조회 → 최근 3개월 반복 후보 → AI 의미 해석 → 사용자 승인 → 저장된 계획 재조회 → 순수 Dart 계산**을 연결할 수 있다. 서버와 공유 계산의 부품은 제공되며 실제 앱 연결을 완료한 상태는 아니다.

| 구간      | 제공 범위                                                                                           | 남은 연결                                                                          |
| --------- | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 후보·해석 | detectRecurring, 분석 HTTP/지문, reviewRecurring                                                    | B의 Snapshot/DTO 매핑, 작업 추적·재접속·실패 목록                                  |
| 확인·저장 | POST /recurring-decisions, 기존 Snapshot의 recurringPlans/recurringPlanRevisions/recurringDecisions | B의 금액·일자·출금 계좌 확인/승인 화면과 성공 후 Snapshot 교체                     |
| 금액 계산 | expandRecurring, 기존 calculateCurrentAmount                                                        | B가 승인 계획의 필요한 회차와 기존 의무를 중복 없이 합쳐 홈/미리보기 입력으로 전달 |
| 실행 서버 | 소스·격리 DB 검사 완료                                                                              | 승인된 배포 절차에서 새 JAR와 013_recurring_access.sql 적용, 실기기 공동 인수      |

2026-11-04 확인한 팀원 `hyeyeon-dev`의 #221에는 분석 대기 화면과 `AnalysisWaitSession` 경계가 있다. 실제 분석·승인 API 호출과 위 공유 계산 함수 연결은 해당 브랜치에도 아직 없다. 이 변경에서는 팀원 브랜치의 미통합 화면을 가져오거나 모바일 제품 파일을 수정하지 않는다.

사용자 확인 후 계산식은 기존 **U = B − E − (R − O)**다. B는 같은 asOf의 선택 계좌 잔액, E는 계산 구간의 승인된 미출금 의무 잔여액, R은 보호액, O는 보호액으로 충당하도록 명시 연결한 겹침이다. 이미 반영된 출금·취소·카드대금은 기존 규칙으로 중복을 제거한다. 예를 들어 B=1,000,000원, E=200,000원, R=100,000원, O=0원이면 U=700,000원이다. 아직 미승인인 50,000원 후보는 이 값에 넣지 않고, 승인 후 현재 구간의 미출금 의무로 연결되면 U=650,000원이 된다. 이는 계산 예시이며 특정 사용자의 결과가 아니다.

‘이번 달 후보’ 목록과 홈 U의 기간은 구분한다. 홈은 기존 급여 구간 규칙을 사용하므로 달력 말일까지 남은 돈으로 임의 변경하지 않는다. 계산 계좌·급여 구간·카드 청구·보호 설정·조회 완전성 등 필요한 입력이 없으면 정보 부족을 표시한다. 감마 초기 상태의 미설정 항목을 AI 추정만으로 확정하지 않는다.

새 반복 계획의 회차를 서버 의무로 저장해 지급 연결/보호금 배정 대상으로 삼는 후속 API와 향후 계획 편집·취소는 이번 신규 승인 API의 범위 밖이다. 현재 로컬 투영 ID를 기존 UUID 의무 API에 보내지 않는다. 해당 조작을 제공하려면 서버 작업도 추가로 필요하며, 프론트 화면 연결만으로 완료됐다고 표시하지 않는다.
