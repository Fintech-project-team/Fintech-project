# 앱 구조·의존성·상태 수명

이 문서는 최신 제품 범위를 구현하기 위한 구조 기준안이다. 폴더/클래스/라이브러리가 이미 생성됐다는 의미는 아니다. 제품 결정은 [제품 기준](product-baseline.md), 담당/문서 경로는 [2인 운영 기준](team-plan.md)을 따른다. 최신 업무표가 이전 로드맵의 서버 재계산 요구를 대체한다.

## 1. 의존성 방향

```text
Flutter bootstrap: 객체 생성·의존성 연결·수명 종료
  View → 기능 ViewModel/Controller
           ├─ 금융 Repository → API client / 보안 저장소 adapter
           └─ payse_calculation: 불변 입력 → 불변 결과

API bootstrap
  route → application service → Repository / 트랜잭션
                      ├─ 권한·필드·소유권·버전·배정 제약 검증
                      └─ LLM gateway → 외부 API

PostgreSQL: 원천 참조·확정 설정·사용자/세션·버전·변경 기록
```

화면이 DB·외부 LLM·보안 저장소에 직접 접근하지 않는다. 계산 패키지는 UI·HTTP·DB·LLM·전역 세션을 참조하지 않는다. 서로 다른 앱 기능의 ViewModel끼리 직접 호출하지 않는다. 여러 데이터가 필요한 작업은 작은 application service에서 조합한다.

Flutter 공식 가이드의 UI/데이터 분리와 의존성 주입 원칙을 적용한다. 별도 use-case 계층은 복합 작업에만 도입한다. 모든 필드 조회에 빈 전달 클래스·추상 팩토리·공통 BaseManager를 만드는 구조는 요구하지 않는다. [Flutter 아키텍처 권고](https://docs.flutter.dev/app-architecture/recommendations), [Flutter 구조 가이드](https://docs.flutter.dev/app-architecture/guide)

### PAYSE 응답 변환 경계

MVP의 준비 합성 JSON은 PAYSE 계약으로 직접 제공할 수 있다. 사용하지 않는 CODEF 중간 응답·별도 변환 서버를 만들지 않는다. 후속 실제 금융 연동에서는 공급자/조회 기능별 adapter가 필드·날짜·금액 단위·원천 상태를 PAYSE 계약으로 변환한다. 이는 형식 변환이며 U·연간 소비·반복 후보 수치·미래 잔액의 서버 계산이 아니다.

Flutter의 API client가 응답을 받고 FinancialRepository가 값 유무·버전·참조를 확인해 불변 앱 모델을 제공한다. 각 화면은 공급자 원문을 직접 해석하지 않는다. 로컬 계산 모듈에는 확인된 입력과 누락 상태를 전달하며 실패 값을 0으로 보정하지 않는다. API JSON·DB 테이블·Dart 클래스의 모양을 강제로 일치시키지 않는다.

같은 계약의 fake repository와 실제 서버 repository를 교체할 때 화면/계산의 금융 의미가 바뀌지 않아야 한다. 공통 형식 도입을 이유로 전역 싱글톤·거대 BaseManager·새 마이크로서비스·공급자별 화면 분기를 추가하지 않는다. LLM에는 기존 최소 입력만 전달하며 공통 금융 응답 전체를 자동 전송하지 않는다.

## 2. 싱글톤과 전역 상태 제한

| 대상                                              | 수명·생성 방식                                                                  | 금지할 방식                                                                                           |
| ------------------------------------------------- | ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| HTTP transport·보안 저장소 adapter·불변 환경 설정 | 앱 시작 지점에서 생성해 생성자로 전달. 필요하면 앱 수명 동안 한 인스턴스 재사용 | 각 화면의 `Service.instance`, 숨은 전역 조회, 사용자별 상태를 transport의 전역 헤더에 무조건 덮어쓰기 |
| 로그인 컨텍스트·금융 Repository·계정 스냅샷 캐시  | 인증 세션에 묶음. 로그아웃·탈퇴·세션 교체/종료 시 폐기                          | 앱 전체 static `currentAccount`, 계정 전환 뒤 남는 잔액/추천 캐시                                     |
| 화면/시트 ViewModel·입력 초안                     | 해당 화면 또는 기능 흐름 수명. 명시적으로 dispose                               | 모든 화면을 한 AppController에 넣거나 화면마다 금융 원본 복사본 유지                                  |
| 시뮬레이션/조정 초안                              | 기능 흐름 메모리. 확정 원본과 별도 불변 객체                                    | 전역 싱글톤·DB 자동 저장·기기 영구 복원                                                               |
| 계산 함수                                         | 상태 없는 함수. snapshot·ruleVersion·asOf·입력 전달                             | 내부 DateTime.now(), 전역 잔액, 임의 난수, DB 조회                                                    |
| API DB pool·LLM HTTP client                       | API 시작 시 생성·주입, 서비스 종료 시 닫음                                      | 요청별 계정/트랜잭션을 전역 서비스 필드에 저장                                                        |
| API 요청 컨텍스트·DB 트랜잭션                     | 요청/트랜잭션 범위                                                              | 서버 인메모리 로그인 플래그를 DB 대신 권위로 사용                                                     |

한 인스턴스 재사용과 전역 접근 가능한 싱글톤은 다르다. 생성 책임은 bootstrap에 모으고 사용하는 클래스는 필요한 인터페이스만 생성자로 받는다. 라이브러리를 쓰더라도 기능 코드가 어디서든 컨테이너에서 의존성을 찾아오는 service locator 방식은 피한다. 상태 관리·DI 패키지 이름은 아직 확정하지 않는다(C12).

핵심 객체를 두 개의 독립된 앱/세션 테스트 컨텍스트에 생성해도 잔액·PIN 시도 수·초안이 공유되지 않아야 한다. 리스너·타이머·스트림·진행 중 응답은 소유자가 종료할 때 해제하거나 결과 반영을 취소한다.

## 3. 상태의 단일 소유자

| 상태                  | 소유자                                                                   | 화면 갱신 원칙                                                            |
| --------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| 금융 원본/확정 설정   | 원본은 서버의 버전 있는 JSON 또는 DB, 확정 설정은 DB; 앱은 불변 Snapshot | 성공한 최신 스냅샷 하나에서 홈·계산 내역·계획 화면 파생                   |
| 원격 로그인 유효성    | 서버 DemoSession(userId 기준)                                            | 로컬 PIN 성공과 별개. 서버 거절을 PIN 성공으로 무시하지 않음              |
| 로컬 잠금             | LocalLockController                                                      | 네트워크 없이 PIN 확인. 사용자 활동·백그라운드 경과로 잠금 판정           |
| 예정 지출/보호액 입력 | 각 편집 ViewModel                                                        | Snapshot 복제 후 초안 계산. 저장 전 원본 캐시를 직접 변경하지 않음        |
| 소비 목록·결과        | SimulationViewModel                                                      | snapshotVersion/inputRevision/ruleVersion 및 세션 식별에 맞는 결과만 채택 |
| 금융사 동의·실패 연출 | ConnectionFlowController                                                 | 최종 성공 요청 전 서버 연결 상태를 성공으로 확정하지 않음                 |

ViewModel의 상태는 loading/ready/insufficient/error/saving 등 서로 구분 가능한 상태로 표현한다. `isLoading`, `isSuccess`, `isFailed`를 독립 플래그로 남발해 동시에 참이 되는 상태를 만들지 않는다. 구체 enum/타입은 상세 구현에서 정하되 빈 목록·0원·조회 실패·미계산을 같은 값으로 합치지 않는다.

## 4. 앱 수명·잠금·로그아웃

1. 앱 시작 시 보안 저장소의 세션·PIN 설정 존재 여부를 읽고 적절한 진입 화면을 정한다. 금융 데이터는 PIN 확인 후 재조회한다.
2. PIN 잠금은 열린 기능 흐름 위에 잠금 화면을 표시한다. ViewModel을 폐기하지 않아 잠금 해제 시 입력이 남는다. 인증 전 금융 화면을 그리거나 읽을 수 있는 접근성 트리에 남기지 않는다.
3. 앱 프로세스가 종료되면 메모리 초안도 사라진다. 재실행은 확정 데이터 복원이며 가상 시나리오 복원은 아니다.
4. 로그아웃·탈퇴 성공 시 세션 범위 객체·금융 캐시·추천·초안을 폐기한다. 종료 토큰은 삭제하고 재인증 전 금융 캐시를 노출하지 않는다. 탈퇴는 PIN 등 기기 계정 정보를 함께 삭제한다. 다른 계정의 늦은 응답을 현재 계정에 적용하지 않는다.
5. 잠금의 10분은 금융 스냅샷 시각과 별개다. 주입 가능한 활동 시계로 검사하고, 타이머 틱이 멈추는 백그라운드에서는 복귀 시 경과시간을 다시 판단한다.
6. 코드 화면의 3분 표시 타이머는 서버 세션 만료·PIN 잠금과 독립이다. 화면 종료 시 취소하고 0:00 이하로 내려가지 않는다.

일반 새 로그인과 같은 기기의 PIN 복구는 다른 동작이다. 사용자 답변 C01에 따라 유효한 기존 세션 토큰+그 사용자의 합성 이름·전화번호와 별도 코드로 재확인하고, 성공한 경우 로컬 PIN만 다시 설정한다. 새 세션을 만들거나 다른 기기의 세션을 종료하지 않는다. 복구 API 경로명은 상세 계약에서 정하되 deviceId만으로 복구를 허용하지 않는다.

## 5. 계산·비동기·성능

- 홈·연간 소비 집계·반복 후보 규칙·예정 지출 편집·모아둘 돈 편집·시뮬레이션·조정은 같은 로컬 계산 모듈을 호출한다. 위젯·서버 route에 산식을 복제하지 않는다.
- 입력 변경 즉시 예전 결과를 해제하거나 ‘이전 기준’으로 표시한다. 결과 적용 때 입력 revision·snapshot version·ruleVersion·현재 session을 모두 대조한다.
- 기본 계산은 순수 함수다. 상세 계획의 1,000거래/300미래이벤트/5소비/세구간 벡터로 기기 p95 100ms 목표를 측정한다. 이 수치는 보관 한도가 아니다.
- 계산으로 UI 지연이 측정되면 isolate를 사용한다. 데이터가 1년치라는 이유만으로 복잡한 worker pool·상시 isolate 서비스를 먼저 만들지 않는다. isolate로는 직렬화 가능한 불변 입력만 보내고 DB client·BuildContext·Repository를 전달하지 않는다. [Flutter 백그라운드 처리](https://docs.flutter.dev/cookbook/networking/background-parsing)
- `payse_calculation`은 Flutter에서 실행하는 순수 Dart 모듈이다. 서버에 같은 금액 엔진을 설치할 의무가 없다. 서버에는 저장 입력/참조 검증만 둔다. 서버 언어를 계산 공유 때문에 Dart로 강제하지 않는다.

## 6. API 확정·경합 제어

API는 최종 B/U 업로드를 금융 원천으로 받지 않는다. 세션 소유권·허용 필드·버전·참조·보호/정산 배정 한도를 검증한 뒤 승인 설정을 원자 저장한다. **서버에서 U·계좌 합산 결과·미래 잔액을 재계산하지 않는다.** 저장된 새 원천/설정을 받은 Flutter가 다시 계산한다. DB 제약에 필요한 합계 검사와 사용자 화면 금융 산출을 구분한다. [OWASP 입력 검증](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html)

계정당 활성 세션 하나는 DB 제약/트랜잭션으로 지킨다. 권고 구현은 `userId`에 대해 `endedAt IS NULL`인 행의 부분 UNIQUE와 원자적 발급이다. API 프로세스 싱글톤의 메모리 플래그로 구현하면 여러 요청/프로세스 사이에서 경합을 막을 수 없다. [PostgreSQL 부분 유일 인덱스](https://www.postgresql.org/docs/current/indexes-partial.html)

확정 쓰기는 계정 단위 버전 비교와 조건부 갱신 또는 동등한 행 잠금으로 경쟁 쓰기를 막는다. 계정/작업 범위의 멱등 키와 요청 내용 대조를 DB에 유지한다. 타임아웃 뒤 같은 요청은 같은 키로 확인하며, 원본 버전 변경 후 사용자가 다시 승인한 새 내용에는 새 키를 사용한다. eventId/의무 회차의 중복 방지는 멱등 키와 별도로 필요하다.

네트워크 성공과 저장 성공을 혼동하지 않는다. 커밋 후 응답 유실은 실패로 단정해 새 작업을 만들지 않고 동일 요청 확인/재조회로 처리한다. 클라이언트 한 번 클릭 방지는 보조이며 DB 중복 방지를 대체하지 않는다.

## 7. 표시 연출과 금융 데이터 분리

금융사 불러오기 확률·지연은 `DemoConnectionPresentationPolicy` 같은 별도 화면 정책에 둔다. 이 이름은 구조 예시이며 필수 클래스명이 아니다. 난수·지연 함수를 주입해 테스트에서 실패 기관을 재현할 수 있어야 한다. 공통 금융 계산 패키지에는 난수가 없어야 한다.

연출 완료/제외 목록 확정 후 `POST /institution-links` 한 논리 작업을 수행한다. 자동 다음 화면 이동도 API 성공 뒤에만 한다. 실제 요청 실패는 실제 오류다. 다시 시도 연출 성공을 실제 API 성공으로 바꾸지 않는다. 중복 탭·화면 재진입·응답 역전으로 연결 API를 여러 번 저장하지 않도록 흐름 상태와 멱등성을 적용한다.


이 경로는 새 구현의 권고 배치다. 기존 `packages/finance-core`와 둘 다 계산 권위를 갖도록 만들지 않는다. 실제 저장소 구조를 확인한 뒤 한 곳을 선택/대응시키고 공통 문서에 기록한다. 이미 운영되는 API를 무단 이동하거나 Node 골격을 Dart 앱 구현 완료로 간주하지 않는다.

총 2명이 공동 PM이다. A는 데이터·DB·API, B는 Flutter·UI·로컬 계산을 담당한다. 최신 업무표의 데이터/서버 업무 집중을 완화하도록 계산 구현 책임을 B로 조정했다. 공통 계약은 작성 담당과 영향을 받는 다른 담당자가 확인한다. 별도 PM 승인을 추가하지 않는다. 기능 세부 문서는 공통 계약을 링크하고 산식/금액 의미를 독자적으로 재정의하지 않는다.

## 9. 검토 기준

- 두 계정·두 앱 컨텍스트를 만들 때 mutable state가 공유되지 않는가?
- 로그아웃 뒤 이전 계산·HTTP·LLM 응답이 화면을 덮지 않는가?
- 잠금은 초안을 유지하고 실제 이탈은 초안을 지우는가?
- 같은 revision의 홈·계산 내역·미리보기와 저장 성공 후 새 스냅샷 기반 로컬 결과가 일치하는가?
- 두 동시 로그인/확정 요청에서도 DB 제약이 유지되는가?
- 화면용 난수·3분 타이머가 금융 계산·세션 만료에 영향을 주지 않는가?
- 순수 패키지를 UI·네트워크 없이 시험할 수 있는가?

캡슐화는 책임 분리다. 기기 코드의 절대 열람 불가를 보장하지 않는다. 난독화도 역공학 방지 보장이 아니므로 비밀 키는 API에만 둔다. [Flutter 난독화의 한계](https://docs.flutter.dev/deployment/obfuscate)

## 2026-10-19 공통 앱 초기화 범위

`apps/mobile/lib/main.dart`, `lib/app/`, `test/app/`와 Android/iOS 소스를 초기화했다. 이는 위 구조 기준을 구현할 시작점이며 Repository·ViewModel·순수 계산·제품 화면이 모두 완성됐다는 뜻은 아니다. 새 상태 관리·라우터·Service Locator 패키지는 추가하지 않았다. 기능과 공유 데이터 파일은 필요한 작업에서 생성하며 실제 역할·검사는 [Flutter 전환](harness/FLUTTER_TRANSITION.md)을 따른다.
