# MVP와 직후 LLM의 개발 구조

현재 목표는 [MVP v0.3](mvp-scope.md)의 **수동 입력 → 저장 → 쓸 수 있는 돈 계산·표시**다. Flutter 앱과 API의 경계, 앱 측 순수 계산, 서버 확정 데이터·기기 읽기 캐시라는 기존 원칙은 유지한다. 첫 MVP에 mock-bank·거래 수집·LLM·별도 배분 시뮬레이터를 필수로 연결하지 않는다.

## 단계별 흐름

1. **현재 Must:** 사용자가 월급일·급여 통장 잔액·예정 지출·모아둘 돈을 입력한다. 앱→API가 입력을 저장하고 앱의 순수 계산 코드가 홈·계산 내역·미리보기를 만든다.
2. **MVP 직후:** 사용자가 예정 지출 문장을 입력한다. 앱→API→LLM이 입력·분류 후보를 만들고 사용자가 확인하면 기존 예정 지출 저장 경로로 들어간다. 후보만으로 차감하거나 자동 지급 처리하지 않는다.
3. **선택 확장:** F07을 구현할 때 API→합성 금융 제공자(mock-bank)와 거래 매칭을 연결한다. F12·F11·다계좌·다른 AI 기능은 각각 별도 범위다.

기존 저장 원칙을 유지하기 위해 최소 API·저장 구현은 필요하다. 화면 개발은 같은 JSON 합성 사례로 병행할 수 있으나 메모리 대역의 성공을 서버 영속 저장 완료로 보고하지 않는다. 프레임워크·DB의 실제 선택은 초기화 명세에서 확정하며 이번 문서는 설치하지 않는다.

## 기능 경계 제안

| 영역                        | 현재 책임                              | 제한                                                                |
| --------------------------- | -------------------------------------- | ------------------------------------------------------------------- |
| onboarding / period         | 월급일·첫 기간·초기 입력               | 월급일 경계의 미결정 정책을 임의 확정하지 않음                      |
| balance                     | 급여 통장 잔액 입력·02-3 보정          | 보정 체크 금액을 새 잔액에서 재차 차감하지 않음                     |
| recurring / obligations     | 예정 지출 CRUD·03-1 지급 처리          | '반복' 이름이 자동 탐지·다음 기간 생성을 의미하지 않음              |
| spending                    | 홈·계산 내역·변경 미리보기             | F06 사용 현황·일/주 예산·What-if를 넣지 않음                        |
| allocation / reserved-funds | 모아둘 돈 CRUD                         | 역할·기존 폴더 이름을 독립 배분 탭·계좌 이체의 요구로 해석하지 않음 |
| shared / app                | 화면 이동·공통 UI·API·읽기 캐시        | 금융 계산식을 복사하거나 화면에서 저장소를 직접 호출하지 않음       |
| api                         | 확정 입력 저장·상태 전이·버전 검증     | 잔액과 지급 상태를 부분 저장하지 않음                               |
| contracts                   | JSON 데이터·명령·오류·언어별 검증 사례 | 앱·DB에 의존하지 않음                                               |
| finance-core 개념           | B−F−P와 계산 내역의 순수 계산          | UI·네트워크·DB·LLM·암묵적 현재 시각에 의존하지 않음                 |

위 표는 기능 경계 제안이다. 현재 저장소의 `apps/mobile/app/`·`src/`와 Node 패키지는 이전 골격이다. Dart 파일이나 새 폴더를 만드는 권한은 이 표가 아니라 실제 초기화 명세와 [역할 정책](ownership.md)에서 정한다. Flutter 경로·검사·계산 연결은 [전환 기준](harness/FLUTTER_TRANSITION.md)을 따른다.

기존 TypeScript finance-core/contracts를 Flutter에서 직접 import하지 않는다. 순수 계산을 Dart 어디에 둘지 초기화에서 결정하고 언어별로 계산을 중복 구현하지 않는다. API의 원자적인 지급·잔액 보정은 확정 입력 상태 전이이며, 화면 계산식의 서버 복제를 뜻하지 않는다.

## 저장·동시성·상태

- 확정 입력은 서버, 기기에는 마지막 확정 상태의 읽기 캐시를 둔다. SQLite나 상태 관리 패키지를 이번 문서에서 임의 지정하지 않는다.
- 미리보기는 임시 상태다. 저장 성공 후 관련 화면을 같은 version으로 갱신한다. 실패·충돌·오래된 입력을 구분한다.
- 03-1 지급 처리는 입력 잔액 차감+paid 전환, 02-3 보정은 잔액 덮어쓰기+paid 전환이다. [계산 규칙](calculation-rules.md)의 차이를 UI·API에서 보존한다.
- 앱을 다시 열어도 확정 입력을 조회할 수 있어야 한다. 월급일 자동 마감·이월이나 완전한 오프라인 동기화가 구현됐다는 뜻은 아니다.

## LLM을 붙일 경계

API 내부의 작은 지출 후보 생성 경계 뒤에 선택한 제공자를 둔다. 서버에서 키를 관리하고 입력·출력 스키마를 검증한다. 지금은 연결 위치와 후보/확정 항목의 구분만 정하며 범용 에이전트·벡터 DB·여러 제공자·MCP를 미리 구축하지 않는다.

후보에는 사용자 입력 근거와 확인 필요 항목을 남긴다. 사용자 확인 후 기존 F02 저장 경로를 사용하며, 후보 생성 실패 시 수동 입력으로 계속 진행한다. LLM 도입으로 계산 코드나 지급·잔액 보정 계약을 바꾸지 않는다. [확장 기준](EXTENSION_POINTS.md)과 [계약](contracts.md)을 함께 따른다.

E2E 자동화·디자인 시스템은 현재 별도 보류 상태다. 기존 스킬은 요청받은 작업에 적용하는 지침이며 시스템 구현 완료를 뜻하지 않는다.
