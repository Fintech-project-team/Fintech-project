# PAYSE-CALC-1 — 통합 계산 기준

근거: 로드맵 v8 공통 계산 규격, 상세 계획 v7 §1·§7, 기존 27개 결정 중 최신 자료가 대체하지 않은 항목, 사용자 후속 답변·M 결정·최신 업무표. 최신 업무표가 실행 위치에 우선한다. 구현 검증 작업은 [남은 설계 작업](open-decisions.md)으로 구분한다.

## 실행과 입력

계좌 합산·현재 금액·소비 집계·반복 후보 수치·미리보기·시뮬레이션·조정 비교는 순수 Dart로 기기에서 실행한다. 서버는 더미/설정 제공·LLM 해석·확정 입력의 저장 제약 검증을 담당하며 사용자 금액 결과를 계산하지 않는다. 계산 함수는 네트워크·DB·LLM·현재 기기 시각을 스스로 읽지 않는다.

불변 snapshot, asOf, ruleVersion, inputRevision, 선택 계좌, 급여/카드 일정 및 사용자가 확인한 가정을 입력으로 받는다. 같은 입력이면 같은 결과다. 통화 KRW, 업무 날짜 Asia/Seoul, 금액과 중간 합계의 절댓값 상한은 9,000,000,000,000원이다.

## 현재 금액

```text
B = 계산에 포함하는 계좌의 같은 기준시각 잔액 합계
E = 현재 계산 범위의 승인된 미출금 의무 잔여액 (중복 제거)
R = 포함 계좌에서 보호하도록 설정한 금액
O = E 중 R에서 충당하기로 명시적으로 연결된 예약 겹침
R_eff = R - O
U = B - E - R_eff
```

이전 P=E, S=U다. 이전 F를 보호 순차감액으로 쓸 때 F=R_eff다. 사용자가 설정한 모아둘 돈 총액은 R이며 O가 있으면 F와 R이 다르다. 화면에는 R과 겹침 O의 조정 근거를 구분한다.

- 입금 완료 급여는 B에 들어 있으므로 다시 더하지 않는다. 예정 급여는 현재 U에 더하지 않고 시뮬레이션 예정 이벤트로만 사용한다.
- 스냅샷 반영 거래 ID는 다시 재생하지 않는다. 기초잔액으로 재구성하는 방식과 스냅샷 방식은 혼합하지 않는다.
- 미승인 추천·취소 의무·정산 완료분은 E에서 제외한다. 일부 정산이면 남은 금액만 포함한다.
- 연체 미지급 의무를 기간 종료만으로 지급 완료 처리하거나 없애지 않는다. 시뮬레이션의 가상 정산은 실제 DB 지급 상태와 별개다.
- 연결은 의무/청구/정산/이체 식별 근거로 확인한다. 같은 금액·가맹점·날짜만으로 병합하지 않는다.
- 선택 계좌 사이 이체는 합계 B와 소비 총액을 바꾸지 않는다. 선택 밖 계좌로 이동하면 선택 범위 잔액은 변하지만 소비와 구분한다.
- 선택한 예금·적금도 B에 합산한다(C03). 유동성 판단으로 자동 제외하지 않으며 선택 밖 계좌는 합산하지 않는다. B/U는 실제 금융기관 출금 가능액 보증이 아니다.
- 제외 계좌 잔액을 B에서 뺀 뒤 그 계좌 보호액을 R에 다시 넣어 차감하지 않는다.
- M5 확정: 새 보호액/증액은 같은 계좌의 모든 R 합계 ≤ max(0, 해당 잔액), 전체 R 합계 ≤ max(0, 선택 B)를 **함께** 검사한다. 일부 계좌 초과를 다른 계좌 여유로 자동 상쇄하지 않는다. 기존 과대 보호액 감소는 허용한다. 음수 U나 R+E>B라는 사실만으로 저장을 거절하지 않는다.
- 잔액 감소만으로 R을 자동 축소하지 않는다. 명시 배정한 의무가 정산되면 해당 출금·E 정산·배정 R 해제를 함께 처리한다. 보호액을 줄이는 것만으로 B는 늘지 않는다.
- O는 해당 E 금액·R 금액 이하이며 한 의무에 여러 보호액을 배정한 합계도 의무 한도를 넘지 않아야 한다. 불명확한 연결로 임의 상계하지 않는다.
- 배정 한도는 **미해제 배정액 = 배정액 − 해제액**의 합계로 검사한다. 정산으로 이미 해제된 배정까지 현재 R/E 한도에 다시 넣지 않는다. R은 해제까지 반영한 현재 보호 설정이며, 원래 배정/해제 기록은 정정 근거로 보존한다.

## 시뮬레이션 구간

| 구간 | 범위     | 표시                |
| ---- | -------- | ------------------- |
| C1   | [t0, p1) | 다음 월급일까지     |
| C2   | [p1, p2) | 다다음 월급일까지   |
| C3   | [p2, p3) | 다다다음 월급일까지 |

p1~p3는 순서가 확인된/사용자가 가정한 급여일이다. 전체 종료 상한은 `min(p3, t0에서 달력 3개월 뒤)`다. 90일로 바꾸지 않으며 없는 월말 날짜는 말일 보정한다. 비정기 급여로 세 번째 구간이 잘리면 불완전 구간을 표시한다. 같은 세 개의 완전한 달 또는 현재 기간에 미래 세 주기를 추가하는 의미가 아니다.

구간의 오른쪽은 제외한다. p1 당일 입금/출금은 C2, p2는 C3, p3는 범위 밖이다. 종료값은 종료 직전 기준이다. 급여일 29~31일의 없는 날짜는 말일 예정일, 휴일 이동은 확인된 월별 일정만 사용한다.

**현재 홈의 입금 확인 전 처리와 미래 시뮬레이션의 예정 급여 처리는 구분한다.** 사용자의 후속 답변 C02를 다음처럼 적용한다.

1. 급여일 도달 후 실제 급여 입금 확인 전에는 급여일 당일·연체 미지급 예정 지출을 ‘입금 확인 후 반영 대기’로 분리하고 홈 E에 넣지 않는다. 해당 의무를 취소·지급 완료로 바꾸거나 삭제하지 않는다.
2. 월급 미입금이 이어지면 같은 대기 정책을 유지하고 미입금 상태·반영 대기 의무를 표시한다. 예정 급여를 B에 선가산하지 않는다.
3. 급여 입금이 스냅샷에서 확인되면 다음 급여일까지의 구간으로 전환한다. 반영 대기 의무의 미정산 잔여액과 새 구간 의무를 중복 없이 한 번 포함한다.
4. 실제로 출금이 확인돼 B가 줄었다면 그 원본 잔액을 유지한다. 이미 정산된 금액은 다시 E에 넣지 않는다. ‘급여 전 예정 지출 반영 보류’가 실제 출금 숨김·U 음수 강제 0원 처리를 의미하지 않는다.
5. 이전 날짜의 일반 연체 포함 원칙보다 이 급여 미입금 상태의 사용자 결정이 우선한다. 미래 비교는 확인된/가정된 급여 이벤트와 반열린 구간을 사용한다. 홈의 지난 급여일을 그대로 p1로 넣어 길이가 음수인 미래 구간을 생성하지 않는다. 새 급여 가정이 없으면 영향을 받는 미래 기간을 정보 부족으로 둔다.

급여 입금의 명시 거래 연결·부분 입금·confirmed 상태는 [공통 데이터 모델](data-model.md)의 v1.0 임시 합의를 따른다. ‘금액이 같으면 급여 입금’으로 추정하지 않는다.

## 입력·이월·시간 정밀도

- 소비는 1~5건, 양의 원화 정수, 유일 itemId, 이름·금액·구매일·결제 방식·필요 카드/출금일 근거를 포함한다. 0건이면 결과 해제, 6건은 제한한다.
- 구매일은 최대 종료 상한 전까지. 짧은 비교 기간을 선택해도 입력을 삭제하지 않고 현재 범위 밖임을 표시한다. 하루 평균/권장 생활비는 v1.0 계산 범위에 포함하지 않는다.
- 즉시출금은 구매일, 카드 일시불은 확인된 결제일에 현금 이벤트를 한 번 생성한다. 카드 승인일 현금 차감은 없다. 카드 구매일보다 결제일이 이르면 거절한다.
- 실제 시각이 있으면 그 시각을 사용한다. 날짜만 있으면 일 마감 순액으로 처리하며 일중 순서는 미정이다. 같은 날 입금/출금은 일중 부족 가능성만 경고하고 실제 최초 부족 시각·일중 최대액으로 확정하지 않는다.
- ‘기준일 구매는 스냅샷 이후’는 이미 반영된 거래를 재생하지 않기 위한 조건이지 정확한 결제 시각을 만들어내는 규칙이 아니다(C11).
- 이월할 값은 예상 현금 H와 남은 의무·보호 상태다. 예약을 이미 뺀 A를 기초잔액으로 이월해 다시 예약을 빼지 않는다. 음수 H도 그대로 이월한다.
- 반복은 확인된 주기/금액/예정일 또는 명시된 사용자 가정으로 필요한 회차만 생성한다. occurrence 식별로 기존 등록·청구·가상 생성 중복을 막는다. 월말 처리와 월간 계획 승인 범위는 [공통 데이터 모델](data-model.md)을 따른다.

## 미래 산식과 결과

```text
H(t) = B(t0) + 이후 예정 입금 - 이후 예정 출금
A(t) = H(t) - 남은 범위 내 지출 예약 - 남은 유효 보호액
남은 유효 보호액 = 남은 R - 남은 예약과 겹치는 O
차이(t) = A_allItems(t) - A_baseline(t)
```

A에도 U와 같은 O 겹침 보정을 적용한다. 가상 출금 때 H 감소와 의무 예약 해제를 같이 처리한다. 청구서 총액과 포함 승인 내역을 동시에 차감하지 않는다. 신규 가상 구매가 기존 청구에 포함되지 않았으면 별도 증분만 반영한다.

| 결과                     | 필수 의미                                                                                         |
| ------------------------ | ------------------------------------------------------------------------------------------------- |
| 기준                     | dataVersion/ruleVersion/inputRevision, 기준시각·기간·가정·정밀도                                  |
| 기간별 baseline/allItems | 시작 H, 종료 H, 종료 직전 A, 기간 중 최소 H/A, 차이                                               |
| 부족                     | 최초 확인 가능한 계획상/현금 부족 시점·금액, 최대 부족액, 주기 종료 결과                          |
| 최대 부족액              | 같은 관측/예측 지점 집합에서 max(0, −minA), max(0, −minH). 날짜만 있는 날은 일 마감 기준임을 명시 |
| 개별 영향                | 품목·구매일·출금일·반영 금액·귀속 기간·청구 근거                                                  |
| 한계                     | 미입력·미확정 근거, 범위 밖 의무, 잘린 구간, 일중 순서 불확정                                     |

최대 부족액은 위 결과 표의 필수 계약에 포함한다. 실제 일중 최대 부족을 계산했다고 표시하지 않는다. 현금 부족과 계획상 부족을 더해서 총부족액으로 만들지 않는다.

계좌별 결제 자금 부족은 최신 U2/D6에 따라 v0.8 P1이다. P0에서 합계가 충분하다고 개별 계좌 출금 성공을 보장하지 않는다.

필수 정보가 없으면 영향받는 금액은 null/insufficientData이며 0원이 아니다. 결제일 자체가 없어 어느 구간에 영향을 주는지 알 수 없으면 관련 전체 비교가 미완성이다. 기간 밖 결제는 미반영 의무로 안내하고 영향 없음으로 표현하지 않는다. 세 기간의 잔액/차이 행을 합산하지 않는다.

## 연간 소비와 반복 후보

- 확정 범위는 조회 시점까지 최근 달력1년, 동의·연결한 전체 계좌/카드다. 홈 선택 계좌와 독립이다. 전체 1년치 더미를 준비하며 실제 연동 조회 성능/가능성을 검증한 뜻은 아니다.
- 기간 경계의 구현 기준안은 `(asOf에서 달력1년 전, asOf]`다. 없는 2월29일은 해당 월 말일로 보정한다. 날짜만 있으면 시작 업무일 제외·종료 업무일까지 확보된 거래를 사용하고 시작/종료 월이 부분 월임을 표시한다. 최종 API/로컬 벡터에서 동일 경계를 사용한다.
- 구매·이용일을 알면 그 날짜로 집계한다. 판단할 수 없을 때만 근거 있는 통장 출금일로 대체하고 `dateBasis=withdrawalFallback`과 해당 거래 참조를 남긴다. 둘 다 미상이면 누락/미계산을 표시한다.
- 이미 인식한 구매의 환불은 **환불 반영일**에 음수 소비로 반영한다. 과거 구매를 지우고 같은 환불을 다시 빼는 이중 차감은 금지한다. 미성립 승인 취소와 이미 성립한 구매의 환불을 구별한다. 환불이 더 많으면 해당 기간 순소비액은 음수일 수 있다.
- 카드 구매와 대금 출금을 중복 소비로 세지 않는다. 구매내역이 없는 청구 총액을 여러 가상의 구매에 임의 배분하지 않는다. 확인된 중복/연결 근거로 처리하고 불명 자료는 누락·불확정 범위를 표시한다.
- 연간·월별 순소비액, 분석 대상·기간, 확보/누락 범위, 원천 근거와 날짜 대체 여부를 산출한다. 부분 자료 결과를 전체 소비라고 표현하거나 소비 원인·업종을 증거 없이 추정하지 않는다.
- 반복 탐지는 최근 달력3개월의 월간 반복, 정규화명 일치·3회 이상·월별 날짜 ±5일·중앙값 ±10%를 유지한다. 같은 달 유사 구매 3건을 월간 세 회차로 세지 않는지 검증한다. 예정액은 마지막 확인 금액이며 중앙값을 예정액으로 바꾸지 않는다.
- 정규화/그룹 의미는 LLM이 보조할 수 있다. 반환 후 실제 근거 ID로 로컬 규칙을 다시 검증하며 LLM이 임의 amount/dueDate를 생성하게 하지 않는다. 취소·중복·가격 변경·월말·일정 미상 사례로 사용 검증한다. 이 검증은 새 정책 재선택 요구가 아니다.

## 자동 지급 연결과 수동 정정 — M6 확정

1. 자동화는 원천 ID·명시된 청구/정산/더미 매핑으로 지급 연결을 제안/적용하는 기능이다. 동일 금액·날짜·이름만으로 실제 지급을 확정하지 않는다. 불명확하면 확인 필요로 남긴다.
2. 사용자는 PAYSE 내부의 잘못된 연결을 해제하거나 올바른 거래로 재연결할 수 있다. 계획 금액·예정일 등 사용자 입력도 수정 가능하다. **원천 계좌 잔액·카드 사용액·거래 금액/날짜/거래처는 수정 불가**다.
3. 부분 정산은 유효 배정액만 의무에서 해제한다. 하나의 출금을 여러 의무에 배정하더라도 출금 총액을 넘지 않으며, 한 의무에 중복 반영하지 않는다.
4. 잘못 연결한 거래를 해제하면 해당 잔여 의무를 복원한다. 그 연결 때문에 해제한 보호 배정도 기록 근거에 따라 복원한다. 이후 별도 변경이 있으면 덮어쓰지 않고 최신 버전 확인을 요구한다.
5. 이 복원은 새 보호금액 증액과 구별한다. 복원 뒤 보호 부족이 드러나면 표시하고 실제 잔액/거래를 조작하지 않는다. 관련 연결·배정·변경 기록·버전은 서버 한 트랜잭션으로 저장하고 Flutter가 새 스냅샷으로 U를 계산한다.
6. 자동 연결·수동 정정·재시도 모두 같은 경제적 거래/의무 식별을 사용한다. 같은 정정 재시도가 의무/보호액을 두 번 복원하면 안 된다.

정정 예: B=700,000원, 다른 지출을 월세300,000원 지급으로 오연결해 E=0, R=0이면 U=700,000원이다. 연결 해제 후 실제 B는 그대로이고 월세 E=300,000원이 복원되어 U=400,000원이다. 이는 원천 출금을 환불 처리한 결과가 아니다.

## 산술 예

| 사례                   | 산술·기대값                                         |
| ---------------------- | --------------------------------------------------- |
| 기본                   | 2,000,000 − 500,000 − 400,000 = 1,100,000           |
| 카드 300,000 정산      | 1,700,000 − 200,000 − 400,000 = 1,100,000           |
| 보호액과 같은 의무     | 1,000,000 − 300,000 − (300,000 − 300,000) = 700,000 |
| 위 의무 정산           | 700,000 − 0 − 0 = 700,000                           |
| 관리비 20,000 감소     | U = 1,120,000                                       |
| 보호 설정 100,000 감소 | U = 1,200,000, B 불변                               |

위 예시는 산술 기대값이며 실제 계산 패키지·API·기기 테스트 통과 근거가 아니다. TC-C06 등 과거 검토 결과는 [검토 이력](reconciliation-report.md)에서 확인한다.
