# MVP v0.3 계산과 상태 변경 규칙

기준은 [현재 MVP](mvp-scope.md)의 수동 입력·급여 통장 1개·첫 월급일 전 범위다. 아래 기본식과 두 잔액 변경 동작은 이번 구현·테스트 기준이다. 원문의 '미확정' 표는 사용자 인터뷰·프로토타입으로 검증할 가설 상태를 뜻하며, 명시된 기준식까지 개발자가 임의로 바꿔도 된다는 의미가 아니다.

## 기본 계산

`쓸 수 있는 돈 = B − F − P`

- B: 사용자가 입력하고 명세된 동작으로 갱신한 급여 통장 잔액.
- F: 현재 등록한 모아둘 돈 합계. 앱 안에서 확보하는 계획이며 실제 이체가 아니다.
- P: 이번 관리 기간의 예정 지출 중 **아직 안 나간 항목**의 합계. 이미 나간 항목은 제외한다.

같은 입력·계산 버전은 같은 결과를 만든다. 기준 시각과 관리 기간은 입력으로 받고 내부에서 현재 시각을 임의 조회하지 않는다. 금액은 KRW 정수이며 Node/JSON 경계의 안전한 정수 범위를 Dart에서도 검증한다. 기간 중 예상 최저 잔액·계좌별 부족·예상 소득·일/주 예산을 기본식에 추가하지 않는다.

카드 **대금**은 수동 예정 지출에 포함한다. 신용카드 **사용 거래 자동 반영**은 F07에서도 제외된 별개 범위다. F07 이전에는 소비 사용액을 따로 집계하지 않는다.

## 동작별 변경

| 동작                                 | 급여 통장 잔액 B   | 아직 안 나간 예정 지출 P  | 결과                                           |
| ------------------------------------ | ------------------ | ------------------------- | ---------------------------------------------- |
| 미지급 예정 지출 추가·금액 수정·삭제 | 유지               | 변경한 항목으로 다시 합산 | 새 B−F−P                                       |
| 모아둘 돈 추가·수정·삭제             | 유지               | 유지                      | 새 F로 재계산                                  |
| 03-1 이미 나갔어요, 금액 x           | B−x로 한 번 변경   | 해당 항목 제외, P−x       | 쓸 수 있는 돈 유지                             |
| 같은 지급 처리 재시도·중복 탭        | 재차 차감하지 않음 | 재차 반영하지 않음        | 첫 처리 결과 유지                              |
| 02-3 새 잔액 N과 이미 나간 항목 체크 | **N으로 덮어쓰기** | 선택한 미지급 항목을 제외 | **N−F−새 P**. 체크 금액을 N에서 다시 빼지 않음 |
| 저장 전 미리보기·취소·저장 실패      | 확정 상태 유지     | 확정 상태 유지            | 임시 결과와 저장 완료를 구분                   |

03-1은 '앱의 기록에 출금을 반영'하는 동작이다. 실제 은행 잔액을 조작하거나 이체를 실행하지 않는다. 순수 계산 함수는 입력 객체를 수정하지 않으며, 확정 입력의 상태 변경과 화면 계산을 구분한다.

02-3의 체크는 **사용자가 새로 입력한 잔액에 이미 반영된 출금**을 뜻한다. 이는 원문의 '현재 잔액으로 덮어쓰기'와 '그 사이 이미 나간 예정 지출 체크'를 함께 만족시키도록 구체화한 해석이며, 별도 프로토타입에서 확인한 동작은 아니다. UI 설명과 API 명령도 이 의미를 사용한다. 여러 항목과 잔액 갱신은 한 번의 저장 단위로 처리한다. 부분 성공·중복 차감·서로 다른 버전의 혼합을 허용하지 않는 계약은 [contracts](contracts.md)에 정리한다.

## 합성 예시와 확인할 불변 조건

원문 예시는 기준일 10/12, 다음 월급일 10/25다. 테스트에서는 연도·Asia/Seoul 기준 시각을 fixture에 명시해 실행 날짜와 분리한다.

| 사례                                                        |         B |       F |       P | 쓸 수 있는 돈 |
| ----------------------------------------------------------- | --------: | ------: | ------: | ------------: |
| 원문 기본: 구독 200,000 + 카드 대금 85,000                  | 1,715,000 | 500,000 | 285,000 |       930,000 |
| 03-1에서 구독 200,000을 이미 나갔어요 처리                  | 1,515,000 | 500,000 |  85,000 |       930,000 |
| 위 지급 처리를 다시 요청                                    | 1,515,000 | 500,000 |  85,000 |       930,000 |
| 기본 상태에서 02-3으로 잔액 1,500,000 입력 + 구독 지급 체크 | 1,500,000 | 500,000 |  85,000 |       915,000 |
| 기본 상태에서 미지급 카드 대금만 100,000으로 수정           | 1,715,000 | 500,000 | 300,000 |       915,000 |
| 기본 상태에서 모아둘 돈 합계만 600,000으로 수정             | 1,715,000 | 600,000 | 285,000 |       830,000 |
| 부족 사례                                                   |   100,000 |  80,000 |  50,000 |       -30,000 |

마지막 사례처럼 신용카드 자동 반영이 없어도 음수는 가능하다. 계산 결과를 임의로 0으로 바꾸지 않는다. 화면의 부족 안내 표현은 제품 확인이 필요하며, 테스트가 그 가설 검증까지 완료한 것은 아니다.

금액 변경·항목 제거, 중복 지급 요청, 02-3의 이미 지급된 항목 재선택, 저장 실패·충돌 시 원상태 유지, 입력 불변, 정수 범위를 관련 계층에서 검사한다. 지급 상태 전이는 서버 계약 테스트, 순수 계산은 실제 Dart 계산 패키지 테스트로 확인하고 언어를 중복 이식하지 않는다.

## 구현 전에 결정할 경계

| 항목         | 미결정 내용과 처리                                                                                                |
| ------------ | ----------------------------------------------------------------------------------------------------------------- |
| 월급일       | 29~31일·휴일 보정, 오늘이 월급일인 경우의 다음 날짜, 설정 후 월급일 변경 시 기간 재해석. 해당 로직 구현 전에 결정 |
| 기간 경계    | 다음 월급일 당일의 지출 포함 여부와 첫 월급일 도달 시 안내. F11 자동 마감·이월을 임의로 구현하지 않음             |
| 과거 예정일  | 날짜가 지났어도 자동 지급 처리하지 않음. 미지급 안내·허용 날짜 범위는 결정 필요                                   |
| 지급 후 편집 | 이미 나간 항목의 금액 수정·삭제·지급 취소 시 잔액 보정 규칙. 미지급 항목의 CRUD 규칙을 그대로 적용하지 않음       |
| 금액 입력    | 입력별 0원 허용·최소/최대 금액, 목적자금·지출이 잔액을 넘을 때 저장 제한 여부. 결과식의 음수와 입력 유효성을 구분 |
| 매월 반복    | 이번 항목에 반복 의도만 보관. 다음 기간 재생성·이월·잔여 목적자금 처리는 F11 단계에서 정의                        |
| 소득·분류    | 월급 외 소득 합산·분류별 금융 정책·목적자금 우선순위를 이번 식에 자동 추가하지 않음                               |

결정이 필요한 부분만 작업 명세에서 분리하고, 결정 없이 해당 동작을 완료로 보고하지 않는다. 모든 개발을 막거나 무관한 단순 작업에 전체 정책 재승인을 요구하지 않는다. 규칙 변경 시 이 문서·계약·계산 버전·합성 기대값과 결정 기록을 함께 갱신한다.
