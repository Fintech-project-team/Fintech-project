# 현재 MVP 데이터와 API 계약 초안

상태: **MVP v0.3 정합성을 반영한 구현 전 제안**. 아래 경로·필드의 실제 스키마는 초기화 작업에서 확정한다. 저장소에는 기존 API 구현이 없으며, 예전 스냅샷 수집·분석·배분 API 초안을 현재 필수 API로 사용하지 않는다. [기능 범위](mvp-scope.md)와 [계산·상태 변경](calculation-rules.md)이 동작의 기준이다.

## 공통 원칙

- 앱과 서버는 언어 독립 JSON 계약을 공유한다. Dart 모델·서버 타입·입력 검증은 같은 사례로 확인하며 TypeScript를 Flutter에 직접 import하지 않는다.
- KRW 안전한 정수, 날짜 YYYY-MM-DD, 시각 ISO 8601, 시간대 Asia/Seoul을 구분한다. 데이터 상태는 `schemaVersion`, `version`, `asOf`로 식별하고 계산 결과에는 `calculationVersion`을 남긴다.
- 서버는 **확정 입력**을 저장하고 앱의 순수 계산 코드가 쓸 수 있는 돈과 계산 내역을 만든다. LLM 응답이나 클라이언트가 보낸 계산 총액을 저장 기준으로 믿지 않는다.
- 상태 변경은 `expectedVersion`과 중복 요청을 식별할 `operationId`를 사용한다. 접근 가능한 사용자·데모 세션 범위는 서버에서 확인한다. 요청의 사용자 ID만으로 다른 데이터에 접근하게 하지 않는다.

## 최소 모델 제안

| 개념      | 필요한 정보와 제한                                                                                                 |
| --------- | ------------------------------------------------------------------------------------------------------------------ |
| 관리 기간 | 기간 식별자, 시작일, 다음 월급일, 시간대. 첫 월급일 이전만 현재 대상                                               |
| 급여 통장 | `accountId`, 입력 잔액, 입력 시점, 입력 출처(manual). 현재 1개                                                     |
| 예정 지출 | `obligationId`, 이름, 금액, 예정일, 매월 반복 의도, 상태(planned/paid). 이미 지급된 항목은 계산 차감 대상에서 제외 |
| 모아둘 돈 | `fundId`, 이름, 금액. 실제 계좌 간 이체·배분 주문이 아님                                                           |
| 상태 버전 | 현재 확정 입력을 함께 읽고 갱신하는 `version`. 화면마다 서로 다른 버전의 합계를 섞지 않음                          |
| 오류      | `code`, `message`, `requestId`. 필드 유효성 오류·버전 충돌·저장 실패를 구분                                        |

LLM 직후 단계의 분류 후보를 준비하더라도 분류 필드를 현재 F02 필수 입력으로 늘리지 않는다. 거래 ID·기관 원문·외부 거래 매칭은 F07을 구현할 때 추가한다. 다음 표는 경로 제안이며 실제 명세 확정이나 배포 완료를 뜻하지 않는다.

| 요청 제안                                         | 목적                                                              |
| ------------------------------------------------- | ----------------------------------------------------------------- |
| GET /health                                       | 서버 상태                                                         |
| GET /v1/mvp-state                                 | 현재 기간·급여 통장·예정 지출·모아둘 돈의 일관된 상태 조회        |
| PUT /v1/mvp-state/setup                           | 온보딩 입력을 하나의 초기 상태로 저장                             |
| POST/PATCH/DELETE /v1/obligations[/:obligationId] | 미지급 예정 지출 생성·수정·삭제                                   |
| POST /v1/obligations/:obligationId/mark-paid      | 03-1 지급 상태와 앱의 입력 잔액을 원자적으로 변경                 |
| PUT /v1/salary-account/balance-reconciliation     | 02-3 새 잔액으로 덮어쓰기 + 이미 나간 항목 체크를 원자적으로 저장 |
| POST/PATCH/DELETE /v1/reserved-funds[/:fundId]    | 모아둘 돈 생성·수정·삭제                                          |

목록의 대괄호 표기는 문서상 생성/개별 대상 경로를 줄인 표현이다. 구현 시 메서드별 실제 스키마를 분리한다. 월급일 변경 API와 지급 후 항목 편집은 관련 미결정 규칙을 먼저 확정한다.

## 두 잔액 변경 명령을 섞지 않기

**mark-paid:** 현재 저장된 미지급 항목의 금액 x를 사용한다. 지급 상태 전환과 입력 잔액 B−x를 한 트랜잭션으로 저장한다. 클라이언트가 임의로 보낸 차감 금액을 쓰지 않는다. 같은 operationId 재시도는 기존 결과를 반환하고 추가 차감하지 않는다. 이미 지급된 항목에 새 요청이 와도 재차 차감하지 않는다.

**balance-reconciliation:** 새 잔액 N과 `paidObligationIds`를 함께 받는다. N은 선택한 출금이 이미 반영된 현재 값이므로 잔액을 N으로 저장하고 선택한 미지급 항목은 paid로 바꾼다. **N에서 체크 금액을 다시 빼지 않는다.** 중복 ID는 상태 변경을 반복하지 않으며 다른 기간·사용자 또는 없는 항목은 저장 전에 검증한다.

두 명령은 잔액 변경과 상태 변경 중 하나만 성공해서는 안 된다. 오류 시 전체 확정 상태를 유지한다. 이미 처리한 operationId는 먼저 기존 결과를 확인하고, 새로운 operationId의 오래된 expectedVersion은 409로 처리한다. 같은 operationId를 다른 내용에 재사용한 경우도 새 변경으로 실행하지 않는다.

서버 확정 입력과 분리된 미리보기는 취소할 수 있어야 한다. 저장 성공 뒤 반환한 상태·version으로 전체 관련 화면을 갱신한다. 실패를 saved로 표시하지 않고, 409는 재조회·재적용을 안내한다. 자동 마지막 쓰기 덮어쓰기를 하지 않는다.

## MVP 직후 LLM 입력·분류 보조

사용자가 요청한 첫 LLM 기능은 **예정 지출 입력·분류를 돕고 사용자가 확인하는 기능**이다. 거래 수집 없이 사용자가 제공한 문장을 입력으로 삼을 수 있다. 현재 Must 구현에 모델·키·프롬프트·새 API를 미리 추가하지 않는다.

후속 초안은 `POST /v1/expense-drafts`처럼 확정 항목과 분리한다. 입력에는 사용자 텍스트, 기준일·시간대, 대상 기간과 `sourceVersion`을 포함한다. 응답 후보에는 후보 식별자, 추출한 이름·금액·예정일·반복 의도·분류 제안, 입력의 근거 구간과 확인 필요 항목을 둔다. 분류 체계·최대 입력·스키마 상세는 이 기능 착수 시 정한다.

모르는 날짜·금액을 확정값으로 채우지 않는다. 후보는 아직 F04 차감 대상이 아니다. 사용자가 수정·확인한 뒤 일반 F02 명령과 같은 서버 검증·중복 방지·저장 과정을 거치고 F09로 재계산한다. 후보 확인 시 sourceVersion이 오래됐으면 최신 입력과 기간을 다시 확인한다. 거절한 후보·모델 오류·시간 초과는 기존 입력을 변경하지 않으며 수동 입력 경로를 유지한다.

모델은 확정 데이터 직접 저장, 지급 처리, 잔액 변경, 이체, 최종 금액 계산 권한을 갖지 않는다. 모델별 confidence를 같은 확률로 취급하지 않는다. 제공자 교체는 후보 입력·출력 경계 뒤에서 처리하며 여러 제공자를 현재 동시에 구현하지 않는다.

## 확장과 호환성

F07의 계좌 자동 반영·거래 매칭은 별도 수집 경계에서 현재 수동 입력 계약에 연결한다. 그때 외부 거래 ID·원천·수집 시점·중복 반영 방지와 수동 보정 충돌을 정의한다. mock-bank는 이 선택 기능의 합성 제공자이며 현재 Must의 필수 서버가 아니다. 기관 인증·실제 금융사 연결을 이미 구현했다고 설명하지 않는다.

기존 contracts는 빈 Node 골격이므로 이번은 문서 초안 정정이다. 배포된 계약·저장 데이터의 마이그레이션을 수행한 것이 아니다. 구현 이후의 호환되지 않는 변경은 schemaVersion·기존 데이터 처리·소비자별 검사와 함께 검토한다. 개인정보·키·원문 전체를 디버그 로그나 fixture에 넣지 않는다.
