# 데이터·API 기초 계약

개정일 2026-10-18. [최신 업무표](references/work-brief.source.md)와 후속 직접 결정(CODEF는 참고, PAYSE 공통 형식 사용)을 반영한 설계 기초다. 실제 JSON Schema·OpenAPI·SQL DDL 완성본은 아니다. 데이터 소유권·계산 위치·저장 경계는 확정이며 경로명·물리 분할은 아래 권장안을 담당자끼리 확인한다.

## 데이터 경계와 서버 책임

```text
서버: 사용자별 PAYSE 공통 계약의 합성 금융 데이터 + 연결 메타데이터 + 확정 설정
   → 버전 있는 Snapshot / 거래 페이지
Flutter: 불변 domain model → 로컬 규칙·금액 계산 → 화면
Flutter의 필요한 근거 → 서버 LLM 게이트웨이 → 해석 결과 → 로컬 검증·계산
사용자가 확정한 설정/연결 → 서버 권한·입력·제약 검증 → DB 영속화 → 새 Snapshot
```

서버는 U·시뮬레이션 결과·소비 집계액을 응답의 계산 권위로 제공하지 않는다. 로컬 산출 금액을 DB 원천처럼 저장하지도 않는다. 권한·버전·참조·잔여 지급 연결 한도·보호 설정 한도를 검증하는 일은 저장 무결성을 위한 서버 책임이다. 인증된 사용자만 저장한다는 조건과 금융 계산 위치를 혼동하지 않는다.

CODEF는 금융 데이터 항목을 검토하는 참고 자료다. MVP에서 CODEF를 호출하거나 그 응답을 복제할 의무는 없다. 실제 금융 API 공급자는 미정이다. 공급자가 정해지면 해당 공식 응답·인증·조회 기간·페이지·정정 규칙을 검증하고 PAYSE 계약으로 변환한다. 내부 ID·연결 메타데이터를 외부 공급자의 공식 필드라고 표시하지 않는다.

## 식별·인증 권장 설계

최신 자료의 ‘간단한 인증 방식 제안’에 대한 권장안이다. 기존에 확정한 단일 세션·로컬 PIN·입력 수명을 유지하며 식별 필드는 이름/전화번호로 줄인다.

1. 서버가 데모 사용자 생성 시 무작위 내부 `userId`를 한 번 발급한다. 합성 이름/전화번호, 별도 코드 검증값을 시드로 연결한다. 전화번호·이름 또는 이들의 단순 해시를 기본키로 삼지 않는다.
2. 정규화된 합성 이름·전화번호는 조회 입력일 뿐이다. 별도 테스트 코드까지 검증하기 전 금융 자료·사용자 설정·토큰을 반환하지 않는다. 중복 매핑/모호한 매칭이면 첫 계정을 임의 선택하지 않는다.
3. 기존 고정 6자리 데모 코드를 재사용하는 안이다. 짧은 고정 코드는 실서비스 인증 수준이 아니며 시도 제한·검증값 보호·전송 보호를 적용한다. 주민번호/통신사 대조나 실제 SMS를 요구하지 않는다.
4. 로그인마다 userId를 새로 만들지 않는다. 활성 세션이 없을 때만 세션 발급; 이미 있으면 기존 로그인 유지·새 로그인 거절. PIN은 로컬 잠금이므로 서버 인증을 대신하지 않는다.
5. 모든 금융 읽기/쓰기는 세션의 userId로 제한한다. 경로의 accountId/reserveId 등이 같은 사용자 소유인지 확인한다. 요청 본문 userId·deviceId를 소유권 근거로 신뢰하지 않는다.
6. 유효 토큰의 PIN 복구는 현재 userId와 식별 입력/코드를 대조하고 새 세션 없이 재확인만 한다. 종료/분실 토큰은 식별 입력부터 신규 로그인한다.
7. 서버의 제출 입력은 요청 처리 뒤 지속 저장하지 않는다. 앱은 실패 재시도 동안 현재 인증 흐름 메모리에만 유지하고 성공/취소/이탈/프로세스 종료에 폐기한다.
8. 동일 데모 자격을 공유한 사람들은 같은 userId다. 개인별 데이터 격리가 필요한 시나리오는 각자 다른 데모 자격을 배정한다. 계정 수는 개발 중 결정한다.

세션 토큰은 충분한 무작위값, 서버에는 검증용 해시, 기기에는 보안 저장소를 사용하는 안이다. PIN 원문·검증값을 서버에 보내지 않는다. 코드의 느린 해시/추가 비밀값 등 정확한 구현은 인증 상세에서 정한다. 해시는 복호화 수단이 아니며, 필요한 암호화 키를 앱 코드·DB와 함께 평문으로 두지 않는다. [OWASP 세션 지침](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

## 공통 전달 형식과 확정된 의미

API는 언어 독립 JSON으로 전달한다. 아래 필드명은 기존 논리 모델과 DB 후보를 연결하는 계약 기초이며, 새 금융 기능을 추가하지 않는다. 실행 가능한 JSON Schema·OpenAPI와 엔드포인트별 완전한 응답은 아직 작성하지 않았다. 구체 상태 코드·페이지 키·기관 코드 목록은 [남은 설계 작업](open-decisions.md)의 구현 항목이다. 서버와 Flutter가 다른 이름·의미를 독자적으로 사용하지 않도록 A가 작성하고 B가 확인한다.

### 공통 타입·값 유무

- 내부 ID는 UUID 문자열, 원천 참조는 문자열이다. 내부 ID와 기관의 계좌번호·승인번호를 같은 식별자로 사용하지 않는다.
- 금액은 KRW 정수다. 단일 값과 중간 합계의 절댓값 상한은 9,000,000,000,000원이다. 방향이 있는 거래 금액은 비음수 크기이며 방향을 따로 해석한다. 잔액의 음수는 허용한다.
- 업무 날짜는 `YYYY-MM-DD`, 확인된 시각은 시간대 오프셋이 있는 시각 문자열이다. 업무 날짜 해석은 Asia/Seoul이다. 날짜만 확인한 거래에 자정이나 임의 시각을 생성하지 않는다.
- `0`은 확인된 0원이다. 조회 실패·미연결·날짜 미상·미계산을 `0`으로 보내지 않는다. `null` 허용 필드는 값 미확인을 뜻하며, 해당 객체 자체가 미조회인 상태와 구분한다.
- 빈 배열은 조회 상태와 함께 해석한다. 완전 조회에서 `[]`이면 해당 범위의 항목이 0개다. 부분 조회·실패의 `[]`를 거래 없음으로 해석하지 않는다.
- 정상 계산용 계좌에는 확인된 잔액·기준시각이 필요하다. 이 값이 없으면 해당 계좌의 조회 실패/정보 부족을 전달하고 영향받는 합계·계산을 완전한 결과로 표시하지 않는다. 이 요구만으로 DB의 금액 컬럼을 일괄 nullable로 바꾸지 않는다.

| 청구      | `amountKRW`, `dueDate`                                        | 확인된 청구 금액, 확인된 결제 예정일 또는 null                                             | 청구 금액과 포함 사용 내역을 중복 차감하지 않음. 일자 미상 시 해당 미래 비교 제한                   |
| 청구      | `includedTransactionRefs`                                     | 확보한 포함 거래 참조 배열. 명세의 완전/부분/미제공 여부를 함께 전달                       | 같은 사용자/카드 참조인지 검증. 배열만으로 명세 완전성을 판단하지 않음                              |

가맹점·거래 설명·상품 표시명 등 원천에 있는 표시 정보는 의미와 출처를 보존해 전달한다. 이 표에 없다는 이유로 원천 정보를 삭제하지 않는다. 반대로 외부 공급자가 제공하지 않는 값을 정상 원천 사실로 채우지 않는다. 정확한 표시 필드와 코드 목록은 화면 요구값을 기준으로 #17/#20에서 정한다.

### 버전·조회 범위·관계

- `dataVersion`은 사용자 금융 자료·확정 설정을 함께 해석하는 버전이다. 원천/설정/연결이 바뀌는 저장은 새 버전을 반환한다. 단순 페이지 조회로 자료 버전을 바꾸지 않는다.
- `sourceVersion`은 준비 금융 자료의 버전, `ruleVersion`은 로컬 계산 규칙 버전이다. 계산 규칙 변경을 원천 거래 변경으로 표시하지 않는다.
- `asOf`는 계산 기준시각이다. 각 잔액의 기준과 자료 버전이 맞는지 확인한다. 수집 시각을 잔액 기준시각으로 바꾸지 않는다.
- 조회 범위에는 대상 계좌/카드, 요청 기간, 실제 확보 기간, 누락 범위, 조회 성공·부분·실패·미연결의 구분이 필요하다. 이를 표현할 정확한 JSON 키·상태 코드는 #20의 산출물이며 여기서 임의 코드값을 확정하지 않는다.
- 페이지가 나뉘어도 같은 자료 버전으로 조회한다. 중간에 버전이 바뀌면 다른 버전의 페이지를 섞어 완전한 연간 집계로 표시하지 않는다.
- `snapshotId`를 별도로 추가하는 것은 필수가 아니다. 기존 사용자/자료/원천/규칙 버전과 기준시각으로 동일 조회 묶음을 식별할 수 있는지 먼저 검증한다.
- 청구의 포함 거래 참조, 원거래/환불 참조, 예정 의무와 출금의 `SettlementLink`를 우선 사용한다. 내부 이체 등의 추가 관계가 필요하면 근거와 관계를 정의한다. `economicEventId`와 `transferPairId`를 모든 객체에 일괄 추가하지 않는다.
- API 필드와 DB 컬럼은 1:1일 필요가 없다. 전달 객체·DB 저장 모델·Dart 계산 모델 사이의 대응 책임을 기록하고 각각 독립된 금융 계산 권위로 만들지 않는다.

### 더미와 양쪽 구현의 인수 조건

| ------------------------ | -------------------------------------------------------------------- | ------------------------------------------------------------------------ |

위 표는 검증할 계약 사례이며 생성·실행을 완료했다는 기록이 아니다. 5은행·4카드, 달력1년·최근3개월 규칙, 고정 기준시각, 계좌 잔액과 거래의 일치, 반복 회차·청구·정산 근거는 같은 더미 묶음에서 검증한다. 로그인할 때마다 금융 자료를 초기화하거나 ID를 새로 발급하지 않는다. A의 더미/서버와 B의 fake repository는 같은 계약·자료 버전의 사례를 사용한다. 예상 계산 결과는 로컬 계산 검증 자료이며 서버의 금융 산출 응답이 아니다.

## 조회 규격 보완

- 로그인 후 연결 전 Snapshot은 그 사용자가 선택할 기관 목록·종류·건수·연결 상태·dataVersion 등 최소 정보만 반환한다. 동의 전 금융 거래 원문을 모두 내려주지 않는다.
- 연결 성공 후 허용된 계좌/카드/확정 설정과 기준시각을 제공한다. 거래 페이지는 같은 source/dataVersion 기준을 유지해 중간 갱신 자료가 한 연간 집계에 섞이지 않게 한다.
- 연간 자료는 홈 계산 미선택 계좌도 포함한다. 기관 동의/연결 제외와 홈 계산 계좌 선택을 다른 필드로 관리한다.
- 기간은 달력1년~asOf다. 경계는 [계산 기준](calculation-rules.md)의 시작 제외·종료 포함 구현 기준안으로 API/로컬 벡터를 맞춘다. 날짜만 있는 자료를 임의 시각으로 바꾸지 않는다.
- 최소 분석 결과는 기간·대상·누락 범위·월별/연간 순소비액·근거 ID·구매일/출금일 대체 여부다. 이 결과는 **Flutter 로컬 산출물**이며 금융 API의 서버 집계 요구가 아니다.

## 공통 쓰기 규약

- 금융 설정 쓰기는 `expectedDataVersion`, `ruleVersion`, `idempotencyKey`를 포함한다. 인증 발급/종료는 금융 설정 버전과 별도다.
- 세션 소유권 → 허용 필드/형식 → 최신 버전 → 참조/범위/배정 제약 → 설정/연결/기록/버전 원자 저장 순서다. 서버의 U 재계산 단계는 없다.
- 저장 성공 뒤 새 원천/설정을 반환하고 Flutter가 같은 함수로 다시 계산한다. 데이터 갱신 전 초안 결과를 확정 결과로 표시하지 않는다.
- 사용자에게 원천 잔액·카드 사용액·임의 지급 완료 상태를 직접 수정하는 API를 주지 않는다. 지급 완료는 유효 연결 근거로 결정된다. 정정 요청은 내부 연결을 해제/재연결한다.
- 신규/증액 보호 합계는 같은 계좌 잔액과 선택 전체 잔액 상한을 함께 검사한다. 원천 잔액 하락으로 이미 초과된 R은 자동 축소하지 않는다. 전체 과대 보호액을 줄이는 수정과 새 증액은 구별한다.
- 잘못된 지급 연결 정정으로 과거에 해제한 보호 배정을 복원해야 할 수 있다. 정정 전후 변경 기록으로 해당 해제만 되돌리며 현재의 다른 변경을 덮지 않는다. 복원 뒤 부족은 표시하고 원천 잔액을 늘리지 않는다.
- 보호/의무 배정 합계에는 미해제분만 포함한다. 이미 해제한 배정 이력을 현재 보호액과 비교해 정상 정산을 거절하지 않는다.
- 같은 키·같은 내용은 같은 논리 결과, 같은 키·다른 내용은 409. 유효 세션의 오래된 버전은 `409 STALE_DATA`, 형식/범위 오류 422, 인증 실패 401·접근 금지 403으로 구분하는 계약안이다.
- 음수 U는 저장 거절 사유가 아니다. 음수 보호 설정·타 사용자 참조·중복 지급 연결은 입력/무결성 오류다.

## LLM·자동화 경계

로컬 규칙이 근거와 후보를 만들고 서버가 필요한 해석 입력만 전달한다. LLM은 ID·이름·이유·증거 참조를 반환한다. `category`를 의미 미정으로 보내지 않는다. 기존 네 분류의 `transactionType` 사용은 설계 권장안이다. LLM 제안만으로 사용자가 확정한 분류·계획을 덮어쓰지 않는다. 임의 금액·일정·SQL/DB 수정·자동 승인 권한을 LLM에 주지 않는다.

자동 지급 연결은 확인된 원천 ID/청구/명시 매핑을 사용한다. 같은 금액·날짜·상호만으로 확정하지 않는다. 근거가 부족하면 확인 필요로 남기고 사용자가 내부 연결을 바로잡는다. 사용자별 금액 산출은 로컬, 서버는 저장 가능성·참조·중복만 검증한다.

금액은 KRW 정수, 단일 값/중간 합계 절댓값 상한 9,000,000,000,000원이다. nickname은 앞뒤 공백 제거 후 grapheme 1~12개·이모지 허용·중복 허용·특수문자만 불가·null 되돌리기이며 원천 상품명과 분리한다. 정확한 허용 문자 표는 화면 상세와 같은 벡터로 검증한다.

사용자 이름은 `name` 하나로 통합한다. 인증 대조와 허용 화면 호칭에 같은 서버 저장값을 쓰고 로그인 201에 필수 반환한다. 인증 식별값만 정규화 후 공백 없이 저장하며 금융 상품명·거래 메모·계좌 별칭의 원문 규칙은 유지한다. 확정된 세 이름·기존 SQL/시드 이행 경계는 [인증 설계 §2](../apps/api/docs/v0.6/auth-design.md)를 따른다. 금융 Snapshot이나 reverify 응답에 이름 필드를 추가하는 결정은 아니다.

## 연결 상태·표현 보완 — 사용자 채택 5·6·7

- `name`은 합성 계정 조회·입력 대조·이름+전화번호 인증 제한·로그인 201 표시값에만 사용한다. 금융 소유권/권한은 `userId`다. 호칭 위치는 프론트 담당자가 정한다.
- alpha·beta·gamma 모두 최초 연결 전 상태를 지원한다. 각 계정 원본의 공통 메타정보·기관 목록을 사용하고 institutionLinks/coverage는 [], 금융 키는 생략한다. alpha 자료를 다른 계정에 재사용하거나 계정별 연결 전 JSON 복제를 의무화하지 않는다.
- 최초 연결 전 응답 생성과 재로그인을 구분한다. 이미 저장된 연결·계좌 선택·설정은 해당 userId로 복원하며 로그인 때문에 초기화하지 않는다.
- FakeRepository와 실제 API는 같은 부분 연결·종속 참조 규칙을 따른다. 원본 fixture는 보존하고 별도 사용자 상태를 입력으로 API 표현을 만든다. 카드/계좌 배열만 필터링하거나 금융 원천 ID를 접근 제한이라는 이유로 null로 바꾸지 않는다.
- 정확한 허용 키·제한 표현·상태 전이·실패 기준·예시는 [v0.6 응답 모델](../apps/api/docs/v0.6/response-models.md)이 기준이다. 연결된 미선택 계좌(included=false)는 계속 조회 가능하다. 이 추가로 실제 API/FakeRepository 구현 완료를 뜻하지 않는다.
