# 데이터·API 공통 경계

PAYSE 데이터의 책임 경계와 문서 연결을 정의한다. 필드 사전·HTTP 규격·공개 투영·실제 DB 사전은 아래 상위 문서에 한 번만 정의한다. 문서와 준비 도구의 존재를 실제 API·금융기관 연동 완료로 표시하지 않는다.

| 확인할 내용                               | 단일 기준                                |
| ----------------------------------------- | ---------------------------------------- |
| 객체 필드·타입·필수 여부·수정 권한·관계   | [공통 데이터 모델](data-model.md)        |
| 인증·조회·쓰기 요청/응답·오류·멱등 재시도 | [v0.6 HTTP 계약](api-contract.md)        |
| 연결 전/부분 연결·누락·페이지·공개 필드   | [v0.6 응답 모델](api-response-models.md) |
| 실제 테이블·컬럼·제약·SQL과 이행 상태     | [DB 구조](database-schema.md)            |
| 계산식·기간·급여·반복·정정                | [계산 기준](calculation-rules.md)        |
| 의존성·생성자 주입·상태 수명              | [앱 구조](app-architecture.md)           |

## 데이터 경계와 서버 책임

```text
서버 준비 원천·확정 설정 → 권한/버전/참조를 적용한 Snapshot·거래 페이지
Flutter Repository → 불변 앱 모델 → 로컬 계산 → 화면
필요한 근거 → 서버 LLM 게이트웨이 → 해석 결과 → 로컬 검증
사용자 확정 설정 → 서버 저장 제약 검증 → 원자 저장 → 새 Snapshot
```

금융 수치 계산과 저장 제약 검증의 책임은 [앱 구조](app-architecture.md)를 따른다. API JSON·DB 행·Dart 모델은 목적에 따라 달라도 되지만 각 변환이 필드 의미·수정 권한·누락 상태를 보존해야 한다.

CODEF는 항목 검토용 참고 자료다. MVP에서 직접 호출하거나 응답을 복제할 의무는 없다. 후속 금융 API 공급자가 정해지면 공식 응답·인증·조회 기간·페이지·정정 규칙을 확인하고 adapter에서 PAYSE 계약으로 변환한다. PAYSE 내부 ID·연결 메타데이터를 외부 공급자의 공식 필드라고 표시하지 않는다. 공급자가 제공하지 않은 값을 정상 원천 사실로 생성하지 않는다.

## 식별·인증 기준

현행 인증·이름 계약은 [HTTP 계약의 인증 절](api-contract.md), 내부 토큰 보호·권한·잠금 설계는 [인증 내부 설계](../apps/api/docs/v0.6/auth-design.md)를 따른다.

## 핵심 논리 모델

필드·타입·null·수정 권한은 [공통 데이터 모델](data-model.md)에만 정의한다. 물리 저장 대응은 [DB 구조](database-schema.md)를 따른다. 필드 하나가 추가됐다는 이유만으로 같은 이름의 DB 컬럼·테이블을 자동 추가하지 않는다.

## 공통 전달 형식과 확정된 의미

언어 독립 JSON을 사용하며 API와 Flutter가 서로 다른 의미를 독자적으로 정의하지 않는다. 공통 계약 변경은 [작성·공유 기준](development-notes.md)에 따라 영향받는 담당자끼리 확인한다.

### 공통 타입·값 유무

[공통 데이터 모델의 공통 규칙](data-model.md)을 따른다. 실행 가능한 JSON Schema/OpenAPI는 문서 사전과 별도 산출물이며 MD만으로 생성·검증 완료를 주장하지 않는다.

### 계좌·카드·거래·청구의 기초 필드

[공통 데이터 모델](data-model.md)의 객체 사전을 사용한다. 원천의 상품명·가맹점·설명은 의미와 출처를 보존하며 인증 식별값의 공백 금지를 일괄 적용하지 않는다.

### 버전·조회 범위·관계

버전과 관계의 의미는 [공통 데이터 모델](data-model.md), 조회 투영·페이지 조립은 [응답 모델](api-response-models.md)을 따른다. `snapshotId`는 의무 필드가 아니다. 기존 사용자·자료·원천·규칙 버전과 기준시각으로 조회 묶음을 식별할 수 있는지 먼저 확인한다. 기존 청구/원거래/환불/정산 참조로 해결할 수 있는 관계에 `economicEventId`·`transferPairId`를 모든 객체에 일괄 추가하지 않는다.

### 더미와 양쪽 구현의 인수 조건

| 사례                  | 서버/준비 자료에서 확인              | Flutter에서 확인                                                 |
| --------------------- | ------------------------------------ | ---------------------------------------------------------------- |
| 정상 잔액 0           | 확인된 잔액·기준시각·성공 상태       | 실제 0원으로 표시·계산                                           |
| 실패·일부 누락        | 조회 상태·누락 범위·확보된 원천 유지 | 빈 자료/0원으로 실패를 숨기지 않음                               |
| 연결 전·부분 연결     | 공개 허용 필드와 종속 참조 제한      | 숨겨진 정보를 원천 null 또는 권한 있는 빈 목록으로 오해하지 않음 |
| 같은 거래의 복수 조회 | 안정된 내부 ID와 명시 관계           | 같은 거래·카드 구매/대금을 중복 집계하지 않음                    |
| 정정·취소·부분 환불   | 원거래 참조·자료 버전·근거 보존      | 같은 버전의 정정 규칙 적용                                       |
| 잘못된 소유자 참조    | 서버 거절·타 사용자 자료 비공개      | 실패를 저장 성공으로 표시하지 않음                               |

이 표는 공통 인수 사례이며 실행 결과가 아니다. 실제 생성·검사 상태는 [더미 사용 기준](../apps/api/fixtures/docs/dummy-data.md)과 해당 작업 보고서로 확인한다. 동일 원본에서 생성한 API와 FakeRepository 표현이 같은 공개 규칙을 따르는지 검증하고, 예상 계산 결과를 서버 금융 산출 응답으로 반환하지 않는다.

## 조회 규격 보완

기관 연결과 홈 계산 계좌 선택, 연간 범위, 버전 고정 페이지는 [HTTP 계약](api-contract.md)과 [응답 모델](api-response-models.md)을 따른다. 연간/월별 소비 결과는 [계산 기준](calculation-rules.md)의 로컬 산출물이다.

## 공통 쓰기 규약

[HTTP 계약의 쓰기·경합·재시도 절](api-contract.md)을 단일 기준으로 한다. 저장 형식과 DB 잠금 구현은 [DB 구조](database-schema.md)에서 연결한다. 하위 구현 안내에서 별도 순서를 정의하지 않는다.

## API 경로 권장안

v0.6 경로·요청·오류는 [HTTP 계약](api-contract.md)에만 정의한다. 후속 버전에서 승인/분류/정산/조정 경로를 구현할 때 [제품 버전 경계](product-baseline.md)를 적용하고 v0.6 구현 완료로 포함하지 않는다.

후속 버전의 아래 경로는 기존 권장안을 보존한 것이며 배포·구현된 API가 아니다. 실제 기능 착수 시 해당 버전의 요청·응답·오류를 구체화하며 현재 v0.6 완료 범위를 늘리지 않는다.

| 후속 권장 경로                                      | 책임                                                               |
| --------------------------------------------------- | ------------------------------------------------------------------ |
| `POST /recurring-analysis`                          | 로컬 후보/근거의 소유권 확인 후 LLM 해석; 서버 금융 수치 생성 없음 |
| `POST /recommendations/{id}/approve` 또는 `exclude` | 근거·허용 설정·참조 검증 후 사용자 승인/제외 저장                  |
| `PATCH /transactions/{id}/classification`           | PAYSE 네 거래 분류 변경; 원천 사실 변경 없음                       |
| `POST /settlement-links/corrections`                | 유효 연결 해제/재연결과 관련 배정·이력·버전을 원자 저장            |
| `POST /reserve-adjustments/confirm`                 | 한 보호 설정 확정; 가상 items/결과 영속 저장 없음                  |
| `POST /plan-explanations`                           | P1 설명; 최소 근거만 전달하며 금융 쓰기 없음                       |

반복 후보의 로컬 ID만으로는 서버가 승인/제외 대상을 확인할 수 없다. 후속 요청은 후보 ID·규칙/원천 버전·근거 거래 ID 집합을 포함하고, 승인 시 사용자가 확인한 금액·예정일·출금 계좌를 전달한다. 서버는 근거의 소유권·존재·버전과 저장 제약을 검증하여 결정을 저장한다. 승인 전 후보 수치를 모두 서버에 영구 보관해야 한다는 요구는 아니다.

## LLM·자동화 경계

로컬 규칙이 근거와 후보를 만들고 서버는 필요한 해석 입력만 전달한다. LLM은 ID·이름·이유·증거 참조를 반환한다. 의미 미정인 `category`를 보내지 않는다. 기존 네 분류의 `transactionType` 사용은 v0.7 설계 권장안이며 별도 소비 카테고리 추가가 아니다. LLM 제안만으로 사용자가 확정한 분류·계획을 덮어쓰지 않는다. 임의 금액·일정·SQL/DB 수정·자동 승인 권한을 LLM에 주지 않는다.

자동 지급 연결은 확인된 원천 ID·청구·명시 매핑을 근거로 한다. 금액·날짜·상호만으로 확정하지 않는다. 근거가 부족하면 확인 필요로 남기고 사용자가 내부 연결을 정정한다. 적용 버전·정정 결과는 [계산 기준](calculation-rules.md)을 따른다.

## 이름 계약

[HTTP 계약](api-contract.md)의 단일 이름·인증 입력 규격을 따른다. 기존 SQL/시드 이행 상태는 [DB 구조](database-schema.md)에 분리해 기록한다.

## 연결 상태·표현 기준

[응답 모델](api-response-models.md)이 세 계정 최초 상태·재로그인·부분 연결·접근 제한의 단일 기준이다. 구현 상태는 각 앱의 문서와 검사 결과에서 확인한다.

테스트 사건은 `apps/api/testing/scenarios/` 준비 도구에서 선택한다. 일반 서비스에 시나리오 실행 API 또는 테스트 전용 저장 필드를 추가하지 않는다. 공통 사용자 구조에서도 `/demo-sessions` 주소와 세션 정책은 유지한다.
