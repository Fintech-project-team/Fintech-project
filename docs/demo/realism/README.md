# 공통 더미 현실성 개선 요청

작성 2026-10-29(B). 처음에는 생성기 반영을 A에게 요청하는 자료로 작성했고, 같은 날 A·B 합의로 데이터 작성은 B가 맡게 됐다(§0). 이 폴더의 문서·스크립트만으로는 공통 더미·생성기·계약을 바꾸지 않는다.

2026-10-29 갱신: #132(거래명·적요 분리 `labels-1`, 반품·취소 `reversals-1`, 청구 항목 v4 계약) 반영 후 기준선으로 고쳤다. 1단계는 #132로 반영됐고 남은 요청은 2단계다.

## 0. A·B 합의(2026-10-29, 우선 적용)

혜연(B)과 성현(A)이 구두로 상의했고 A가 동의했다. 아래 내용이 §1 이후의 "A에게 요청" 내용보다 우선한다.

- **추가 방식**: 기존 공통 더미(`apps/api/fixtures/generated/`의 v3, `generated-v4/`의 v4)는 그대로 둔다. B가 만든 생활 흐름 데이터를 별도 사례로 **추가**한다. 기존 데이터가 작업에 방해가 되면 다른 경로로 옮길 수 있다(A 허락).
- **기본값**: 앱과 서버 준비 자료가 기본으로 읽는 데모 데이터는 B의 데이터로 한다.
- **작업자와 범위**: B(혜연)가 맡는다. B가 바꾸는 것은 **더미 생성 스크립트와 그 결과 JSON**뿐이며, 그 밖의 API 코드·계약·DB·테스트는 바꾸지 않는다.
- **대상**: 현재는 데모알파. 기능 개발을 마친 뒤 데모베타·데모감마도 B가 작성할 예정이다.
- **작업자 변경**: 개발 진행에 따라 작업자가 바뀔 수 있다. 바뀌면 이 절을 고친다.
- 따라서 §2의 2단계와 §7의 결정 사항은 B가 진행·결정하고 A에게 공유한다. 사례를 등록하는 생성 결과 파일(catalog·manifest·server-seeds 등) 중 무엇을 B가 고칠지는 작업 명세에 경로를 적어 A와 확인한다.

## 1. 요청

- 기존 회귀용 사례를 포함한 **모든 공통 더미 사례**의 거래 내역을 실제 통장·카드 내역처럼 바꿔 주세요. 새 사례를 하나 더하는 방식이 아니다.
- 데모알파는 B가 앱(#29 거래 내역)을 먼저 만들려고 로컬 사본을 만들었다. 그 규칙을 기준안으로 넘긴다. 최종 기준은 공통 생성기 결과이며, 반영되면 앱 에셋을 그 결과로 바꾼다.

## 2. 진행 순서(제안)

1. **1단계 — 이름·적요(#132에서 반영됨)**: 21개 사례 모두 거래명과 적요가 분리됐다(`transaction_labels.py`). §4-1은 참고 예시이며 #132의 이름 체계를 다시 바꿀 필요는 없다.
2. **2단계 — 생활 흐름(남은 요청)**: §4-2~4-6. 거래를 지우거나 더하므로 사례마다 바꾸면 안 되는 근거 거래 목록을 먼저 정하고 사례별로 진행한다. 데모알파는 근거 36건(급여·월세·통신비·카드 청구·체크카드 짝·적금 이체·수리비)을 보존한 예시가 있다.
3. 각 단계 뒤 기존 서버·DB 테스트와 `realism_check.py` 합격선을 확인하고, B가 앱 에셋·동일성 테스트를 맞춘다.

### 4-3. 카드

- 삼성 신용카드: 주 사용 카드(카페·식사·배달·쇼핑·택시·후불교통·전자책), 월 25건 안팎.
- 국민 체크카드(생활비 통장): 장보기·반찬·약국. 카드 사용 1건마다 같은 날·같은 금액의 생활비 통장 출금을 만들고 `card_account_pair`로 연결한다.
- 현대 신용카드: 구독과 가끔 사용. 기존 청구서(9월 110,000)가 있는 달에는 다른 사용을 더하지 않는다.

### 4-4. 할부(#130 원칙 유지)

- 구매 기록은 1건이며 회차를 복제하지 않는다. `installmentCurrent/Total`은 명시한 합성 원천 값이며 구매일·총액에서 계산하지 않는다.
- 카드대금 출금에는 그 달 할부 청구분을 넣는다. 청구분도 생성기 표에 명시한 값으로 둔다(총액÷개월 계산 금지). 지금 #130 사례는 회차는 있는데 카드대금에 할부분이 없다.
- 상태를 섞어 둔다: 이번 달 구매(#130의 10/18 1/3), 진행 중(2/6 또는 8/24), 끝난 할부(3/3).

### 4-5. 환불

카드 환불은 `card_refund`와 `originalTransactionId`로 원거래와 연결하고, 다음 달 카드대금에서 차감한다.

### 4-6. 잔액

계좌 잔액(`balanceKRW`)은 각 사례의 기대값을 지키도록 그대로 두고, 거래 흐름을 맞춰 조회 시작 잔액과 날짜별 잔액이 0원 이상이 되게 한다. 사례 의도로 음수가 필요하면 예외로 표시한다.

## 5. 합격 기준

1. 모든 사례에서 거래명 = 적요 0건.
2. 시작 잔액·일별 잔액 ≥ 0(의도 예외는 catalog에 표시).
3. 카드대금 차이 = 그 달 할부 청구분(명시 표로 설명), 그 밖의 차이 0(의도 예외 표시).
4. 기존 테스트(사례별 기대값·근거·ID 보존, DB 적재) 통과. 데모 계열 홈 계산 B 2,000,000·E 300,000·R−O 400,000·U 1,300,000 유지.
5. 다시 생성해도 바이트 단위로 같은 결과.

## 6. 하지 말 것

- 할부 청구 금액·회차를 총액÷개월이나 구매일로 추정하지 않는다.
- 청구 항목(`statements[].items`)은 #132의 v4 계약(`PAYSE-DRAFT-4`·`PAYSE-API-0.6-4`)과 `generated-v4/`를 따르며 이 작업에 섞지 않는다. 스크립트의 `--statement-items`·`--statement-cases`는 v4 확정 전 초안이라 쓰지 않는다(v3 파일에 items를 넣고 필드 이름도 v4와 다르다).
- 사례 검증 의도(부분 정산·범위 밖 환불·급여 대기 등)를 바꾸지 않는다.

1. 거래 수: 데모알파 사본은 월 68건(연결 시 100건 페이지 9쪽). 회귀 사례도 같은 규모로 할지, 월 30~40건으로 줄일지.
