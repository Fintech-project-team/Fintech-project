## 문서 위치와 변경

문서 위치와 담당자 간 확인은 [팀 운영 기준](team-plan.md)의 문서 경로·변경 조건을 따른다. 공통 디자인은 [design.md](design.md), 모바일 상세는 `apps/mobile/docs/`, API 상세는 `apps/api/docs/`, 더미·기능 상세는 실제 해당 폴더의 `docs/`에 둔다.

- 같은 의미를 새 파일에서 다시 정의하지 않는다. 새 MD가 필요한지 위 표의 기존 담당 문서부터 확인한다.
- 세부 문서는 상위 규칙을 링크하고 실제 구현에만 필요한 내용을 작성한다. 단순 전달 계층·빈 기능 폴더를 문서 형식 때문에 만들지 않는다.
- 공통 내용을 옮길 때 의미·기존 예외·미구현 표시는 보존하고, 기존 경로는 짧은 안내와 필요한 장 링크를 남긴다. 특정 작업의 작성·검토·조회·검증 결과와 당시 허용 범위는 [이력 폴더](../apps/api/docs/history/README.md)에 출처별 원문을 보존하고 현행 규칙과 구분한다. 날짜가 있는 원문·과거 작업 기록을 최신 규칙으로 다시 쓰지 않는다.
- 새 정책 충돌은 구체 상황·양쪽 근거·추천안을 제시해 결정받는다. 이미 확정된 정책은 구현/사용 검증이 남았다는 이유로 다시 미결정으로 만들지 않는다.

## 기능 개발 전에 적을 최소 내용

기존 상세 문서가 있으면 그 문서에 아래 내용을 보완한다. 실제 새 기능에만 해당 폴더의 간결한 MD를 만들고 별도 일반 스타일 문서를 복제하지 않는다.

1. **목적·범위:** 어떤 사용자 동작을 지원하고 어느 버전·이슈에 속하는지, 현재 구현 상태.
2. **책임·호출 경계:** 실제 진입점과 application service·Repository/외부 adapter의 책임. 불필요한 BaseManager·한 줄 전달 계층을 설계하지 않음.
3. **입력·출력:** 상위 계약 링크, 실제 mapper와 원천/미상/비공개 표현 차이. 동일 필드 사전 복제 금지.
4. **권한·저장:** 세션 소유자, 읽기/쓰기 범위, 원자 트랜잭션과 재시도 경계. 적용되지 않는 항목은 해당 없음으로 표시.
5. **실패·검사:** 정상·오류·타 사용자·중복/경합 중 해당 사례, 실행할 검사와 미구현 의존성. 문서 검사와 API/DB/기기 검증을 구분.

## 공동 변경과 공유

공통 의미·응답 모양이 바뀌면 API·모바일·DB·더미·검사 소비자를 적고 관련 담당자끼리 변경 전후를 확인한다. 상대 담당자의 파일을 임의 수정할 권한이 자동으로 생기는 것은 아니다. 가독성·호출 관계·설명 정확성은 diff 리뷰로 확인하며 주석 형식 검사 통과로 대신하지 않는다.

새 문서는 해당 개발 변경과 같은 PR에 포함한다. PR에는 **문서 경로·바뀐 입력/출력·상대 담당자 확인 사항·검증/미검증**을 짧게 적는다. 구현 전 초안도 공유 대상이며 파일 생성·저장소 업로드·팀원 확인을 각각 구분한다.

## 기준 문서와 구현 상태

데이터 필드·HTTP·응답 투영·DB 사전의 기준은 위 표의 상위 문서다. 기존 `apps/api/docs/data-model-draft.md`·`database-design.md`·`v0.6/api-contract.md`·`v0.6/response-models.md`는 상위 기준의 안내 경로다. API 내부 보안 설계와 검증 사례는 해당 폴더에 둔다.

반복 계획/버전·이름·급여 확인의 확정 또는 임시 정책은 [공통 데이터 모델](data-model.md)과 [HTTP 계약](api-contract.md)을 따른다. 문서 통합만으로 미구현 SQL 이행·실제 인증·API/FakeRepository의 모든 공개 투영이 완료됐다고 표시하지 않는다.
