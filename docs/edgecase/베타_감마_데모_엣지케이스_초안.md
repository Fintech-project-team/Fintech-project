# 베타·감마 데모 계정 엣지케이스 초안

작성일: 2026-10-28 · 상태: 논의용 초안

## 목적과 범위

알파는 정상 흐름의 기준 계정으로 유지하고, 베타는 비정기 현금 흐름, 감마는 거래 해석이 어려운 상황을 검증한다. 아래는 **제안 시나리오와 기대 대응**이며 현재 구현이나 LLM의 실제 성능을 뜻하지 않는다. 우선순위 P0는 기본 시연과 안전한 미확인 처리를 위한 제안, P1은 확장 검증이다.

초점은 월급일·예상 금액·계좌는 알지만 **해당 회차의 실제 입금 근거가 없어 계산에 영향을 받는 상황**이다. 다만 부수입·반복 지출 등 월급 외 데이터도 함께 넣어 앱 전반의 대응을 살핀다. 월급 정보 자체가 아직 설정되지 않은 초기 적재와 설정 후 시나리오는 구분한다.

## 현행 기준과 판단 경계

다음은 로컬 [실행 공통 계약](../payse-execution-contract.md), [계산 규칙](../calculation-rules.md), [데이터 모델](../data-model.md)의 기준이다. 계약상의 목표와 현재 구현을 구분한다.

- **입금 확인**: 급여 완료의 현재 임시 기준은 명시적 입금 거래 연결과 `confirmed` 사건이다. 금액·날짜 일치만으로 확정하지 않는다. 거래 미수신, 실제 미입금, 앱에 확인 기록만 없는 상태는 다르다.
- **계산**: 예정 급여는 현재 잔액 B에 더하지 않는다. 급여일 도달 후 입금 확인 전 해당일·연체 미지급 예정 지출을 홈 E에서 분리해 대기한다. 실제 출금은 원천 잔액에 유지하며, 확인 후 미정산 대기 의무를 중복 없이 반영한다. 필요한 가정이 없는 미래 기간은 영향 범위만 정보 부족으로 둔다.
- **역할**: Flutter/Dart는 급여 경계와 금융 수치를 계산한다. LLM은 허용된 근거·후보의 의미 해석을 돕고, 서버는 권한·소유권·버전·참조와 응답을 검증한다. LLM은 후보 밖 거래 ID, 금액·일정·급여 완료 사실을 만들거나 설정을 자동 저장하지 않는다. 분석 결과가 저장되어도 금융 승인이나 원천 변경이 아니다.
- **분석 시점**: 확인 기록이 없다는 이유만으로 곧바로 사용자에게 넘기거나 새 거래로 간주하지 않는다. 공개된 거래와 기존 유효 결과·진행 작업을 확인하고, 최초 연결·원천 갱신 등 해당 실행 조건에 따라 필요한 분석을 평가한다. 동일 입력은 재사용하고 단순 재조회·로그인·캐시 소실만으로 재호출하지 않는다. 일반 미분류는 10건 이상 또는 최장 60초 대기이며 현재 계산의 미해결 의존성은 묶음 대기 예외다. 독립적인 ‘지금 분석’ 기능은 제공하지 않는다.
- **질문과 보류**: 특정 거래가 월급인지 묻는 질문과 회차 입금 근거가 없어 거래 선택·아직 미입금·나중에를 제시하는 질문은 구분한다. ‘아직 미입금’은 별도 저장 계약 전까지 기기 안내이며 원천 `unknown`을 미지급 확정으로 바꾸지 않는다. 같은 보류·근거에 강제 재질문하지 않고 분석 완료만으로 팝업·푸시하지 않는다. 사용자 직접 열람 시 질문하고 근거 변화 시 목록을 갱신한다.
- **정보 부족과 실패**: 부분 조회·조회 실패·계좌별 asOf 불일치는 영향을 받는 대상만 정보 부족으로 두고 가능한 거래와 계산은 유지한다. AI 비활성·실패는 미입금이 아니다. 실패 후 공급자 재호출은 사용자 재시도로만 진행하고 유효 결과·진행/완료 불명 작업을 먼저 확인한다.
- **후보의 의미**: 아래 ‘판단 가능’은 합성 단서로 후보를 제시할 수 있다는 테스트 가설이지 실제 성능이 아니다. ‘판단 불가’는 입력만으로 정답을 결정할 근거가 없는 경우다. 후보 선택·직접 선택 화면과 구체 UX는 제안이며 현재 구현 완료를 뜻하지 않는다. 분석 상태·후보 상태 이름도 논리 설계이며 공개 필드 확정이 아니다.
- **구현 상태**: 실행 계약에 따르면 LLM 게이트웨이·후보 해석·질문/보류 및 급여 확인 버튼 연결 등은 미완료다. 구현 여부는 해당 버전의 코드와 실행 결과로 다시 확인한다. 금융 연결은 실제 연동이 아닌 합성 상태로 재현한다.

### 거래 데이터 표기와 검증 범위

아래 금액·날짜는 합성 거래 예시다. ‘급여’, ‘가족’, ‘경비’, ‘병원비’ 등은 **시나리오 작성자가 아는 실제 사정 또는 평가용 정답 라벨**이며, 거래 화면이나 LLM 입력에 그대로 제공된다는 뜻이 아니다. 앱이 수신한 값과 정답 라벨을 분리하고, 입사·이직·가족 관계 등은 원천 거래에서 자동으로 아는 정보로 넣지 않는다. 사용자에게 질문할 때도 확인하지 않은 사유를 사실로 표현하지 않는다.

PAYSE의 `merchantName`·`description`은 null이 가능한 합성 원천 표시값이다. 입금·출금은 방향이며 표시 문구와 구분한다. 표시 문구로 `김대표`나 `급여`가 제공되는 예시는 **PAYSE 내부 fixture 가정**이다. 기관마다 실제 제공 여부·필드·길이를 확인한 사례가 아니며, 실제 마이데이터 표준 응답과 호환된다고 주장하지 않는다. 같은 사례에 표시값이 없거나 일반적인 표시만 있는 변형도 둔다. 실제 연동 전 제공 기관의 최신 표준 규격과 실제 응답을 확인하고 매핑한다.

## 데모와 별도로 검증할 입력 오류

타 사용자 거래 ID가 섞인 응답, 허용되지 않은 ID 생성 등은 실제 정상 거래 예시가 아니라 **권한·계약 오류를 주입하는 별도 테스트**다. 서버가 소유권과 참조를 검증해 거부하는지 확인한다. 실제 금융 공급자가 그런 형태의 데이터를 제공한다고 가정하지 않는다. 사용자 요청에 따라 기존 G11의 지시문 문자열은 데모 사례에서 제외했다.

## 재현과 평가 방법

1. **독립 fixture**: 각 사례에 사용자에게 실제 공개된 거래 값·null/누락 값과 별도 정답 라벨, 고정된 `asOf`·sourceVersion·계좌 연결/조회 범위·거래 ID·설정·회차·입금 확인 상태를 명시한다. 원천 거래와 잔액은 실제 입출금이 일관되도록 작성하고, 타임라인이 충돌하는 사례는 별도 스냅샷으로 분리한다. 초기 데이터의 설정 없음과 시나리오 적재된 설정을 구분한다.
2. **정답과 관찰 분리**: 비공개 테스트 라벨에 실제 거래 성격·회차·정답 없음/판별 불가·기대 사용자 행동을 둔다. 모델 입력에는 실제로 서비스가 가진 정보만 제공한다. 정답이 불명인 사례를 억지 단일 정답으로 채점하지 않는다.
3. **같은 조건 비교**: 알파 정상 기준과 베타·감마를 같은 기준시각·연결 조건에서 비교하고, 이름·금액·날짜 하나만 바뀐 짝 사례 및 후보 순서 변경을 둔다. 모델 ID·프롬프트/입력 버전·실행 횟수를 기록한다.
4. **측정**: 급여 후보 누락, 잘못된 급여 확정, 정답 없음/모름 처리, 사용자 확인 요구·거절 후 회복, 데이터 부족 판별을 각각 기록한다. 사례별 성공·실패·미구현·미실행을 구분한다. 모델 confidence를 실제 정답률로 간주하지 않는다.
5. **결정적 검증**: 잘못된 ID·소유권·중복·버전·스키마를 서버가 거부하는지, Flutter가 원천/설정과 규칙에 따라 재계산하는지 별도 확인한다. LLM 정답 여부만으로 금융 계산의 정확성을 판단하지 않는다.
6. **완료 판정**: 각 ID별 입력·기대 결과·실제 결과·근거·담당자·실행일·미구현 항목을 남긴다. 앱 화면, 서버/LLM, 로컬 계산을 각각 관찰하고 테스트 미실행을 통과로 기록하지 않는다.

| 5    | ‘아직 미입금’ 선택 후 언제 어디서 재확인할까? 별도 지속 저장이 필요한가?                                       | 현재는 기기 안내이며 원천 unknown 유지가 기준이다. 지속 기록이 필요하다면 별도 계약이 필요하다.                                                 |
| 6    | 급여·상여·경비가 한 거래에 합쳐진 경우 사용자가 표현할 수 있는 성격·회차·보호 선택은 무엇인가?                 | 금액만으로 분해하거나 보호를 해제할 수 없다. 큰 입금 보호 정책 적용 및 현재 구현을 확인해야 한다.                                               |
| 7    | P0별 기준시각·거래와 잔액·정답 라벨·기대 상태 및 A/B 담당, 서버 원본과 모바일 사본 동기화는 어떻게 관리할까?   | 재현성과 계약 일관성이 필요하다. 각 사례의 asOf, 연결/설정 상태와 수동 확인 전후를 명시해야 한다.                                               |
| 8    | LLM 평가에서 어떤 오류와 목표를 우선할까?                                                                      | 허위 확정 방지는 서버/앱 검증까지 포함해 측정하고, 후보 누락·모름 처리·사용자 부담을 별도로 기록해야 한다. 합의 전 임의 임계값을 정하지 않는다. |
| 9    | 동률·월말 보정·휴일 이동·다음 달 지급·서로 다른 회차의 동일 예정일을 어떤 짝 사례로 배치할까?                  | 명목 회차와 계산 경계는 다를 수 있다. 기존 계산 규칙을 재결정하지 않고 테스트 입력·기대값을 정한다.                                             |
| 10   | 초기 적재·선택 시나리오 적재와 분석 결과/설정의 유지 범위를 데모에서 어떻게 보여줄까?                          | 기본 DB 적재는 설정이 비어 있으며 별도 시나리오만 확정 설정을 포함한다. 기기 보류와 서버 저장 분석 결과의 수명도 다르다.                        |

**추가 관찰**: 일상 데이터에서 거래 표시 문구가 실제 사유를 충분히 담지 않는 경우와 수집 범위 부족은 서로 다른 실패다. 모델이 그럴듯한 후보를 내더라도 근거가 없으면 확정하지 않는 사례와, 모델 호출 없이도 판별 가능한 원천 오류·권한 오류를 분리해 평가한다. 대량의 엣지케이스를 한 계정에 몰아넣으면 어떤 단서가 실패 원인인지 알기 어려우므로 독립 사례와 단일 변수 짝 사례를 우선한다.
