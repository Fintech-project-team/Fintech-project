# 첫 개발 순서

1. A/B가 [제품 기준](product-baseline.md)과 [화면 규칙](v0.6-screen-rules.md)을 기준으로 v0.6 데이터 항목·사용자 ID·관계·조회/쓰기 경계를 확인한다.
2. A: P0 데이터 명세, 사용자별 1년치 더미 JSON과 검증 사례, DB 구조/ERD, API 명세, 데모 식별·인증 설계. PAYSE 공통 필드·값 유무·자료 버전·정상/실패 사례를 먼저 인계한다. CODEF는 참고 자료이고 실제 공급자 매핑은 후속 실연동 작업이다.
3. B: 같은 계약의 fake repository로 Flutter 화면·순수 Dart 계산 모듈을 준비한다. 생성자 주입과 수명별 상태 관리로 화면마다 계산식을 복제하거나 가변 전역 싱글톤에 의존하지 않는다.
4. A의 P1 서버 구현 후 설정 저장·재로그인 유지·사용자 격리·중복 로그인·버전 충돌을 B와 통합 검증한다. fake 경로의 성공을 서버 저장 완료로 보고하지 않는다.
5. v0.7 실제 LLM 연동과 반복 후보, v0.8 복수 소비 시뮬레이션, v0.9 돌발지출·조정·수동 정정, v1.0 전체 흐름 통합·검증을 [버전 기준](product-baseline.md)에 맞춰 연결한다. 수치 산출은 Flutter다.

세부 인수 기준은 [팀 계획](team-plan.md), 코드 경로·검사 준비는 [전환 상태](harness/FLUTTER_TRANSITION.md)를 따른다. 본 순서는 구현 완료 보고가 아니다.

작업 날짜·담당은 [팀 계획의 GitHub 연결](team-plan.md)을 참조한다. 서버 P1은 구현 순서이며 저장 유지 등 필수 완료 조건의 생략 권한이 아니다. 사용성 범위 변경은 [미승인 목록](open-decisions.md)에서 별도 관리한다.
