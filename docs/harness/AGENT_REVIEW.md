# 에이전트 수정·자기검증·기록

목표는 최초 수정 범위 준수, 계약 위반 재작업 0건, 필수 검사 누락 0건, 작은 작업의 절차 부담 최소화다. 통과한 검사는 결과가 유효하면 재실행하지 않는다. 발생한 사건은 수정 후에도 기록한다.

## 최초 범위를 지키는 수정 반복

1. 첫 수정 전에 작업 명세의 목적·완료 조건·허용 경로와 기존 변경을 확인한다. 사용하는 계산 정책·입출력 계약, 필수 검사와 선택 이유를 정한다. 문서 작업도 변경하는 지침과 검사기의 계약을 확인한다.
2. 이 목적과 허용 경로를 이번 수정 반복의 기준으로 고정한다. 기존 변경을 보존하고 작은 단위로 구현한다. 다른 담당자의 코드는 연결 확인을 위해 읽을 수 있다.
3. 변경 후 diff로 범위를, 관련 정책·계약으로 동작을 자기검증한다. 문서·설정 작업은 최신 사용자 요구와 완료 조건을 연결 문서까지 대조한다. 인원·역할·절차·상태처럼 바뀐 주제와 그 참조만 확인하며 하네스 PASS로 내용 검증을 대신하지 않는다. 범위 밖에 실제로 쓴 변경이 있으면 이번 작업이 만든 부분만 원복하고 기존 변경을 보존한다.
4. 위반을 발견하면 원인과 횟수를 남기고 최초 범위 안에서 고친다. 실패했거나 수정의 영향을 받는 검사만 다시 실행하고 범위·계약을 다시 확인한다.
5. 범위 안에서 해결할 수 없으면 BLOCKED와 원인·필요 경로를 보고한다. 통과시키려고 allowedPaths·역할·기준 커밋·계약·기대값·검사기를 바꾸거나 임시 구현을 다른 경로에 복사하지 않는다.
6. 완료 전 필수 검사 목록과 최신 유효 결과를 대조해 빠진 검사를 보완한다. 사용자가 별도로 범위 변경을 승인하면 이유와 새 기준을 남긴다. 범위 확장으로 앞선 위반 기록을 없애지 않는다.

계약 위반 0건은 수정 전에 기존 계약을 확인해 달성한다. 누락 0건은 완료 전에 필수 검사와 실행 근거를 대조해 달성한다. 이미 발생한 횟수를 0으로 고쳐 목표를 달성했다고 보고하지 않는다.

## 통과 결과의 재사용

- 같은 검사 명령·대상·입력·설정·의존성·실행 환경에서 얻은 통과 결과를 재사용한다. 결과가 가리키는 변경과 현재 변경의 관계를 확인한다.
- 관련 코드나 설정 변경, 새 실패, 실행 환경 변경, 결과 누락·불명확으로 유효성을 확인할 수 없을 때만 관련 검사를 다시 실행한다. 영향 범위를 판단할 수 없으면 보수적으로 해당 검사를 실행한다.
- 같은 작업에서 이미 읽은 문서는 바뀐 부분과 새로 필요한 부분만 읽는다. 계획·설명·최종 보고를 작성했다는 이유만으로 같은 문서나 검사를 반복하지 않는다.
- 실제 검증은 GATE_MATRIX.md와 기존 실행 명령을 따른다. --plan은 계획, --format은 포맷일 뿐 통과 증거가 아니다. 도구 미설치·명령 누락은 BLOCKED로 기록한다.
- 현재 verify-change.mjs는 한 번 호출할 때 전체 검사를 실행하며 이전 PASS를 자동 재사용하지 않는다. 최종 변경에서 한 번 실행하고, 이후 수정은 영향을 받은 검사의 개별 명령과 결과를 보완한다.
- 이전 종합 보고서의 FAIL·BLOCKED를 PASS로 바꾸지 않는다. 이전 보고서 상태, 보완한 검사, 재사용한 통과 근거를 구분해 보고한다. 최종 변경에 필요한 검사 근거가 하나라도 없으면 완료로 보고하지 않는다.

| 규칙 수행 부담        | 불필요한 문서 재독·절차·중복 검증이 있었는지와 이유를 한 줄로 기록한다.                                                           | 매 작업마다 시간을 재는 절차를 추가하지 않는다. 시간이 필요하면 직접 측정한 구간만 분으로 적고 도구 대기를 구분한다. | 부담 없음 또는 관련 문서·절차와 개선할 점; 선택적으로 실측 시간 |

0건은 확인한 범위에서 사건이 없다는 뜻이다. 미확인은 근거가 없어 판단할 수 없다는 뜻이며 0으로 환산하지 않는다. 해당 없음은 적용 대상이 없는 경우에만 이유와 함께 쓴다. 최종 PASS만으로 이전 사건이 0건이었다고 판단하지 않는다.

예를 들어 범위 밖 수정 원복 후 통과했다면 범위 위반은 1건이다. 계산·계약·운영 지침·완료 조건 위반이 없는 단순 문서 수정이면 재작업은 해당 없음이다. 승인된 3인 운영 요구를 빠뜨려 문서를 다시 고쳤다면 운영 지침 위반 재작업 1건으로 기록한다. 필수 검사 실행 불가를 BLOCKED로 정확히 알렸다면 누락은 0건일 수 있으나 작업이 PASS가 된 것은 아니다.

## 기록 위치와 검토

작업 시작 시 ID·유형·에이전트와 확인 가능한 모델·규칙 기준 커밋을 남긴다. 지침에 미커밋 변경이 있으면 파일과 변경 내용도 기록한다. 사건이 생길 때 경로·원인·수정 결과를 짧게 메모한다.

종료할 때 [.github/PULL_REQUEST_TEMPLATE.md](../../.github/PULL_REQUEST_TEMPLATE.md)의 네 행을 작성한다. 문제가 있거나 미확인인 항목만 설명을 덧붙인다. PR 생성 전에는 .harness/reviews/<작업ID>.md에 보관하고 최종 보고에 요약한다. 기록을 위해 검사만 다시 실행하지 않는다.

PR 작성 시 같은 기록을 본문에 옮기고 리뷰 지적을 반영한다. 작성자 기록만 있으면 리뷰를 받았다고 표시하지 않는다. 개인→develop→main 통합 PR에서는 원본 작업 ID·PR을 링크해 같은 작업을 중복 집계하지 않는다.

.harness/는 Git 공유 대상이 아니다. 동료가 근거를 확인하도록 명령·상태·관련 오류를 요약하거나 허용된 CI 산출물을 연결한다. 비밀값·실제 금융정보·개인 PC 경로는 공유하지 않는다. 일반 기여자는 기록 때문에 공통 docs/ 수정 범위를 넓히지 않는다. 기록은 Git 작업의 실행 승인이 아니다.

현재 하네스는 네 지표의 수집·집계·정확성을 자동 검사하지 않는다. 작성자와 리뷰어가 확인한다. 사건 수는 사람의 평가나 merge 점수로 쓰지 않고 반복 실수를 줄이는 데 쓴다.

작업 유형·범위·규칙 버전이 비슷한 작업끼리 사건 수와 부담 사유를 비교한다. 표본 수·미확인 수를 함께 보고 해당 없음과 미확인을 0건으로 집계하지 않는다. 숫자가 줄었어도 조건이 다르면 규칙이나 도구의 효과로 단정하지 않는다. 기록 자체가 부담이면 양식을 줄인다.
