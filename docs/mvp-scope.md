# 최소 MVP 범위

상태: 두 방향을 함께 구현하는 범위 · 2026-09-28. 이전 보고서의 '휴대폰 연결 우선' 순서는 이 문서로 대체한다.

## 확정 사항

- Android 우선, Expo/React Native/TypeScript로 이후 iOS를 고려한다.
- 더미 금융 API는 별도 서버로 실행한다. 실제 금융사 연결과 자동이체는 없다.
- Flowcast의 사용 여유·What-if와 목적별 배분 계획을 한 앱에 포함한다.
- 현금 흐름 계산은 앱의 공통 finance-core가 담당한다. 서버는 저장과 분석 담당이다.
- AI는 반복 지출 후보를 탐지·분석한다. 규칙+범용 LLM/Jev 교체 지점을 분리한다.
- 실제 휴대폰 연결·설치는 뒤로 미룬다. 최종 완료 형태인 Android 기기 시연은 유지한다.

## 초기 구현 범위 제안

| 화면           | 최소 행동                                                        |
| -------------- | ---------------------------------------------------------------- |
| 데모 연결      | 합성 사용자·계좌·거래 스냅샷 조회, 조회 시각 표시                |
| 지출 후보 확인 | 카드 청구·주거비·공과금·구독·대출 상환·보험 후보 확인/제외/수정  |
| 사용 여유      | 가용금액·계산 근거·일별 기준·부족 상태, 즉시 출금 What-if        |
| 배분 계획      | 고정비·생활비·저축·비상금 계획 수정, 계좌별 부족, 은행 이동 안내 |

결과 화면의 두 탭으로 사용 여유·배분을 묶을 수 있다. 초기 fixture는 계좌 3개·과거 3개월·정상/부족/지출 변경 3개 사례를 제안한다. fixture 기준일을 고정해 테스트 날짜에 따라 결과가 바뀌지 않게 한다.

Google/Kakao 로그인은 계획에 남겨두되 첫 흐름에서는 명확히 표시한 데모 사용자를 쓴다. 실제 공개 서비스에 데모 접근을 그대로 노출하지 않는다. 대화형 AI·계좌 상품 추천·완전한 오프라인 동기화·iOS 배포는 후속 확장이다.

## 검증 순서

1. 공통 구조·하네스 → 공통 계약과 금융 규칙 검토.
2. PC에서 mock-bank → api 조회, 계약 검증, 계산 단위 테스트.
3. 두 기능의 화면 구현과 저장·오류 처리. 브라우저 확인은 보조 검증이며 네이티브 동작을 보증하지 않는다.
4. Android 빌드와 실제 기기 설치·통신·은행 링크 검증.

## 최소 MVP 완료 조건

- 별도 더미 서버 데이터로 두 화면 흐름이 연결되고 지출 수정이 양쪽에 일관되게 반영된다.
- 배분·What-if가 실제 잔액과 거래를 변조하지 않는다.
- 정상/부족/변경 사례, 카드 청구 중복, 내부 이체, 저장 실패를 재현한다.
- 확정한 지출·계획이 재실행 후 유지되고 오래된 스냅샷이 표시된다.
- 후속 Android 실기기 검증까지 마쳐야 '시연 완료'로 표시한다.
