# 최소 MVP 범위

개발 관리자 포함 4명의 기여자가 사용 여유와 목적별 배분을 한 앱에 구현한다. 휴대폰 연결은 후속 단계다.

## 확정 사항

- Android부터 개발하고 Expo/React Native/TypeScript로 이후 iOS를 준비한다.
- 금융 데이터는 별도 더미 서버의 합성 데이터다. 실제 금융기관 연결과 자동이체는 없다.
- 앱의 finance-core가 현금 흐름을 계산한다. 서버는 저장과 분석을 담당한다.
- AI는 반복 지출 후보와 근거를 제안한다. 규칙·범용 LLM·Jev를 같은 입력·출력으로 교체할 수 있게 한다.
- 최종 완료 형태는 Android 실제 기기에 설치해 시연하는 것이다. 지금은 PC 기반 개발부터 한다.

## 초기 화면 제안

| 화면           | 최소 동작                                                       |
| -------------- | --------------------------------------------------------------- |
| 데모 연결      | 합성 사용자·계좌·거래 조회와 조회 시각 표시                     |
| 지출 후보 확인 | 카드 청구·주거비·공과금·구독·대출 상환·보험 후보 확인·제외·수정 |
| 사용 여유      | 가용금액·근거·일별 기준·부족 상태·즉시 출금 What-if             |
| 배분 계획      | 고정비·생활비·저축·비상금 계획 수정·계좌별 부족·은행 이동 안내  |

사용 여유와 배분은 결과 화면의 두 탭으로 묶을 수 있다.
초기 데이터는 계좌 3개·과거 3개월·정상/부족/지출 변경 3개 사례를 제안한다. 기준일을 고정해 실행 날짜에 따라 결과가 달라지지 않게 한다.
Google/Kakao 로그인은 계획에 유지한다. 첫 흐름은 데모 사용자임을 표시하고 실제 공개 서비스에 데모 접근을 그대로 노출하지 않는다.
대화형 AI·계좌 상품 추천·완전한 오프라인 동기화·iOS 배포는 이후 추가한다.

## 개발과 검증 순서

1. 공통 구조와 하네스를 준비하고 데이터 형식·금융 규칙을 검토한다.
2. PC에서 mock-bank→api 조회, 데이터 형식 검사, 계산 테스트를 실행한다.
3. 두 기능의 화면·저장·오류 처리를 연결한다. 웹 미리보기는 네이티브 동작 검증을 대신하지 않는다.
4. Android 빌드·실제 기기 설치·통신·은행 링크를 검증한다.

## 완료 조건

- 더미 서버로 두 화면 흐름이 연결되고 지출 수정이 양쪽에 같은 결과로 반영된다.
- 배분과 What-if는 원본 잔액·실제 거래를 바꾸지 않는다.
- 정상·부족·변경, 카드 청구 중복, 내부 이체, 저장 실패를 재현한다.
- 확정 지출과 계획은 재실행 후 유지되고 오래된 스냅샷은 표시된다.
- 실제 Android 기기 검증을 마친 뒤에만 시연 완료로 보고한다.
