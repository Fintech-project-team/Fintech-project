# 남은 설계 작업 — 확정 사항 재질문 금지

확정 정책, 개발자가 채울 구현 값, GitHub와의 미승인 범위 변경을 구분한다. 이미 결정된 제품 항목은 다시 선택하도록 요구하지 않는다. 과거 기준의 변경 근거는 [검토 이력](reconciliation-report.md)에 보존한다. 첫 번째 표는 개발 중 채울 값·산출물이며 이미 결정한 정책의 보류가 아니다. 범위 변경 요청은 마지막 절에 별도로 표시한다.

## 확정 경계와 구현 권장안

- 기존 세션 PIN 복구·급여 입금 후 지출 반영·선택 잔액 합산은 [제품 기준](product-baseline.md)과 [계산 기준](calculation-rules.md)을 따른다.
- 운영 복원 직후에는 연결 0·선택 0·미계산이며, 지정 계좌를 선택한 뒤 기준 금액을 검증한다. 연결 전 목록·건수·버전과 연결 후 금융 자료의 공개 범위는 [응답 모델](api-response-models.md)을 따른다. 조회 필드를 이유로 물리 테이블 수를 자동 증가시키지 않는다.
- 총 2명·공동 PM이며 과거 계정 수·HMAC 제안을 현행 요구로 적용하지 않는다. 최초·최대·종료 부족, 우발 입력 폐기, 일중 순서 불확정은 각 기준 문서를 따른다. 구현 패키지는 담당자가 선택한다.
- 토큰 종료·소실·유효 토큰 복구는 [HTTP 인증 계약](api-contract.md)을 따른다. 기기 토큰만 소실되고 서버의 기존 활성 세션이 남아 있으면 운영 종료 전에는 새 로그인을 허용하지 않는다.
- 의미가 정해지지 않은 `category`는 v0.6 계약에서 제외한다. v0.7의 기존 네 거래 분류 `transactionType` 사용은 **설계 권장안**이다. 반복 후보는 ID·이름·이유·근거로 표현하며 별도 소비 카테고리를 추가하지 않는다. API/화면 담당자가 의미·응답 계약을 확인한다.
- 실패 연출을 **계정의 연결 흐름별 최초 시도 1회**로 관리하는 방식은 재현 가능한 구현 권장안이다. 실제 서버 실패와 구별하고 같은 흐름 재시도에서 재추첨하지 않는다. 사용자 직접 선택으로 기록하지 않는다.

검증 미실행, 기술 선택 미완료, 사용자 정책 미결정은 같은 상태가 아니다.

## 후속 공급자 연동 — MVP 완료의 선행 조건 아님

실제 금융 API 공급자·상품·인증·조회 기간·정정 방식은 미정이다. 공급자 선정 후 공식 규격과 PAYSE 필드의 대응·미제공 필드·페이지/정정 규칙을 검증한다. CODEF 직접 사용이나 동일 형식 더미 생성으로 되돌리지 않는다. 공통 형식을 만들었다는 사실만으로 금융기관·마이데이터 API 호환을 검증했다고 표시하지 않는다.
