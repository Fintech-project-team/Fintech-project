# PAYSE 실행 공통 계약

AI·Flutter·API의 실행 경계와 확정 결정을 정의한다. **정책 확정·권고 설계·구현 완료를 구분한다.** 새 HTTP·DB·Snapshot 필드는 이 문서만으로 추가되지 않는다. 전달 계약은 `PAYSE-DRAFT-3` / `PAYSE-API-0.6-3`, 계산은 `PAYSE-CALC-1`을 유지한다.

## 필수 참조와 단일 기준

AI 해석·실행 시점·승인·보류·재사용을 구현·변경·검증할 때 이 문서의 해당 절을 **필수로 읽는다**. 서버 LLM 작업과 Flutter의 분석 요청·상태 조회·결과 복구·재시도 연동은 [API 상세](../apps/api/docs/llm-execution.md)의 관련 절도 필수다. 과거 결정·원문 대조·검사 결과 조사 때만 [검토 이력](../apps/api/docs/history/2026-10-27-execution-review.md)을 필수로 읽는다. 작업별 경로는 [검사 기준](harness/GATE_MATRIX.md)에 따라 `readBefore`에 넣는다.

| 주제                                                          | 규칙의 원본                                                                |
| ------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 제품 범위·P0/P1·비용 총상한/차단선/여유액·종료 시각 잠정 폐기 | [제품 기준](product-baseline.md), [API 비용](product-baseline.md#api-비용) |
| 금융 계산·반복 수치·급여 경계·지급 연결 정정                  | [계산 기준](calculation-rules.md), [데이터 모델](data-model.md)            |
| 인증·금융 쓰기·멱등 순서·공개/페이지                          | [HTTP 계약](api-contract.md), [응답 모델](api-response-models.md)          |
| 계층 책임·상태 수명·원천과 해석                               | [앱 구조](app-architecture.md), [데이터 경계](data-contracts.md)           |
| 신규 실행 경계·Q1~Q4                                          | 이 문서. API 상세가 공통 정책을 다시 정의하지 않음                         |

최신 사용자 결정 → 대체되지 않은 기존 합의·공통 계약 → 권고 설계 순으로 적용한다. 최신 작업 요청의 **불확실한 금융 영향은 확인 후 적용** 원칙을 유지한다. 과거 ‘AI 판단 후 통보·정정’ 방향을 무조건 자동 승인으로 확대하거나 confidence를 정답률·승인 임계값으로 쓰지 않는다.

## 보존·복구 확정 기준

| 결정           | 확정 기준                                                                                                                                                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1 키 관리     | 외부 관리형 키 서비스의 상위 키와 결과별 데이터 키를 분리하는 봉투 암호화를 적용한다. 제품·알고리즘·운영 권한·도입 비용은 구현 전에 구체화한다.                                                                                       |
| D2 보존·폐기   | 일반 결과는 최초 저장부터 달력3개월. AI 참고자료이면서 중요보존 플래그가 활성화되면 장기 보존한다. 예외는 이 3개월 폐기에만 적용하며 탈퇴 후1년 파쇄는 유지한다. 백업·복제본·키를 포함한 복구 가능성을 관리한다.                      |
| D3 재시도      | 유효 DB 결과 우선, 공급자 재호출은 사용자 다시 시도로만 수행한다. 완료 불명 재시도도 허용하되 중복 실행 가능성을 알리고 기존 시도·예약을 보존한다. **최대 횟수는 지정하지 않는다**. 자동 재호출이나 비용 제한 해제는 허용하지 않는다. |
| D4 재시도 식별 | 상세 운영 기록은 종료 후7일, 본문 없는 최소 재시도 식별 기록은 최초 작업 접수부터 달력3개월 보관한다. 재시도로 기산일을 연장하거나 비용 기록을 초기화하지 않는다. 결과·키·비용 장부의 수명은 각각 분리한다.                           |

중요보존을 해제하면 최초 저장 시각 기준의 원래 3개월 기한으로 돌아간다. 이미 기한이 지났으면 **즉시 폐기 대상**으로 전환하며 기간을 다시 시작하지 않는다. 탈퇴 계정의 일반 결과는 기존 3개월 기한을 연장하지 않고, 중요보존 결과도 탈퇴 후1년에는 파쇄한다. 이미 폐기한 자료는 플래그를 다시 켠다고 복원되지 않는다.

**장기 보존과 현재 분석에 사용할 자격은 별개**다. 중요보존은 필수 참조 지정이 아니며 비활성·구근거 결과도 보관만 유지할 수 있다. 참조하려면 활성·보관 허용·현재 관련 원천/버전 유효·현재 접근 권한을 모두 충족해야 한다. 사용자 정정·원천 사실이 우선하며, 장기 보존을 거래 정정의 미래 전체 규칙 확대나 금융 설정 자동 변경으로 해석하지 않는다. AI 참고자료 분류·플래그 설정 주체/권한은 API 설계에서 구체화하며 모델 출력만으로 보존/참조 권한을 바꾸지 않는다. 상세 저장·키·복구 조건은 [API 상세](../apps/api/docs/llm-execution.md#분석-결과운영-기록과-보관)를 따른다.

## 책임·보관·응답 채택

- Flutter/Dart는 집계·반복 후보 수치·차이·부족·급여 경계·U·미래 H/A·대안·영향 범위를 계산한다. API는 권한·소유권·버전·참조·저장 제약·LLM 중계, AI는 의미·허용 후보·검증된 지표 설명만 담당한다. 서버 운영 제어가 금융 중요도·반복성·부족 여부를 다시 계산하지 않는다.
- 원천·확정 설정·로컬 산출·발화 원문 구간·AI 후보·운영 기록을 구분한다. 이는 논리적 출처 구분이며 새 v3 필드가 아니다. 원천 잔액·급여 근거·거래를 AI나 사용자 확인으로 덮어쓰지 않는다. 원천에 이미 반영된 급여 재가산·보호금 중복 차감을 금지한다.
- 원천·확정 설정은 기존 DB에 유지한다. 로컬 계산 후보·사용자 보류·가상 소비·조정 초안은 흐름/세션 메모리다. LLM 해석·설명·회고 결과는 이 로컬 객체와 분리해 Q1대로 암호화 저장한다. DB에 저장했다고 후보가 승인되지는 않는다. 로그아웃·계정 교체·흐름 종료·프로세스 종료 시 기기 메모리를 폐기하되 저장된 분석 결과를 함께 삭제하지 않는다. PIN 잠금만으로 흐름 메모리를 폐기하지 않는다.
- 사용자는 서버에만 연결하고 서버는 DB와 LLM에 각각 연결한다. 서버는 입력·권한 검증 → 유효 DB 결과 조회 → 필요한 LLM 요청 → 응답 검증·암호화·DB 커밋 → Flutter 전달 순서로 처리한다. 요청 입력의 영구 보관은 승인되지 않았으며 임시 평문은 처리 후 해제하고 로그에 남기지 않는다. 분석 저장/조회·키 관리·폐기·공개 통신은 미구현이며 구체 스키마는 별도 설계한다.
- 거래와 가능한 로컬 계산을 먼저 표시하고 분석 대기와 계산 제한 사유를 구분한다. 근거/coverage 부족은 영향받는 범위만 보류하며 전체 분석 완료로 표시하지 않는다.
- 신규 요청은 사용자·세션·Snapshot 버전·asOf·선택·관련 설정·근거를 일관되게 사용한다. 인증 정보·원천 전체 JSON·계좌번호를 모델에 자동 전송하지 않는다. 내부 입력 이름·키 구성 제안은 API 상세에 있으며 공개 계약 승인을 뜻하지 않는다.
- 진행 중 응답은 같은 사용자·현재 세션 epoch·관련 입력 지문·inputRevision·버전·작업ID에서만 채택한다. 이전 세션의 늦은 응답을 새 화면에 적용하지 않는다. 재로그인 후 DB 결과는 저장 당시 세션과의 일치가 아니라 **현재 인증·소유권·접근·관련 입력/버전**을 다시 검증해 새 조회 응답으로 제공한다. 전체 dataVersion만 달라져도 기존 응답의 버전을 덮어쓰지 않고 재검증한다.
- 분석은 `notNeeded/eligible/queued/running/candidateReady/failed/deferred/cancelled/stale`, 후보는 `unreviewed/approved/excluded/deferred`의 논리 상태로 구분한다. 이 이름은 구현 제안이다. candidateReady는 확정 입력이 아니며 승인/제외는 정의된 서버 저장 성공 후만 확정한다. 무응답·보류는 승인·실제 미지급 확정이 아니다.
- 결과의 활성/비활성, 필수/일반 참조, 중요보존 여부, 작업 진행 상태를 독립적으로 구분한다. **필수 참조도 위 보존·복구 기준의 현재 참조 자격을 충족해야 하며 사용자 정정과 원천 사실이 우선**이다. 비활성화·장기 보관·실제 폐기는 다르다. 구체 컬럼·변경 권한은 공개 스키마 확정 전 별도 설계하며 모순 상태를 검증한다.
- 동일 입력은 재사용/진행 작업 관찰, 관련 입력 변화는 이전 결과 stale 처리다. 모델·프롬프트·규칙·스키마 변경은 캐시 미사용 조건이며 과거 전량 재분석 명령이 아니다. 단순 재조회·캐시 소실만으로 AI를 재호출하지 않는다.
- DB 결과가 없다는 사실만으로 미전송을 단정하지 않는다. 진행/완료 불명 작업을 먼저 확인하고 중복 호출을 막는다. 실패·유실 후 재호출은 사용자의 **다시 시도**로만 요청하며 유효 DB 결과가 발견되면 모델 호출 없이 반환한다. 최초 자동 분석과 기존 회고 열람은 각 EX 조건을 유지하며 독립적인 수동 분석 버튼으로 확대하지 않는다.
- 원문 속 지시문은 데이터로 취급한다. 후보 밖 ID·금액/일정 생성·SQL/저장 명령을 거절한다. 설명 숫자는 검증된 metricId로 표시하며 자유 문장을 실행값으로 쓰지 않는다. 자연어 후속 계약의 실제 원문 span 추출만 별도 검토한다.
- 금융 쓰기는 기존 HTTP 계약의 **인증·형식 → 기존 키/본문 대조·replay → 신규 버전/참조/제약 → 원자 저장·영수증·버전 → 새 Snapshot의 Dart 계산** 순서다. 응답 유실은 같은 키·본문으로 확인하고 새 키를 자동 만들지 않는다. AI 지문과 금융 멱등 키는 별개다. 외부 호출 중 DB 사용자 잠금을 유지하지 않는다. 취소/장애가 커밋 전 확인되면 해당 미완료 업무 변경을 롤백한다. 이미 커밋된 결과는 유지하고, 커밋 여부 불명은 조회/멱등 확인 전 성공·미실행으로 단정하지 않는다. 인증 실패 제한·외부 비용 기록은 지우지 않는다. 상세는 [SQL 취소 기준](../apps/api/docs/sql-style.md#취소실패와-커밋-경계)을 따른다.

## 동작별 실행 조건

아래는 기존 계약을 적용한 실행 명세다. **미구현 경로의 완료 선언이 아니다.** 권고 상태·운영 프로필은 API 상세에서 구분한다. AI 접수 게이트는 AI 하위 경로만 제한하며 정상 금융 조회·쓰기·Dart 계산을 차단하지 않는다. 모든 동작은 위 응답 채택·저장 경계를 따른다.

확인 질문 키 권고는 사용자 범위·questionType·대상 ID(없으면 payMonth)·관련 근거 지문·policyVersion이다. `isSalaryTransaction`(월급/아님/나중에)과 `missingReceiptForMonth`(거래 선택/아직 미입금/나중에)를 구분한다. ‘아직 미입금’은 별도 저장 계약 전까지 기기 안내일 뿐 원천 unknown을 미지급 확정으로 바꾸지 않는다. 거래 금액/상태/명시 참조·관련 급여 설정·후보 집합 변화만 근거 변경이며, 탭·시각·로그인 변경은 제외한다. 새 근거·메모리 소실 뒤 재접속도 강제 팝업을 만들지 않는다. 목록·상세 배치는 B 설계다.

자연어 후속 분기는 실제 span·조건 종류·후보 ID·누락만 허용한다. “60만원”→600000원, “다음 달”→고정 Asia/Seoul 기준일의 월 범위 변환은 Dart이며 임의1일을 구매일로 확정하지 않는다. 유효한 기존 조건을 재사용하고 누락 조건만 확인한다. 목표·가정·구간·부분 결과를 표시하고 늦은 추출이 사용자의 수정을 덮지 않게 한다.

## 공통 반례·인수 조건

기존 테스트를 읽은 `정의 확인`, 목표 벡터인 `신규 정의`, 미구현/예외 가능성의 `공백 확인`은 **제품 실행 PASS가 아니다**. 관련 동작 구현·회귀 검증에서는 해당 EX와 아래 AT를 함께 필수 참조한다. AT19의10건/60초는 **Q2 확정 인수 조건**이며 AT20은 **D3의 최대 횟수 미지정·자동 재호출 금지·중복/비용 검증** 기준이다. 그 외 미확정 프로필 수치를 승인하지 않으며 나머지 AT도 근거 상태와 실행 여부를 구분한다.

API `demo-ready.json`의 `sourceVersion=fixture-3:alpha:2026-10-19:base:demo-ready`, `dataVersion="1"`, `asOf=2026-10-19T12:00:00+09:00`, ruleVersion=`PAYSE-CALC-1`을 사용한다. 선택 계좌는 `6069b37a-abf5-56fc-8bf0-153f5301fd1c`(1,500,000원), `67521b1b-de86-54cf-98ba-91bb04d0a256`(500,000원)이다. 이 ID는 검증할 fixture를 고정한 근거이며 제품 코드에 하드코딩하라는 지시가 아니다.

9월분 9/25 급여는 confirmed이며, 월세 30만원은10/22, 카드값 11만원은10/10 완납, 통신비 5만원은10/25의 다음 구간이다. 비상금은40만원이며 배정은 없다. 기대값은 **B2,000,000 / E300,000 / R400,000 / O0 / U1,300,000원**이다. 이 값은 fixture·산식 기준이며 모바일 통합 실행 PASS를 뜻하지 않는다.

모바일 홈 테스트의 `alphaWithReceipt()`는 다른 자료다. alpha-ready 사본에9/25 근거를 추가하여 **E360,000 / O60,000 / U1,300,000**이다. U가 같다는 이유로 demo-ready 통합 검증으로 대체하지 않는다. 현재 모바일 기본 alphaReady/계정 매핑과 API demo-ready의 차이는 남은 B 동기화다.
