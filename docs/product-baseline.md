# 제품·버전 기준

개정일 2026-10-15. [최신 업무표](references/work-brief.source.md)를 최우선 적용한다. v8/v7에서 달라진 점은 [충돌 보고](reconciliation-report.md)에 기록한다.

## 범위와 실행 책임

PAYSE는 Flutter iOS·Android에서 `파악 → 판단 → 조정`을 제공하는 MVP다. 개발자는 **총 2명이며 두 사람 모두 공동 PM**이다. 별도 PM·디자이너·QA 인원을 전제하지 않는다.

실제 금융기관 연결·본인확인·SMS는 구현하지 않는다. 서버는 준비된 사용자별 더미 금융 데이터를 제공하고 예정 지출·모아둘 돈 등 확정 설정을 저장한다. **사용 가능 금액·계좌 합산·소비 분석 수치·시뮬레이션·조정 비교는 Flutter 기기에서 계산한다.** 서버는 권한·입력·소유권·버전·저장 제약을 검증하며 U나 미래 잔액을 계산해 반환하지 않는다. DB 제약을 위한 범위·합계 검사는 화면 금액 계산과 구분한다.

LLM은 서버 게이트웨이를 통해 호출한다. 거래명·유형·설명 해석을 반환하며, 금융 금액/일정의 규칙 계산과 최종 결과 구성은 로컬이 담당한다. 계좌 계산을 서버로 보내는 이전 확정 재계산 문구는 적용하지 않는다. 서버 역할을 LLM 호출 하나로 축소하지도 않는다.

Flutter/Dart·PostgreSQL은 확정이다. 서버 언어·프레임워크·상태 관리 도구는 개발자가 위 책임 경계를 지키며 선택한다. Dart API는 선택 가능한 기존 권장안이며 필수 스택이 아니다. 자체 LLM 서버는 요구하지 않는다.

## 최신 업무표의 우선순위

| 우선순위 | 작업·산출물                                               |
| -------- | --------------------------------------------------------- |
| P0       | 데이터 항목·타입·관계 정의 → 데이터 명세서                |
| P0       | 사용자별 계좌·카드·거래·핵심 시나리오 준비 → 더미 JSON    |
| P0       | 사용자 식별·확정 계획·보호 설정 저장 설계 → ERD·DB 스키마 |
| P0       | 금융 조회·사용자 설정 CRUD 설계 → API 명세                |
| P0       | 사용자 매핑·별도 인증·세션·접근 차단 검토 → 인증 설계안   |
| P1       | 더미 조회·설정 저장 서버 구현 → 실제 API 동작 확인        |

1차 완료는 위 P0 설계·준비 산출물을 갖추는 단계다. **P1 서버 구현**은 그 다음 우선순위로 보존한다. 서버 저장을 구현·검증하지 않은 상태에서 ‘재로그인 후 설정 유지가 동작하는 MVP’라고 판정할 수 없다. 설계 완료와 작동하는 MVP 통합 완료는 서로 다른 단계다.

## 사용자 식별·인증·저장

- 식별 입력은 **합성 이름·전화번호**다. 주민번호 앞7자리·통신사는 현행 필수 수집 항목에서 제외한다. 이름·전화번호만으로 기존 계정에 접근할 수 없다.
- 권장 인증안은 사전 생성 데모 사용자 + 별도 고정 테스트 코드 + 서버 세션이다. 기존 코드/PIN 흐름을 재사용하며 실제 회원 생성·SMS·본인확인이 아니다. 이름/전화번호는 대상 조회, 코드는 별도 자격 확인, 내부 userId는 데이터 소유권에 쓴다. 세부 설계는 [데이터 계약](data-contracts.md)의 권장안이다.
- 이름은 앞뒤 공백만, 전화번호는 명시적으로 허용한 공백·하이픈만 정규화한다. 그 밖의 문자를 무조건 삭제해서 대조하지 않는다.
- 제출 정보는 **현재 인증 흐름의 메모리에만 유지**한다. 실패 재시도는 유지하고, 성공·취소·흐름 이탈·앱 프로세스 종료 시 폐기한다. 서버는 대조 요청 수명 동안만 취급하며 제출 원문을 DB·로그·오류 추적·LLM에 남기지 않는다. 사전 합성 시드 저장은 별개다.
- 사용자별 활성 세션 하나: 기존 로그인 유지·신규 로그인 거절. 기존 결정의 자동 만료 없음·로그아웃/탈퇴/운영 종료를 유지한다. 이 데모 정책을 실서비스 보안 기준이라고 주장하지 않는다.
- 기기 PIN은 6자리, 동일 숫자·연속 오름/내림 제한. 재실행·10분 무입력/백그라운드 후 잠금, 5회 오류/분실은 기존 유효 토큰+현재 합성 식별 정보·코드 재확인 후 PIN만 재설정한다. 새 세션을 발급하지 않는다.
- 토큰이 없거나 종료됐으면 식별 입력부터 새 로그인한다. 서버에 이전 활성 세션이 남았는데 기기 토큰만 소실되면 운영 종료 전에는 신규 로그인을 허용하지 않는다.
- 3분 코드 표시 타이머·‘다시 받기’의 표시 전용 동작은 유지한다. 코드 재발급/실제 만료 기능을 새로 추가하지 않는다.
- 금융 데이터·확정 설정은 안정적인 내부 userId에 귀속된다. 같은 사용자로 재로그인하면 유지하고 다른 userId는 접근할 수 없다. 하나의 데모 자격을 여러 사람이 공유하면 같은 사용자로 취급된다는 한계를 숨기지 않는다.
- 로그아웃·데모 탈퇴는 세션/기기 접근 정보를 정리하며 서버 금융 설정을 초기화하지 않는다. 운영 시드 복원은 별도다. Participant/HMAC 식별 구조는 추가하지 않는다.
- 합성값만 요구해도 실제 값이 우발적으로 제출될 수 있다. ‘실제 정보가 서버에 올 수 없다’고 단정하지 않는다.

## 금액·보호·보존

`U=B−E−(R−O)`: B 선택 잔액, E 미정산 의무, R 보호 설정, O 명시 배정 겹침. 예금·적금도 선택하면 합산하고 미선택이면 제외한다. 자동 계좌 간 충당은 가정하지 않는다.

급여일 당일·연체 미지급 예정 지출은 급여 입금 확인 뒤 홈 E에 반영한다. 예정 급여 선가산·실제 출금된 B 복원·음수 숨김은 하지 않는다. 날짜만 있으면 일 마감 결과만 확정하고 일중 순서는 불확정이다.

보호 신규/증액은 계좌별 보호 합계와 전체 합계를 모두 검사한다. 잔액 하락으로 기존 R을 자동 축소하지 않는다. 지급 정정은 원천 거래를 고치지 않고 내부 연결·잔여 의무·보호 배정을 바로잡는다. [계산 기준](calculation-rules.md)을 따른다.

확정 계획/설정은 서버 DB에 보존한다. 가상 소비·추가 미래 가정·결과·조정 초안은 기능 메모리만 사용한다. 잠금에서 유지하고 실제 흐름 이탈/프로세스 종료에서 폐기한다.

## API 비용

사용자 지정 **API 운영 비용 총상한 50,000원, 기한 2026-11-05**를 적용한다. 모델별·개발자별·월별로 각각 50,000원을 배정하지 않는다. 정확한 일중 종료 시각은 별도 운영 설정이며 문서가 임의로 확정하지 않는다. 이 날짜를 앱 출시일로 바꾸지 않는다.

서버에서 누적 사용량·진행 중 호출의 예상 최대 비용·재시도 비용을 함께 통제한다. 원화 한도에는 환산·세금·결제 수수료 영향을 고려하여 보수적인 중단 여유를 두는 방식이 권장된다. 구체 호출 수/토큰/여유액은 담당자가 산정한다. 공급자의 예산 알림만으로 중단을 보장하지 않는다. [OpenAI 지출 한도](https://developers.openai.com/api/docs/guides/spend-limits)

PostgreSQL 버전·배포 서비스·마이그레이션 도구는 개발 선택이다. 서버/DB 호스팅에 별도 유료 예산이 승인됐다고 해석하지 않는다. 기존 LLM 첫 평가 대상 gpt-6-luna/Responses API/Structured Outputs는 유지하되 실제 계정 접근·호출·품질은 아직 검증하지 않았다.
