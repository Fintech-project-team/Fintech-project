## 공통 설계 원칙과 합리성 검토

### 결정 1. 계산 위치와 확정 권한을 분리한다

- **Flutter 로컬:** 원본 스냅샷을 조회한 뒤 사용 가능 금액, 반복 후보의 규칙 계산, 소비 1~5건의 최대 3개월 시뮬레이션, 조정안 비교를 순수 Dart 함수로 계산한다. 입력을 바꿀 때마다 네트워크 요청하지 않는다.
- **경량 API:** 인증·사용자 소유권·입력·버전·중복 요청을 검증한다. 확정 쓰기에서는 DB 원본과 사용자가 승인한 변경 입력으로 같은 계산 규격을 실행하고 원자적으로 저장한다. LLM 호출도 이 API의 한 모듈이 담당한다.
- **DB:** 원본 더미 계좌·거래, 승인된 예정 지출, 확정 설정과 최소 변경 기록을 보존한다. DB는 LLM도 아니고, 앱이 보낸 계산 결과를 그대로 승인하는 계산 서버도 아니다.
- **외부 LLM API:** 거래명 해석·분류, 반복 후보 추천 이유, 선택적 계획 대안 설명을 제공한다. 금액 생성·확정·저장 권한과 DB 접근 권한을 주지 않는다.

**최소 운영 구성은 관리형 DB 1개 + 경량 API/LLM 게이트웨이 1개다.** DB는 **PostgreSQL**(지원되는 안정 버전 고정, 개발/통합 데이터 분리, 마이그레이션 관리, 세부는 미결정 M9)이다. 금융 원본은 **CODEF 응답 형식을 따르는 합성 더미**이며, 첫 LLM 평가 대상은 **`gpt-6-luna` + Responses API + Structured Outputs**다(운영 기준은 미결정 M8). 외부 LLM 서비스 호출은 별도이며, 자체 계산 전용 서버·자체 LLM 추론 서버는 불필요하다. 이는 두 개의 논리적 구성요소를 뜻하며 물리 서버 두 대를 직접 운영하라는 뜻은 아니다. 한 API 배포 안에서 검증·재계산·LLM 호출을 모듈로 나눈다.

이 범위는 이벤트 정렬·정수 덧셈/뺄셈으로 구현할 수 있어 로컬 처리에 적합하다는 설계 판단이다. 3개월은 데이터의 시간 범위이지 복잡한 모델 추론이 아니다. 실제 성능은 기기 QA로 확인하고, UI 지연이 측정되면 isolate로 옮긴다. Flutter는 비용이 큰 계산을 별도 isolate에서 수행하는 방법을 제공한다. [Flutter 공식 문서](https://docs.flutter.dev/cookbook/networking/background-parsing)

### 결정 2. 단일 계산 규격을 앱과 API가 공유한다

기본안은 **Flutter 앱 + 경량 Dart API + 순수 Dart `payse_calculation` 패키지 + 관리형 DB**다. Dart의 서버 실행·공유 패키지 지원을 활용할 수 있다. [Dart 공식 문서](https://dart.dev/server)

- 패키지는 Flutter UI, DB, 네트워크, LLM에 의존하지 않는다. 동일 입력·동일 `ruleVersion`이면 동일 결과를 반환한다. 기준시각을 입력받고 기기 현재시각을 함수 안에서 읽지 않는다.
- 단일 규격에는 금액 단위, 대상 계좌, 거래 상태, 결제 일정, 중복 키, 기간 경계, 보호 자금, 미래 가정, 오류 상태를 포함한다.
- API가 다른 언어로 이미 구현되어 있다면 이전만을 위해 재작성하지 않는다. 동일 버전의 규격·JSON 입출력·기대값 테스트 벡터를 두 구현에서 실행하고 **원 단위까지 일치**해야 한다. 이 경우 규칙 변경 때 양쪽을 동시에 검증하는 비용을 일정에 포함한다.
- 공유 코드나 결과 해시만으로 클라이언트가 신뢰되는 것은 아니다. API가 DB에서 다시 읽은 원본으로 검증·재계산해야 한다.
- P0는 계산값을 DB의 유일한 원본으로 저장하지 않는다. 확정 입력을 저장하고 필요할 때 파생한다. 성능상 결과 캐시를 둔다면 API가 생성한 값에 `dataVersion`, `ruleVersion`, `asOf`를 붙이고 원본 변경 시 무효화한다.

### 결정 3. 확정 쓰기는 신뢰 경계 안에서 처리한다

클라이언트 검증은 빠른 안내용이다. 클라이언트 요청을 우회할 수 있으므로 API 검증도 필요하다. [OWASP 입력 검증 지침](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html)

1. 앱은 사용자 승인 변경 입력, `expectedDataVersion`, `ruleVersion`, `idempotencyKey`를 보낸다. 계산한 최종 잔액·가용금액은 확정 입력 필드로 받지 않는다.
2. API는 인증된 데모 세션과, 그 세션에 연결된 데모 계정의 객체 소유권(결정 5), 허용 필드, 원 단위 정수·범위·날짜·상태 전이·연결 계좌·중복 키를 검증한다. 가입·로그인 형식 화면, 데모 계정 세션·계정별 데이터 격리·중복 로그인 차단은 P0다(결정 4).
3. API는 DB 원본을 트랜잭션 안에서 읽고 요청 버전과 비교한다. 다르면 `409 STALE_DATA`; 새 스냅샷으로 다시 비교한 후 사용자가 재확정한다.
4. 최신 원본에 승인된 변경만 적용하고 공통 규격으로 재계산한다. 음수 가용금액 자체는 저장 오류가 아니라 부족 상태다. 음수 보호 설정·알 수 없는 거래 연결 등 유효하지 않은 입력은 거절한다.
5. 원본/설정·필요한 연결 상태·최소 변경 기록·새 데이터 버전을 함께 커밋한다. 앱은 응답을 받아 화면과 로컬 캐시를 갱신한다. 타임아웃 재시도는 같은 멱등 키를 사용하고, 같은 키에 다른 입력은 거절한다.

이 경로가 필요한 작업은 계좌 선택·설정 변경, 예정 지출 직접 추가·승인/수정/취소, 모아둘 돈 추가·수정, 더미 돌발지출 반영, 모아둘 돈 확정 변경이다. 로컬 미리보기에는 이 쓰기 경로를 호출하지 않는다. 오프라인에서는 마지막 동기화 시각을 표시한 조회·미리보기만 가능하고 확정 저장 성공으로 표시하지 않는다.

LLM 키와 DB 비밀 자격증명은 API의 환경변수/비밀 저장소에만 둔다. 앱 번들·원격 설정·소스 저장소·클라이언트 로그에 넣지 않는다. 게이트웨이에 인증·요청량 제한·타임아웃·구조 검증을 둔다. [OWASP 비밀정보 관리 지침](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)

### 결정 4. 본인인증은 형식만, 데모 계정은 공유해서 쓴다

- 초기 흐름은 국내 금융 앱 구조를 따른다: 약관 동의 → 본인 확인 정보 → 인증번호 → 간편 비밀번호 6자리 설정 → 금융사 고르기 → 받아올 정보 동의 → 불러오기 → 계좌 선택. 간편 비밀번호는 금융 정보를 받아오기 전에 만든다. 다시 사용할 때는 간편 비밀번호로 로그인한다. 생체 인증은 범위에서 제외한다.
- 금융사 정보 제공 동의는 형식만 구현한다. 사용자가 고르고 동의한 금융사의 계좌·카드만 스냅샷에 포함한다. 실제 마이데이터의 인증서 인증 단계는 이번 범위에서 빼고 정식 서비스 때 추가한다. 이미 금융사 연결과 계좌 선택을 마친 공유 계정이면 이 단계들을 건너뛴다.
- 본인 확인 정보(이름·주민등록번호 앞 7자리·통신사·휴대폰 번호)는 진행자가 건네는 **합성값**을 입력한다. 실제 본인 확인과 문자 발송은 하지 않으며, 실제 본인확인 연결 준비 기능도 만들지 않는다(실제 인증은 후속 범위).
- 서버는 입력값을 DemoAccount에 미리 저장한 합성 가입 정보와 대조하고, 입력값은 저장하지 않는다(결정 5).
- 앱 화면에는 테스트용 앱이라는 안내 문구를 넣지 않는다. 가상 데이터라는 사실, 합성 가입 정보와 테스트 코드는 진행자가 테스트 전 안내·카드·참여 동의서로 알린다.
- 인증번호 단계에서 테스트 코드를 입력해 **미리 만들어 둔 데모 계정 중 하나에 로그인**한다. 계정 수와 코드는 보류(미결정 M1)이며 문서의 `000001`~은 예시다. 새 사용자를 만들지 않으며, 데모 계정은 개발자와 테스트 참여자가 돌려 쓴다.
- 테스트 코드는 고정값이며 만료·재발급이 없다. 실제 문자를 보내지 않는다. 인증번호 화면의 3분 타이머와 "인증번호 다시 받기"는 일반 금융 앱처럼 보이게 하는 표시용이다: 타이머는 0:00에서 멈추고, 다시 받기는 0:00 이후 활성 스타일로 바뀌지만 눌러도 동작하지 않으며, 0:00 이후에도 같은 테스트 코드로 진행할 수 있다(결정 U1, 10/15 변경). 데모 세션 정책과는 별개다.
- 데모 계정 하나에는 동시에 활성 세션 하나만 허용한다. 사용 중인 계정의 코드를 입력하면 가입 정보 불일치·없는 코드와 같은 응답(`401 INVALID_CODE`)을 주고, 앱도 같은 토스트("인증번호가 맞지 않아요")로 안내한다. 계정이 사용 중이라는 사실은 노출하지 않는다.
- 데모 세션은 만료되지 않는다. 잠금은 로그아웃·탈퇴 때만 해제하며, 로그아웃하지 않으면 다른 사람은 그 계정을 쓸 수 없다. 로그아웃 없이 앱을 지우거나 기기를 잃으면 잠금이 남으므로, 개발자가 DB에서 해당 세션을 직접 종료하는 운영 절차를 둔다.
- 앱에서 10분 동안 입력이 없으면 간편 비밀번호 입력 화면으로 잠근다. 백그라운드에 10분 이상 있다가 돌아올 때도 같다. 세션은 그대로 유지되므로 잠금 해제는 서버 요청 없이 기기에서 간편 비밀번호만 확인하고, 해제 후에는 보던 화면으로 돌아간다.
- 데모 계정에서 추가·수정한 예정 지출·모아둘 돈·설정은 로그아웃이나 탈퇴 뒤에도 서버에 그대로 남는다. 앱에는 원래 상태로 되돌리는 기능을 두지 않으며, 일반 사용 흐름에서는 다음 사용자가 이전 사용자가 바꾼 상태에서 시작한다. 사용성 테스트의 시작 조건은 운영자가 **테스트 환경 복원 절차**(상세 계획 7-3)로 맞추며, 이 절차는 사용자 기능이 아니다.
- 탈퇴는 이 기기의 가입 정보·간편 비밀번호를 지우고 세션을 끝내는 동작이다. 서버의 계정 데이터는 지우지 않는다.
- 간편 비밀번호와 세션 토큰은 기기 보안 저장소에만 둔다. 다시 사용할 때는 간편 비밀번호를 확인하고 저장된 세션을 그대로 쓴다.
- 간편 비밀번호는 숫자 6자리다. 같은 숫자 6개(111111)나 1씩 오르거나 내리는 연속 숫자(123456·654321)는 쓸 수 없다. 6번째 숫자를 입력하는 즉시 입력을 지우고 "같은 숫자나 연속된 숫자는 쓸 수 없어요."를 표시하며 만들기 단계에 머문다. 확인 단계에서 다르면 "비밀번호가 일치하지 않아요."를 표시하고 다시 입력받는다.
- 금융사 불러오기 화면의 진행과 실패는 앱의 표시 연출이다. 더미 데이터는 항상 받아올 수 있지만, 일반 금융 앱처럼 보이도록 금융사를 차례로 처리하고(1곳당 1~1.5초), 금융사 연결을 처음 할 때만 금융사별 10% 확률로 "다시 시도" 상태를 만든다(한 번에 최대 2곳). "다시 시도"를 누르면 2~3초 뒤 반드시 완료된다. 실패한 금융사가 남으면 "○○ 제외하고 계속하기"(1곳)·"N곳 제외하고 계속하기"(2곳 이상)를 제공하고, 은행이 모두 빠져 계산할 계좌가 없으면 계속하기를 막는다. 사용성 테스트용으로 진행자가 실패 연출을 끄고 켤 수 있는 개발 설정을 둔다(앱 화면에는 노출 안 함).
- 받아올 정보 동의는 앱이 기억했다가, 불러오기 연출을 마치고 계속할 때 최종 금융사 목록(동의한 금융사 − 제외한 금융사)으로 `POST /institution-links`를 한 번 보낸다. 이 요청이 실제로 실패하면 연출이 아닌 실제 오류(조회 실패 상태)로 안내한다.

### 결정 5. 가입 정보는 합성값이고, 금융 데이터는 데모 계정이 소유한다

| 객체 | 역할 | 핵심 필드 |
|---|---|---|
| `DemoAccount` | 가상 금융 데이터·확정 설정의 소유 단위. 합성 가입 정보와 테스트 코드를 미리 저장 | demoAccountId, testCode, syntheticIdentity, displayName |
| `DemoSession` | 어떤 기기가 어떤 DemoAccount를 언제 썼는지의 기록, 권한 판단의 기준 | sessionId, demoAccountId, deviceId |

1. 가입 정보(이름·주민등록번호 앞 7자리·통신사·휴대폰 번호)는 **모두 합성값**이다. DemoAccount마다 합성 가입 정보와 테스트 코드를 DB에 미리 저장하고, 진행자가 참여자에게 이 값을 건넨다. 실제 본인확인과 그 연결 준비 기능은 만들지 않는다.
2. 실제 개인정보는 수집하지 않는다. 참여자 식별용 객체(Participant)와 식별 키(HMAC)는 두지 않는다. 사용성 테스트 참여자는 진행자 기록의 참가 번호(P01…)와 sessionId 대응으로만 구분하며, 이 대응표에는 실명·연락처를 적지 않는다.
3. 계좌·거래·예정 지출·모아둘 돈·카드 설정·급여 일정·금융사 연결·계좌 선택·계좌 이름 등 모든 금융 데이터와 확정 설정은 DemoAccount에 속한다.
4. 여러 참여자가 같은 DemoAccount를 순차적으로 쓸 수 있고, 저장된 변경은 다음 참여자에게도 보인다. 동시에는 활성 세션 1개만 허용한다(결정 4). 참여자별 금융 데이터 분리 기능은 만들지 않는다.
5. API의 금융 데이터 접근 권한은 인증된 DemoSession에 연결된 demoAccountId로만 검증한다. 요청 본문의 계정 ID는 믿지 않는다.
6. 확정 변경 최소 기록(`ChangeRecord`)은 demoAccountId와 sessionId를 가지며 개인정보를 넣지 않는다.

## 공통 계산 규격 — PAYSE-CALC-1

### 현재 사용 가능 금액과 수입 처리

> 표기 대응: 결정 요약본의 B(선택 계좌 잔액)·F(보호할 목적자금)·P(승인된 미지급 예정 지출)·S(B−F−P)는 이 문서의 B·R_eff·E·U와 같다. 이 문서는 예정 지출을 모아둘 돈에서 낼 때의 겹침(O)을 따로 둔다.

```text
B(t) = 동일 기준시각 t의 연결·포함 계좌 잔액 합계
E(t,h) = 현재 시점부터 다음 월급일 h 직전까지 남은,
         승인된 미출금 예정 지출의 합계(중복 의무 제거)
R(t) = 포함 계좌 잔액 안에서 아직 보호 중인 모아둘 돈
O(t,h) = E 중 R에서 충당하기로 명시적으로 연결한 중복 예약액
R_eff(t,h) = R(t) - O(t,h)
U(t,h) = B(t) - E(t,h) - R_eff(t,h)
```

- **입금 완료 급여/수입은 B에 이미 포함된다. 수입을 다시 더하지 않는다.** 미래 급여는 현재 U에 더하지 않고 시뮬레이션에서만 예정 입금 이벤트로 반영한다. 잔액 스냅샷 방식과 과거 거래 전량 합산 방식을 동시에 적용하지 않는다.
- 수동/더미 기초잔액에서 재구성할 때만 `기초잔액 + 이후 반영 완료 수입 - 이후 반영 완료 출금`으로 B를 만든다. 스냅샷에 반영된 거래는 다시 재생하지 않는다. 자기 계좌 간 이체는 포함 계좌 전체 자산을 늘리거나 줄이지 않는다.
- E는 사용자 승인된 유효 의무 중 잔액에 아직 반영되지 않은 금액이다. 미승인 추천·취소·출금 완료는 제외한다. 연체 미출금은 없어진 지출이 아니므로 별도 경고와 함께 현재 E에 포함하고 예측에서는 기준시각의 우선 출금으로 보수적으로 배치한다.
- R은 새 저축 출금이 아니라 기존 잔액의 보호 설정이다. 합산 대상에서 뺀 계좌의 보호액은 다시 R에 넣지 않는다. 부족해져 R이 B보다 커져도 설정을 자동 축소하지 않고 부족을 표시한다. 새로 만들거나 늘리는 모아둘 돈은 비음수 B 이내로만 허용하고, 기존 과대 설정을 줄이는 것은 허용한다(복수 계좌에서 상한·귀속 기준은 미결정 M5).
- 기본은 E와 R의 목적이 겹치지 않는 데이터다. 겹치면 의무별 `fundingReserveId/allocatedAmount`로 명시한다. O는 각 의무 금액과 보호액 이하이고 전체 배정은 보호액을 넘지 않아야 한다. 같은 목적이라는 추측으로 자동 상계하지 않는다. 연결이 불명확하면 확정 계산을 막고 정정을 안내한다.
- 예정 지출과 실제 출금액이 다를 수 있다. 카드 결제 예정 금액은 결제일 전 카드 사용에 따라 다음 스냅샷에서 갱신된다(예: 300,000 → 345,000). 출금이 확실한 근거로 의무에 연결되면 의무를 정산하고 "이미 나간 돈"에 **실제 출금액**으로 표시한다. 출금액은 이미 B에 반영됐으므로 E에서 뺀다(`remainingAmount = max(0, amount − 정산액)`). 예정보다 많이 나가도 초과분을 E에서 다시 빼지 않고, 적게 나가면 남은 금액만 E에 남긴다. 금액만 같거나 비슷하다는 이유로 연결하지 않으며, 연결이 확실하지 않으면 예정일 지난 미출금처럼 E에 계속 포함하고 표시한다.
- 보호 자금에서 실제 출금되면 B가 줄고, 해당 E가 정산되며, 배정한 R도 같은 금액만큼 해제된다. 그래서 지출과 보호 해제를 함께 반영해 이중 차감을 막는다. 보호 설정을 줄이는 것만으로 B가 늘어나지는 않는다.
- U가 음수이면 값을 0으로 덮지 않고 부족액 `max(0,-U)`와 함께 표시한다. 이 수치는 PAYSE의 계획상 금액이며 금융기관이 보증하는 출금 가능액이 아니다.

**산식 검증 예:** B=2,000,000원(이미 입금된 급여 포함), 미출금 카드 대금 300,000원, 승인 예정 지출 200,000원, 별도 보호액 400,000원이면 U=1,100,000원. 카드 대금 출금 후 B=1,700,000원·E=200,000원이 되어 U는 그대로다. 별도 예로 B=1,000,000원·R=300,000원·E=300,000원이 같은 목적자금에 전액 연결되면 O=300,000원, U=700,000원이다. 해당 지출 후 B=700,000원·E=R=O=0으로 U=700,000원을 유지한다.

### 최대 3개월과 월급 주기 경계

**본 개정의 기간 해석:** ‘다음·다다음·다다다음 월급 주기’를 **현재부터 첫째·둘째·셋째 다음 월급일까지 도달하는 세 구간**으로 정의한다. 현재 구간에 미래 완전한 세 주기를 덧붙여 약 네 달을 계산하지 않는다. 화면에서는 아래 실제 날짜와 명칭을 함께 표시한다.

| 구간 | 범위 | 화면 명칭 |
|---|---|---|
| C1 | `[t0, p1)` | 다음 월급일까지 — 현재 주기의 남은 기간 |
| C2 | `[p1, p2)` | 다다음 월급일까지 |
| C3 | `[p2, p3)` | 다다다음 월급일까지 |

`t0`는 스냅샷 기준시각, `p1~p3`는 t0 이후의 확인된/가정된 월급일이다. **종료 상한은 `min(p3, t0에서 달력상 3개월 뒤)`**다. p2/p3 일정이 없고 사용자가 선택한 반복 가정도 없으면 해당 후속 구간은 생성 가능한 것처럼 꾸미지 않고 정보 부족으로 둔다. 3개월 뒤 날짜가 해당 월에 없으면 말일을 쓴다. 비정기 급여로 p3가 상한 밖이면 마지막 구간을 잘라 불완전 구간이라고 표시한다. 다음 급여일 자체가 없으면 주기 비교는 정보 부족이다. 구매일은 `[t0, 종료 상한)` 안에서만 입력한다.

- 왼쪽 경계 포함·오른쪽 경계 제외. 급여일 당일의 입금·출금은 모두 다음 구간에 속한다(결정 D5): p1 당일 입금/출금은 C2, p2 당일은 C3, p3 당일은 범위 밖이다. 홈의 "다음 월급일까지 쓸 수 있는 돈"도 p1 당일 출금을 포함하지 않는다.
- **구간 전환은 월급 입금 확인 시점이다(결정 D5, 10/15).** 날짜가 월급일이 되어도 급여 입금 거래가 스냅샷에 반영되기 전에는 p1을 오늘 월급일로 유지하고 이전 구간으로 계산하며, 예상 월급을 쓸 수 있는 돈에 미리 더하지 않는다. 입금이 확인되면 p1을 다음 월급일로 옮기고, 월급일 당일 출금을 포함한 다음 구간의 예정 지출로 다시 계산한다. 월급일이 지나도 입금이 없으면 이전 구간을 유지하고 "월급 미입금" 상태로 표시한다(화면 09-14·09-15). 종료일 당일과 이후 결제는 ‘범위 밖 미반영 의무’로 금액·날짜를 따로 안내하며 영향이 없다고 표시하지 않는다.
- 날짜는 Asia/Seoul의 업무 날짜로 계산하고 스냅샷은 `asOf`와 반영 완료 거래 식별자를 가진다. 기준일의 이미 반영된 거래와 남은 이벤트를 분리한다. 날짜만 입력하는 UI는 기준일 당일의 앞으로 실행할 가상 구매를 허용하고, 그 이벤트를 스냅샷 직후로 정규화한다. 기준일 이전 구매는 거절한다. 실제 반영 여부는 날짜만으로 추정하지 않고 스냅샷의 반영 ID로 판단한다.
- 미래 월급일이 29~31일이고 그 달에 그 날짜가 없으면 말일을 예정일로 쓴다. 휴일 이동은 자동 추정하지 않고 명시된 월별 날짜를 사용한다. 카드도 실제 카드사 규칙을 추정하지 않고 더미 청구 일정 또는 사용자가 확인한 결제 예정일을 쓴다.
- 같은 날 정확한 시각이 확인되면 시각순으로 계산한다. 날짜만 있으면 순서를 만들지 않고 **일 마감 순액**으로 계산하며 **일중 순서 불확정**을 표시한다(결정 D4, 이전의 출금 먼저 가정은 폐기). 같은 날 입금과 출금이 함께 있으면 "순서에 따라 잠시 부족할 수 있음" 경고를 표시하되, 일중 최소 잔액·최초 부족 시각은 확정하지 않으므로 부족 지표(최초 부족 시점·최대 부족액)에 넣지 않는다. 복수 소비는 결제 수단·계좌별로 대조한다.

### 이벤트 계산·기간별 출력·중복 방지

```text
H(t) = B(t0) + t0 이후 t까지의 예정 입금 - 예정 출금
A(t) = H(t) - 해당 주기 끝까지 남은 지출 예약 - 남은 유효 보호액
차이(t) = A_모두반영(t) - A_기존(t)
```

실제 구현은 t0 스냅샷 이후 미반영 이벤트만 순서대로 재생한다. H는 예상 계좌 잔액이고 A는 현재 U와 같은 예약 규칙을 적용한 예상 사용 가능 금액이다. 시뮬레이션에서는 기존 승인 지출에 가상 소비 출금 이벤트를 더하되 가상 목록은 실제 승인 상태로 저장하지 않는다.

- 상한 때문에 마지막 구간이 잘리면 해당 비교의 지출 예약도 잘린 구간 끝까지 계산한다. 이후 의무는 삭제하지 않고 범위 밖 목록에 남긴다.
- 기간별로 시작/종료 예상 잔액, **종료 직전 예상 사용 가능 금액**, 기간 중 최소 A, 최초 계획상 부족 시점/금액, 최소 H/현금 부족을 구별해서 출력한다. A의 부족은 보호·예정 지출을 유지하기 어렵다는 뜻이며 실제 계좌 잔액 H의 부족과 다르다. 기간별 금액은 이월 잔액 기반이므로 세 행을 합산하지 않는다.
- 이전 기간의 **H와 남은 의무·보호 상태**를 이월한다. 이미 E/R을 뺀 A를 다음 기간 기초잔액으로 이월해서 다시 빼지 않는다. 출금 시 H 감소와 해당 예약 해제를 동시에 처리한다.
- 즉시 출금은 구매일에 출금 이벤트 1개. 카드 일시불은 승인일에 현금 차감 없이 확인된 대금 결제일에 출금 이벤트 1개다. 카드 청구서 총액과 그 총액에 포함된 개별 승인을 함께 차감하지 않는다.
- 더미 데이터에 `obligationId`, `settlementId`, `statementId`, 포함된 거래 ID를 명시한다. 청구서 총액을 현금 출금의 대표 이벤트로 쓰고 포함 승인내역은 설명용으로 연결한다. 청구서에 아직 포함되지 않은 신규 가상 구매만 별도 증분으로 더한다. 같은 금액·날짜라는 이유만으로 동일 의무라고 추측하지 않는다.
- 가상 목록의 각 `itemId`는 유일하다. 기존 의무를 또 입력한 것이 명시적으로 확인되면 중복 오류를 반환한다. 동일 이름의 실제 별도 구매는 허용한다. 중복 연계 여부가 불명확하면 경고/확인 없이 자동 차감하지 않는다.
- 부분 출금은 미출금 잔여액만 E에 둔다. 취소는 미출금 의무와 그 의무의 보호 배정 연결을 해제하되 아직 보유한 보호액 R 자체를 자동으로 없애지 않는다. 이미 출금한 지출은 취소만으로 B를 올리지 않고 환불 입금 이벤트가 반영될 때만 B가 증가한다.
- 미래 급여·반복 지출·보호 설정 유지 여부는 사용자가 확인한 설정이나 명시적으로 선택한 반복 가정이 있어야 한다. 가변 생활비를 반영하지 않았다면 그 사실을 표시한다. 계획에 넣지 않은 지출이 없을 것이라고 LLM이 가정하지 않는다.
- 입력된 미래 일정은 ‘사용자 확인 예정’, 반복 가정은 ‘가정 기반 예측’, 반영 완료 스냅샷은 ‘현재 기록’으로 구별한다. **설정 확정과 미래 사건 발생 확정은 다르다.**
- 필수 수입·결제일·의무 연결 정보가 없으면 영향받는 기간의 절대 금액은 `null/insufficientData`다. 이전까지 계산 가능한 구간은 유지한다. 결제일을 전혀 몰라 어느 구간에 영향을 주는지 모르면 관련 전체 비교를 미완성으로 표시한다. 정보 부족을 0원·영향 없음·계획 유지 가능으로 바꾸지 않는다.
- 세 구간 계산 능력은 P0다. 원본 정보가 부족한 특정 사례에서 일부 구간이 미계산인 것과, 구현 자체가 한 구간만 지원하는 것을 구분한다.

쓰기 공통 필드는 `expectedDataVersion/ruleVersion/idempotencyKey`다. 데모 계정 ID는 요청 본문에서 받지 않고 인증 세션에서 결정한다(결정 5). 계산된 잔액/가용금액·임의 승인 상태·다른 데모 계정 참조는 허용 필드가 아니다. 모든 확정 쓰기는 ChangeRecord에 demoAccountId·sessionId와 함께 남긴다. 검증 실패 422, 인증/권한 오류 401/403, 오래된 데이터/같은 멱등 키에 다른 본문 409로 처리한다. 알려지지 않은 규격 버전은 재동기화 후 재확정한다. 데모 세션은 만료되지 않는다. lastActiveAt은 남은 잠금을 운영자가 확인하는 용도로만 갱신한다. 운영자가 강제 종료한 세션의 요청은 401로 거절하고, 앱은 인증번호 입력부터 다시 안내한다.

**검증의 한계:** API 검증은 DB 더미 원본과 규칙에 대한 무결성을 보장한다. 사용자가 입력한 미래 급여나 확인 날짜가 현실에서 반드시 발생함을 증명하지는 않는다. 자금 이동 기능은 구현하지 않는다.

**저장 전 미리보기 규칙 (03-2 예정 지출 수정·03-5 모아둘 돈 수정 공통)**

1. 입력값이 바뀌면 Flutter가 공통 계산 패키지로 로컬 재계산한다.
2. 저장 전에는 "변경하면 쓸 수 있는 돈 A원 → B원"으로 미리보기만 보여준다.
3. 미리보기는 DB 설정을 바꾸지 않는다.
4. 저장을 누르면 변경 입력만 API로 보낸다(계산 결과는 보내지 않는다).
5. API 검증·저장에 성공하면 최신 스냅샷을 다시 받아 화면을 갱신한다.
6. 저장에 실패하면 미리보기 금액을 확정된 금액처럼 표시하지 않고 기존 금액을 유지한다(충돌은 09-6).
7. 모아둘 돈 금액을 바꿔도 계좌 잔액은 늘지 않는다. 바뀌는 것은 쓸 수 있는 돈뿐이다.

와이어프레임 예시는 같은 기준 데이터(B 2,000,000원 · E 500,000원 · R 400,000원 → U 1,100,000원)를 쓴다. 03-2 관리비 200,000원 → 180,000원이면 U 1,120,000원, 03-5 비상금 400,000원 → 300,000원이면 U 1,200,000원이다.

**계좌별 출금 제약:** v0.6의 쓸 수 있는 돈은 포함 계좌를 합산한 값이다. 특정 결제 계좌의 출금 부족(예: A계좌 100,000원·B계좌 1,000,000원일 때 A계좌에서 나갈 카드 대금 300,000원)은 계산·표시하지 않으며, 통합 금액이 충분해도 모든 카드 대금이 해당 계좌에서 출금 가능하다는 뜻이 아니다. v0.6에서는 처리하지 않는다. 계좌별 출금 부족은 v0.8 F08-13(P1)에서 다룬다(결정 U2). v0.6 사용성 테스트용 시드는 특정 결제 계좌의 출금 부족이 생기지 않도록 금액을 맞춘다(특히 데모 계정 4).

P0 후보 규칙은 **최근 달력 3개월**(90일로 바꾸지 않고, 없는 월말 날짜는 보정) 거래에서 월간 반복부터 시작한다: **정규화 거래명 일치·3회 이상·월별 날짜 ±5일·금액이 중앙값 대비 ±10% 이내**(결정 D8). 이 수치는 채택했지만 성능 검증 전이다(미결정 M4: 재수신 중복·월말·변동 금액·가격 변경·비반복 유사 구매 평가 필요). 공백/대소문자/명시된 결제 접두어 제거 규칙을 버전 관리한다. 예상액은 마지막 확인 금액, 예정일은 확인된 반복 일정에 따라 산출한다. 일정이 없거나 변동 금액이면 자동 승인 후보 대신 확인 필요로 남긴다. 카드 거래는 구매 반복일과 실제 청구 출금일을 분리한다. 이름 변형 해석을 LLM이 돕더라도 새 그룹의 금액은 규칙으로 다시 계산하고 근거를 검증한다.

LLM 응답 최소 필드는 `candidateId`, `normalizedName`, `category`, `recommendationReason`, `evidenceIds`다. **LLM의 임의 amount/dueDate는 받아들이지 않는다.** 근거 원본의 숫자를 참조할 수 있어도 추천 수치의 권위는 규칙/사용자 확인에 있다. 거래명에 포함된 지시문도 데이터로 취급한다.

```text
DB 원본 거래 → API 규칙 후보(금액·일정·근거)
                    → 외부 LLM(이름·유형·추천 이유)
                    → API 응답 구조/근거 검증
                    → 앱 확인·승인/제외
                    → API 원본 검증·중복 검사·재계산·DB 저장
                    → 새 스냅샷 → 앱 로컬 재계산
```

## 5. v0.9 — 돌발지출 이후 자금 계획 조정

v0.8은 소비 전 가상 판단이다. v0.9는 DB 더미 원본에 이미 반영된 변화를 바탕으로 설정을 바꾸는 단계다. 실제 금융거래·송금을 실행하는 기능은 아니다.

**변경 범위:** 모아둘 돈 설정액 1종을 우선 완성한다. 자유 입력한 비음수 금액을 비교할 수 있고 부족 상태는 그대로 보여준다. 이미 예정 지출에 배정한 보호액보다 낮게 줄이는 입력은 P0에서 거부한다. 배정 해제를 함께 편집하는 고급 조정은 후속이다. 추천 금액 자동 최적화·복수 프리셋은 필수가 아니다.

```text
준비된 더미 돌발지출 → API 원자적 반영 → 새 DB 스냅샷
  → 앱 로컬 금액·원인 확인 → 보호액 초안 → 로컬 전후 비교
  ├─ 유지/취소: 초안 폐기
  └─ 확정: 승인 입력·버전·멱등 키 전송
        → API 원본 재조회·검증·재계산
        → DB 설정/변경 기록/버전 커밋 → 앱 재조회·결과 확인
```

미리보기 중 다른 변경이 발생하면 API는 충돌을 반환한다. 앱은 새 기준으로 전후 금액을 보여주고 다시 승인을 받는다. v0.8의 가상 items·가정·LLM 대안은 확정 요청에 포함하지 않는다.

| 구분 | 내용 |
|---|---|
| 수행자 | 개발자 A 또는 DB 권한을 받은 진행자 |
| 도구 | 서버 저장소의 운영 스크립트(예: `restore_demo_account --account N`). 공개 API·앱 UI 없음 |
| 기준 데이터 | 데모 계정별 시드: 계좌·잔액·거래·예정 지출·모아둘 돈·카드 설정·급여 일정·금융사 연결 상태·계좌 선택·계좌 이름·반복 후보 상태. 기준 상태는 금융사 연결 전(결정 U3): 금융사 연결·계좌 선택 없음, 계좌 이름은 기본값 |
| 복원 범위 | 지정한 DemoAccount의 금융 데이터와 확정 설정 전체를 한 트랜잭션으로 시드와 같게 바꾸고 dataVersion을 올림 |
| 건드리지 않는 것 | 지난 DemoSession, 기존 ChangeRecord(복원 자체는 kind=operator_restore로 추가), 다른 데모 계정 |

**절차**

1. 테스트 시작 전 해당 데모 계정의 기준 데이터를 확인한다.
2. 지정한 데모 계정에 활성 세션이 있는지 확인한다.
3. 필요하면 운영자가 그 세션을 종료한다(활성 세션이 있으면 스크립트는 복원하지 않고 멈춘다).
4. 시드로 테스트 상태를 복원한다.
5. 테스트 참여자가 로그인한다.
6. 사용자 과제를 진행한다.
7. 테스트를 마치고 결과를 참가 번호로 기록한다.
8. 참여자가 로그아웃한다.
9. 다음 참여자 테스트 전에 4단계 기준 상태로 다시 복원한다.

**복원 전후 체크리스트**

- [ ] 복원 전 해당 계정 활성 세션 0개
- [ ] 거래·예정 지출·모아둘 돈·카드 설정·금융사 연결·계좌 선택 건수와 값이 시드와 일치
- [ ] 앱 공통 계산 패키지와 API의 U가 계정별 기준 벡터와 일치(데모 계정 1은 TC-C01: U 1,100,000원)
- [ ] dataVersion 증가, 이전 캐시를 가진 기기는 409 후 최신 스냅샷 조회
- [ ] 기존 ChangeRecord가 그대로이고 operator_restore 기록 1건 추가
- [ ] 참가자별 테스트 시작 상태 기록: 참가 번호·데모 계정·복원 시각·dataVersion·시작 U

**구분 원칙:** 로그아웃·탈퇴는 세션과 기기 정보만 다루고 계정 데이터를 바꾸지 않는다. 복원은 운영자만 하며 테스트 기록(참가 번호 기록)을 지우지 않는다.

**MVP 한계:** 더미 원본과 사용자 입력/가정으로 만든 계획 지원 도구다. 계좌 합계 기준 현금 흐름은 특정 출금 계좌의 실제 지급 능력·카드 한도·은행 처리 시각을 보증하지 않는다. 수수료/이자·할부·변동 급여 예측·일반 카드사 청구 규칙 자동 수집·장기 투자/대출 분석은 제외한다. 개발 전 설계 검토로 로컬 가능성을 판단했으며 실제 성능·구현 정확성은 위 테스트를 통과해야 확정된다. 본인인증은 형식이며 가입 정보는 모두 합성값이다. 실제 신원을 확인하거나 실제 개인정보를 수집하지 않는다. 데모 계정은 공유하므로 이전 사용자의 변경이 다음 사용자에게 남고, 로그아웃하지 않은 계정은 운영자가 풀기 전까지 다른 기기에서 쓸 수 없다.
