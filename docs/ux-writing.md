# PAYSE UX 라이팅 가이드

> 문서 버전: v1.0 · 작성일: 2026-11-24 · 확정일: 2026-11-24(혜연 결정)  
> 적용 대상: PAYSE 앱 v0.6 QA 및 이후 문구 작성  
> 상태: 팀 기준(G-01 채택). 10절의 남은 결정은 합의 전까지 확정 결함으로 판정하지 않는다.

## 1. 목적과 적용 범위

PAYSE의 문구는 사용자가 **지금 돈의 상태를 이해하고, 계산의 근거를 확인하며, 다음 행동을 선택하게** 돕는다. 친근한 표현을 쓰되 금액·기간·저장 여부를 모호하게 만들지 않는다.

이 문서는 토스의 원칙을 참고해 PAYSE에 맞게 작성한 기준이다. 원문의 요약과 PAYSE 자체 제안을 구분한다. 앱인토스 입점 여부는 확인하지 않았으며, 해당 플랫폼의 모든 규정을 PAYSE의 의무로 간주하지 않는다.

- 적용: 제목, 본문, 버튼, 입력 안내, 오류, 토스트, 상태 라벨, 빈 화면, 확인 창, 접근성 읽기 문구.
- 별도 관리: 약관 원문, 금융기관이 제공한 명칭, 사용자 입력 이름, 내부 로그·검증 메시지, 테스트 전용 안내.
- 현재 범위: v0.6에서 실제 노출되는 기능. 이후 버전의 추천·시뮬레이션을 이미 제공하는 것처럼 안내하지 않는다.
- 문구 수정으로 계산 규칙, 인증 정책, 저장 동작을 바꾸지 않는다. 문구가 실제 동작과 충돌하면 기능·정책 확인 사항으로 함께 기록한다.

현재 문구 목록과 체크리스트는 읽기 전용으로 참고했다. 이 문서는 앱 코드 수정이나 실기기 QA 완료 보고서가 아니다. 아래의 **수정 예시는 별도 표시가 없는 한 제안 문구**다.

## 2. 참고 원칙과 PAYSE의 적용 방향

### 2.1 토스의 8가지 원칙

토스는 명확성, 간결함, 친근함, 존중, 공감을 바탕으로 여덟 가지 작성 원칙을 설명한다. 아래는 각 원칙의 짧은 요약과 PAYSE에서 사용할 질문이다. [출처: 토스의 8가지 라이팅 원칙들](https://toss.tech/article/8-writing-principles-of-toss)

| 원칙 요약                     | PAYSE에서 확인할 질문                                       |
| ----------------------------- | ----------------------------------------------------------- |
| 다음 행동을 예측하게 한다     | 계좌 조회와 계산 대상 변경을 버튼만 보고 구별할 수 있는가?  |
| 불필요한 단어를 덜어낸다      | 금액의 조건을 해치지 않고 줄일 수 있는가?                   |
| 내용 없는 문장을 없앤다       | 제목을 반복하는 대신 필요한 계산 근거를 제공하는가?         |
| 핵심 정보에 집중한다          | 이 화면에서 판단할 금액·기간·상태가 먼저 보이는가?          |
| 말로 해도 쉬운 표현을 쓴다    | ‘가용액’ 대신 사용자가 이해할 설명이 있는가?                |
| 강요보다 선택을 돕는다        | 소비나 설정 변경을 압박하지 않는가?                         |
| 널리 이해할 수 있는 말을 쓴다 | 금융 지식이나 특정 유행어를 알아야 이해할 수 있지는 않은가? |
| 상황 속 감정을 살핀다         | 부족한 금액을 알릴 때 사용자를 평가하지 않는가?             |

### 2.2 앱인토스 가이드에서 참고한 기준

가이드는 해요체, 능동형과 긍정형, 과하지 않은 경어, 명사를 이어 붙이지 않는 표현을 권한다. 의미 전달에 필요한 수동형·부정형·경어의 예외도 설명한다. 버튼은 다음 행동을 예측하게 해야 하며, 다이얼로그 왼쪽 버튼에는 ‘닫기’를 제시한다. [출처: 앱인토스 UI/UX 가이드 — UX 라이팅·다크패턴 방지 정책](https://developers-apps-in-toss.toss.im/design/consumer-ux-guide)

PAYSE에서는 아래 세 가지를 자체 기준으로 구체화한다.

1. **정확한 금융 상태를 먼저 전달한다.** 긍정적으로 바꾸느라 실패·부족·미확인을 감추지 않는다.
2. **정보를 닫는 것과 행동을 취소하는 것을 구분한다.** 모든 왼쪽 버튼을 ‘닫기’로 통일하지 않고, 5절의 동작별 규칙을 제안한다. 이는 토스 규칙을 그대로 옮긴 것이 아니다.
3. **문장 역할에 따라 표기한다.** 안내 본문과 오류 문장은 마침표를 쓰고, 제목·버튼·라벨은 쓰지 않는 PAYSE 규칙을 제안한다.

## 3. G-01에서 합의할 기본 규칙

2026-11-24 혜연 결정으로 아래 규칙을 채택했다(적용: v0.6 QA부터). QA 판정 기준으로 사용한다.

| 항목           | PAYSE 제안                               | 예시·예외                                                        |
| -------------- | ---------------------------------------- | ---------------------------------------------------------------- |
| 기본 말투      | 사용자에게 설명하는 문장은 해요체        | ‘저장했어요.’ / 버튼·메뉴는 ‘저장하기’, ‘계좌·카드’ 가능         |
| 요청 표현      | 보조 용언은 띄어 쓰는 편집 기준 채택     | ‘확인해 주세요’, ‘골라 주세요’, ‘확인해 보세요’                  |
| 마침표         | 안내·오류·토스트의 서술문에는 사용       | 한 줄이어도 ‘인증번호가 맞지 않아요.’                            |
| 제목·버튼·라벨 | 끝에 마침표를 쓰지 않음                  | ‘계산 내역’, ‘저장하기’, ‘입금 확인 전’                          |
| 질문           | 실제 확인이 필요할 때 물음표 사용        | 확인 창 제목 ‘로그아웃할까요?’                                   |
| 완료 표현      | ‘되었어요’가 필요하면 ‘됐어요’로 축약    | 앱의 저장 성공은 ‘저장했어요.’, 확인된 출금 상태는 ‘출금됐어요.’ |
| 확인 창        | 질문은 ‘~할까요?’, 실행 버튼은 동작 명시 | ‘로그아웃할까요?’ / ‘취소’ · ‘로그아웃’                          |
| 재시도         | 같은 작업을 반복하면 ‘다시 시도’         | 최신 데이터 조회는 ‘다시 불러오기’로 구별                        |
| 금액           | 기존 QA F-11 유지: 정수·천 단위 쉼표·원  | ‘1,250,000원’, ‘-30,000원’, ‘0원’                                |
| 용어           | 동일 개념에는 용어표의 이름 사용         | ‘쓸 수 있는 돈’, ‘남겨둘 돈’, ‘예정 지출’                        |

띄어쓰기·축약·마침표 혼용은 우선 **제품 문구의 일관성 문제**로 분류한다. 허용 가능한 표현을 모두 맞춤법 오류라고 부르지 않는다. 단, 예/아니요로 답할 때의 ‘아니오’는 ‘아니요’로 바로잡을 대상이다. 로그아웃의 버튼 구성 변경은 A-25 재결정과 묶어 관리한다.

### 말투의 강도

| 상황             | 작성 방향                                     | 제안 예시                                                         |
| ---------------- | --------------------------------------------- | ----------------------------------------------------------------- |
| 일반 안내        | 사용자가 할 일을 직접 설명                    | ‘계산에 포함할 계좌를 골라 주세요.’                               |
| 저장 성공        | 무엇을 저장했는지 명시                        | ‘월급 정보를 저장했어요.’                                         |
| 금액 부족        | 금액과 기준을 설명하고 판단은 사용자에게 맡김 | ‘남겨둘 돈과 예정 지출을 모두 확보하려면 30,000원이 더 필요해요.’ |
| 처리 결과 미확인 | 성공·실패를 단정하지 않음                     | ‘저장 결과를 확인하지 못했어요.’                                  |
| 입력 오류        | 수정할 값을 알려 줌                           | ‘인증번호를 다시 확인해 주세요.’                                  |

‘과소비했어요’, ‘이대로면 위험해요’, ‘이 정도는 써도 괜찮아요’처럼 사용자를 평가하거나 소비의 안전성을 보장하는 문구는 쓰지 않는다. 근거 없는 ‘안심하세요’, 오류 상황의 농담·축하·느낌표도 피한다.

## 4. 문장과 화면 요소별 표기

### 4.1 띄어쓰기와 종결

- 띄어쓰기 규칙은 ‘해주세요’라는 문자열 하나에만 적용하지 않는다. ‘골라주세요 → 골라 주세요’, ‘입력해주세요 → 입력해 주세요’도 같은 대상으로 본다.
- 한 단어인 동사를 임의로 나누지 않는다. ‘로그아웃 하시겠습니까?’의 제안안은 ‘로그아웃할까요?’다.
- 완료된 앱 동작은 ‘수정했어요’, ‘저장했어요’처럼 쓴다. 외부 사건의 상태는 ‘출금됐어요’, ‘요청이 만료됐어요’처럼 쓸 수 있다.
- ‘처리되었을 수 있어요’를 ‘처리했어요’로 바꾸지 않는다. 축약하더라도 ‘처리됐을 수 있어요’처럼 불확실성을 유지한다.
- ‘없어요’나 ‘할 수 없어요’를 금지하지 않는다. 실제로 없는 정보, 불가능한 동작, 복구할 수 없는 결과는 분명하게 설명한다.

### 4.2 마침표는 줄 수가 아니라 역할로 결정

| 요소                       | 규칙             | 제안 예시                                       |
| -------------------------- | ---------------- | ----------------------------------------------- |
| 화면·시트 제목             | 마침표 없음      | ‘첫 계산을 준비했어요’                          |
| 확인 창 질문 제목          | 물음표 사용      | ‘변경을 취소할까요?’                            |
| 안내 본문·입력 오류·토스트 | 서술문 끝 마침표 | ‘비밀번호가 맞지 않아요.’                       |
| 여러 문장 본문             | 각 문장에 마침표 | ‘정보를 불러오지 못했어요. 다시 시도해 주세요.’ |
| 버튼·탭·필드명             | 마침표 없음      | ‘다시 시도’, ‘월급일’                           |
| 짧은 상태·배지·메타 정보   | 마침표 없음      | ‘출금 계좌 미확인’, ‘11월 24일 14:30 기준’      |

같은 문자열도 실제 역할을 보고 판정한다. 오류 문구를 한 줄로 표시했다고 제목으로 분류하지 않는다. 10-2·10-3·10-5가 모두 입력 오류라면 같은 마침표 기준을 적용한다.

### 4.3 기호·날짜·동적 문구

- 진행 상태에 말줄임표를 쓴다면 ‘…’ 하나로 통일한다. 말줄임표를 붙여야만 진행 상태가 전달되게 만들지 않는다.
- 같은 수준의 보조 정보는 ‘은행명 · 계좌 끝 4자리’처럼 구분한다. ‘계좌·카드’처럼 묶인 명칭 안의 가운데점은 띄우지 않는다.
- 기간은 ‘11월 25일~12월 24일’처럼 실제 날짜로 설명한다. 좁은 목록에서는 ‘11/25~12/24’를 사용할 수 있다. 연도를 넘거나 과거 기록과 혼동할 때는 연도도 표시한다.
- 내부 기간의 끝 날짜가 조회에서 제외되는 값이라면, 이를 그대로 포함되는 마지막 날짜처럼 표시하지 않는다. 구현된 기간 계약과 표시 날짜를 함께 확인한다.
- 괄호는 횟수·단위 등 짧은 보조 정보에 사용한다. ‘비밀번호가 맞지 않아요. (2/5)’처럼 본문과 카운터의 형태를 정해 일관되게 적용한다.
- 금액의 음수 부호, 거래 방향, 단위를 생략하지 않는다. 계산되지 않은 값에 ‘0원’을 대입하지 않는다.
- 버튼의 이동 화살표는 UI 아이콘으로 관리한다. 화면 읽기에서 ‘보기’와 화살표를 불필요하게 중복 읽지 않게 한다.
- 동적으로 붙는 이름·금액의 조사, 줄바꿈, 긴 계좌명, 빈 값까지 확인한다. TSV의 문자열 조각만으로 완성 문장을 판정하지 않는다.
- 약관·외부 기관명·사용자 별명은 일반 문구 통일을 이유로 임의 변경하지 않는다.

## 5. 확인 창과 버튼

### 5.1 행동과 결과가 일치하는 이름

| 버튼          | 사용할 때                             | 사용하지 않을 때                           |
| ------------- | ------------------------------------- | ------------------------------------------ |
| 닫기          | 안내창만 닫고 끝남                    | 실제 작업을 취소하거나 입력을 버림         |
| 취소          | 확인 중인 행동을 실행하지 않고 돌아감 | 무엇을 취소하는지 두 가지로 해석될 수 있음 |
| 계속 작성     | 입력을 유지하고 편집으로 돌아감       | 편집 내용이 실제로 사라짐                  |
| 변경 취소     | 저장하지 않은 변경을 버림             | 이미 저장한 변경을 되돌리는 기능이 아님    |
| 저장하기      | 변경을 실제로 저장함                  | 단순 미리보기·다음 단계 이동               |
| 다시 시도     | 방금 실패한 동일 작업을 다시 수행함   | 최신 정보 조회만 수행함                    |
| 다시 불러오기 | 최신 정보나 현재 상태를 새로 조회함   | 저장 요청을 다시 전송함                    |

버튼을 ‘취소 + 동작 이름’으로 구성하는 것을 기본으로 하되, 그 조합 자체가 모호하면 더 구체적으로 쓴다. 예를 들어 예정 지출 취소 확인 창은 ‘취소 / 취소하기’ 대신 **‘돌아가기 / 예정 지출 취소’**를 제안한다. 돌아가기가 현재 편집 화면과 입력을 실제로 유지하는지도 확인한다.

‘확인’은 단순 안내를 읽고 닫는 상황에서만 허용한다. 로그아웃·삭제·저장 등 상태를 바꾸는 실행 버튼에는 행동을 적는다. 버튼 전체를 일괄적으로 ‘~하기’로 바꾸지 않고, 같은 기능의 대표 라벨을 재사용한다.

### 5.2 확인 창 작성 순서

1. 제목: 실행할 행동을 묻는다.
2. 본문: 바뀌는 대상과 사용자가 알아야 할 영향을 설명한다. 제목의 반복만 있으면 생략한다.
3. 버튼: 실행하지 않는 선택과 실행하는 선택을 구별한다.

| 상황           | 제목 제안                    | 버튼 제안                     | 본문에 필요한 사실                           |
| -------------- | ---------------------------- | ----------------------------- | -------------------------------------------- |
| 로그아웃       | ‘로그아웃할까요?’            | ‘취소’ / ‘로그아웃’           | 다음 이용에 필요한 절차 등 확인된 영향만     |
| 저장 전 이탈   | ‘변경을 취소할까요?’         | ‘계속 작성’ / ‘변경 취소’     | 어떤 미저장 입력이 사라지는지                |
| 예정 지출 취소 | ‘이 예정 지출을 취소할까요?’ | ‘돌아가기’ / ‘예정 지출 취소’ | PAYSE 계획 변경과 실제 금융 거래 취소의 차이 |

**A-25 재결정 필요:** 현행 체크리스트에는 ‘로그아웃 하시겠습니까?’와 ‘아니오/네’가 지정되어 있다. 위 문구는 대체 제안이며, 합의 전에는 현행을 새 말투 규칙 위반으로 확정하지 않는다. 채택 시 A-25·화면 명세·문구를 함께 갱신한다. 로그아웃 성공 확인 후 기기 정보를 지우는 기존 동작은 문구 변경과 별개로 유지한다.

## 6. PAYSE 핵심 용어표

현재 문구 목록과 QA 문서에서 사용하는 이름을 바탕으로 정했다. 문맥에 필요한 짧은 설명은 허용하되 서로 다른 개념을 같은 말로 합치지 않는다.

‘월급 입금 확인 전’과 ‘입금 확인 전’처럼 짧아진 표현은 주변 문맥으로 대상이 명확하면 허용한다. ‘오늘은 월급일’은 실제 조건이 추가된 정보이므로 단순 변형이라는 이유로 삭제하지 않는다.

### 금융 상태를 지키는 문구 규칙

- 현재 금액에는 기준 기간과 정보 시점을 확인할 수 있는 경로를 둔다. 모든 화면에 긴 설명을 반복할 필요는 없다.
- 음수 계산값은 부족 상태로 전달한다. 이를 정상적인 ‘0원’이나 ‘계산 불가’로 바꾸지 않는다.
- 잔액 미확인, 금액 부족, 월급 입금 확인 전은 다른 상태다. 같은 오류 문구를 공유하지 않는다.
- 월급일 도래를 입금 완료로 표현하지 않는다. 입금이 확인된 근거가 있어야 ‘입금됐어요’라고 쓴다.
- 남겨둘 돈과 예정 지출의 중복 반영을 조정하는 경우, 단순히 두 금액을 모두 빼는 설명만으로 계산 결과를 정당화하지 않는다. 실제 차감 금액과 ‘따로 빼지 않는’ 이유를 계산 내역에서 확인하게 한다.
- PAYSE에서 지출 계획을 취소한 것을 금융기관의 결제 취소나 환불 완료라고 표현하지 않는다.
- 오래된 정보로 보여 주는 값은 최신 조회가 완료된 값과 구별한다. 조회 실패를 ‘거래 없음’으로 바꾸지 않는다.

## 7. 오류·완료·빈 화면의 작성 틀

### 7.1 오류: 확인된 사실 → 영향 → 가능한 행동

G-10의 ‘무엇이 안 됐는지 → 그대로인 것 → 할 일’을 기본 틀로 사용한다. 다만 **그대로인지 확인할 수 없으면 유지됐다고 쓰지 않는다.** 단순 입력 오류마다 세 문장을 채울 필요도 없다.

| 상태               | 제안 문구                                                          | 행동·확인 조건                                                      |
| ------------------ | ------------------------------------------------------------------ | ------------------------------------------------------------------- |
| 입력값 오류        | ‘인증번호가 맞지 않아요.’                                          | 해당 입력을 수정할 수 있어야 함                                     |
| 조회 실패          | ‘거래 내역을 불러오지 못했어요.’                                   | ‘다시 불러오기’; 이전 내역을 남기면 기준 시각 표시                  |
| 저장 실패가 확정됨 | ‘변경 내용을 저장하지 못했어요.’                                   | 실패가 확인된 경우에만 사용. 입력 유지 여부와 재시도 가능 여부 확인 |
| 저장 결과 미확인   | ‘저장 결과를 확인하지 못했어요. 최신 정보를 불러와 확인해 주세요.’ | 상태 조회가 가능한 흐름에만 사용. 무조건 재저장하도록 유도하지 않음 |
| 정보 변경으로 충돌 | ‘정보가 바뀌었어요. 최신 내용을 확인한 뒤 다시 저장해 주세요.’     | ‘다시 불러오기’; 불러올 때 미저장 입력에 미치는 영향도 안내         |
| 월급 주기 미상     | ‘월급 주기를 알 수 없어 이번 기간의 거래를 보여드릴 수 없어요.’    | 실제 지원하는 ‘전체 거래 보기’로 연결                               |
| 처리 중            | ‘저장하고 있어요’                                                  | 아직 완료로 표시하지 않음                                           |
| 저장 성공          | ‘예정 지출을 저장했어요.’                                          | 저장 성공이 확인된 뒤에만 노출                                      |
| 정상 조회 결과 0건 | ‘이 기간의 거래 내역이 없어요.’                                    | 조회가 성공했고 해당 범위가 비어 있을 때 사용                       |

### 7.2 로그인 결과 불명 문구

TSV에는 로그인 결과를 확인하지 못한 상황에서 ‘서버’, ‘테스트 담당자’, ‘세션 종료’를 안내하는 문구가 있다. 이 문구를 짧게 바꾸는 과정에서 **로그인이 이미 처리됐을 가능성**을 없애면 안 된다.

일반 사용자용 첫 문장 제안은 **‘로그인 결과를 확인하지 못했어요.’**다. 뒤에 붙일 행동은 실제 복구 경로가 확인된 뒤 확정한다.

- 재시도가 안전하고 지원되면 해당 행동을 안내한다.
- 로그인 상태 확인이 필요하면 지원되는 확인 절차를 안내한다.
- 담당자의 수동 처리가 필요한 데모 환경이면 테스트용 안내로 명시하고 일반 사용자용 문구와 분리한다.
- 존재하지 않는 고객센터, 자동 복구, 대기 시간을 문구로 약속하지 않는다.

원인을 모르는 오류에 ‘인터넷 연결을 확인해 주세요’를 공통으로 붙이지 않는다. 연결 문제, 인증 문제, 결과 미확인, 서비스 오류를 실제로 구분할 수 있는 만큼 안내한다.

### 7.3 개발 용어의 처리

‘서버’, ‘세션’, 오류 코드가 있다는 이유만으로 내부 파일까지 교체하지 않는다. 사용자 노출 여부와 복구에 필요한 정보를 먼저 확인한다. 제품 화면은 사용자가 이해하고 실행할 수 있는 안내를 사용하고, 진단 세부 정보는 실제 지원되는 상세 영역이나 테스트 기록에서 다룬다. 기술 용어를 지우느라 인증·보안상의 의미를 바꾸지 않는다.

## 9. G-01~G-13 QA 판정 기준

기존 체크리스트의 번호를 유지한다. 기준 합의 후에도 **문구 후보 발견 → 노출·역할 확인 → 실제 동작 대조 → 판정** 순서를 따른다.

| ID   | 기준                                                | 확인 방법                                       |
| ---- | --------------------------------------------------- | ----------------------------------------------- |
| G-01 | 이 문서의 채택 규칙·예외·적용 버전을 기록           | 채택일과 A-25 등 미결정 사항 확인               |
| G-02 | 요청 표현의 보조 용언 띄어쓰기 통일                 | 문자열 검색 후 사용자 노출 문장 검토            |
| G-03 | 안내·오류·토스트의 마침표, 제목·버튼·라벨의 생략    | 같은 역할의 실제 화면을 비교                    |
| G-04 | 확인 창 질문은 ‘~할까요?’                           | 제목 비교. A-25는 재합의 전 별도 표시           |

| G-07 | 핵심 용어표 적용, 의미가 다른 항목은 구별           | 홈·계산 내역·계획·거래 화면을 교차 확인         |

### 판정 상태

- **결함:** 합의된 기준 위반 또는 실제 동작과 다른 안내가 확인됨.
- **개선 제안:** 이해·일관성을 높일 수 있으나 현재 의미나 계약에 오류가 확인되지 않음.
- **확인 필요:** 노출 여부, 실제 동작, 정책, 기존 결정과의 우선순위가 미확인.
- **예외:** 이유와 적용 범위를 기록한 의도적 차이.

문구 취향 차이를 결함으로 분류하지 않는다. 특히 ‘다시 불러오기’, 짧은 상태 라벨, 외부 사건의 수동형은 문맥에 따라 올바를 수 있다.

### 수정 우선순위

1. 금액·기간·저장·인증 결과를 오해하게 하는 안내, 실행 결과와 다른 버튼.
2. 해결 경로가 없는 오류, 서로 다른 상태를 같은 문구로 표현한 경우.
3. 용어·말투·띄어쓰기·마침표 등 의미를 해치지 않는 일관성 문제.

현재 QA의 심각도 체계가 있으면 그 체계를 사용한다. 위 순서는 문구 검토의 우선순위이며 새로운 심각도 코드를 도입하는 것은 아니다.

### 기록 양식

| G 번호 | 화면·상태           | 파일·줄/문구 ID | 현재 문구 | 문제·근거                     | 제안 문구 | 실제 동작 검증                  | 판정                     |
| ------ | ------------------- | --------------- | --------- | ----------------------------- | --------- | ------------------------------- | ------------------------ |
| G-__   | 화면 ID와 노출 조건 | 목록 위치       | 원문      | 이 가이드 항목 또는 기능 계약 | 수정안    | 버튼 결과·기기 캡처·확인한 버전 | 결함/제안/확인 필요/예외 |

같은 원인은 한 이슈에 묶고 영향 위치를 함께 기록한다. 문구가 같아도 결과 미확인과 실패 확정처럼 상태가 다르면 별도로 검토한다.

## 11. 유지·관리

- 문구 목록에 역할, 화면, 노출 조건, 일반/데모/내부 구분, 확정 상태를 추가해 관리하는 것을 권장한다.
- 같은 상황의 대표 문구를 정하되 서로 다른 동작을 하나의 공통 문자열로 강제하지 않는다.
- 변경 시 문구뿐 아니라 대응 화면 명세·QA 기대값을 함께 갱신한다.
- 검증은 실제 변수 값이 들어간 화면에서 진행한다. 기존 F-13의 320dp·글자 크기 1.3배/2배 조건과 접근성 읽기 순서도 확인한다.
- 이번 QA에서 iOS를 확인하지 않았다면 Android 확인 결과를 iOS 검증으로 확대해서 보고하지 않는다.
